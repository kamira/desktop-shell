    即回上游保守 `defaults()`。經核 `CapabilityMatrix::defaults()` 本體始終未含該鍵，無上游污染。
  - 所有變更操作（`create_alpha_surface` / `set_alpha` / `set_mode` / `set_opacity`）第一步即
    `supported()`（= `backend.has(kPerPixelAlphaCapability)`）閘控。

    (d) 唯讀查詢（`alpha_profile`/`is_per_pixel`）於降級下安全回 nullptr / false；(e) `destroy`
    **不受**能力閘控（釋放恆安全），未知 id 結構化回 `Invalid` 不崩潰。全數通過。

## 組合設計判定 — pass

- **雙層一致**：`create_alpha_surface` 委由後端 K1 `create_surface` 建實體 surface，另在服務層
  記憶體 `records_` 記 `AlphaProfile`；`destroy_alpha_surface` 同步 `backend_.destroy_surface` +
  `records_.erase`。實測建立後 `backend.has_surface`==服務 `has_alpha_surface`，銷毀後雙層皆釋放。
- **後端衝突無半份狀態**：後端已存在同名 surface 時，`backend_.create_surface` 回 false → 服務回
  `Invalid` 且**不 push 記錄**（`records_` 不新增）。獨立探針證實 `has_alpha_surface`==false、
  `alpha_surface_count`==0，無殘留半份狀態。服務層重複 id 由 `find()` 先攔（回 Invalid，後端不動）。
- **opacity clamp / 有限值守衛**：`normalize_opacity` 對 `!std::isfinite` 回 false → `Invalid`；
  有限值 `std::clamp` 至 [0,1]。獨立探針驗證 2.5→1.0、-9.0→0.0，NaN / Inf 回 `Invalid` 且**不改
  先前狀態**（維持 0.0），建立時的非有限 opacity 亦拒絕且不建 surface。
- **抽象解耦**：服務持 `KernelBackend&` 基底參考，經抽象基底指標操作亦成立（測試
  `WorksThroughAbstractBackend` + 探針覆核）；真實後端上線後同介面可換底，下游不受影響。
