## 3. 契約審查（獨立）

**問題：本契約是否讓致動器能以具名命令掛上而不需相依具體致動器？** —— **是。**

- 掛載面 `register_command(CommandId, CommandHandler)`：致動器只提供「具名字串 id + `std::function`
  處理器」即可掛上；呼叫端 `dispatch(id, args)` 僅需 id 與參數字典，編譯期不 include 任何致動器標頭、
  連結期不相依任何致動器 target。解耦成立。
- 具名字串 id（非數字 opcode）：穩定、可讀、跨模組邊界不變形、不耦合編號分配。合宜。
- **register / dispatch / unregister 語意**（逐一覆核，與測試對照）：
  - `register_command`：空 id、空 handler、已存在 id 一律回 `false` 且不變更狀態（`RejectsEmptyIdAndNullHandler`、
    `DuplicateRegistrationRejectedNoOverwrite` 證實）。
  - `dispatch`：未知命令回 `CommandResult{NotFound}` 並附含 id 的訊息，不崩潰、不丟例外（`Unknown…DoesNotCrash`）；
    已知命令原封轉呼處理器並回傳其結果（Ok/Failed 由處理器決定，`HandlerReturnValuePropagates`、`HandlerFailurePropagates`）。
    另有 `dispatch(id)`、`dispatch(Command)` 便捷多載。
  - `unregister`：回是否確有移除（未知 id 回 false），移除後可重註冊（`UnregisterRemovesCommand`、`ReRegisterAfterUnregisterSucceeds`）。
- **值型別跨邊界穩定性**：`CommandValue` 為封閉 `std::variant<monostate,bool,int64,double,string>`，
  存取一律型別安全（相符回值、否則回 `std::nullopt`，不 UB 不丟例外）；`CommandArgs` 以 `std::map` 有序、
  遍歷決定性。跨致動器邊界不變形。消毒器組建佐證無 UB。
- **內省面**：`has_command` / `command_count` / `command_ids`（有序）供診斷，不洩漏處理器內部。

API 面最小、封閉、可版本化（`contract_version()` = `e6_01/1.0.0`），符合 architecture.md「Q3 意義加重」
對承重契約需帶版本欄位的要求。

## 6. 特別覆核：實作者提的兩點

### (1) `CommandValue` 封閉集合（null/bool/int/double/string）是否足夠？下游是否需 bytes / 清單型別？

**判斷：對相位 1 驗收而言足夠，pass 不阻擋；但附前瞻建議。**

- 下游致動器（E3-01…E3-11）尚未實作（`modules/actuators` 目前為空），無現存消費者能證實封閉集合不足。
- 就已知需求前瞻檢視：
  - **bytes**：variant 中的 `string` 型別為 `std::string`，其為**二進位安全容器**（可含內嵌 `\0`，
    `as_string()` 以值回傳保留全部位元組）。故 E3-07 剪貼簿寫入、E3-11 螢幕擷取回傳影像等位元組需求
    **技術上可經 String 承載**，非硬缺口。
  - **清單**：E3-01 外部命令執行的 `argv` 是最像清單的情境。目前只能以多個具名參數（`arg0/arg1/…`）
    或單一分隔字串表達——可行但不夠優雅、也不自我文件化。
- 契約已帶版本欄位（`e6_01/1.0.0`），architecture.md 明示承重 API 從第一版就備相容策略以供演進。
- **結論**：我**認同**實作者「封閉集合 + 複合結構以多個具名參數表達」的相位 1 選擇。**不阻擋驗收。**
  **前瞻建議（非缺陷）**：待 E3-01（argv 清單）與 E3-11（影像位元組）落地、出現真實消費者時，
  重新評估是否顯式新增 `Bytes` 與/或 `List` 型別（而非以 String 超載位元組、以多具名參數超載清單），
  以取得型別安全與自我文件化；屆時循 `contract_version()` 做相容遞增即可。

### (2)「重複註冊拒絕不覆蓋」語意是否符合下游需求？是否該提供明確 `replace` API？

**判斷：拒絕不覆蓋為承重註冊表的正確預設，pass 不阻擋；相位 1 不需 `replace`。**

- 拒絕不覆蓋的理由（避免致動器被無聲遮蔽 silent shadowing）對承重契約是**正確且防禦性的預設**——
  我認同。無聲覆蓋在載入多模組時最易造成難查的行為漂移。
- 「是否需要 replace」：**取代能力已存在**——`unregister(id)` 後 `register_command(id, …)` 即可有意取代
  （`ReRegisterAfterUnregisterSucceeds` 證實）。相位 1 引擎層為單執行緒純邏輯、未宣稱亦不需執行緒安全，
  故「取代非原子」不構成問題。
- **結論**：我**認同**現行語意，相位 1 **不需**額外 `replace` API。**前瞻建議（非缺陷）**：若日後
  出現對**原子取代 / upsert** 的真實需求（例如 E8-04 行程內模組熱重載時需原子換手處理器），
  可再新增 `replace(id, handler)` 或 `upsert`，同樣循版本遞增。目前不加是恰當的最小面。
