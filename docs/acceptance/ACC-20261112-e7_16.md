## append-only 的結構保證覆核（本 ACC 的核心）— pass

CHG 的宣稱是：append-only 靠**結構**，「不是『檢查後拒絕覆寫』，是**連覆寫的管道都不存在**」。
這個差別是真實的，所以本節不接受文件說法，而是逐段讀實作本體、再以探針反證。

### 核心 Value 樹在哪、套件分頁的 Value 樹在哪

```
settings_pages.hpp:254    SettingsPage core_;                                  // 核心分頁
settings_pages.hpp:255    std::map<std::string, SettingsPage> package_pages_;  // 套件分頁
settings_pages.hpp:256    SettingsContributionSource& source_;
settings_pages.hpp:100        Value values;                      // 每個 SettingsPage 各自一棵
settings_pages.hpp:101        std::vector<EditableField> fields; // 由該頁的 values 算出
```

兩者是**不同的成員、不同的物件**，各自持有一棵自己的 `Value`。

`Value`（`engine/format/document.hpp:103`）是**深值型別**——私有成員只有
`ValueType type_` / `bool bool_` / `double num_` / `bool integral_` / `std::string str_` /
`std::vector<Value> list_` / `std::vector<Member> map_`，**無任何 `shared_ptr` / `unique_ptr` /
裸指標 / 參照**（自行 grep `document.hpp` 確認）。因此複製一棵 `Value` 永不產生別名。
E7-14 `EditableField` 同樣以值持有 `Value current` 與 `Path path`，**不持有指進樹裡的指標**，
故欄位清單也不是共用儲存的管道。

### 兩者之間有沒有任何可寫的接點

把每一條能寫到 `core_` 的程式路徑列完：

1. **建構子**（`settings_pages.cpp:126-141`）：`core_ = make_page(kCorePageId, …, std::move(core_values), std::move(core_schema))`。
   輸入只有**呼叫端給的** core_values / core_schema，**完全不碰 `source_`**。
2. **`refresh()`**（`settings_pages.cpp:143-178`）：全函式只寫一個成員——第 177 行
   `package_pages_ = std::move(rebuilt);`。`core_` 在該函式中**既未被讀也未被寫**
   （連 `core_.values` 重算都沒有）。逐行讀過，無例外。
3. **`apply_page_edit()`**（`settings_pages.cpp:211-240`）：
   ```cpp
   if (page_id == core_.id) { target = &core_; }
   else { auto it = package_pages_.find(page_id); if (it != …end()) target = &it->second; }
   ```
   `target` 恰為其中**一個**物件。套件分頁永不可能成為 `&core_`：`page_id == core_.id` 先被測，
   且套件分頁的 id 不可能是 `"core"`（見下）。這條路徑的輸入是**呼叫端給的 new_value**，
   不是任何貢獻內容。
4. **其他所有公開存取器皆為 const**：`core_page()` 回 `const SettingsPage&`、
   `core_values()` 回 `const Value&`、`page()` 回 `const SettingsPage*`、
   `package_values()` 回 `const Value*`、`pages()` 回**副本** `std::vector<SettingsPage>`。

**結論：不存在任何「套件貢獻 → 核心 Value 樹」的可寫接點。** 這是資料流上的事實，
不是一道檢查。

### 關鍵反證：把那道檢查拿掉，核心值還是不會被改

CHG 的保證 3（保留 page id 守門）**本身是一道檢查**（`check_contribution_id` 的 `throw`）。
那麼：值層的 append-only 到底靠結構，還是其實靠這道檢查？本驗收者以**突變 2（移除該守門）
＋自寫探針 A** 直接問這個問題：

### 第 3 項的判定

**值層的 append-only 是結構保證，不是檢查後拒絕。** 依據：

- 核心與套件分頁是**兩個物件、兩棵深值 `Value` 樹**，`Value` 與 `EditableField` 皆無指標/共享
  語意，複製不產生別名（探針 B2 另以「宣告一棵與核心完全相同的樹」實測位址不同、改一邊不影響
  另一邊）。
- `refresh()` 的唯一寫入是 `package_pages_ = std::move(rebuilt)`；`core_` 在該函式中零讀零寫。
- 對外只有 const 存取；`pages()` 給副本（探針 B3 實測改副本不影響登錄）。
- **把保留 id 檢查整個拿掉，核心值仍不被改動**（探針 A）——若 append-only 靠那道檢查，
  這裡就會被改到。

**同時誠實指出：保留 page id 守門確實是「檢查後拒絕」，但它守的是另一件事——
id 空間的唯一性/列舉無歧義，不是核心值不被覆寫。** 探針 A 顯示守門拿掉後退化的後果是
`page_ids()` 出現重複的 `"core"`（大小 2 且兩項相同）、佔位者的值只能從 `package_values("core")`
這條旁路看見；核心值毫髮無傷。CHG 的保證 3 原文就寫成「→ `throw`」而非結構保證，
**並未把這道檢查說成機制**，故 CHG 在這一點上**沒有把紀律講成機制**。

**唯一需要記住的邊界（非缺陷）**：`apply_page_edit(kCorePageId, …)` 是一條**對核心可寫**的公開路徑。
它是使用者編輯核心設定的正當入口，輸入來自呼叫端而非任何套件貢獻。因此精確的不變式不是
「核心不可變」，而是「**沒有任何貢獻衍生的資料能到達核心**」——實作與文件講的正是後者。
