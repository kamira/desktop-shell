## 審查發現

**除頻（de-frequency / coalescing）正確性 — 通過（本單元核心）**

- 有效分級 = 同一指標所有存活需求中「最高頻者」：`effective_tier_of` 以 `higher_tier` 折疊全部
  需求，`higher_tier` 依 `tier_rank`（High=3 > Normal=2 > Low=1 > OnDemand=0）取較頻繁者，
  位階相同回第一引數。語意正確：誰要得最頻繁就用誰的頻率，其餘消費者搭便車。
- 一份採集供所有消費者：`advance` 走訪 `metrics_`（以 `MetricId` 為鍵，每指標恰一筆狀態），
  故同一指標每輪**只輸出一次**，天然去重——不是每消費者各一份。由 `OneSampleServesAllConsumers`
  機械證明（`std::count(...) == 1`）。
- 拉高頻率會提前下次採集：`add_demand` 既有指標路徑重算 `interval_of`，若 `now_+iv < next_due`
  即把 `next_due` 提前。由 `RaisingFrequencyPullsNextSampleEarlier` 覆蓋（Low→加 High 後
  next_due ≤ 1）。
- 降頻採「下次採集後生效」：`remove_demand` 撤掉最高需求後不動 `next_due`，待既排定之下次採集
  發生後即以新（較長）間隔續行。屬刻意且有文件的選擇——最多多採一份、絕不漏採，對 idle 門檻
  無害。由 `DroppedCadenceTakesEffectAfterNextSample` 精確覆蓋（t=5 沿舊時機採一次，t=6..12
  皆不採，t=13 依 Normal 間隔再採）。
- 撤銷最後一筆需求即停止追蹤（`metrics_.erase`），之後 advance 不再回傳該指標。

**分級間隔 / on-demand / 跨間隔不補採 / 時間單調 — 通過**

- 間隔映射：High=1 / Normal=8 / Low=64（可經 `set_interval` 覆寫，0 夾到 1、對 OnDemand 為
  no-op）。各級於固定 tick 數內採集次數經 `count_samples` 驗證恰符（High 64、Normal 8、Low 1、
  自訂 Normal=4→16）。
- on-demand 非週期：OnDemand→間隔 `nullopt`→`periodic_due` 恆 false，只有 `request_now` 設下的
  `pending_now` 能觸發，且採一次後即清旗標。`NeverSamplesPeriodically`（100 tick 零採）與
  `RequestNowFiresExactlyOnce` 覆蓋；`request_now` 對週期指標亦可強制即刷（`ForcesImmediateRefresh…`）、
  對未追蹤 id 為 no-op。
- 跨多間隔不補採：`advance` 設 `next_due = now + iv`（以 now 為基、非累加），跳過 100 個間隔仍只
  採一份。直接對應 NFR-01 idle 門檻（久閒醒來不一次灌爆）。由 `NoCatchUpBurstAcrossManyIntervals`
  覆蓋。
- 時間單調：`now < now_` 回空清單且不推進 `now_`；`now == now_` 允許（首次 advance(0) 所需）。
  同一 tick 重複 advance 不會二採（`next_due` 判定把關）。由 `BackwardTimeIsIgnored` 覆蓋。
- 決定性輸出順序：以首次登記序 `order` 排序，消除 `unordered_map` 走訪不定性。由
  `DueMetricsFollowRegistrationOrder` / `MixedTiersDueTogetherWhenAligned` 覆蓋。

## 保留意見（皆非阻斷，供後續單元參考）

- **OnDemand-only 指標事後加入週期需求**：指標建立時 `next_due` 一律設為建立當下的 `now_`
  （即使首個需求是 OnDemand）。若之後在較晚 tick 才加入週期需求，`add_demand` 的
  `candidate < next_due` 比較不會生效（`next_due` 仍停在建立時的舊值），下次 advance 會立即採
  一份。此為「新轉週期之指標盡速首採」的合理行為，非缺陷；現有測試（`OnDemandDoesNotSuppress…`
  於 tick 0 建立）未觸及「時間已推進後才轉週期」這一角，屬可補強的邊角，不影響判定。
- **降頻延後生效**語意已如上分析為刻意設計（最多多採一份）；建議未來若有嚴格節能模式需即時
  降頻，再於呼叫層以 `request_now` 之反向手段（重排 next_due）補強，本層契約無須改動。
- 契約層未談執行緒安全（相位 1 單執行緒、注入邏輯 tick）；真實採集迴圈接入時的併發屬上層責任。
