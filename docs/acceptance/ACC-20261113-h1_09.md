## 4. 本驗收者找到的缺陷

### F1 —— **阻擋項**：拒收一份存檔之後，下一次 `save()` 就把它永久毀掉

**這一條是驗收標準第三句的正面反例，可重現，走的是本單元自己的公開 API。**

`save()`（`edit_assembly.cpp:845-866`）**完全不查** `last_intake_`：不論 `restore(name)`
是成功、是 `VersionTooNew`、是 `Malformed` 還是 `MissingVersion`，
`save(name)` 一律把目前記憶體佈局序列化後 `storage_.put(name, text)` 覆寫過去。

最小重現（只用公開 API，**沒有做任何編輯**，就是「開機 → 還原失敗 → 自動存檔」）：

```cpp
ds::layout::MemoryLayoutStorage storage;
storage.put("desktop", USER_FILE);              // 使用者真正的佈局
ds::host::edit::EditAssembly app(storage);      // 開機：記憶體佈局是空的
app.restore("desktop");                         // 被拒收 → 保留（空的）佈局
app.save("desktop");                            // 離開時自動存檔 → **覆寫**
```

本驗收者實跑的五種拒收分類，使用者的佈局**全部消失**：

| 使用者手上的檔案 | `restore` | `save` | 使用者資料還在？ | 覆寫後檔案 |
|---|---|---|---|---|
| 多打一個 tab 縮排 | `Malformed` | **`Ok`** | **否** | 30 bytes（空 elements） |
| 不小心刪掉版本行 | `MissingVersion` | **`Ok`** | **否** | 30 bytes |
| 版本打成 `1,0` | `MalformedVersion` | **`Ok`** | **否** | 30 bytes |
| 新版程式寫的 `2.0` | `VersionTooNew` | **`Ok`** | **否** | 30 bytes |
| `x: 1e400` 手滑 | `Malformed` | **`Ok`** | **否** | 30 bytes |
| （對照）正常檔 | `Ok` | `Ok` | 是 | 142 bytes |

為什麼這是「救不回來」而不是「呼叫端的事」：

1. **相位 1 的後端是 `MemoryLayoutStorage`，沒有版本、沒有備份、沒有 `.bak`。**
   被覆寫就是沒了。CHG §4 以「相位 1 沒有磁碟可以被寫到一半」把原子性論證掉——
   那對**撕裂寫入**成立，但相位 1 真正的資料毀損路徑不是撕裂寫入，是
   **一次完整、合法、通過往返自驗的寫入，蓋掉本層刻意拒絕讀取的資料**。
   `VersionTooNew` 尤其諷刺：本層拒收它正是為了保護它（「不降級」），
   結果下一次 `save()` 就把它刪了。
2. **CHG 的第二道防線寫的是**「載入失敗 → 不把壞狀態寫回；storage 原文原封不動，
   **使用者還改得回來**」。前半句屬實（`restore` 那一瞬間），後半句**不成立**——
   「還改得回來」要求檔案活到使用者去改它，而本單元的下一個正常操作就會把它刪掉。
   32 支復原測試裡的 `EXPECT_EQ(fx.stored(), before)` 全部只跨越 `restore` 這一次呼叫，
   **沒有任何一條斷言跨越「拒收之後的 save」**。
3. **本層有足夠資訊可以擋**：`last_intake_` 就在成員裡，`save()` 不看它。
   標頭、CHG、worklog 三處都**沒有**任何「拒收之後不要存檔」的呼叫端契約
   （本驗收者 grep 過）。
4. 目前 `host/app/` 尚未消費 `EditAssembly`（全庫零呼叫端），所以這是**潛伏**缺陷；
   但本單元就是負責定義這條路徑契約的裝配層，而驗收標準點名的正是這個危害。

**本驗收者不代為修補。** 可能的修法（供 I1 與實作者裁量，非本 ACC 的指定方案）：
`save()` 在 `name` 的上一次 intake 為不可用時回一個新的具名 `SaveStatus`
（例如 `RefusedSourceWouldBeOverwritten`）並拒絕提交，另開一個明確的覆寫入口；
或 `put()` 前先把原文另存一份具名備份。無論哪一種，都需要一條跨越
「拒收 → save」的回歸斷言，否則這個洞沒有任何測試保護。

### F2 —— `edit_property` 的非有限守衛是**淺的**；CHG 自述第 4 條不完整

`edit_assembly.cpp:769` 的守衛是 `value.is_number() && !std::isfinite(value.as_number())`。
值若是 **Map 或 List**，`is_number()` 為 false，守衛整個跳過，裡面的 NaN / Inf
就**經公開 API 進入持久化狀態**：

```
edit NaN bare         -> NonFiniteValue        （擋住了）
edit nested-map NaN   -> Ok                     ← NaN 進到 state
edit Inf nested list  -> Ok                     ← Inf 進到 state
state cfg.inner       = nan   isfinite=0
```

CHG 的「已知限制」第 5 條說「`reset()` **是**那個不消毒的後門，把關交給 `save()`
的往返自驗」——**`edit_property` 是第二個後門**，而 CHG 沒有提到它，也沒有測試覆蓋它。

後果與嚴重性（本驗收者實測）：

- **把關確實有效、且是 fail-closed**：之後的 `save()` 一律 `VerifyFailed`，
  storage 一個位元組都沒被動（這點與 CHG 宣稱一致，是好的）。所以**不是資料毀損**。
- 但**診斷說不出是哪一欄**：`last_message()` 只有
  `往返自驗不通過（Ok）：`——狀態是 `Ok`、原因為空字串。呼叫端拿不到任何線索去定位
  被汙染的路徑。對一個以「具名、可觀測的降級」為設計原則的單元，這是明顯的落差。
- 可以復原，但要**事先知道路徑**：本驗收者實測把 `cfg.inner` 改回 0 之後 `save()`
  仍 `VerifyFailed`（`arr[0]` 還是 Inf），逐一把 `arr[0]` 也改掉才復綠。
  `EditAssembly` **沒有 `remove_property`**，所以除了逐路徑覆寫就只剩
  `remove_element`（整個元件丟掉）或從外面 `reset()`。

不作為阻擋項（fail-closed、無資料毀損），但應補守衛（遞迴檢查）或至少補
「`VerifyFailed` 要說出第一個對不上的元件 / 欄位」，並補測試。

### F3 —— 三條防線沒有任何斷言殺得死（K-012 家族）

本驗收者自行追加三個 CHG 未列的突變，三個都**存活**：

| 突變 | 結果 | 說明 |

| **MX5**：拿掉 `to_device_px` 的 `isfinite` 守衛 | **存活** | 註解自己寫「防禦：即使呼叫端漏了」。今日所有呼叫端都先過 `clamp_finite`，故不可達。但它正是 `float-cast-overflow` 的最後一道牆：日後有人新增一個略過 `clamp_finite` 的呼叫端時，刪掉它不會有任何測試紅 |

## 6. 上游 `ds::format::parse()` 丟例外 —— 獨立驗證

1. `ingest_layout_text` 對 `parse()` 的唯一呼叫（`:415`）在 try 內，

   `parse()` 之前就被判 `MalformedVersion`，那段文字根本不會被餵進去。

## 8. 保留意見（不構成本次判定依據）

- **R1**：邏輯像素在 API 面沒有型別標記，呼叫端誤傳裝置像素本層收得下且無徵兆（見條件 5）。

- **R3**：`H1-07` 是 `units.json` 宣告的相依，但未被連結也未被消費；本層另造
  `LogicalPlacement`（`double`）而非沿用 `ComponentPlacement`（`PixelPoint` / `PixelSize`）。
  兩者語意同為邏輯像素但表示型別不同，日後容易漂移。本驗收者判斷**不是缺陷**
  （驗收標準原文未點名 H1-07，且 double 對拖曳累加是合理選擇），但 CHG 應寫明為何
  宣告相依卻不消費。
- **R4（上游，非本單元）**：深層巢狀會打爆堆疊。本驗收者實測（預設 8 MiB stack）：
  巢狀 10000 層（約 50 MB 文件）→ `Ok`；**14000 層（約 98 MB）→ SIGSEGV**。
  把 stack 開到 64 MiB 後同一輸入回到 `Ok`，確認是 `engine/format/` 的**遞迴解析
  ／遞迴解構**耗盡堆疊，不是 OOM。SIGSEGV **不是 try/catch 接得到的**，所以本單元
  「對外不 throw / 不崩潰」的承諾在這個邊界之外。手改存檔到 50 MB 以上不是現實情境，
  故**不作為阻擋項**，但記下：這是「救不回來」的硬下界，且與 F1 不同，它不在本單元可修範圍。
- **R5**：`poll_reload` 先呼叫 `reloader_->poll()`（E7-07 內部已解析一次），再
  `source_->content()` 自行重新解析一次 —— 同一份文字被解析兩次。相位 1 無正確性問題
  （單執行緒、`MemorySource`），但相位 2 接真實檔案監看時，兩次讀取之間檔案可能變動，
  屆時 E7-07 的診斷報告與本層實際採用的內容可能對不上。建議在接真實後端的單元複查。
- **R6**：CHG / 派工說明寫 base 為 `48589a5`，PR #244 實際 base 為 `563375b`
  （該 commit 只動 `docs/backlog/`，程式碼與 CMake 零命中，兩者等價）。文件精確度。
