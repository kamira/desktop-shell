### F4 —— **阻擋項**：存檔被「部分丟棄」之後，下一次 `save()` 無聲毀掉被丟掉的那一塊

**與 F1 同一條驗收標準、同一個類別、同樣可重現、同樣走公開 API，而且是修訂 2 自己
新寫的那段防線刻意放過的。**

修訂 2 的防線用 `IntakeReport::usable()` 當述詞，而 `usable()` 的定義
（`edit_assembly.hpp:285-288`）是 `Ok || Repaired || Migrated`。
於是當目標存檔是 `Repaired` **且 `dropped_elements > 0`** 時——也就是本層**明確知道
自己從那份檔案裡丟掉了整個元件**時——`save()` 一路放行。

最小重現（公開 API，沒有做任何編輯，就是「開機 → 還原 → 離開時存檔」）：

```cpp
// 使用者手改存檔時把第二個元件的 id: 那一行刪掉了（一行的筆誤）
storage.put("desktop", /* 兩個元件，第二個缺 id，帶 tune: 777 等整組設定 */);
ds::host::edit::EditAssembly app(storage);
app.restore("desktop");   // Repaired；dropped_elements = 1；記憶體只剩 1 個元件
app.save("desktop");      // Ok —— 第二個元件的所有設定就此永久消失
```

本驗收者實跑的輸出（`-DDS_WERROR=ON` 與 sanitizer 兩個建置，輸出逐字相同）：

```

target_is_readable=1
dry_run_save("desktop")=Ok      ← 呼叫端的預檢也看不到任何警訊
save=Ok
storage 裡現在有的名字： 'desktop'          ← 沒有 .rejected，沒有任何備份
rejected_backups=0 saves_refused_target=0
tune:777 還在？ **永久消失，沒有任何備份**
```

**四種丟棄原因全部中獎**（各自獨立重現，被丟掉的那個元件都帶著 `tune: 777`）：

| 使用者的筆誤 | `restore` | `dropped` | `save` | `tune: 777` |
|---|---|---|---|---|
| 第二個元件缺 `id` | `Repaired` | 1 | **`Ok`** | **永久消失** |
| 第二個元件缺 `type` | `Repaired` | 1 | **`Ok`** | **永久消失** |
| 兩個元件 `id` 重複 | `Repaired` | 1 | **`Ok`** | **永久消失** |
| 第二個元件 `id` 型別錯（寫成數字） | `Repaired` | 1 | **`Ok`** | **永久消失** |

為什麼這是阻擋項，而不是保留意見：

1. **它正是驗收標準第三句的反例，與 F1 字面上同一條。**
   使用者刪掉一行 → 那個元件的整組設定永久消失、沒有備份、沒有任何一個回傳值說了
   「我正要毀掉東西」。相位 1 的 `MemoryLayoutStorage` 沒有版本、沒有 `.bak`，
   被覆寫就是沒了。「救不回來」沒有尺寸門檻。
2. **本層在做決定的那一行手上就握著判據。** `save()` 內的 `target` 就是一份完整的
   `IntakeReport`，`target.dropped_elements` 與 `target.degraded()` 都在手上，
   被 `usable()` 這一個述詞整個丟掉。`degraded()` 這個函式**本來就存在**
   （`edit_assembly.hpp:290`），而且它的註解寫的正是「讀進來的東西與檔案裡寫的不完全一樣」。
3. **修訂 2 新增的兩個「問得到」的 API 都回答錯了。** `target_is_readable()` 回 `true`、
   `dry_run_save("desktop")` 回 `Ok`。這兩個 API 是這次修訂為了讓呼叫端
   「不必自己猜」才加的——它們現在在資料即將被毀的那一刻給出綠燈。
   這比修訂 1 的「呼叫端沒東西可問」更難被發現。
4. **沒有任何呼叫端契約。** 本驗收者 grep 過 `edit_assembly.hpp`、CHG、worklog 三處：
   沒有任何一句寫「`dropped_elements > 0` 時不要直接存回原檔」。
   標頭反而給了相反的印象——`Overwrite` 的註解寫「**連『明示丟棄』都不真的丟掉位元組**」。
5. **測試把這個行為當成正確的釘了下來，而且理由是錯的。**
   `OverwriteGuard.RepairedTargetIsStillOverwritable`（`tests/h1/test_h1_09_recovery.cpp`）
   用的正是「第二個元件缺 id」這個輸入，斷言 `save` 回 `Ok`，
   註解寫「`Repaired` / `Migrated` 都算『讀得出來』—— **使用者的資料已經在記憶體裡了，
   覆寫不會毀掉它**」。**後半句對 `dropped_elements > 0` 的情況是假的**：
   被丟棄的那個元件**不在**記憶體裡，正因為不在，覆寫才會毀掉它。
   這條測試會讓下一個讀碼的人相信這個洞是刻意且安全的。
6. **修法很小，而且修訂 2 已經把零件都做好了。** 可能方向（供 I1 與實作者裁量，
   **非本 ACC 的指定方案**）：把 `save()` 的述詞由 `!target.usable()` 改為
   `!target.usable() || target.dropped_elements > 0`；或在丟棄數 > 0 時
   不拒絕但**先備份為 `<name>.rejected` 再覆寫**（沿用既有機制，不必新增 API）。
   無論哪一種，都需要一條跨越「部分丟棄的 restore → save」的回歸斷言，
   並把 `RepairedTargetIsStillOverwritable` 的輸入換成「只有欄位被消毒、零丟棄」
   的那種 `Repaired`——否則修完還是沒有測試保護。

> **為什麼要特別區分「欄位被消毒」與「元件被丟棄」**：兩者都走 `Repaired`，
> 但語意完全不同。欄位被消毒（例如幾何是 NaN 被歸 0）時，存回去是**自我修復**，
> 是對的；元件被丟棄時，存回去是**把使用者的資料扔掉**。
> 判據就是 `dropped_elements`，本層已經在算它了（M14 那條突變保護的就是這個計數器）。

### 其他新發現（不作為阻擋項）

- **R7 —— 實作者「重讀目標涵蓋查 `last_intake_`」的推論不成立；兩者覆蓋不同集合。**
  CHG 與標頭都寫「後者只擋得住『restore 失敗 → save』這一條路，擋不住『從來沒 restore
  過就 save』」。前半句**不準確**：`last_intake_` 方案還擋得住一條重讀方案擋不住的路——
  **還原失敗的是 A，存檔寫的是 B**。本驗收者實測（E9-05 本來就支援多 profile）：

  ```
  storage: home = 壞檔案, work = 完好的佈局
  restore("home") = Malformed   記憶體元件數 = 0
  save("work")    = Ok          refused = 0
  → work 的 cpu 元件：不見了（176 bytes → 30 bytes）
  ```

  本驗收者**不把它列為阻擋項**，理由是本層分辨不出「使用者剛失敗就誤存到別的 profile」
  與「使用者刻意從空白建一份新佈局存到 work」——那需要呼叫端契約，不是本層單方面能決定的
  （這一點與 F4 不同：F4 的判據本層手上就有）。但 CHG 把重讀寫成嚴格更好的方案是**不對的**，
  標頭與 CHG 都應該寫明「本層只保護同名目標」，否則呼叫端會以為多 profile 也被蓋住了。
  正解可能是兩道一起做。

- **R8 —— `.rejected` 的備份寫入本身沒有守衛，會蓋掉一個**可讀的**同名 profile。**
  CHG「已知限制 8」只說了備份不輪替（連續兩次明示丟棄，第二次蓋掉第一次——
  本驗收者實測確認：第 1 次備份含 `ONE`，第 2 次之後只剩 `TWO`）。但還有一條沒寫到：
  `storage_.put(name + kRejectedSuffix, existing)` **不先看那個名字有沒有東西**。實測：

  ```
  storage: d = 壞檔案, d.rejected = 使用者自己的一份好佈局
  save("d", Overwrite::DiscardUnreadable) → Ok
  → d.rejected 原本的好佈局：被備份蓋掉了
  ```

  情境刻意、機率低，但這是**修訂 2 自己新增的一條寫入路徑**，而它是這次修訂裡
  唯一一個「沒有先檢查就 `put()`」的地方——與本單元其餘部分的原則不一致。

- **R9 —— `save()` 現在會解析目標，於是 R4 的 SIGSEGV 多了一個入口。**
  修訂 1 的 `save()` 從不碰目標的內容，R4（深層巢狀打爆堆疊）只在 `restore` / `poll_reload`
  走得到。修訂 2 之後，**完全沒有 restore 過的 `save()` 也會解析目標**。實測（預設 8 MiB stack）：

  ```
  巢狀  6000 層（約 36 MB）→ save = Ok
  巢狀 14000 層（約 196 MB）→ **SIGSEGV（退出碼 139）**，連一行 save= 都沒印出來
  ```

  SIGSEGV 不是 try/catch 接得到的，所以本單元「對外不 throw / 不崩潰」的承諾在這個邊界外，
  **而這次修訂把那個邊界的觸及面從『載入』擴大到『存檔』**。與 V1.7 的 R4 一致，
  本驗收者**不列為阻擋項**（根因在 `engine/format/` 的遞迴解析，不在本單元鎖定範圍，
  且需要手改出 ~200 MB 的存檔），但請 I1 把它一併帶進 R4 的上游單元，
  並請 CHG 的「已知限制 9」補上這一句——那一條目前只談效能，沒談這個。

- **R10 —— 深層守衛掛在 `edit_property` 而不是共用的 `write_property`。**
  `apply_drop` 直接走 `write_property`，繞過 `contains_non_finite`。
  今日不可達（E7-15 只產生字串值，`dropgen.cpp` 全檔無 `Value::number`，自行查證），
  故不是缺陷；但 F2 本身就是「守衛放錯位置」，建議順手移到 `write_property`。

- **R11 —— 修訂 2 新增的診斷碼裡，有一行沒有任何斷言殺得死（K-012，F3 的同一家族）。**
  本驗收者自行追加的突變 **V1**（`describe_mismatch` 的
  「元件 '<id>' 的 properties 往返後不一致」那一支整個不回報）→ **存活**。
  `DeepNonFiniteGuard.VerifyFailedNamesTheOffendingFields` 斷言的是**非有限掃描**那段訊息
  （它在 `describe_mismatch` **之前**就 return 了），所以 `describe_mismatch` 的
  properties 分支從來沒被任何斷言走到。嚴重性低（純診斷字串），但這正是 F3 的教訓：

### 兩條「等價突變」的說法 —— 本驗收者各自獨立驗證

**M27：成立。** CHG 的論證（NaN 讓後面每個 `>=` / `<=` 都是 false）本驗收者認為不完整——
它只談了 NaN，沒談 ±Inf。本驗收者自行補完並用差分探針窮舉：

```
窮舉 x/y/width/height ∈ {NaN, ±Inf, 0, ±1, 1e-320, ±kCoordLimit, ±(kCoordLimit+1),
                          kExtentLimit, kExtentLimit+1, -1e-9, ±1e300, ±0.5}
  = 19^4 = 130,321 組  → 原式與突變式的回傳值差異 **0 組**
另加隨機 4,000,000 組（x/y/w/h ∈ [-2e6, 2e6]） → 差異 **0 組**
```

補上推論：±Inf 也被範圍比較擋掉（`+Inf <= kCoordLimit` 為 false；
`-Inf >= -kCoordLimit` 為 false；width 的 `-Inf >= 0.0` 為 false、`+Inf <= kExtentLimit` 為 false），
所以四個欄位的 NaN 與 ±Inf 在有沒有 `finite() &&` 時結果都相同。
**這確實是等價突變，CHG 的處置（不補斷言實作寫法的測試，改以兄弟突變 M28 證明受保護）正確。**
K-016 要的「明寫 `isfinite`」理由也成立，該行應保留。

**M31：不成立——它不是等價突變。** CHG 寫「`left + s.width*scale` 與 `(s.x + s.width)*scale`
是同一條 double 算式，差異只在極少數 ULP」。前半句不對：`left` 是
**已經過 `clamp_finite` 的** `s.x * scale`，而且 `x*s + w*s` 與 `(x+w)*s` 在浮點下本來就不是
同一個值。本驗收者用差分探針實測：

```
隨機 3,000,000 組（12 種縮放，x ∈ [-1e6,1e6]，w ∈ [0,1e6]）   → 像素差異 0 組
針對「真值貼著 .5 取整邊界」構造 663,135 組                    → 像素差異 **39,124 組**
  例：x=-311820.55261569237  w=376612.82534296508  s=1.1 → 原式 71271 / 突變式 71272
      x=-451682.21715042065  w=779001.21715042065  s=1.5 → 原式 490979 / 突變式 490978
```

差異是**真的 1 px**，不是 ULP：ULP 差落在 `lround` 的 .5 邊界上就會翻面。
實務機率極低（300 萬組均勻隨機取樣命中 0 次），所以**本驗收者不把它列為缺陷**，
而且 CHG 真正想防的那條（「先各自取整再相加」）確實由 M30 擋住了。
但「**等價突變**」是一個很方便的標籤，這一條**用錯了**：正確的說法是
「存在行為差異，但需要刻意構造，且只差 1 px」。**請 I1 要求 CHG 改掉這個用詞**——
等價突變代表「不可能被任何測試殺死」，而 M31 是可以被殺死的（在反漂移表裡加一組
貼著 .5 邊界的案例即可），只是沒人去加。

## 4. 本驗收者找到的缺陷

### F1 —— **阻擋項**：拒收一份存檔之後，下一次 `save()` 就把它永久毀掉

**這一條是驗收標準第三句的正面反例，可重現，走的是本單元自己的公開 API。**

`save()`（`edit_assembly.cpp:845-866`）**完全不查** `last_intake_`：不論 `restore(name)`
是成功、是 `VersionTooNew`、是 `Malformed` 還是 `MissingVersion`，
`save(name)` 一律把目前記憶體佈局序列化後 `storage_.put(name, text)` 覆寫過去。

最小重現（只用公開 API，**沒有做任何編輯**，就是「開機 → 還原失敗 → 自動存檔」）：

```cpp
ds::layout::MemoryLayoutStorage storage;
storage.put("desktop", USER_FILE);              // 使用者真正的佈局
ds::host::edit::EditAssembly app(storage);      // 開機：記憶體佈局是空的
app.restore("desktop");                         // 被拒收 → 保留（空的）佈局
app.save("desktop");                            // 離開時自動存檔 → **覆寫**
```

本驗收者實跑的五種拒收分類，使用者的佈局**全部消失**：

| 使用者手上的檔案 | `restore` | `save` | 使用者資料還在？ | 覆寫後檔案 |
|---|---|---|---|---|
| 多打一個 tab 縮排 | `Malformed` | **`Ok`** | **否** | 30 bytes（空 elements） |
| 不小心刪掉版本行 | `MissingVersion` | **`Ok`** | **否** | 30 bytes |
| 版本打成 `1,0` | `MalformedVersion` | **`Ok`** | **否** | 30 bytes |
| 新版程式寫的 `2.0` | `VersionTooNew` | **`Ok`** | **否** | 30 bytes |
| `x: 1e400` 手滑 | `Malformed` | **`Ok`** | **否** | 30 bytes |
| （對照）正常檔 | `Ok` | `Ok` | 是 | 142 bytes |

為什麼這是「救不回來」而不是「呼叫端的事」：

1. **相位 1 的後端是 `MemoryLayoutStorage`，沒有版本、沒有備份、沒有 `.bak`。**
   被覆寫就是沒了。CHG §4 以「相位 1 沒有磁碟可以被寫到一半」把原子性論證掉——
   那對**撕裂寫入**成立，但相位 1 真正的資料毀損路徑不是撕裂寫入，是
   **一次完整、合法、通過往返自驗的寫入，蓋掉本層刻意拒絕讀取的資料**。
   `VersionTooNew` 尤其諷刺：本層拒收它正是為了保護它（「不降級」），
   結果下一次 `save()` 就把它刪了。
2. **CHG 的第二道防線寫的是**「載入失敗 → 不把壞狀態寫回；storage 原文原封不動，
   **使用者還改得回來**」。前半句屬實（`restore` 那一瞬間），後半句**不成立**——
   「還改得回來」要求檔案活到使用者去改它，而本單元的下一個正常操作就會把它刪掉。
   32 支復原測試裡的 `EXPECT_EQ(fx.stored(), before)` 全部只跨越 `restore` 這一次呼叫，
   **沒有任何一條斷言跨越「拒收之後的 save」**。
3. **本層有足夠資訊可以擋**：`last_intake_` 就在成員裡，`save()` 不看它。
   標頭、CHG、worklog 三處都**沒有**任何「拒收之後不要存檔」的呼叫端契約
   （本驗收者 grep 過）。
4. 目前 `host/app/` 尚未消費 `EditAssembly`（全庫零呼叫端），所以這是**潛伏**缺陷；
   但本單元就是負責定義這條路徑契約的裝配層，而驗收標準點名的正是這個危害。

**本驗收者不代為修補。** 可能的修法（供 I1 與實作者裁量，非本 ACC 的指定方案）：
`save()` 在 `name` 的上一次 intake 為不可用時回一個新的具名 `SaveStatus`
（例如 `RefusedSourceWouldBeOverwritten`）並拒絕提交，另開一個明確的覆寫入口；
或 `put()` 前先把原文另存一份具名備份。無論哪一種，都需要一條跨越
「拒收 → save」的回歸斷言，否則這個洞沒有任何測試保護。

### F2 —— `edit_property` 的非有限守衛是**淺的**；CHG 自述第 4 條不完整

`edit_assembly.cpp:769` 的守衛是 `value.is_number() && !std::isfinite(value.as_number())`。
值若是 **Map 或 List**，`is_number()` 為 false，守衛整個跳過，裡面的 NaN / Inf
就**經公開 API 進入持久化狀態**：

```
edit NaN bare         -> NonFiniteValue        （擋住了）
edit nested-map NaN   -> Ok                     ← NaN 進到 state
edit Inf nested list  -> Ok                     ← Inf 進到 state
state cfg.inner       = nan   isfinite=0
```

CHG 的「已知限制」第 5 條說「`reset()` **是**那個不消毒的後門，把關交給 `save()`
的往返自驗」——**`edit_property` 是第二個後門**，而 CHG 沒有提到它，也沒有測試覆蓋它。

後果與嚴重性（本驗收者實測）：

- **把關確實有效、且是 fail-closed**：之後的 `save()` 一律 `VerifyFailed`，
  storage 一個位元組都沒被動（這點與 CHG 宣稱一致，是好的）。所以**不是資料毀損**。
- 但**診斷說不出是哪一欄**：`last_message()` 只有
  `往返自驗不通過（Ok）：`——狀態是 `Ok`、原因為空字串。呼叫端拿不到任何線索去定位
  被汙染的路徑。對一個以「具名、可觀測的降級」為設計原則的單元，這是明顯的落差。
- 可以復原，但要**事先知道路徑**：本驗收者實測把 `cfg.inner` 改回 0 之後 `save()`
  仍 `VerifyFailed`（`arr[0]` 還是 Inf），逐一把 `arr[0]` 也改掉才復綠。
  `EditAssembly` **沒有 `remove_property`**，所以除了逐路徑覆寫就只剩
  `remove_element`（整個元件丟掉）或從外面 `reset()`。

不作為阻擋項（fail-closed、無資料毀損），但應補守衛（遞迴檢查）或至少補
「`VerifyFailed` 要說出第一個對不上的元件 / 欄位」，並補測試。

### F3 —— 三條防線沒有任何斷言殺得死（K-012 家族）

本驗收者自行追加三個 CHG 未列的突變，三個都**存活**：

| 突變 | 結果 | 說明 |
|---|---|---|
| **MX5**：拿掉 `to_device_px` 的 `isfinite` 守衛 | **存活** | 註解自己寫「防禦：即使呼叫端漏了」。今日所有呼叫端都先過 `clamp_finite`，故不可達。但它正是 `float-cast-overflow` 的最後一道牆：日後有人新增一個略過 `clamp_finite` 的呼叫端時，刪掉它不會有任何測試紅 |
| **MX6**：拿掉 `resolve_placement` 結尾的 `box.right = max(right,left)` / `bottom = max(bottom,top)` | **存活** | `AbsurdNumbers.ResolveNeverOverflowsTheDoubleToIntCast` 的 `EXPECT_LE(box.left, box.right)` 在有沒有這兩行時**都成立**（夾限本身已保證），所以那兩條斷言對這兩行是**恆真**的 |

三者**都不是缺陷**（都是多餘的保險，刪掉不改變今日行為），但它們說明一件事：
CHG 的「14/14 KILLED、0 存活」只對**它自己挑的那 14 條**成立，本單元確實存在
「有防線、沒有斷言保護」的行。記為保留意見，不作為阻擋項。

  `LogicalPlacement`（`double`）而非沿用 `ComponentPlacement`（`PixelPoint` / `PixelSize`）。
  兩者語意同為邏輯像素但表示型別不同，日後容易漂移。本驗收者判斷**不是缺陷**
  （驗收標準原文未點名 H1-07，且 double 對拖曳累加是合理選擇），但 CHG 應寫明為何
  宣告相依卻不消費。
- **R4（上游，非本單元）**：深層巢狀會打爆堆疊。本驗收者實測（預設 8 MiB stack）：
  巢狀 10000 層（約 50 MB 文件）→ `Ok`；**14000 層（約 98 MB）→ SIGSEGV**。
  把 stack 開到 64 MiB 後同一輸入回到 `Ok`，確認是 `engine/format/` 的**遞迴解析
  ／遞迴解構**耗盡堆疊，不是 OOM。SIGSEGV **不是 try/catch 接得到的**，所以本單元
  「對外不 throw / 不崩潰」的承諾在這個邊界之外。手改存檔到 50 MB 以上不是現實情境，
  故**不作為阻擋項**，但記下：這是「救不回來」的硬下界，且與 F1 不同，它不在本單元可修範圍。
- **R5**：`poll_reload` 先呼叫 `reloader_->poll()`（E7-07 內部已解析一次），再
  `source_->content()` 自行重新解析一次 —— 同一份文字被解析兩次。相位 1 無正確性問題
  （單執行緒、`MemorySource`），但相位 2 接真實檔案監看時，兩次讀取之間檔案可能變動，
  屆時 E7-07 的診斷報告與本層實際採用的內容可能對不上。建議在接真實後端的單元複查。
- **R6**：CHG / 派工說明寫 base 為 `48589a5`，PR #244 實際 base 為 `563375b`
  （該 commit 只動 `docs/backlog/`，程式碼與 CMake 零命中，兩者等價）。文件精確度。

## 10. 判定

**fail** —— 唯一阻擋項為 **F1**：驗收標準第三句
「使用者可直接改動持久化狀態，故錯誤不得讓佈局進入救不回來的狀態」不成立。
五種拒收分類在下一次 `save()` 之後使用者的佈局全部永久消失，該次 `save()` 回報
`Ok`、無警示、無測試、無呼叫端契約；而 CHG 把這塊寫成已被「三道防線」覆蓋。
本單元**有足夠資訊**（`last_intake_`）在本層擋住它，修法很小。

F2 / F3 與 R1–R6 皆**不作為阻擋項**，但 F2（守衛深度與 `VerifyFailed` 的診斷）
建議一併處理，因為它與 F1 同屬「降級要具名、要說得出是什麼壞了」這一條設計原則。

除 F1 之外，本單元的接線正確性、容忍式讀取、版本分流、DPI 語意、上游例外圍堵、
測試密度與突變強度都**達到或超過**本驗收者對 medium 風險單元的預期；
CHG 的可查宣稱絕大多數屬實，不符的 3 項已逐條列出。
