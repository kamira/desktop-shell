## 5. 「不得改變既有合法輸入的解析結果」—— 次正規數那一條，實測而非推論

這是本輪最可能藏退步的一條，也是實作者自己標明「後半是推論、沒有窮舉證明」的那一句。
本驗收者從兩個方向處理。

### 5a. 機制：為什麼「拒絕集合 == 原本會丟的集合」由構造上必然

`/usr/include/c++/13/ext/string_conversions.h:82-90`（libstdc++ `__gnu_cxx::__stoa`，
`std::stod` / `std::stoi` 的共同實作）：

```cpp
const _TRet __tmp = __convf(__str, &__endptr, __base...);
if (__endptr == __str)        std::__throw_invalid_argument(__name);
else if (errno == ERANGE || _Range_chk::_S_chk(__tmp, std::is_same<_Ret, int>{}))
                              std::__throw_out_of_range(__name);
```

`std::stod` 丟 `out_of_range` 的條件**就是** `strtod` 之後 `errno == ERANGE`，
而新實作檢查的是同一個 `errno == ERANGE`。兩者判據同一個，故集合相同不是巧合。
`std::stoi` 多一道 int 範圍檢查，而 `digits_to_int`（輸入已由 `all_digits` 保證無正負號）
恰好在 `> INT_MAX` 時回 `false` —— 判據同樣對齊。

以**同一支差分程式**分別連 `origin/main` 與受驗 head 的 `document.cpp` 編成兩個二進位，
餵同一份 token 語料，逐行比對判定（`THROW <型別>` / `ParseError(line=N)` /

## 保留意見（判定 pass，但記下；皆不構成阻擋）

**(a) 生產呼叫端的數量 CHG 數錯了，而且是往少的方向錯。**
CHG 與測試檔首都寫「八個生產呼叫端」並列舉七類（`permission_store` / `install_store` /
`layout_store` / `ui_state` / 三個 widget）。本驗收者自行列舉 `ds::format::parse(` 的生產呼叫端，
實得 **9 個**，CHG 漏了 `engine/format/hot_reload.cpp:49` 與 `src/kernel/draggable_surface.cpp:271`。
逐檔檢查 `catch` 計數：9 個檔中只有 `content/widgets/note_widget.cpp` 有 1 個 `catch`，
而它包的是 `content_.set_text()`（非法 UTF-8），**不是** `parse()` 呼叫；
`host/app/host_main.cpp` 零 `catch`。
故「無任何呼叫端接得到這個例外」這個嚴重性結論**成立**，數字錯在**低估**暴露面，
不影響本單元任何正確性判定。不在本單元 write_scope 內可改之處（CHG 不在本驗收者寫入範圍），
留給 I1 收尾時更正措辭。

**(b) 「14 條突變、全部被殺、零存活」的計數措辭偏鬆。**
CHG 表格列 **12** 條（M1…M12，其中 M3→M3b、M12→M12b）。「14」是把被作廢的 M3 / M12 也算進去，
而那兩條正是**死在編譯器、未被測試殺死**的。CHG 緊接在表格下方的註解把這件事說清楚了，
所以不是隱瞞；但表頭那一句「14 條突變…全部被殺」與註解內容互相拉扯。記下。

**(c) CHG 的 sanitizer 旗標寫成 `-fno-sanitize-recover=undefined`，CI 實際用 `-fno-sanitize-recover=all`。**
本驗收者以 CI 的 `all` 跑過（第 9 節），結論不變。純為措辭不精確。

**(d) 「拒絕次正規數」是一個設計選擇，值得日後重新考慮。**
`1e-320` 這類語法合法、`strtod` 也給出可用結果的次正規值，現在一律是 `ParseError`。
這**不是退步**（第 5 節已證明它在改動前會終結行程），也符合驗收標準點名
`1e-400`（下溢）須成為 `ParseError` 的意旨，且標頭已把這條契約寫明。
但若日後希望次正規值被當成合法 `Number` 收下，做法是把 ERANGE 細分為「上溢」與「下溢」
（下溢時 `strtod` 的回傳值仍可用）。屬格式語意的擴充，不屬本單元。

**(e) 次正規的判定與標準程式庫實作相關，本輪只在一套工具鏈上量過。**
「ERANGE 是否用於次正規」由 C99 交給實作決定。本驗收者量的是 glibc + libstdc++ 13。
在別的標準程式庫上，**改動前與改動後會一起漂移**（兩者判據同一個 `errno == ERANGE`），
所以「不改變既有行為」這個相對性質仍然成立；會漂移的是「哪些 token 被拒絕」這個絕對集合。
本單元 `platform: neutral` 且不含 `#ifdef`，`strtod` / `errno` 為 C 標準程式庫 —— 此點未違反平台中立。

**(f) 既有且未變：`parse_map_block` 的重複 key 偵測是兄弟數的 O(n²)。**
實測（`-O2`）兄弟數 2000 / 8000 / 16000 → `origin/main` 6 / 120 / 268 ms，
受驗 head 4 / 95 / 261 ms，**兩版相同**。這是耗時而非行程結束，與本單元的驗收標準無關，
純粹記錄本驗收者量到的事實，不屬本單元範圍。

**(g) `errno` 在超範圍解析後留在 ERANGE。**
實測 `origin/main`（`std::stod`，libstdc++ 的 `_Save_errno` 只在 `errno == 0` 時回填）
與受驗 head（`strtod`）**行為完全相同**：超範圍後 `errno = 34 (ERANGE)`，合法解析後 `errno = 0`。
**不是本單元引入的副作用**。

**(h) 理論上的 locale 差異，在本庫不可達。**
非 `C` 的 `LC_NUMERIC` 下，舊版（`std::stod` 不檢查 endptr）與新版（檢查 endptr，
不符即視為非數字）對 `1.5` 的判定原則上會不同。全庫 grep `setlocale` / `std::locale` /
`imbue` 的生產程式碼**零命中**，故 `LC_NUMERIC` 恆為 `"C"`；實測兩版對 `1.5` 皆為
`Number 1.5`。記錄備查，不構成行為差異。

## 判定理由

**Result: pass。**

1. **兩類缺陷的錨點都由本驗收者自寫 probe 在 `origin/main` 上獨立複現**：四種點名輸入
   確實丟 `std::out_of_range`（且確為 `logic_error` 分支），深層巢狀確實 SIGSEGV 139。
   修法有可談的前提，不是對著不存在的缺陷做的動作。
2. **行號是真的**：自行構造 N=2…12（交錯空行與註解，使邏輯行數 ≠ 物理行號）與
   `format_version` 的 N=1…9，回報行號一一正確；深度超限的行號亦由獨立生成器驗過。
3. **反向斷言承重，而且是可歸因的承重**：本驗收者自建的 V1-A 突變讓驗收標準點名的四支
   測試全部照樣通過，**只有**窮舉邊界那一支殺得死它。零存活、零編譯器誤殺、錨點皆命中一次。
4. **實作者自報的 M3/M12 → M3b/M12b 改寫經獨立複核成立**：改寫後兩條都編譯零警告、
   都由測試殺死；它沒有把編譯器的功勞記成測試的。
5. **「不得改變既有合法輸入的解析結果」以 10810 個 token 的逐一差分證明**：
   1784 列差異無一例外都是「老版 THROW → 新版 ParseError」，**零列**是「老版成功 → 新版失敗」。
   本輪原本最可疑的次正規數（`1e-320` 等）在改動前**就會終結行程**，故拒絕它不是退步；
   這一點同時有 libstdc++ `__stoa` 的源碼機制佐證（判據是同一個 `errno == ERANGE`）。
6. **上限 64 的兩端都抽驗過**：下界自寫掃描器得全庫最深 6 層（與宣稱同一個檔）；
   上界以縮小 `ulimit -s` 得 72–80 KiB，對照組證明失敗來自深度而非行程起步，
   預設 8 MiB 餘裕 ≈ 100 倍。宣稱成立且保守。
7. **解構路徑以「回傳樹的真實深度」量測**，不是推論：成功時樹深 ≤ 64，超限時沒有樹；
   至上限樹的複製＋解構、超限例外展開 200 次、清單路徑超限（含深度 60000）全部存活，
   且在 ASan + UBSan + float-cast-overflow 下零診斷。
8. **公開入口逐一列舉逐一測**：`parse()` 與 `parse_scalar()` 在 16 種極端 token × 5 個位置
   加 10 種結構性敵意輸入下 `VIOLATIONS=0`；`parse_scalar()` 原本也會丟，本單元一併修好。
