## 【裁定】反向斷言那一條 —— 三個問題

### (1) `ImageDimensions` 算不算「E4 公開介面上的像素型別」？

**事實先自行核對**（`I1.1` 的更正正確，`I1` 派工裡「現況沒有被違反」那句話是錯的）：

```
modules/elements/image_element.hpp:51  struct ImageDimensions {
                                   :52      int width = 0;   // 固有像素寬；有效來源須 > 0。
                                   :53      int height = 0;  // 固有像素高；有效來源須 > 0。
                                   :49  // 來源影像的固有尺寸（影像自身資料的像素寬高，
                                   //    非螢幕座標 / 非擺放位置；NFR-02）。
                                   :70  virtual ImageDimensions dimensions() const = 0;   ← 公開純虛介面
                                  :122  ImageDimensions source_dimensions;                 ← 公開 RenderModel 欄位
```

`I1` 的樣式為什麼抓不到它，本驗收者實測重現：

```

→ 12 筆，全部是 alpha 合成模式家族（AlphaMode::PerPixel / kPerPixelAlphaCapability /
  AlphaProfile composite_ 的 PerPixel 預設 / alpha_query）。
```

型別名 `ImageDimensions` 與欄位名 `width` / `height` **都沒有 pixel 字樣**，只有註解有；
而 `I1` 的樣式等於問「有沒有 pixel 這個識別字」，不是問「有沒有像素語意的幾何型別」。
`I1` 自己的結論（「我的樣式回答了一個比我提出的問題更窄的問題，而我把窄答案當成寬答案報了出去」）
**正確**，且這正是知識庫「檢查器要對得上被檢查物的實際形狀」的第 N 次現身。

**裁定**：

- **字面**支持「算」：它是 E4 公開介面（純虛函式回傳型別 + RenderModel 欄位）上的整數型幾何欄位，
  註解自己寫「像素」。字面讀「不得出現任何像素型別」，它出現了。
- **意圖**支持「不算」：驗收標準自己把危害機制寫明了 ——「往上滲會在**相位 3 換後端時**才爆」。
  `ImageDimensions` 是**來源影像自身資料的固有尺寸**：一張 PNG 有多少像素，
  換 win32 / cocoa / wayland 後端**不會改變**，也不隨 DPI 縮放、不參與擺放。
  它不在「換後端會爆」的集合內。該標頭 `:49` 也已明寫「非螢幕座標 / 非擺放位置；NFR-02」。
- **本驗收者採意圖讀法，`I1.1` 的判斷成立**：這條驗收標準要防的是 **widget / 螢幕的擺放幾何**
  （座標 / 尺寸 / 偏移）滲上去。`ImageDimensions` 不是那個東西。
  `I1.1` 明說「那是一個判斷，不是一條定理」並提請裁定，處理方式正確。

**但附一條**：這個判斷之所以安全，靠的是「固有尺寸 vs 擺放幾何」這條語意界線，
而那條界線**只寫在註解與基線的 `justification` 字串裡，沒有任何機器形式**。
若未來有人在 `image_element.hpp` 裡加一個真的擺放幾何欄位並取名 `width` / `height`，
基線比對會紅（多一筆）；但若取名後**同時**把現有兩筆挪走，`finding_keys` 只比
`(file, identifier, rule)`、**不含行號**，就比不出差別。此為假想情境，列為保留意見而非阻擋。

### (2) 把它列成具名基線，會不會讓反向斷言對真正的滲透失效？基線機制本身是不是後門？

**不是後門。** 判定依據（自行讀碼 + 突變實證）：

| 後門要成立需要 | 現況 |
|---|---|
| 基線能被悄悄清空 → 退化成「等於空集合」 | **不行**：`BaselineIsNonEmptyAndEveryEntryIsJustified` 釘住 `baseline.size() == 2`、每筆 `file` 必須是 `image_element.hpp`、`rule` 必須是 R3、`justification` 非空。M12（基線變空集合）→ **1 紅**，本驗收者重現。 |
| 掃描器回空集合就過關 | **不行**：斷言是 `==` 而非 `<=`。M11（掃描目標枚舉回空）→ **3 紅**；M13（R3 判定永不成立）→ **4 紅**。**一個永遠回空集合的掃描器在這個斷言下是紅的。** |
| 多出一筆真滲透能被基線吸收 | **不行**：`EXPECT_EQ(got, expected)` 是 **vector** 相等，不是集合包含，連重複鍵都算差異。M8（E4 滲入 `ds::host::PaintBox`）、M9（kernel 滲入 `int widget_offset_px`）各 **2 紅**。 |
| 放寬基線不被看見 | 需要同時改 `host/compose/pixel_boundary.cpp` 的 `expected_baseline()` **與** 測試的 `size() == 2` 斷言，**兩處都在 diff 裡**。 |

結論：`I1.1` 選「具名附理由的基線 + 等於比對」而不是「把規則挖掉」，**方向正確**，
而且比豁免清單嚴格 —— 豁免清單只會放過，等於比對**兩個方向都會紅**。

**真正的洞不在基線，在三條規則的可見範圍**（見下一題）。

## 覆核 `I1` 與 `I1.1` 的 float-cast-overflow 發現

### (a) 這個分界對不對 — **對，逐字重現（g++ 13.3.0）**

```
probe.cpp:  volatile double d = 1e20;  int i = static_cast<int>(d);

g++ -fsanitize=address,undefined -fno-sanitize-recover=all -fno-omit-frame-pointer -g
  （= gate_sanitizers 的旗標）
  → 建置 rc=0；UBSAN_OPTIONS=print_stacktrace=1 ASAN_OPTIONS=detect_leaks=1 執行 rc=0
  → **零報告**，印出 i=-2147483648
g++ -fsanitize=address,undefined,float-cast-overflow -fno-sanitize-recover=all …
  → probe.cpp:4:30: runtime error: 1e+20 is outside the range of representable values of type 'int'
  → 執行 rc=1
```

GCC 的 `-fsanitize=undefined` **不包含** `float-cast-overflow`，故 CI 的 `gate_sanitizers`
對「浮點 → 整數溢位」這一族 UB 沉默。`I1` 與 `I1.1` 的數字與結論**一致且正確**。

### (b) H1-07 自己那兩處夾限是否正確、M18 是否真的釘住 — **正確、真的釘住，且在真實程式上實證**

兩處夾限：

```
host/compose/media_compose.cpp:28  constexpr double kMaxLogicalPx = 100000.0;
                              :35  if (!(logical > 0.0)) logical = 0.0;        ← NaN 走這裡（K-002）
                              :36  if (logical > kMaxLogicalPx) logical = kMaxLogicalPx;  ← 轉型前夾限
                              :37  return std::max(0, scale_logical(static_cast<int>(logical), scale));
host/compose/widget_compose.cpp:53-56  kRoundLimit = 1e18 夾限後才 std::llround，再 clamp_to_int
```

**夾限都在轉型「之前」**，這是關鍵（夾在之後救不了已經發生的 UB）。

本驗收者不只在合成 probe 上驗，**直接在真實程式上驗**：把 M18 套進
**sanitizer 建置**，以 CI 的 `UBSAN_OPTIONS` / `ASAN_OPTIONS` 跑 `test_h1_07`：

```
cmake --build <scratchpad>/Bsan --target test_h1_07   → rc=0、TU=2
UBSAN_OPTIONS=print_stacktrace=1 ASAN_OPTIONS=detect_leaks=1 ./test_h1_07  → rc=1
  sanitizer 報告數（runtime error|AddressSanitizer|LeakSanitizer|SUMMARY:）→ **0**
  唯一的紅：MediaCase.AbsurdPresentationParamsAreClampedNotCollapsedAndNotUndefined
```

**即：在真實程式、真實 CI 旗標下，這個 UB 讓 `gate_sanitizers` 零報告，唯一抓到它的是那條斷言。**
`I1.1` 說「M18 原本只紅 1 條、是突變逼它補強的」—— 該斷言現在的形狀
（巨大值必須夾限成**填滿格位的大按鈕、四顆按鈕仍然存在**；只有 NaN / 負值才算 0）
本驗收者複核為正確，而且它正是 K-002 的解藥：**崩塌成 0 是一個看起來正常的空版面**。

## 保留意見（判定 pass，但記下；皆不構成阻擋）

1. **反向斷言對 `float` 型絕對幾何零覆蓋**（裁定第 3 題）。這是本次驗收最實質的發現：
   `ds::kernel::{ResolvedPlacement, Size, ScreenExtent}` 與 `edge_snapping` 的 `SnapResult::rect`
   是 kernel 公開介面上的絕對擺放幾何，標頭自己寫「像素只在此出現」，而三條規則**結構性**看不到。
   建議另開單元把它們變成具名基線。
2. **`ResolvedPlacement` 把「x, y = 左上角」的原點慣例寫進 kernel 公開介面，而 Cocoa 的
   `NSRect` 原點在左下角。** 相位 3 時這是零診斷的失配。本單元管不到，但正是驗收標準
   擔心的那類失敗。

   同檔內把基線欄位挪位置 / 換所屬 struct 而鍵不變的假想情境比不出差別。
4. **R2 合取的漏抓面與 R3 的結構性漏抓**（見「附帶裁定」）：
   `geometry_words()` 不含 `w` / `h` / `len` / `span`；R3 跳過所有含 `(` 或 `{` 的行，
   故函式宣告與大括號初始化欄位不在視野內。現況經本驗收者寬掃描確認無漏網者，
   但這是「現在剛好沒有」而非「不可能有」。
