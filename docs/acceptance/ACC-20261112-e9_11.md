## 三態與有損投影覆核 — pass

### 三態在查詢介面上真的是三態

讀實作本體（非註解）：`permission_store.cpp:221-231`，`decision()` 查無紀錄回
`PermissionDecision::Undecided`（**不是** `Denied`）；`is_decided()` 即
`decision(...) != Undecided`。`revoke()`（`:254-261`）是 `by_key_.erase(...)` → 紀錄消失
→ 下次查詢回 `Undecided`；`deny()`（`:250-252`）寫入一筆 `Denied` → 留在 `Denied`。
型別是具名三態枚舉（`permission_store.hpp:114-118`），非 `bool`、非 `optional<bool>`。

自建探針 B（31 項斷言，ASan + UBSan 下跑，**全部成立**）：

```
B1 三態可區分        ok 未決/已授予/已拒絕三個值皆不同；ok 三者兩兩不等（沒有塌成兩態）
                     ok is_decided 區分未決與已拒絕
B2 revoke vs deny    ok revoke 後回到 Undecided；ok deny 後停在 Denied
                     ok 撤銷過的進 gate.undecided（該再問）；ok 被拒的進 gate.denied（不再問）
                     ok needs_prompt() 為真（因為有未決）
```

**`revoke()` 與 `deny()` 在每一條查詢路徑上都沒有塌成同一個狀態**：`decision()`、
`is_decided()`、`PermissionGate.undecided` / `.denied`、`needs_prompt()`、
`permissions_awaiting_decision()` 六條路徑全部能區分。使用者裁定的「Q-C 權限在安裝時問」
因此實作得出來（探針 B8 另驗：已拒絕 + 已授予 → 待問清單為空；把已拒絕那項 `revoke()`
之後 → 該項**又回到待問清單**，正是「可以再問」）。

### 有損投影的方向 —— 讀實作本體，不看註解

`permission_store.cpp:354-370` 的 `compose_host_environment` 本體：

```cpp
for (const std::string& perm : permissions) {
    if (ledger.decision(package_id, perm) == PermissionDecision::Granted) {
        env.grant_permission(perm);
    }
}
```

條件是 `== Granted`（白名單），**不是** `!= Denied`（黑名單）。`Undecided` 與 `Denied`
都不呼叫 `grant_permission()`。**不存在「未決當樂觀預設授予」的路徑。**
探針 B3 實測：`Granted` → 進集合；`Undecided` → **不**進集合；`Denied` → 不進集合。

### `loadable` 為真 iff 每一項宣告的權限都是 `Granted`

`permission_store.cpp:342`：`gate.loadable = gate.withheld.empty();`，而 `withheld` 在
`Undecided` 與 `Denied` 兩個 case 各 `push_back` 一次（`:331-338`）。故
`loadable ⇔ 沒有任何一項是 Undecided 或 Denied ⇔ 每一項都是 Granted`。

探針 B4 以「逐項加授權」掃過整條邊界：

```
ok 0/3 授予 → 不可載入      ok 1/3 授予 → 不可載入
ok 2/3 授予（部分授權）→ 不可載入          ← 「部分授權也可載入」的路徑不存在
ok 3/3 授予 → 可載入
ok 其中一項改拒絕 → 立刻不可載入
```

### 測試結構（讀本體，不看案例名稱）

### 撤銷落盤

`permission_store.cpp:254-261`：`revoke()` 在 `erase` 成功後**呼叫 `flush()`**；
`revoke_package()`（`:263-280`）在 `removed > 0` 時 `flush()`；`set()`（`:233-244`）在狀態
真的改變後 `flush()`。三條寫入路徑都是 write-through。

探針 B6 實測（新物件 / 同後端）：

```
ok 重啟1：授予活過來            ok 重啟1：拒絕活過來（沒退回未決）
ok 重啟2：撤銷也落盤（沒變回已授予）          ok 重啟2：拒絕仍在
```

「已授予 → 撤銷 → 重啟 → 又變成已授予」這個靜默降級**不存在**；M1 突變（移除 `revoke()`
的 `flush()`）正是打這一點，而它確實打紅 3 個案例（見下）。

**誠實邊界（與 E9-10 同）**：相位 1 無真實行程重啟可測、engine 層不得有真實檔案 I/O
（G1b / `PHASE-PLAN.md`），後端是 `MemoryInstallStorage` 這個**記憶體替身**。「重啟」
= 「後端存活、狀態物件解構後重新建構」。CHG 與 `.hpp` 檔首都明說了這一點，**沒有把替身
說成真實持久化**。本驗收者認可此為相位 1 唯一合法的模型，但它**不是**真實跨行程持久化的
證據 —— 相位 2 換上真實磁碟後端時這一條需重驗。

### `missing` 的內容與順序

驗收標準要求「`missing` 附缺項」，只斷言 status 不夠。實作者的兩項宣稱逐一覆核：

1. **內容與順序都釘住** —— 成立。
   `Gate.DeniedPermissionMakesLoadFailAsMissingPermissionWithTheMissingItemListed`（:513）
   斷言 `r.missing == {"net.connect"}`（**不是**空清單、**不是**全部權限）、
   `r.message` 非空、且 `r.missing == evaluate_permissions(ledger, pkg).withheld`。

   以 `a.denied, b.granted, c.undecided, d.denied` 四項交錯宣告，釘住
