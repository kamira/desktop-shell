## 實作者請我覆核的三點

1. **`MetricValue` 封閉性是否足夠** — **足夠。** 主維度 `number`（供繪圖 / 正規化 / 歷史）＋
   可選 `text`（列舉 / 顯示表述，如 "Charging"、"82°C"）＋ `valid`（未知保守預設 false）三者
   對任意指標皆可渲染（數值、或文字、或未知），且刻意不塞更多型別以維持最小。屬合理封閉。
   *保留意見（非阻斷）*：`operator==` 在 `valid==false` 時仍比較 `number`／`text`，故兩個「未知
   但 number 不同」的值會判不等。目前所有 `unknown()` 皆 number==0，測試未觸及此角，語意無害；
   若日後有「帶殘值的未知」需求可再收斂。

2. **instance 為第一級是否恰當** — **恰當。** 單值指標＝恰一個實例（`kSingleInstanceId ""`），
   多實例（每核心 / 每磁碟）＝列舉多個，消費者一律走 `instance_count()` + `instance(i)`，
   無需為單值特例分叉。這讓六要素中的「可列舉實例」成為第一級而非附掛，正合平台「不限於」
   的主軸；單值指標需 `add_instance` 一次的小儀式成本可接受。

3. **重複 id 保守拒絕是否合理** — **合理。** `register_metric` 遇重複 id 回 `false` 且不覆寫，
   理由（兩感測器爭同一 id 是 bug，不該靜默勝出）成立；配合 `add_provider` 回「本次成功新增數」，
   可在不崩潰下讓衝突可見。已由 `RejectsNullEmptyIdAndDuplicate` 與 `AddProviderReportsOnlyNewlyAdded`
   覆蓋。優於 last-wins 或直接擲例外。
