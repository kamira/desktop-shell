   讀法，本單元不滿足它 —— 新元件型別的**投影**那一步必須由認得其 `RenderModel` 型別的人
   提供，這是 C++ 型別系統的必然，`widget_render.hpp` 檔頭也寫明了。
4. **內建 renderer 不吃 `WidgetRenderer::metrics_`。** `draw_linear` / `render_progress` /
   `render_gauge` 都用 `default_row_metrics().track_half_height`（固定 5），而
   `paint()` 的列幾何用 `metrics_`。若呼叫端用 `set_metrics()` 改了 `track_half_height`，
   `RowGeometry.track` 會變而**實際畫出來的軌道不會變**。repo 內目前沒有任何呼叫端用
   `set_metrics()`（已 grep 確認），故是潛在的不一致而非現行缺陷。根因是 `ElementRenderer`
   的簽章只收 `(draw, area, sink)`，拿不到 metrics。
5. **`PaintSummary.drawn` 的語意比註解弱。** 註解寫「成功分派並畫出元件的筆數」，實際
   `ElementRendererTable::draw` 只要 kind 查得到且 `area` 非空就回 `Drawn`，renderer
   內部可能一筆指令都沒下（例如 `render_gauge` 遇到 `dial.empty()`、`draw_linear` 遇到
   `track.empty()`）。`RadialKind.DegenerateAreaIsReportedAndNothingIsDrawn` 自己就
   斷言 1×1 錶盤「仍是合法面積」→ `Drawn`。它實際是「分派成功的筆數」。
6. **`gauge` 的錶盤是實心方塊，不是弧。** `render_gauge` 以 `fill_box(dial, Track)` 畫底盤
   —— `PaintSink` 只有三個原語、沒有弧 / 環，這是刻意的設計目標（新 kind 不得要求平台新增
   原語）。後果是 CPU 在畫面上從「細長條」變成「實心方塊 + 一根線」。這是不是「不退步」
   屬於視覺判斷，**本驗收者無法驗**：本機無 MSVC、無 Windows，沒有人在真實螢幕上看過改寫
   後的畫面（`gate_windows` 證明的是「建得起來、像素測試通過」，而 `test_h1_01` 的像素
   斷言用的是預設 kind `Bar`，碰不到 gauge 這條路徑）。列為人工核准停點時值得看一眼的事。
7. **`track_strip` 的中心線公式在負座標下與舊式不等價。** 舊 `y + row_h/2`，新
   `(cell.top + cell.bottom)/2`；`cell.top = y ≥ 0` 時兩者恆等（已證），但 C++ 整數
   除法向零截斷，`2y + row_h` 為負時兩者會差 1。repo 內沒有任何呼叫端傳負的 `bounds`。
8. **`host_main.cpp` 尚未註冊任何新 kind（CHG §已知限制 3），而那一步一做就會製造出
   repo 第一個同時連進兩份 `ds::elements::RenderModel` 定義的 target**（`desktop_shell_host`
   已經經 `c2_02` 拉進 `e4_03`）。本驗收者的探針 3 顯示那會是**安靜讀到錯值**、零診斷。
   做這一步之前必須先處理型別衝突（C1-06 / C2-07 的 pimpl 橋接是 repo 內的現成範式），
   或維持兩側分離。這一條交回 `I1`（知識庫寫入是 `I1` 職責，本驗收者未改 `errors.md`）。
9. **CHG 的 `Autonomy` 未宣告、`## Status` 仍為 `Paused`** —— 符合契約（實作者不自我驗收、
   收尾由收尾者改）。本驗收者**未改** CHG 的 Status。

   `register_kind` / `add_projector` / `params` 三個擴充點逐一改壞，全部被打紅。
