- Project: desktop-shell

- Status: Confirmed
- 配套：`docs/architecture.md`（分層與擴充點）、`docs/ai-guideline.md`（可驗收條款）、

---

## 一句話

一個桌面平台核心：提供監測、互動、視窗、繪製等子系統，讓第三方組件掛上去，
在桌面上長出監控面板、桌面角色、召喚式啟動器或任何別的東西。

**本次主要需求是 `core` 與 `module`。** `artifact` 是後續範例，它們的角色是驗證擴充點真的能用。

---

## 為什麼是一個平台，不是一個工具

起點是四個各有十年開發史的產品：Rainmeter（系統監控）、end-4 illogical-impulse
（Linux 桌面 shell）、SAO Utils（ACG 風格啟動器）、伺か Ukagaka（桌面角色）。
攤平列出得到 220 個候選功能。

若照產品分組，這是四個專案的聯集，做不完。但按**功能類型**重新分類後，它們塌縮到
15 個原語上，其中五個——alpha surface、圖層、輸入策略、命中測試、命令匯流排——
就撐起約七成的項目。

四個產品的差異其實只是同一組視窗原語的四種參數取值：

| 呈現形態 | 圖層 | 輸入策略 | 命中策略 | 生命週期 |
|---|---|---|---|---|
| 監控面板 | 桌面層 | 穿透 | 部分區域 | 常駐 |
| 桌面角色 | 桌面層偏上 | 可互動 | **具名區域** | 常駐 |
| 召喚面板 | 最上層 | **獨占焦點** | 全域 | 召喚式 |
| 短暫浮層 | 最上層 | 不可互動 | 無 | 短暫 |

第三欄的矛盾是全案技術風險最高的地方：監控面板必須永遠不取得焦點，召喚面板必須
強制搶到前景，而**兩者要在同一個行程內共存**。這是唯一真正困難的部分，其餘多半
是工作量不是難度。

看清這點之後，那四個產品就不再是四個目標，而是**四個驗證核心的範例**。

## 核心與組件

```
platform + engine + module（本次主要需求，152 項）
├── 監測子系統   CPU / GPU / 記憶體 / 儲存 / IO / 網路 / 電池 / …
├── 互動子系統   事件、命令分派、致動器
├── 視窗子系統   surface kernel、四參數 profile
├── 繪製子系統   paint / transform / clip / text 基座
├── 描述子系統   宣告式格式、變數、求值
├── 擴充子系統   腳本引擎、模組載入
├── 封裝子系統   套件格式、manifest、持久化
└── 介接 / 宿主 / 治理

artifact（產出物 / 驗證器，24 項）
├── CPU Usage Widget
├── GPU Usage Widget
└── …
```

| 層 | 現況 | 內容 |
|---|---|---|
| **platform** | **30** | 對系統的操作（`src/**`）—— 換平台只有這裡要改 |
| **engine** | **64** | 平台中立的引擎邏輯（`engine/**` 62 + 後端契約 E1-25/E1-26 於 tests/scripts）—— 換平台一行不動 |
| **module** | **58** | 掛在擴充點上的提供者：`sysinfo` 25 / `elements` 22 / `actuators` 11 |
| **artifact** | **24** | 桌面上顯示的產出物：profiles 7 / widgets 9 / 內容 3 / apps 5 |
| 合計 | **176** | |

> `platform` + `engine` = 平台本身（先前合稱 `core`，94 項）。

> 分層寫在 `units.json` 的 `layer` / `subsystem` 欄位，機械可複算。
> 草案原記「核心 160 / 組件 21 = 181」，與現況相差 5 個單元（僅 `E8-06` 有定義，其餘 4 個無出處）。
> **派工一律以 `units.json` 為準**，見 `docs/architecture.md`。

### 產出物（artifact）的角色是驗證，不是功能

CPU Usage Widget 的意義不是「有一個 CPU 掛件」，而是**證明監測子系統的擴充點
真的能被外部使用**。所以組件不是有空再做的功能，是每塊核心能力的驗收條件。

推論：**沒有驗證器的核心能力不該先做。** 沒有消費者就設計 API，形狀只能靠猜，
而錯誤會在寫第 20 個組件時才浮現，那時已有 19 個要改。

### 平台的實質內容是五個擴充點

| # | 擴充點 | 契約 | 掛什麼 |
|---|---|---|---|
| 1 | 指標 | 統一指標介面（名稱/值/單位/範圍/歷史/列舉實例） | 感測器：CPU、GPU、任意來源 |
| 2 | 元件 | 繪製基座 + 元件註冊 | 視覺元件：長條、直方圖、任意型別 |
| 3 | 動作 | 命令匯流排 | 致動器：音量、電源、任意副作用 |
| 4 | Profile | 四參數（圖層／輸入策略／命中策略／生命週期） | surface 型態 |
| 5 | 腳本 | 腳本引擎 + 模組載入 | 行為與自訂邏輯 |

擴充點 1 決定了「包含但不限於」能不能成立。若組件直接相依個別感測器，每加一個
指標就要改組件——那不是「不限於」，是「限於當初寫進去的那幾個」。

## 四階段，每階段配一個驗證器

| 階段 | platform | engine | module | artifact | 合計 | 驗證器 |
|---|---|---|---|---|---|---|
| **A** | 26 | 52 | 34 | 5 | **117** | CPU/GPU Usage Widget |
| **B** | 2 | 9 | 9 | 4 | **24** | 最小角色範例 |
| **C** | 2 | 1 | 7 | 2 | **12** | 最小啟動器範例 |
| **D** | 0 | 2 | 8 | 13 | **23** | 最小浮層範例 |

階段 A 佔全部單元 66%、佔平台本身（platform+engine）83%。B/C/D 的能力目前沒有消費者，所以排後面——不是不重要，
是現在設計它們的 API 等於猜。

**每階段的完成定義**：核心能力做完，**且**該階段範例在不修改 `src/` 的前提下
載入運作。測試斷言 `src/` 的 git diff 為空。

## 三個定案決策

### 目標平台：先 Windows，之後跨平台

四個參考品有三個是 Windows 原生。而 Windows 唯一比 Linux 難的那幾件事——工作區管理、
系統匣接管、通知守護——在本專案裡本來就該排除：它們是桌面環境的職責，不是桌面平台的。

代價是一條硬約束：**核心 API 不得出現絕對座標與數字 z-order。** Wayland 沒有全域
座標系，client 不知道自己在哪也不能自己定位。所以 `setPosition(x, y)` 在 Wayland
上不是難以實作，是**無法表達**。定位一律走 `anchor(edge, offset)`，圖層一律走具名
列舉，自由定位標記為可失敗的能力。

### HTML 渲染引擎：獨立行程隔離、選配

只有「桌面上放網頁」這一個組件真的需要渲染引擎。AI 對話、圖庫瀏覽、網頁抓取
常被誤以為需要，實際都不需要（後者是 HTTP + 解析，不是渲染）。

要警惕的效應：一旦桌面上能放網頁，所有人——包括自己——都會拿它當萬用出口，因為
寫 HTML 比寫描述語言容易。三個月後原生組件系統萎縮，描述語言沒人用，而你做出了
一個步驟更多的 Electron。抑制手段：**第一版的 web 組件不接指標介面**。

### 格式與擴充介面：從第一版就帶版本

平台的產品就是它的 API 面。格式與模組介面從第一版起帶版本欄位與相容策略——
不是為了外人，是因為**你自己的組件就是這個 API 的第一批消費者**。

不做的是沙箱、崩潰隔離、線上分發、工作坊。

## 硬性約束

| # | 約束 | 為什麼 | 怎麼驗 | 狀態 |
|---|---|---|---|---|
| 1 | idle 記憶體與 CPU 門檻 | 24/7 常駐。這是驗收指標，不是效能優化議題 | 常駐 30 分鐘後量測 | 待 NFR-01 |
| 2 | 核心不得出現絕對座標與數字 z-order | 否則跨平台是重寫不是移植 | 建置期 lint（`E1-22`） | **CI 尚無建置步驟** |
| 3 | 能力閘控 API 必須有 `has()` 保護 | 同上 | 同上 | **同上** |
| 4 | 契約測試不得包含平台分支 | 一旦分平台，它就不是契約，是兩套各自為政的測試 | `backend_guard.py` | **已實作 ✓** |
| 5 | 組件載入不得需要修改核心 | 否則擴充點是假的 | `E8-06` 斷言 `src/` diff 為空 | 待 `E8-06` 入 units.json |
| 6 | 較早階段不得依賴較晚階段 | 被依賴者應提前，而非讓依賴者延後 | `stage_check.py`（G1c） | **已實作 ✓** |
| 7 | 描述格式錯誤須定位到行 | 靜默失敗會讓描述語言變成不可用 | 單元測試（`E7-06`） | 待實作 |
| 8 | 每個 PR 的變更落在該工作單元宣告的範圍內 | 讓「不得擴權」從紀律變成機器強制 | `scope_check.py` | **已實作 ✓** |

## 分相位（與階段正交）

開發機目前是 macOS，目標平台是 Windows。**Mac 期是對抗平台語意滲漏最強的時機**——
沒有任何真實平台可以滲進來。

風險不是編不過。QML 在 Mac 上編得很順，這才是危險處：核心會安靜地長成 macOS 的
形狀，而你察覺不到。

關鍵是把「平台耦合」拆成兩類，用相反策略：

| 類別 | 現況項數 | 特徵 | Mac 期做法 |
|---|---|---|---|
| **語意分歧** | 29（**全部在 core**） | 不同平台的「意義」不同——Wayland 不能自搶焦點、沒有全域座標 | **只寫介面 + null 後端 + 契約測試，禁止真實後端** |
| **API 分歧** | 34 | 語意一致，只是呼叫方式不同。CPU% 在哪裡都是 CPU% | **可直接實作 macOS 版**，之後補 Windows 版 |
| **平台中立** | 113（`engine` 64 + `module` 24 + `artifact` 24 + `platform` 1） | 與 OS 無關 | 照常做 |

把兩者用同一種策略處理是主要失敗模式：對前者太寬鬆會長歪，對後者太保守會白白
閒置 34 個現在就能做的單元。

**`engine` / `module` / `artifact` 三層合計 146 項，語意分歧為 0**——29 項語意分歧全部集中在 `platform`。
因此契約定稿後，這 146 項與平台後端完全無關，可無限並行。

**相位 1（Mac）** 強制起手是能力矩陣 → 契約測試組 → null 後端——契約先於實作，
否則測試會照著後端寫。`backend_guard.py` 在 `src/kernel/backend/` 出現 `win32/`
或 `cocoa/` 時直接讓 CI 紅燈。

**相位 2（Windows）** 的回收點：**契約測試一行都不用改**。同一組測試在相位 1 被
null 後端驗過，現在拿去跑 win32 後端。守住了就是換後端，沒守住就是重寫。

## 明確不做

以下不是暫時不做，是**決定不做**，避免六個月後被重新提出：

- **桌面環境職責**：工作區管理、系統匣接管、通知守護、鎖定畫面。鎖定畫面尤其：
  Windows 的 Winlogon 不可取代，自製的只是吃輸入的全螢幕視窗，Ctrl+Alt+Del 就破。
- **相容既有格式**：不吃 Rainmeter 的 INI skin、不實作 SHIORI 協定、不相容既有 SSTP。
  四個參考品的功能聯集在任何一個既有格式裡都表達不出來，硬相容只會讓核心被最舊的
  那個格式綁架。
- **開放式第三方生態的治理設施**：沙箱、崩潰隔離、線上差分更新、工作坊。
- **HTML 正則抓取**：對方改版即失效的維護黑洞。HTTP + 結構化解析保留。
- 完整清單（31 項）見 `desktop-shell-scope-v1.md` 附錄 A。

## 成功長什麼樣

**階段 A（相位 1）**：核心能力就緒，CPU/GPU Usage Widget 在不修改 `src/` 的前提下
載入並顯示正確數值。契約測試組全綠，相位閘門通過，idle 資源達標。

**階段 A（相位 2）**：同一組契約測試在 win32 後端上通過。實機目視確認面板位於
桌布之上、一般視窗之下。

**整體**：任何人（包括你自己）能寫一個新組件掛上去，而不需要動核心一行。

**不是**功能對齊任何一個參考品——那是四個十年產品的聯集，不是驗收條件。

## 什麼會讓這個專案失敗

1. **輸入策略共存做不出來。** 「不搶焦點的面板」與「獨占焦點的 modal」在同一行程內
   共存，是全案最可能翻車的地方。做不出來的話語言選擇要重議，而且要在相位 1 就知道。
2. **平台語意滲進核心。** 靠自制力守不住，所以有 lint 與 backend_guard。但機械閘門
   只擋得住已知模式，設計層面的滲漏擋不住。
3. **擴充點設計錯誤。** 五個契約若形狀不對，會在寫第 20 個組件時發現，那時已有
   19 個要改。這是為什麼每階段都綁一個驗證器。
4. **資源門檻守不住。** 24/7 常駐的東西，idle 吃掉 300MB 就沒人會留著它。這條在
   相位 1 就要量，不能等功能做完。
5. **範圍蔓延。** 220 個候選項目擺在那裡，每一個看起來都只要「再加一點」。
   `P2` 與 `OUT` 的判定就是為了對抗這件事，改判要開 CHG。
