# 相位計畫 — Mac 期 → Windows 期

## 為什麼要分相位

開發機是 macOS，Q1 定案是 Windows 優先。直覺會覺得這是阻礙，但只要加一道機械閘門，
Mac 期反而是**對抗平台語意滲漏最強的時機**——因為沒有任何真實平台可以滲進來。

風險不是「編不過」。QML 在 Mac 上編得很順，這才是危險處：kernel 會安靜地長成
macOS 的形狀，而你察覺不到。`scripts/backend_guard.py` 就是為此存在。

## 三種平台關係，兩種相反策略

| 類別 | 數量 | 特徵 | Mac 期策略 |
|---|---|---|---|
| **語意分歧** | 29 | 不同平台的「意義」不同。Wayland 沒有全域座標系、client 不能自搶焦點——不是難以實作，是**無法表達** | **只寫介面 + null 後端 + 契約測試。禁止真實後端。** |
| **API 分歧** | 34 | 語意跨平台一致，只是呼叫方式不同。CPU% 在哪裡都是 CPU% | **可直接實作 macOS 版**，相位 2 補 Windows 版 |
| **平台中立** | 113 | 與 OS 無關 | 照常做 |

**把兩者用同一種策略處理是主要失敗模式**：對語意分歧項太寬鬆會長歪，對 API 分歧項
太保守會白白閒置 34 個可以現在做的單元。

## 相位 1（Mac）

- 允許後端：`null`
- 可推進：**144 / 176 單元**
- 語意分歧項的「完成」定義：介面定稿 + null 後端通過契約測試 + 能力矩陣涵蓋該能力
  —— 這些單元在相位 2 會**另開 CHG** 補真實後端，不算重做

### 起手三項（必須最先完成，順序不可換）

| 序 | 單元 | 為什麼在最前面 |
|---|---|---|
| 1 | `E1-21` 能力矩陣宣告檔 | 沒有它，「哪些能力可能不存在」無處記載 |
| 2 | `E1-25` kernel 契約測試組 | 定義「任何後端必須滿足什麼」。**寫在後端之前**，否則測試會照著後端寫 |
| 3 | `E1-24` null 後端參考實作 | 契約的第一個實作。跑得起來就證明介面沒綁平台 |

`E1-01`/`E1-02`/`E1-03` 已改為相依 `E1-25`——契約先於實作，機器強制。

### 機械保證

| 閘門 | 擋什麼 |
|---|---|
| `E1-22` 能力閘控 lint | kernel 呼叫可能不存在的能力卻沒有 `has()` 保護 → 建置失敗 |
| `E1-26` / `backend_guard.py` | 相位 1 出現 `backend/win32/` 或 `backend/cocoa/` → CI 紅燈 |
| 契約測試平台分支檢查 | `tests/contract/` 出現 `sys.platform`、`win32`、`darwin` 等字樣 → CI 紅燈 |

第三道最容易被忽略：契約測試一旦分平台，它就不再是契約，是兩套各自為政的測試。

## 相位 2（Windows）

- 允許後端：`null`, `win32`
- 工作：29 個語意分歧項的 win32 後端 + 34 個 API 分歧項的 Windows 實作
- **契約測試不改一行**。它們在相位 1 已被 null 後端驗證過，
  現在拿同一組去跑 win32 後端——這才是相位 1 的投資回收點

### 切換程序

1. 開一份 CHG 記錄相位切換決策（Risk: medium）
2. 更新 `docs/backlog/phase.json` 為 `{"phase":2,"allowed_backends":["null","win32"]}`
3. 對每個 `backend_followup: true` 的單元開後續 CHG

## 相位 3（跨平台，若走到）

- 允許後端：`null`, `win32`, 以及 wlroots / cocoa 其一
- 此時能力矩陣裡的 `⚠` 項（`E1-08` 拖曳、`E1-09` 吸附、`E5-12` 手勢）會第一次真的回報
  `has() == false`。若相位 1 的紀律守住了，這裡只是換後端；沒守住，就是重寫。
