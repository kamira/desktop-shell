## 一、`float-cast-overflow`

### 它不是空轉：先證明 `-fsanitize=undefined` 不含它

```
g++ (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
程式：volatile double d = 1e30; sink = static_cast<int>(d);

-fsanitize=address,undefined -fno-sanitize-recover=all
   → rc=0，印出 sink=-2147483648          ← 完全靜默
-fsanitize=address,undefined,float-cast-overflow -fno-sanitize-recover=all
   → rc=1，runtime error: 1e+30 is outside the range of representable values of type 'int'
```

所以少了它不是「少守一點」，是**那一整類轉換完全沒人看**。

### 加之前先量現況，不是賭

```
目前的樹（main 6f0c8a2 + 本分支回寫）全建於新旗標下：
  configure rc=0 / build rc=0
  ctest -j 4 → 100% tests passed, 0 failed out of 185
  float-cast-overflow 報告 → 0
  任何 runtime error / AddressSanitizer / LeakSanitizer → 0
旗標真的進了編譯命令列（不是被 CMake 吃掉）：
  CMakeCache CMAKE_CXX_FLAGS:STRING=-fsanitize=address,undefined,float-cast-overflow …
  flags.make  CXX_FLAGS = -fsanitize=address,undefined,float-cast-overflow … -Wall -Wextra
```

**前次量測（183/183）是在 `15194cf` 上做的，不能沿用**——`H1-07` 之後多了
`host/compose/pixel_boundary.*` 與兩支測試，而那正是浮點轉整數最密集的地方。重量過。

### 再證明它抓得到它宣稱抓的東西

在**真實 repo 程式碼**裡植入一個溢位（`tests/h1/test_h1_07_pixel_boundary.cpp` 末端加一個
`static_cast<int>(1e30)` 的探針），重建該 target 後：

```
ctest rc=8
test_h1_07_pixel_boundary.cpp:367:28: runtime error: 1e+30 is outside the range …
The following tests FAILED:  93 - h1_07_pixel_boundary (Failed)
```

探針已移除，`git status` 對 `tests/h1/` 零輸出。

### 它抓不到什麼（界線要寫清楚）

**抓不到 `K-002` 那一族。** `palette.cpp:16` 的 `clamp01(NaN)` → `std::lround(NaN)` 的
定義域錯誤不在 UBSan 涵蓋內，加這一個旗標**補不到**。兩者是不同的洞，
不要因為多了這一條就以為浮點轉換已全部守住。這句話也寫進了 workflow 的註解裡。

### 我修掉的一條自家空轉斷言

`test_address_and_undefined_are_both_enabled` 原本是**在整份腳本裡**找 `address` / `undefined`
——而這兩個字在上面的註解裡也出現，所以把 `-fsanitize=` 整段刪掉它仍會通過。
那是 **`K-012` 的形狀**，而且本 session 已在 `test_g3_builds_with_ds_werror_on` 犯過一次同樣的錯
（突變 M5 存活）。改成只看 `SAN=` 那一行，並以突變證明它現在會紅（M2）。

## 二、G3c 單元必須在 ubuntu 留下可見的測試

### 它補的洞

`G3b` 擋「測試數下降」。擋不住另一個方向：**一個全新單元一上線就整份躲在 `if(WIN32)` 裡**
——數字沒有下降，只是沒有上升，於是 G3（`>0`）、G3b（不降）、sanitizer 一致性
（兩個 ubuntu 建置一起看不到它，故相等）**三道全綠**，而該單元在 ubuntu 的覆蓋從來不存在
（沒經過 `-Werror`，也沒經過 ASan/UBSan）。

### ⚠ 這不是假想：`H1-05` 現在就是如此（已合併）

```
units.json          H1-05  platform: neutral
host/position/CMakeLists.txt
    if(WIN32)
      …
      # H1-05 邊緣吸附：純幾何，與位置換算同一個單元目錄（同樣不碰 Windows API）。
      add_executable(test_h1_05 …)
      add_test(NAME h1_05_edge_snap COMMAND test_h1_05)
    endif()
```

**該檔自己的註解就寫著「不碰 Windows API」**，卻只因為與 `H1-03` 共用目錄而被包進守衛。
結果：`h1_05_edge_snap` 在 ubuntu 從未建置、從未經 `-Werror`、從未經 sanitizer。
這是本檔要擋的那個失效模式的**活體實例**。

**本檔不修它。** 修法不是把 `add_test` 搬出守衛就好——`test_h1_05.cpp` 連的是
`h1_03_position`，而 `host/position/position_store.cpp` 直接 `#include <windows.h>`，
所以要先把純幾何部分拆出來。那會動到**已合併單元**的結構，依既定規則必須另開單元。
**已向人類提出待裁定。**

### 為什麼不是一律要求，而是依 `platform` 分流

人類核准的字面做法是「`feat/<slug>` 至少一個同名測試」。**先量，發現字面做法會誤殺。**
對 194 個已合併單元實測（以 `ctest -N` 的真實註冊表比對，非靜態推斷）：

| 規則 | 歷史誤殺 | 誤殺者 |
|---|---|---|
| 一律要求 ubuntu 同名測試 | **13** | `W1-01`…`W1-06`、`H1-01`…`H1-04`、`E1-24`/`25`/`26` |
| 僅 `platform: neutral` 要求 | **3** | `E1-24`/`25`/`26` |
| 非 neutral 者改要求 Windows 同名測試 | **6** | `W1-01`…`W1-06`（全族採描述式命名） |

**而下一個待派的 `W1-07` 正屬會被誤殺的那一族**（`platform: semantic-divergence`，
同族的 `W1-01`…`W1-06` 用的是 `backend_win32` / `tray_icon` / `owner_drawn_menu`
這種描述式測試名，沒有一個含 slug）。字面照做會在我派下一個單元時當場紅燈。

所以採第二列：**只對 `platform: neutral` 的單元要求**。剩下 3 個歷史誤殺是 wave 1 的
bootstrap 單元（`E1-24` 的驗收標準本就寫明「契約測試組（E1-25）全綠」，覆蓋由別的單元提供），
以 PR 內文的豁免行處理。

**我沒有加 Windows 側的對稱檢查**：它會誤殺整個 W1 族，而統一命名要動 6 個已合併單元。
`gate_windows` 的硬編碼點名清單（只有 4 個名字）因此仍然覆蓋不全——**承前，未關閉。**

### 判定邏輯與 fail-closed

```
platform=neutral                      → 要求 ubuntu 註冊表中有名稱含 <slug> 的測試
platform=api-divergence|semantic-…    → ::notice:: 跳過（覆蓋由 gate_windows 負責）
其他（含空字串）                        → ::error:: fail-closed
豁免：PR 內文行首 ^ALLOW-NO-UBUNTU-TEST: <理由>
```

未知值一律紅燈，是因為多一個靜默放行的分支，就等於把這道閘門的生效與否
交給 `units.json` 的一個手誤來決定。

### 測試與突變（19 條行為測試，7 個突變全部被擋）

測試以 **PATH 上放一支假 `ctest`** 的方式跑**整段真腳本**，所以連
`sed -n 's/^ *Test *#[0-9]*: *//p'` 的名稱抽取都在覆蓋內——它抽錯的話整道閘門會對
每個單元都說「0 個同名測試」，那是會誤殺一切的失效模式。

| 突變 | 預期 | 實得 |
|---|---|---|
| M1 拿掉豁免的行首 `^` 錨點 | 散文提到標記就開後門 → 紅 | ✅ 1 條失敗 |
| M2 未知 platform 改成靜默跳過 | fail-open → 紅 | ✅ 2 條失敗 |
| M3 拿掉 `grep -c` 的 `\|\| true` | 零命中時腳本提前中止（K-011）→ 紅 | ✅ 4 條失敗 |
| M4 判斷式改成永不成立 | 閘門空轉 → 紅 | ✅ 6 條失敗 |
| M5 拿掉 `is_unit` 限定 | infra 分支被誤殺 → 紅 | ✅ 1 條失敗 |
| M6 弄壞 `sed` 名稱抽取 | 永遠 0 命中 → 紅 | ✅ 5 條失敗 |
| M7 拿掉 `plan.py` 的 `platform=` 輸出 | G3c 失去依據 → 紅 | ✅ 2 條失敗 |

**M6 第一次跑時錨點命中 0 次（我把 `[0-9]` 的 escape 寫錯），那是突變作廢不是通過，已重做。**
這是本 session 第二次靠「錨點必須剛好命中一次」的護欄接住自己——前一次是 M6 在 G3b 命中兩次。

### `grep -cF -e "$SLUG"`

加 `-e` 是為了 slug 以 `-` 開頭時不被當成選項。實際上 slug 來自 `plan.py` 已驗證過的
單元 id（`id.lower().replace('-','_')`），不可能以 `-` 開頭，所以這一條是冗餘的防護，
不是修一個已知的洞——寫在這裡免得日後有人以為它擋過什麼。
