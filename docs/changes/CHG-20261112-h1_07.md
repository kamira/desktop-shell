# CHG-20261112-h1_07 — 實作 H1-07 組件組合裝配（widget = 一或多個組件）

- Date: 2026-11-12 | Branch: feat/h1_07 | Risk: medium | Implemented by: I1.1
- Skill: ai-sdlc-autopilot

## Motivation

H1-07「組件組合裝配（widget = 一或多個組件）」。驗收標準有四句，每一句都是**介面形狀**的承諾：

1. host 消費 **E9-03 Composition**：組件為獨立組合單位，widget 由一或多個組件組成。
2. 組件位置以 **widget 內相對 pixel** 表達，**原點左上**，單位為**邏輯像素（隨 DPI 縮放）**。
3. **反向斷言：E4 與 kernel 的公開介面不得出現任何像素型別** —— H1-07 是全系統唯一知道
   像素的一層，往上滲會在相位 3 換後端時才爆而 `backend_guard` 擋不到。
4. **同一組件須能同時出現在兩個 widget 且呈現型態可不同**（以 **C2-07 媒體控制**為第二案例）。

### 現況（問題）

`host/` 在本單元之前**沒有任何一層知道「組件」這個概念**：

- `host/paint/`（H1-01 / H1-06）畫的是**一個 widget 的一份 RenderModel**：
  `WidgetRenderer::paint(model, bounds, title, sink)` 把 `SystemStatusRenderModel` 的每一筆
  指標切成一列。它認得「列」與「元件 kind」，**不認得「widget 由哪些組件組成」**。
- E9-03 的 `Composition`（插槽 / 綁定 / 替換 / 相容性）在 main 上**完全沒有 host 側消費者**：
  改寫前全 repo `grep -rn "Composition\b" host/` 零命中；`e9_03` 的唯一下游是 `e9_04`（主題）。
- 「同一個組件出現在兩個 widget」在改寫前**無從表達**：widget 的內容是一份寫死的
  render model，沒有「這個格位放哪個組件、在這個 widget 裡長什麼樣」這組概念。

於是驗收標準的第 4 句在改寫前連語彙都不存在，而第 3 句（反向斷言）**完全沒有任何機器防線**。

### 第二個問題：這個單元原本不會被任何 CI 閘門看到

`host/` 既有的每一個子目錄（app / menu / paint / position / tray）都（曾）整份包在
`if(WIN32)` 裡。H1-06 驗收時實測（V1.5 查出、I1 複現）：把一個單元的
`add_executable` / `add_test` 包進守衛，ubuntu 的註冊測試數從 183 掉回 181、該單元零命中，
而 **G3（181>0 通過）、`gate_sanitizers`（兩個 ubuntu 建置都排除它，故 san=181=plain 通過）、
`gate_windows`（硬編碼名單不含它）三道防線全部綠燈**。那個洞由 `CHG-20261112-07` 的
**G3b 註冊測試數下界**補上，但 G3b 擋的是「數字變少」——它**不會**替一個從一開始就躲在
守衛裡的新單元生出覆蓋。

本單元的內容是**純邏輯、平台中立**的（組合模型的消費、相對像素版面、呈現變體的解讀），
沒有任何一行需要 Windows。故照 **H1-06 的先例**（`host/paint/CMakeLists.txt`：三個中立目標與
兩個 `add_test` 在 `if(WIN32)` **之前**，守衛內只剩 GDI 橋接）與 `CHG-20261111-w1_08`，
`host/compose/CMakeLists.txt` **整份不包 `if(WIN32)`**。

### 新增 `host/compose/widget_compose.{hpp,cpp}` → target `h1_07_compose`（守衛外）

組合裝配核心。相依 `e9_03`（E9-03）、`e1_17`（E1-17 DPI）、`h1_06_dispatch`（H1-06 的 `PaintBox`）。

- **組件 = E9-01 `ds::package::Package`**，本層**不重新定義「組件是什麼」**。
- **`WidgetAssembly`**：widget = 一或多個組件。內部持有一個 **E9-03 `Composition`**，
  `declare` / `bind` / `swap` / `unbind` / 相容性 / `validate()` / `compatible_candidates()`
  **一律轉呼叫它**。本層只多加一件事：**每個插槽在 widget 內的像素版面與呈現型態**。
  相容性與完整性的失敗原因**原樣**來自 E9-03，不自己改寫（有測試逐字比對，見 §Verification M17）。
- **`PixelPoint` / `PixelSize`**：邏輯像素的點與尺寸，**原點左上、x 向右、y 向下**。
  刻意是 `int`（像素是可數的離散量）；比例值是上游 E4 / kernel 的表達方式，兩者不混用。
- **像素矩形沿用 H1-06 的 `ds::host::PaintBox`，不另造第二個**：`host/` 裡有兩個長得一樣的
  像素矩形，遲早有人寫轉換函式、然後在某一側漏掉半開區間的慣例。`WidgetLayout` 交出的框
  可直接餵進 H1-06 的 `ElementRendererTable::draw()`。
- **`ComponentPresentation`**：具名變體（字串鍵而非 enum —— 同 H1-06 `ElementDraw::kind` 的理由）
  + 具名 double 參數袋 + `visible`。**呈現型態屬於「組件在這個 widget 裡」，不屬於組件本身** ——
  這是第 4 句驗收標準成立的機制本體。
- **DPI**：`ComponentPlacement` 存**邏輯**像素，`resolve(scale, out)` 乘上縮放係數得實際像素。
  另一個多載 `resolve(const DpiInfo&, ScreenId, out)` 從 **kernel 的 E1-17 取具名螢幕的縮放
  係數** —— kernel 交出來的是**純比值**，不是像素，這正是反向斷言要保住的形狀。
  `sane_scale()` 以 **`!(s > 0.0)`** 而非 `s <= 0.0` 判定（**K-002**：NaN 的任何比較都為 false，
  後者會讓 NaN 落進「係數正常」的分支，把版面乘成垃圾值而呼叫端看到一個「算過了」的結果）。
- **右 / 下緣由「絕對邏輯座標」縮放而來**，不是 `left + scale(width)`：後者在非整數縮放下
  讓相鄰組件出現 1px 的縫（`round((1+1)*1.5)=3` vs `round(1*1.5)+round(1*1.5)=4`）。
- 失敗一律具名不靜默：`ComposeStatus`（EmptySlotId / DuplicateSlot / UnknownSlot /
  DegenerateSize / OutOfBounds / SlotAlreadyBound / SlotNotBound / Incompatible /
  **EmptyWidget**（零個組件的 widget 不是空版面，是不成立的 widget）/ IncompleteComposition）。
  **先驗放置、後動組合**：放置不合法時 E9-03 的組合物件完全沒被碰過（有測試釘住）。
  `resolve()` **全部算完才寫出** `out`，失敗時呼叫端不會拿到半套版面。
- 跨 widget：`appearances_of(component_name, widgets, scale)` 列出具名組件的所有現身，
  `presentation_differs()` 是「呈現型態可不同」的機器判準。

### 新增 `host/compose/media_compose.{hpp,cpp}` → target `h1_07_media`（守衛外，link `c2_07`）

**驗收標準指定的第二案例。** 相依 `h1_07_compose` + **`c2_07`（C2-07 媒體控制）**。

  只有封面的組件綁進「封面 + 傳輸控制」的插槽會被 E9-03 帶原因拒絕。
- `media_part_boxes(model, placed)`：讀 **C2-07 的 `MediaControlRenderModel`**
  （`has_media` / `playback` / `title` / `artist` / `artwork.has_source`），依呈現變體切出
  widget 內相對的像素部件框：
  | 變體 | 部件 |
  |---|---|
  | `expanded` | 封面（左側正方形）+ 曲名 / 演出者（右上兩行）+ **四顆**按鈕（右下一列）= 7 個 |
  | `compact` | 無封面、單行曲名 + **一顆**按鈕（`Playing` → pause，否則 play）= 2 個 |

- 未知 / 空變體 → 歸到 `expanded`（不靜默變成空白）；`visible == false` → 零部件但插槽仍綁定。

### 新增 `host/compose/pixel_boundary.{hpp,cpp}` → target `h1_07_pixel_audit`（守衛外，**零相依**）

**反向斷言的機器化判定。** 刻意不相依任何東西（連 `h1_07_compose` 都不）：它要能在不建置
被掃描的程式碼的前提下判定，且三條規則要能被**合成字串**單獨測試（規則本身可測 = 不會寫成
空轉的檢查）。掃描目標：`modules/elements/*.hpp`（E4）+ `src/kernel/*.hpp`（kernel），
**不遞迴**進 `src/kernel/backend/`（後端就是知道平台細節的地方，不是公開介面）。

> ### 【關鍵】天真的 grep 會給出假的「已被違反」
>
> ```
> grep -rnE '\bpixels?\b|_px\b|Pixel' modules/elements/*.hpp src/kernel/*.hpp
> → 排除註解行後仍有命中，全部是：
>     src/kernel/alpha_surface.hpp:  AlphaMode::PerPixel / kPerPixelAlphaCapability
>     modules/elements/{dim_overlay,gradient_fill,histogram,line_chart}.hpp: per-pixel alpha
> ```
> 那些是 **alpha 合成模式的名稱**（逐像素 alpha 通道 vs 整體透明度），**不是像素座標／
> 尺寸／偏移的型別**。故判定必須針對「像素值的幾何型別」，而不是「pixel 這個字」。

三條互補規則（都只看**去註解、去字串／字元字面值**後的程式碼；行號保留）：

| 規則 | 判定 | 為什麼不誤判 `PerPixel` |
|---|---|---|
| **R1 型別名滲透** | `host/` 像素層自有的像素幾何型別名（H1-06 `PaintBox`、本單元 `PixelPoint` / `PixelSize` / `ComponentPlacement` / `ResolvedComponent` / `WidgetLayout` / `ComponentAppearance`）+ 平台像素矩形（`RECT` / `POINT` / `SIZE` / `CGRect`…） | 名單是**精確比對**，不含 `Pixel` 這個詞；也**刻意不收** `Rect` / `Point` / `Size` 這些混合大小寫通名（`ShapeKind::Rect`、`ds::elements::Point`、`ds::kernel::Size` 都是正當的比例／具名型別） |
| **R2 像素單位識別字** | 識別字拆詞（底線 + CamelCase，轉小寫）後**同時**含「像素單位詞」{px, pixel, pixels} **且**「幾何角色詞」{x, y, left, top, width, height, size, offset, pos, rect, box, origin, bounds, extent, thickness, radius, dx, dy, …} | **合取條件**：`PerPixel` 的詞是 {per, pixel}、`kPerPixelAlphaCapability` 是 {k, per, pixel, alpha, capability} —— **都沒有幾何角色詞**，故不命中。`width_px` / `PixelRect` / `pixel_offset` 則命中 |
| **R3 整數型幾何欄位** | 宣告型別含整數型別 token（int / unsigned / long / short / size_t / intN_t…）且欄位名含幾何角色詞 —— NFR-02 之下 E4 / kernel 的幾何是**比例值**或**具名／索引值**，整數型幾何欄位才是像素的形狀 | 三個排除條件各對應一個**現存**案例：名稱自帶非像素單位詞（`ScrollPosition::offset_lines` 是行數，該標頭明寫「行索引，非像素 y」）、尾端底線的私有成員、`bool` 不算整數（`at_top` 是旗標不是座標） |

> #### 誠實分界：R3 的現況**不是零**，而且我刻意沒把它藏起來
>
> R3 在目前的 main 上恰好命中 **2 筆**，都在
> `modules/elements/image_element.hpp` 的 `ImageDimensions { int width; int height; }`
> （註解明寫「固有**像素**寬／高」，且 `ImageRenderModel::source_dimensions` 用了它，
> 確實在 E4 的公開介面上）。
>
> **為什麼它不是這條驗收標準要防的滲透**：那是**來源影像自身資料的固有尺寸** ——
> 一張 PNG 有多少像素，換平台後端不會改變；該標頭也已明寫「非螢幕座標／非擺放位置；NFR-02」。
> 本斷言要防的是 **widget / 螢幕的擺放幾何**（座標／尺寸／偏移）滲上去，那才是相位 3
> 換後端時會爆的東西。
>
> **處理方式刻意不是「把它從規則裡挖掉」**，而是列成**具名、附理由的預期基線**，
> 斷言的形式是「命中集合 **==** 預期基線」：
> - 多出任何一筆（真的滲透）→ **紅**；
> - 基線那兩筆消失（掃描器瞎了：路徑錯、拆詞改壞、檔案讀不到）→ **也紅**。
>
> 後者就是「寫成只比對不存在的字串就永遠綠」的解藥 —— **一個永遠回空集合的掃描器在這個
> 斷言下是紅的，不是綠的**（已以突變 M11 / M12 / M13 證明，見 §Verification）。
>
> 另外三道反真空：讀不到的檔**明確報錯**（不當成空檔→零命中→乾淨）、掃描檔數下界（≥ 40，
> 現況 45）、讀到的總位元組下界（> 100 000），以及一組**真實檔案對照組**
> （`host/paint/render_dispatch.hpp` 與 `host/compose/widget_compose.hpp` —— 像素正當存在的
> 兩層 —— 必須掃出非零命中）。

#### 【新發現，請 I1 考慮收進知識庫】GCC 的 `-fsanitize=undefined` **不包含** `float-cast-overflow`

施工中在自己的程式裡抓到一處潛伏 UB：`metric_px()` 把呼叫端給的任意 `double` 呈現參數
直接 `static_cast<int>`。`static_cast<int>(d)` 在 `d` 超出 int 值域時是**未定義行為**
（C++17 [conv.fpint]/1），而 `params["button_px"] = 1e20` 就會踩到。

**兩道現成防線同時沉默**（本機實測，g++ 13.3.0）：

```
probe.cpp:  volatile double d = 1e20;  int i = static_cast<int>(d);

g++ -fsanitize=address,undefined -fno-sanitize-recover=all        （= CI gate_sanitizers 的旗標）
   → 建置 rc=0、執行 rc=0、**零報告**，印出 i=-2147483648
g++ -fsanitize=address,undefined,float-cast-overflow -fno-sanitize-recover=all
   → runtime error: 1e+20 is outside the range of representable values of type 'int'
     執行 rc=1
```

也就是說 **CI 的 `gate_sanitizers` 對這一族 UB 是沉默的**（`-Wall -Wextra -Werror` 當然也是）。
與 **K-013**（ASan 抓得到）、**K-014**（ASan + UBSan 都抓不到，只有 `-flto -Wodr`）同一族
「綠燈下的潛伏 UB」，而本條的分界是：**UBSan 抓得到，但要額外開 `float-cast-overflow`**。

**對本單元的處置**：兩處轉型都改成「轉型前先在 `double` 的值域內夾限」
（`metric_px` 的 `kMaxLogicalPx`、`scale_logical` 的 `kRoundLimit`），並補一條斷言。
**那條斷言的形狀也是突變逼出來的**：第一版只斷言「所有部件框非退化且落在組件框內」，
而 M18（拿掉夾限）之下 `static_cast<int>(1e20)` 在本機得 `INT_MIN`、被 `std::max(0, …)`
收成 0，於是「按鈕尺寸 0 → 整列按鈕不產出」—— 剩下的部件確實還是非退化且在框內，
**測試全綠、UBSan 零報告**。改成「巨大值必須被夾限成填滿格位的大按鈕，**四顆按鈕仍然存在**；
只有 NaN / 負值才視為 0」之後，M18 才紅。這正是 K-002 的形狀：
崩塌成 0 是一個**看起來正常的空版面**。

**建議（不在本單元 write_scope 內）**：`gate_sanitizers` 的 `SAN` 旗標加上
`,float-cast-overflow`。本機已實測它會抓到這一族；但**我沒有實測全庫在該旗標下是否零報告**，
所以不能斷言加上去就是綠的 —— 那要一次全庫 sanitizer 建置與執行才算數，且
`.github/workflows/` 不在本單元範圍。請 I1 另開 infra 單元評估。

  `kPerPixelAlphaCapability` 是 {k, per, pixel, alpha, capability}，**都沒有幾何角色詞**。
  這個合取條件的承重性由 **M10** 證明：拿掉它，`DoesNotFlagAlphaCompositionNames` 與
  `AcceptsTheRealAlphaSurfaceShape`（原樣貼上 `alpha_surface.hpp` / `dim_overlay.hpp` 的
  真實形狀）當場變紅，真實標頭的掃描也變紅。
  R3 不命中 `PerPixel` 一族的理由不同：那些不是欄位宣告（`enum` 值 / `const char*` 常數），
  且名稱無幾何角色詞。

## 已知限制（交回 I1，皆不在本單元 write_scope 內）

1. **`gate_windows` 的硬編碼名單仍不含本單元**（`backend_win32` / `tray_win32` /
   `h1_01_paint` / `h1_02_controls`）。本單元**沒有** Windows 專屬目標，所以這對本單元
   的覆蓋沒有影響；真正釘住本單元在 ubuntu 的覆蓋的是 **G3b**（base=183 → head=185）。
   但要說清楚 G3b 的邊界：**它擋「數字變少」，不擋「新單元從一開始就躲在守衛裡」** ——
   若某個未來單元一上線就整份包 `if(WIN32)`，base 與 head 都不含它、數字不降，G3b 放行。
   補強方向：改用**具名測試清單**機器推導（例如要求每個 `feat/<slug>` 分支至少新增一個
   名稱含 `<slug>` 的註冊測試）。需改 `.github/workflows/`，不在本單元範圍。
2. **`ImageDimensions` 是 E4 公開介面上唯一的像素單位型別**（見 §Impact 的誠實分界）。
   本單元把它列成具名預期基線而非豁免，但**那是一個判斷，不是一條定理**：如果 I1 / V1
   認為「固有影像像素尺寸」也該從 E4 的公開介面移走（例如改成具名資源參照 + 由 host 查詢
   真實尺寸），那要動 E4-02 的公開契約，必須另開單元 —— 與 K-014 的修法同一類。
   **本單元不自行決定，提請裁定。**
3. **`host/app/host_main.cpp` 尚未組裝任何 `WidgetAssembly`。** 本單元只提供組合裝配層；
   要讓桌面 app 真的用組件組出 widget，需在 `host/app/**`（不在本單元 write_scope 內）
   建立組裝碼，並把 `WidgetLayout` 的框餵給 H1-06 的分派表。
   **注意**：那一步若同時引入 `c2_02`（bar 側）與其他 E4 家族，就會落進 **K-014**，
   必須先解決同名型別問題（見 K-014 的「短期」解法）。
4. **組件重疊目前是查詢而非驗證**（`boxes_overlap()`）。封面之上疊曲名、按鈕列疊在底圖上
   都是正當版面，所以本層不把重疊當錯誤；但也因此**沒有 z 序概念** ——
   `WidgetLayout::components` 的順序就是插槽宣告順序，呈現層若需要明確的疊放次序，
   要的是 E1-24 的具名圖層（`SurfaceLayer`）而不是本層的數字 z-order（NFR-02）。

5. **`media_part_boxes()` 的版面是一組固定的版型（expanded / compact）**，不是通用版面引擎。

6. **本機從未以 MSVC 建置本單元，也沒有做任何交叉編譯旁證。** 見 §Verification 的誠實分界。
