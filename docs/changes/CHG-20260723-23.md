# CHG-20260723-23 — G3 建置限制並行度，解除單元破百後的 CI OOM/SIGTERM 阻斷

- Date: 2026-07-29 (UTC+0) | Branch: chore/g3-parallelism | Risk: low | Implemented by: I1
- Skill: ai-sdlc-autopilot v1.1

## Motivation
單元數累積破百（目前 ~110 已合併、目標 176）後，**所有 PR 的 G3 閘門開始紅燈**，且非個別單元的程式缺陷：
- 症狀：`gate / G3 tests` 在 ~2 分鐘後失敗，log 出現大量 `gmake[2]: *** [...test_eX_YY...] Terminated`、最終 `gmake: *** [Makefile:146: all] Terminated`、`Process completed with exit code 143`（143 = 128+SIGTERM）。
- 根因：G3 步驟用 `cmake --build build -j`——**`-j` 不帶數字時 make 採「無限並行」**，會同時對所有就緒目標各起一個 g++。單元破百後等於同時起 100+ 個 GoogleTest 翻譯單元編譯，每個 Debug（`-O0 -g`）gtest TU 峰值記憶體可達 ~1.5–2GB，遠超 ubuntu-latest runner 的 16GB，核心 OOM-killer 介入 → 子行程被殺、make 收 SIGTERM → exit 143。
- 這是基礎設施擴展問題，會擋住**每一張** PR（含 #120 E4-24、#125 E4-01 等已驗證正確、本機 g++ 全過的單元），與單元正確性無關。root workflow 不在任何單元 write_scope 內，由 I1 以 bootstrap infra 變更修正。

## Impact（`.github/workflows/governance.yml`，G3 步驟）
把無限並行改為明確上限：
```diff
   cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
-  cmake --build build -j
+  cmake --build build -j 2
```
- `-j 2`：同時最多 2 個編譯 → 峰值記憶體 ~4GB，對 16GB runner 留足安全邊際，且隨單元數成長到 176 仍不會 OOM（峰值由並行度決定，與總單元數無關）。
- 代價：建置時間拉長（並行度砍半），但 G3 本就是唯一需實跑的閘門，且遠比「全紅無法合併」可接受。
- 未動 G3 的其餘邏輯：`-DCMAKE_BUILD_TYPE=Debug`（保留斷言）、真空綠燈防線（`ctest -N` 計數 = 0 即紅）、`ctest --output-on-failure` 皆逐字保留。
- 未動其餘 7 道閘門、未動 `permissions`、未動自動合併步驟。

## 明確不改
- 未改 build type（保留 Debug 以保 `assert`/gtest 斷言語意）。
- 未改 root `CMakeLists.txt` 的 unit GLOB（收檔邏輯正確，問題純在 build 並行度）。
- 未動 units.json、未動任何單元。

## 若日後 -j 2 仍不足（備援）
單元續增或個別 TU 特別肥時，可再降 `-j 1`，或改採「只建置/測試本 PR 變更的單元」的增量策略（需較大 workflow 改造，非本次範圍）。

## Verification
- YAML 有效：僅改一行 `run:` 腳本內容 + 兩行註解，縮排與 block scalar 不變。
- 語意：`cmake --build build -j 2` 為合法 CMake 呼叫，`-j 2` 傳遞給底層 make/ninja 限制並行工作數。
- 效果：峰值編譯記憶體由「無上限」降為約 2 個 TU 的用量（~4GB），低於 runner 16GB，消除 OOM/SIGTERM；G3 可正常跑完 `ctest`。
- 分支 `chore/g3-parallelism` 非 feat/ 單元分支，`plan.py unit-for-branch` 查無對應單元，預期 gate 於 branch-lookup 紅燈；由 I1 以 `gh pr merge --admin` 併入（bootstrap infra 慣例，同 CHG-17~22）。
