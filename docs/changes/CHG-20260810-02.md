## Motivation

`CHG-20260810-01` 修掉 hook 標出的 5 筆之後，回頭確認它們消失時發現一件更重要的事：

**hook 的清單是截斷過的。** `session_start.py:76` 印的是 `pending[:5]` ——
只印按檔名排序的前 5 筆。所以「未收尾 CHG:5 筆」從來不是總數，是第一頁。
修掉前 5 筆的效果不是清空清單，是讓下 5 筆遞補上來。

以 hook 自身的判定邏輯（`status_scope` 取 Status 段第一行，比對
`ACCEPTED=("已驗收","已收尾","accepted","closed")` / `PAUSED`）掃 `origin/main`：

- CHG 總數 **224**，未收尾 **98** 筆（`-01` 修掉 5 筆前是 103）

**這 98 筆全部只是紀錄漂移，沒有任何一筆缺驗收**——逐筆查證結果：

| 分類 | 筆數 | 判定依據 |
|---|---|---|
| medium 風險 | **13** | **13 筆全部都有對應 ACC**：E1-01/02/03/04、E1-08/09、E1-25、E2-01/02、E4-02、E5-12、E6-01、E7-01 |
| low 風險 | **85** | 依 `docs/ai-guideline.md` §7，low 的驗收標準是「單元測試綠燈 + CHG 內留一行可重跑證據（inline 自驗）」，本就不需 ACC |
| 查無合併 commit | **0** | 98 筆全部都在 `origin/main` 找得到 squash merge commit |

漂移有三種寫法，成因同一個：
1. **完全沒有 `## Status` 段**
2. `Proposed — self-verified`
3. `Proposed — 待 V1 驗收` —— 32 筆這樣寫，**其中 30 筆是 low，根本不需要 V1**
   （subagent 樣板句順手抄的，不是真的在等 V1）

**根因（與 `-01` 同一個，這裡才看得出規模）**：合併發生在 PR 端，而 CHG 文件在合併前
就凍結在功能分支上。流程沒有任何一步會回頭改 Status。有 `Accepted` 的那 126 筆是當時
人工補的——靠人記得，就會有 98 筆漏掉。

**為什麼非清不可**：Status 是進場握手判斷「有沒有半途而廢的階段」的唯一依據。
98 筆假陽性 + 只印 5 筆的截斷，合起來的效果是**這道警告永遠不會歸零**，
於是它會被當成背景雜訊略過。一道永遠在響的警報，與沒有警報是同一件事。

- 不改變任何已合併程式碼的行為，不改變任何閘門的判定邏輯。

### 修改步驟

以 scratchpad 腳本（未進 repo）機械改寫，規則：

1. **有 `## Status` 段** → 取代該段內容為新的一行結論 + 補正註記。
2. **沒有 `## Status` 段** → 於檔尾新增。
3. 結論措辭依風險分級：
   - low → `Accepted — self-verified（low risk，依 Guideline §7 免 ACC）。已合併於 <sha> (#<PR>)。`
   - medium → `Accepted — V1 獨立驗收（見 ACC-…）。已合併於 <sha> (#<PR>)。`
4. 合併 commit 以 `git log origin/main --grep=CHG-<date>-<slug>` 查；查不到再以單元代號
   `[E7-01]` 查（早期 commit 用代號而非 CHG id）。

**fail-closed**：查不到合併 commit、或 medium 但查無 ACC，一律**不動**並列入略過清單。
沒有證據就不蓋 `Accepted`——批次改寫最容易犯的錯就是為了數字歸零而蓋掉未知。
實測略過 0 筆，98 筆全部有證據。
