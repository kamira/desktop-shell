## Motivation

`CHG-20260829-01` 收錄的桌面截圖是以 **mingw-w64 交叉編譯 + Wine** 取的 ——
程式碼一行未改，但那不是原生 Windows 的畫面。取像過程本身就暴露了差異有多真實：

- Wine 對 `Segoe UI` 的代用字型換了兩輪才把中文與自繪選單的 `✓` 同時湊齊
  （先用 Droid Sans Fallback，結果換成拉丁字變豆腐）。
- 視窗合成走的是 Wine 的實作，不是 Windows 的。

README 的圖說已據實標明這些限制，但**標明限制不等於沒有限制**。
使用者要求改用實機 Windows 重拍，並選定走 repo 自己的 CI（`windows-latest`）而非個人機器。

### 為什麼必須拆成兩個 PR

**`workflow_dispatch` 的 workflow 檔必須先存在於預設分支才叫得動。**
所以無法「一個 PR 同時加 workflow 並換圖」：

| PR | 內容 |
|---|---|
| **本 PR（A）** | 把截圖 workflow 送進 `main` |
| 手動 dispatch | 取得真 Windows / 真 MSVC / 真 Segoe UI 的截圖 artifact |
| **PR B** | 換掉 `docs/images/host-desktop.png`、`host-tray-menu.png`，並改寫 README 的圖說 |

### 為什麼是 workflow_dispatch，不掛在 pull_request 上

它要跑 GUI、要等數十秒、產出二進位圖檔。**截圖是偶發需求，不是閘門** ——
掛在每個 PR 上只會讓每次 PR 多等十分鐘，而且沒有任何東西應該因為「圖沒拍成」被擋下合併。
本 workflow 因此**不參與**十一道閘門，`permissions` 也只給 `contents: read`。

### 三個已知會咬人的地方，已在檔內處理

| 坑 | 處置 |
|---|---|
| **K-008 命令注入**（G8 `workflow_lint`） | `inputs.seconds` 經 `env:` 傳入，不直接內插進 `run:`。且 `env:` 寫在 `run:` **之前** —— `workflow_lint` 以縮排判定 `run:` 區塊範圍，寫在後面會被算進區塊裡 |
| **K-004 PowerShell ANSI codepage** | runner 把 inline script 寫成無 BOM 的 `.ps1`，PowerShell 會以系統 ANSI codepage 讀它。故 **PowerShell 內容一律純 ASCII**，中文全部留在 YAML 註解（不進 `.ps1`） |
| **K-006 釘死 VS 產生器版本** | 沿用 `gate_windows` 的做法：不給 `-G`，只給 `-A x64` |

### 托盤選單怎麼叫出來

host 的托盤視窗是 **message-only**（parent = `HWND_MESSAGE`），
**`FindWindow` 看不到它** —— message-only 視窗不在桌面 z-order 裡。
必須用 `FindWindowEx(HWND_MESSAGE, ...)`。找到後送 `WM_APP+1` / `WM_RBUTTONUP`，
與 `CHG-20260803-15` 的驗收手法相同；選單彈在當下的游標位置，故先 `SetCursorPos`。

### 拒絕上傳空白截圖

無人桌面的 runner 若始終沒有合成出視窗，`CopyFromScreen` 會得到一張單一顏色的點陣圖。
**那種圖放進 README 就是這個 repo 花十一道閘門在防的東西：看起來有、其實什麼都沒證明。**
故取像後抽樣比對像素，整張同色即 `::error::` 讓步驟紅燈，而不是安靜地上傳。

同一條原則的第三次現身：G0/G3 的「零測試也算紅」、K-002 的「`0.0` 不是失敗值」、
以及本次的「單色圖不是截圖」。

### 尚不確定、屆時要據實回報的事

GitHub-hosted 的 windows runner 是無人桌面環境，**GUI 能不能被合成出來、
`CopyFromScreen` 會不會拿到黑畫面，要 dispatch 之後才知道**。
上面那道單色檢查就是為此而設：拍不到就紅燈，不會生出一張騙人的圖。
若真的拍不到，PR B 就不存在，改為回報「這條路走不通」並保留現有的 Wine 圖與其但書。
