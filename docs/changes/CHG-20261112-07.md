### 1. `.github/workflows/governance.yml`：新增 `G3b 註冊測試數下界`（插在 G3 與 G4 之間）

規則：**PR 不得讓 ubuntu 的註冊測試數下降**。

| 設計決定 | 理由 |
|---|---|
| base 的數字只 configure、不建置 | `ctest -N` 讀的是 configure 時產生的 `CTestTestfile.cmake`（已於 H1-06 驗收時實測：未建置的目錄回 181，與建置後一致）。成本是一次 configure |
| head 的數字沿用 G3 已 configure 好的 `build/` | 同一個 job 的前一步already configure 過，不重跑 |
| 兩個管線賦值都帶 `\|\| true`，再以 `-n` fail-closed | 前者是 `K-011` 的直接教訓；後者不可省，因為 `\|\| true` 的代價是空字串，而空字串在 `-lt` 下會讓 `[` 回 2、被 `if` 當成 false **放行** |
| 另加非數字檢查（`case … in *[!0-9]*`） | 同上：`[ x -lt y ]` 在非數字下回 2，`if` 當 false 放行——那是 fail-open |
| 豁免走 PR 內文的 `ALLOW-TEST-COUNT-DROP:` 且**錨在行首** | 不錨行首的話，任何在內文裡**提到**這個標記的散文都會意外開後門（已實測，見下 M3） |
| 豁免放行時印 `::warning::` | 例外必須看得見，不能靜默 |
| PR 內文經 `env:` 進入 shell，**絕不內插進 `run:`** | `K-008`：2026-08-10 PR #210 的內文真的被當指令執行過。G8 會擋，本檔的測試再釘一次 |

工作目錄都放在 repo **之外**（`../gate-base`、`../gate-base-build`），不在工作區留未追蹤目錄。

## ⚠ 更正我自己在 `CHG-20261112-06` 裡寫的那項更正：分支刪除是**不一致**的

`CHG-20261112-06` 推翻了先前五份 CHG 的「`--delete-branch` 持續無聲失敗」，
結論是「指令有效，成因是 medium 單元走 API 人工合併而該路徑不刪分支」。
**本檔推送前出現第三個資料點，那個結論也太強。**

```
#236  bot AUTO 合併（gate 第 18 步 success）→ 分支**已刪**
#237  bot AUTO 合併（gate 第 18 步 success）→ 分支**仍存在**（停在 64b2960）
      merged_by = github-actions[bot]，head_ref 同一個分支名
```

**同一個步驟、同一個指令，一個刪了一個沒刪。我不知道差別在哪。** 一個未經證實的猜想是
與那兩組重複 CI run 的競態有關（`opened` 與 `ready_for_review` 各觸發一輪，第二輪的
第 18 步在 PR 已合併之後才執行），但我沒有證據，故不當成結論。

**目前站得住的只有三句話**：

1. 經 GitHub API 人工合併的單元分支**確定不被刪**（`feat/e9_10` / `w1_08` / `e7_16` /
   `e9_11` / `c2_11` / `h1_06` 六個全部存活）。
2. bot AUTO 合併的分支**有時**被刪、有時不被刪（#236 vs #237）。
3. 因此「`--delete-branch` 持續無聲失敗」與「`--delete-branch` 有效、成因在合併路徑」
   **兩種說法都太強**。準確的說法是：**刪除行為不一致，成因未查明。**

**建議不變，而且因為這個不一致而更站得住腳**：打開 GitHub repo 設定的
**「Automatically delete head branches」**——它是伺服器端強制、每次合併都生效，
不依賴任何一條指令或合併路徑是否正常。既有的 179 條本環境仍無法清理
（`git push origin :ref` 與 `gh api -X DELETE` 皆被出站代理回 403，GitHub MCP 無此工具）。

**這是我今天第二次把一個觀察推成過強的結論**（第一次是把那道一致性檢查寫成
「真空綠燈防線」，見本檔 §Motivation）。兩次的形狀相同：**從少數幾個一致的觀察，
跳到一個關於機制的全稱陳述。** 兩次都是別人或下一個資料點把我糾正回來。

## 未關閉的缺口

1. **G3 自己那個 `K-011` 實例仍未修**（就在 G3b 的上一行）：
   `N=$(ctest --test-dir build -N 2>/dev/null | sed …)` 沒有 `|| true`，且 `2>/dev/null`
   另把 `ctest` 的訊息吃掉；若 `ctest -N` 真的失敗（**該防線唯一要抓的災難情境**），
   `-e` 當場中止而 `::error::` 印不出來。本檔刻意不修：人類授權的是「補下界檢查」，
   那是另一行的另一個缺陷。**更好的做法是把「管線賦值必須有 `|| true`」這條規則移進
   `scripts/workflow_lint.py`**（G8 已以縮排解析全部 `run:` 區塊），讓它對**每個**步驟生效，
   而不是靠三份各自針對一個步驟的測試。**已向人類提出待裁定（第二次）。**
2. **本步驟不涵蓋「數量不變但覆蓋被換掉」**（見上影響面第 3 項）。
3. **`gate_windows` 的硬編碼名單覆蓋不全**（12 個僅 Windows 建置的測試只點名 4 個）。
   注意 **G3b 幫不上這一項**：它只看 ubuntu 的註冊數。Windows 側要同樣的下界檢查，
   得在 `gate_windows` 裡另做一份。
4. **MSVC 無警告旗標**（承 `CHG-20261112-04`）；`tests/e7/test_e7_09.cpp` 三個誤判警告仍在。

   準確的說法是刪除行為不一致、成因未查明，建議打開 repo 的
