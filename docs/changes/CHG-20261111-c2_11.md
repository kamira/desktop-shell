# CHG-20261111-c2_11 — 實作 C2-11 行程 top-N widget（N 與排序維度可設定）

- Date: 2026-11-11 | Branch: feat/c2_11 | Risk: low | Implemented by: I1.1
- Skill: ai-sdlc-autopilot

## Motivation

C2-11「行程 top-N widget（N 與排序維度可設定）」：把 **E2-19**（行程監看）掛上的**多實例**
指標（每個行程一個 `MetricInstance`）經 E2-01 統一指標介面讀出，依宣告式設定取前 **N** 名，
每名一列，以 **E4-03** 長條 / 量表 / 進度視覺元素 + 格式化文字呈現；**N** 與**排序維度**由
**E7-01** 宣告式格式（含 `format_version` 版本欄位）決定，顯示範圍與單位換算可寫 **E7-05**
公式。這是一個**組裝型 artifact 單元**（非新引擎邏輯）。

與 C2-02（系統狀態 widget）同形，差別在**指標是多實例的**：C2-02 一個指標畫一列（取第 0 個
實例），本單元一個指標畫 N 列。

組裝的四個擴充點：
- **E2-19**（`ProcessSortKey` / `ProcessMonitorProvider::kCpuMetricId` / `kMemoryMetricId` /
  `kCpuUnit` / `kMemoryUnit`）：**排序維度 ↔ 指標 id ↔ 單位的唯一對照來源**。E2-19 PUBLIC
  相依 e2_01 / e2_02，故 E2-01 的 `MetricRegistry` / `Metric` / `MetricInstance` 經它透傳而來
  ——`refresh()` 唯一的讀值入口，widget 完全不觸及任何行程 API 或 provider 型別的實例。
- **E4-03**（`BarElement` / `GaugeElement` / `ProgressElement` / `RenderModel`）：每列的視覺
  渲染描述。
- **E7-01**（`Value` / `parse` / `Document` / `format_version`）：宣告式設定的資料模型；
  `configure_text()` 走其文字解析，**版本欄位的相容性由 E7-01 驗證**（不自行重打版本規則）。
- **E7-05**（`is_formula` / `Evaluator`）：`min`/`max` **靜態**公式（configure 時求值，作用域
  **不含** `value`）+ `transform` **動態**公式（refresh 時以 `value` 綁定當列原始值求值）。

## Impact

### 新增 `content/widgets/process_top_widget.{hpp,cpp}`（`namespace ds::widgets`）

- `ProcessTopWidget`：建構只需一個具名 id（本單元**不**相依 C1-01 / E4-01 / E2-02，故無
  `KernelBackend` / `FontMetrics` / scheduler 注入；相依清單即 units.json 的
  `depends_on`）。各列元素綁具名 surface `"<id>.rows"` + slot = pid。
- `configure(const Value&)`：認得 `sort_by`（**必填**，"cpu"/"memory"）、`top_n`（**必填**，
  非負整數值且須為 `allowed_top_n()` 之一：0=全部 / 3 / 5 / 10）、`kind`（"bar"/"gauge"/
  "progress"/"text"，預設 "bar"）、`min`/`max`（選填、須成對；數字或 E7-05 靜態公式）、
  `transform`（選填 E7-05 公式，語法須符合 `is_formula()`，求值延後至 `refresh()`）。
  **不認得的鍵一律 `Invalid`**（拼錯的鍵不被靜默忽略——否則一份「其實沒生效」的設定看起來
  完全正常）。維度與 N **無預設值**：它們是本單元的需求切片本體，漏寫就該紅。
  失敗為全有或全無（不改既有設定）。
- `configure_text(const std::string&)`：走 E7-01 `parse()` → 相容性驗證 → `Document::root`
  （已去除 `format_version` 的純內容）→ `configure()`。解析 / 版本失敗 → `FormatError`
  （行號 + 訊息留於 `last_error()`）。
- `refresh(const MetricRegistry&)`：以 `metric_id()`（**由設定維度決定**）查詢；具名回報
  `ProcessMetricState`：`Ok` / `NotConfigured` / `Missing`（registry 沒有該 id）/
  `UnitMismatch`（id 在但單位不是該維度的期望單位）/ `NoInstances`。後三者**列清空**。
  `Ok` 時走訪**全部**實例各成一列（刻意**不**讀 `MetricInstance::history()`），依原始值由高
  到低排序（同值以 pid 數值遞增為次序，與 E2-19 `top_processes()` 一致），unavailable 列置後，
  再截斷為前 `top_n`（0 = 全部）。
- `render()`：`available` 且有顯示範圍者依 `kind` 組 Bar / Gauge / Progress（Progress 以「值於
  顯示範圍內的比例」換算百分比，故對 `%` 與 `MB` 兩維度都表達同一件事）；`Text` 種類不掛元素；
  unavailable 列 `display_text` 為 `"—"`（降級顯示，不整列消失）。文字格式一位小數，`"%"`
  緊接無空白、其餘單位以空白分隔（與 C2-02 慣例一致）。
- 具名列舉：`ProcessRowElementKind`、`ProcessTopStatus`（Ok/Invalid/FormulaError/FormatError）、
  `ProcessMetricState`，各附 `to_string()`（NFR-02）。型別名刻意與 C2-02 區隔，兩單元標頭可在
  同一翻譯單元共存。
- `last_error()`：最近一次失敗 / 非 Ok 狀態的人類可讀原因（含 E7-01 行號、E7-05 欄位置）。
  **不靜默吞錯**：個別列降級不中止其餘列，但原因一定留得下來。

## 兩個刻意的設計約束（皆有負向測試證明會擋）

### 1. 切換排序維度 = 換掉註冊的指標（CHG-20260829-05 Q-A 停點裁定）

E2-19 的 `sort_key` / `top_n` **只有建構子參數、沒有 setter**，且 `metric_id()` 依維度回傳
`proc.cpu` 或 `proc.memory`、單位隨之由 `%` 變 `MB`。因此本 widget：

- **不持有、不建立、不重建 provider**。設定裡的維度只做一件事：決定 `refresh()` 去 registry
  要哪一個 id。
- 維度改了就去要另一個 id；舊 id 的指標即使還留在 registry 也**一律不讀**——讀了會讓單位從
  `%` 悄悄變成 `MB`，是「看起來完全正常的假資料」（K-002 的陷阱）。
- 另加**單位對帳**：`Metric::unit()` 必須等於該維度的期望單位，否則 `UnitMismatch`，不讀、
  不猜、不畫。
- **歷史不保留**：widget 自身不存任何時序、也不讀 `MetricInstance::history()`；`configure()`
  與每次 `refresh()` 都把列從頭重建。
- provider 的重建與重新註冊是 **H1-11** 的職責，**不是本單元的**；在重建之前 `refresh()`
  誠實回報 `Missing`（具名狀態，不是一個落在合法值域裡的 0）。

### 2. 沒有顯示範圍就不畫長條（知識庫 K-002 的直接應用）

`proc.cpu` 的 range 是 `bounded[0,100]`——填充比例有意義。`proc.memory` 的 range 是
`at_least(0)`——**無上界**。若憑空塞一個上界（例如沿用 C2-02 的保守預設 `[0,100]`），
「用了 8 GB」與「用了 100 MB」會畫成一樣滿：`fill_ratio ∈ [0,1]` 全數通過、畫面看起來完全
正常，而那是假資料。故解不出顯示範圍時該列 `has_range=false`、**不掛 E4-03 元素**，只出
格式化文字；要畫記憶體維度的長條就得在設定裡明寫 `min`/`max`。
