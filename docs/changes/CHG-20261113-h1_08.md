## Motivation

H1-08「環形量表繪製」：消費 **E4-03 `GaugeElement` 的弧輸出**畫出環形量表，
作為 **H1-06 kind 分派機制的第一個具體案例**。

### 現況（問題）

H1-06 內建的 `gauge` 畫法（`render_gauge`）是「實心圓盤 + 一根指針」，只用到
`angle_degrees`——E4-03 送上來的 `start_angle_degrees` / `sweep_degrees`（**弧**本身）
在繪製層**從未被畫出來過**。量表的「弧」是 E4-03 的核心語意輸出（`bar_gauge.hpp` §Gauge：
「值 → 角度 / 弧」），而繪製層只取了弧上的一個點。

### 第二個問題：非整數 DPI 下的細線

繪製層拿到的是**裝置像素**座標，而環的粗細是**邏輯像素**的設計值。125% 下一條 1px 的細線
是 1.25 裝置像素：橫跨兩個像素、兩邊各淡一半，整圈看起來就是糊的；反鋸齒救不了一個
本來就對不準的邊，只會把它糊得更均勻。驗收標準明文要求自行處理裝置像素對齊。

### 1. 接法：只用 H1-06 的公開擴充點

`install_ring_gauge(table, painter)` 做兩件事：

- `replace_kind(kKindGauge, ...)` —— **明示**覆寫內建的「圓盤 + 指針」畫法。
  用 `replace_kind` 而不是 `register_kind`，是因為 H1-06 刻意把兩者分成兩個名字，
  好讓「我知道我在覆寫」寫在呼叫端而非註解裡；
- `register_kind(kKindRingGauge, ...)` —— 另給一個 `"ring_gauge"` 具名鍵，
  讓組版端可以明確點名環形而不必覆寫 `"gauge"`。

重複安裝回 `false`（`register_kind` 依契約不靜默覆寫），有測試釘住。

### 2. 為什麼新增 `ArcSink` 而不是往 `PaintSink` 加函式

H1-06 的 `PaintSink` 只有三個原語（填矩形 / 文字 / 指針），**沒有弧**；環形量表用矩形
拼不出來（拼出來就是鋸齒，正好違反本單元的驗收標準）。

但**不能**往 `PaintSink` 加純虛擬函式：既有的兩個實作
（`tests/h1/test_h1_06.cpp` 與 `tests/h1/test_h1_06_radial.cpp` 的 `RecordingSink`，
皆宣告為 `final`）會當場編不過，而那兩個檔案**不在本單元的鎖定範圍內**——
改它們等於自行擴權，CI 的 `scope_check` 也會擋。

故 `ArcSink` 是一個**獨立的、可選的**介面：弧走 `ArcSink`，中央讀數文字走 `PaintSink`，
兩者由呼叫端分別提供，誰都不必認識誰。

### 3. 裝置像素對齊（驗收標準：125% / 150% 下細線不得糊成一團）

對齊規則三條，全部在 `compute_ring_geometry()` 這個**純函式**裡：

| 量 | 規則 |
|---|---|
| 筆寬 | `round(邏輯粗細 × scale)`，**整數**且**至少 1** |
| 圓心 | 整數裝置像素 |
| 內 / 外緣半徑 | 整數裝置像素 → 環的兩條邊界落在像素邊界上 |

效果：像素要嘛整格被環覆蓋、要嘛整格沒有，不存在半格。筆刷型 API（GDI `Arc` /
Direct2D `DrawArc`）要的路徑半徑 + 筆寬由 `ArcSpan::mid_radius()` /
`stroke_width()` 提供，筆寬為奇數時路徑半徑自然落在半像素上——正是該類 API 畫出
清晰筆畫所需的位置。反鋸齒**模式**本身屬 E4-24（`engine/render/render_style.hpp` 的
`AntiAliasMode`）的語彙，由實際的 `ArcSink` 實作去設定；本層負責的是先把幾何對齊。

實測（`kCell` 100×100、粗細 6 邏輯像素、內縮 2 邏輯像素）：

| scale | inset | side | radius | stroke | inner |
|---|---|---|---|---|---|
| 100% | 2 | 96 | 48 | 6 | 42 |
| **125%** | 3 | 94 | 47 | **8**（7.5 → 8，不是 7.5px） | 39 |
| **150%** | 3 | 94 | 47 | **9** | 38 |
| 200% | 4 | 92 | 46 | 12 | 34 |

細線（1 邏輯像素）在 125% 下是 1、150% 下是 2 —— 都是整數，**都不是 0**：
壞掉的輸入可以讓線變粗，不可以讓它悄悄消失（K-002 族：最難發現的失敗是「整條不見了」）。

### 4. 指針掃向——H1-06 驗收時裁定「另案」的那一案，**本變更是其落點**

E4-03 `GaugeElement` 的預設弧是 start 135°、sweep **+270°**（數學慣例：0° 指向右、
逆時針為正）。實測掃向為 **0% 左上 → 50% 正下方 → 100% 右上**，從**下方**經過，
與一般量表（下方左側起、經**上方**、到下方右側）相反。

**本層的決定：原封照 E4-03 的弧畫，繪製層不做任何方向轉換。** 三個理由：

1. **值→角度是 E4-03 明文的語意輸出**（`bar_gauge.hpp` 檔頭：「量表的值→角度，是量表
   本身的語意輸出，非版面座標」）。繪製層若偷偷反轉，同一份 `RenderModel` 在不同繪製層
   會長成不同的東西；更直接的矛盾是 `angle_degrees`（元件算的指針角度）與環的值弧終點
   （繪製層算的）會指向兩個不同的方向。本變更反而把這條一致性**寫成斷言**：
   `track.start + value.sweep == GaugeElement::angle()`。
2. **弧本來就可設定**，不必改任何程式碼：`GaugeElement::set_arc(225, -270)`，
   或 E4-03 設定文件的 `start_angle` / `sweep` 欄位。
3. **本層支援負 sweep（順時針）且有測試釘住**（`SweepDirection.NegativeSweepGoesOverTheTop`：
   start 225° / sweep −270° → 0% 左下、50% **正上方**、100% 右下）。也就是說「另案」的
   修法在繪製層已經就緒，缺的只是組版端選一組角度——而組版端
   （`host/app/**`、C2-02）不在本單元的鎖定範圍內，**本單元不動它**。

現行預設弧造成的實際視覺位置另以 `SweepDirection.E4_03DefaultArcSweepsThroughTheBottom`
釘住：那不是在說這個方向「對」，是不讓它再悄悄漂走。

> **給 I1 的交接**：真正要改方向，應開一份改 C2-02 / `host/app` 設定的 CHG
> （`start_angle: 225` / `sweep: -270`），或改 E4-03 的預設值（動公開契約，另案）。
> 兩者都不在 H1-08 的鎖定範圍內。

### 5. 不崩潰、不靜默

所有失敗都有**具名狀態碼** `RingStatus`（`Ok` / `EmptyArea` / `NoArc` / `DegenerateArc`）
＋ `RingGaugeStats` 計數器 ＋ `last_status()`，呼叫端與測試都問得到：

- **退化弧**（sweep 為 0 / NaN / ±Inf，或起始角非有限）→ `DegenerateArc`；
- **上游沒給角度**（`has_angle=false`）→ `NoArc`；
- 這兩種都**退回 H1-06 的線性填充**，不是「什麼都不畫」——`render_gauge` 已立下規矩
  「角度缺失不得讓數值靜默消失」。環畫不出來是幾何問題，值本身仍是有效讀數；
- **值超出範圍 / NaN** → 走 H1-06 既有的 `clamp_unit_ratio`（NaN → 0，K-002）；
- **|sweep| > 360** → 夾限至一圈，**保留正負號**（方向是上游的語意，不是本層的）；
- **退化尺寸 / 反向矩形 / 內縮比格位還大 / 荒謬 DPI（NaN、0、負、1e308、1e-300）**
  → 具名狀態或退化到最小可畫幾何，不產生垃圾座標；
- **NFR-03**（`available=false`）→ 軌道弧仍畫、值弧不畫、`stats().degraded` 加一。

### 6. `float-cast-overflow`：所有 double → int 只有一個入口

`to_int_clamped()` 先查 `std::isfinite` 再夾限到 ±1e7（刻意遠小於 `INT_MAX`，
之後還有 `cx + radius` 這類加法，貼著 `INT_MAX` 夾限等於把溢位推遲到下一個算式）。
直接 `static_cast<int>` 一個非有限或超範圍的 double 是 UB，而
`-fsanitize=float-cast-overflow -fno-sanitize-recover=all` 會**當場中止**，
不是印個訊息——本單元同時踩在「非整數 DPI」（大量轉換）與「值超出範圍不得崩潰」上。

## 遇到的錯誤（1 件，自己的測試抓到的）

### `ArcSpan::visible()` 讓 sweep 為 NaN 的弧通過

- **錯誤**：`Degenerate.ArcSpanWithNanIsNotVisible` 第一次執行就紅燈——
  `sweep_degrees = NaN` 的弧被判為**可見**，會被送進繪製 API。
- **根因**：我在標頭上寫了「一律用正向比較，NaN 的任何比較皆為 false，所以 fail-closed」，
  然後把這條規則套到 `sweep_degrees != 0.0` 上。**大小比較**（`>` / `<`）對 NaN 確實
  一律 false，但**不等於**剛好相反：NaN 與任何值都不相等，`nan != 0.0` 為 **true**。
  同一個 `return` 式子裡，`outer_radius > 0.0` 與 `stroke_width() > 0.0` 真的擋住了 NaN，
  `!= 0.0` 這一段卻放行。
- **為什麼只有測試抓得到**：`-Wall -Wextra -Werror` 不警告（NaN 比較完全合法），
  ASan + UBSan + `float-cast-overflow` 零報告（不是 UB）。這是知識庫 **K-002 那一族**
  （壞掉的值偽裝成一個看起來正常的結果）的另一種寫法。
- **解法**：`visible()` 補 `std::isfinite(sweep_degrees) &&`，並把「`!=` 不是 fail-closed」
  的理由寫在該函式旁邊。突變 **M2** 把這個錯誤放回去，測試立刻重新變紅。
- **知識庫**：建議收為新條目（K-002 族的新形狀）。依 AGENTS.md §2，寫入知識庫是 I1 的
  職責，且 K 編號須由 I1 統一配發以免與同批其他單元撞號，故本單元不自行寫入
  `docs/knowledge/errors.md`，於回報中交給 I1。
