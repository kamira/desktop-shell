## Motivation

H1-09 是**裝配單元**：上面那些上游各自都已完成且各自有測試，但沒有任何一處把它們接成
「使用者真的會走的那一條路」——

```
加元件 / 拖動 / 換 kind / 拖放  →  就地編輯設定值  →  存檔（帶 format_version）
        →  重啟  →  還原  →  熱重載  →  依 kind 分派重畫
```

驗收標準的兩句話就是這條路的兩個端點：「拖動組件 → 存檔 → 重啟 → 位置還原」、
「換 kind → 熱重載 → 造型改變」。

### 真正的難點不在接線，在第三句話

> 「**使用者可直接改動持久化狀態，故錯誤不得讓佈局進入救不回來的狀態。**」

存檔是一份使用者拿編輯器就能改的文字檔。`NaN`、`Infinity`、`1e400`、空字串、負尺寸、
截斷、缺欄位、版本寫成 `2.0` —— 全部是現實輸入。而既有上游在這條路上的預設行為是
**嚴格失敗**：`E9-05 deserialize_layout` 對「某個元件缺 `id`」是 `throw`。接在 host 層就是
**使用者手滑刪掉一行，整個桌面回不來**。

### 關鍵設計決定

#### 1. 讀與寫刻意不對稱

- **寫**：一律 E9-05 `serialize_layout`（`LayoutStore::save` 用的同一個函式）。
  格式的單一事實來源在上游，本層**不自造格式**，結構與 `format_version` 全部沿用。
- **讀**：**不**用 E9-05 `deserialize_layout`（理由見 Motivation）。本層以**同一個結構**
  做容忍式讀取：壞元件具名丟棄並計數，其餘照常還原。

兩條路不得各自漂移 → `FormatParity.TolerantReaderAgreesWithE905OnValidInput` 釘住：
合法輸入下本層讀出的 `LayoutState` 必須與 `deserialize_layout` **逐欄相等**。

#### 2. `format_version` 四種分流

`ds::format::parse()` 自己會擋版本，但不相容一律回行號 0 的泛用訊息，分不出是哪一種。
本層在 parse **之前**先掃一次版本行（`peek_format_version`，純字串、不解析內容）：

| 情況 | 具名狀態 | 行為 |
|---|---|---|
| 缺 `format_version` | `MissingVersion` | 拒收。**不猜**版本 |
| 版本無法解析 | `MalformedVersion` | 拒收 |
| 版本比程式新 | `VersionTooNew` | 拒收、保留現有佈局、不寫回（不降級） |
| 版本比程式舊 | `Migrated` / `MigrationUnavailable` | 走 E7-08 遷移鏈；無鏈則拒收 |

**已知取捨（明文記錄，非靜默）**：E7-01 `parse()` 在版本不相容時直接拒收，舊版文件連
「讀成 `Value` 樹」都做不到。本層的作法是**僅**把版本行的值換成本實作支援的版本
（`restamp_format_version`，只動那一行、其餘位元組不動）以通過 E7-01 的版本閘，取得
**結構**後，把**原始宣告版本**交給 E7-08 `MigrationRegistry` 驅動遷移鏈。語意轉換全部由
註冊的遷移步驟負責，本層一行都不猜；沒有註冊步驟就是 `MigrationUnavailable`。
`restamp` 只換第一個版本行（重複的 key 留給 E7-01 去報錯），由
`VersionGate.RestampStopsAtTheFirstVersionLine` 釘住。

#### 3. DPI 語意（驗收標準明文）

存檔的 `x / y / width / height` 一律是**邏輯像素**（與 H1-07 `ComponentPlacement` 同慣例：
原點左上、widget 內相對）。裝置像素只在 `resolve_placement(placement, dpi_scale)` 這一步
產生，交出 **H1-06 的 `PaintBox`**（半開區間），不另造第二個像素矩形型別。
日後要改這條語意**必須走 E7-08 遷移並升 `format_version`**，不得默默改——
`LogicalPixelSemantics.PersistedGeometryIsScaleIndependent` 釘住「同一份存檔在不同 DPI 下
還原出相同的邏輯像素」。

#### 4. 「救不回來」的防線：判據，而不是一張入口清單

修訂 1 漏了「拒收之後覆寫」；修訂 2 補上了那個入口，卻漏了「部分丟棄之後覆寫」。
**同一條驗收標準被兩個不同的入口攻破兩次**，說明問題不在少補了一個 if，而在**判據選錯了**。

修訂 3 的判據：

> **本層在做覆寫決定的那一刻，知不知道自己沒能完整帶走使用者檔案裡的內容？
> 知道，就不能靜默覆寫。**

機器化成一個述詞（`IntakeReport::carries_everything()`）：讀得出來（`usable()`）
**而且**「沒帶走的內容」計數為 0（`lost_content() == 0`）。

修訂 2 用的是 `usable()`，而 `usable()` 把 `Repaired` 一律當成可以覆寫。
但 `Repaired` 同時涵蓋兩種語意完全相反的情況，這正是 F4 的根：

| | 存回去的意義 | 處置 |
|---|---|---|
| 幾何欄位被消毒（`repaired_fields`） | **自我修復**（把 NaN 寫回成 0） | **允許覆寫** |
| 整個元件被丟棄（`dropped_elements`） | **把使用者的資料扔掉** | **拒絕覆寫** |

##### 「沒帶走的內容」的完整清單

這份清單不是症狀的列舉，是**通道**的列舉：檔案裡的內容只能經由三條通道進到記憶體模型
——根 map 的鍵、每個元件的鍵、以及 `properties` 子樹（原樣攜帶）。
三條通道各自算一個計數器，通道之外的東西只剩排版。

| 來源 | 計數器 | 處置 |
|---|---|---|
| 整份讀不出來（`Malformed` / `MissingVersion` / `MalformedVersion` / `VersionTooNew` / `MigrationUnavailable` / `MigrationFailed` / `StructureInvalid`） | `usable() == false` | **拒絕** → `RefusedUnreadableTarget` |
| 元件帶不進來：缺 `id` / 缺 `type` / `id` 或 `type` 型別錯 / 重複 `id` / 項目不是 Map | `dropped_elements` | **拒絕** → `RefusedIncompleteTarget` |
| 整個 `properties` 區塊型別不對而被丟掉 | `discarded_properties` | **拒絕** → `RefusedIncompleteTarget` |
| 根層出現 `elements` 以外的鍵（如使用者自己加的 `wallpaper:`） | `unconsumed_keys` | **拒絕** → `RefusedIncompleteTarget` |
| 元件層出現 `id` / `type` / `properties` 以外的鍵（如 `note:`） | `unconsumed_keys` | **拒絕** → `RefusedIncompleteTarget` |
| 幾何欄位被消毒（NaN → 0、負尺寸 → 0、超限 → 夾限） | `repaired_fields` | **允許**（自我修復；過度嚴格會讓壞檔案永遠存不回去） |
| 版本被 E7-08 升級（`Migrated`） | 不計 | **允許**（遷移的目的就是把新版寫回去）。但計數器是**在遷移之後**算的：若某個遷移步驟把舊鍵留在原地沒消化掉，那些鍵會被算成 `unconsumed_keys` 而擋下覆寫——這是對的（那些內容真的會在覆寫時消失），修法是把遷移步驟寫完整，不是放寬判據 |
| 註解（`#` 行）、空行、縮排寬度、`1.00` vs `1.0` 這類字面寫法 | 不計 | **允許**，見下 |

> **最後一列是刻意的取捨，寫在這裡而不是藏起來**：本層的序列化是 **值層級**的往返
> （E7-12 的契約就是如此），不是位元組層級。使用者寫在存檔裡的註解與排版**會在覆寫時消失**。
> 若把它也算成「沒帶走」，那麼任何一份人手寫過的存檔都將永遠無法被覆寫——那不是保護，
> 是讓功能不能用。`properties` 的鍵序、數值的整數旗標、字串的轉義都**有**保住
> （`FormatParity` 與 `AtomicSave.SavedTextAlwaysReparsesToTheSameState` 釘住）。

##### 四道防線（第 4 道在修訂 3 換了判據）

1. 載入失敗 → **保留現有記憶體佈局**（與 E7-07「失敗保舊值」同一條原則）。
2. 載入失敗 → **不把壞狀態寫回**；`restore()` 那一次呼叫完全沒碰 storage。
3. `save()` 先序列化、再**往返自驗**，過了才 `storage_.put()`。
4. `save()` 在提交前**重讀目標**並問 `carries_everything()`；答案是否定的就具名拒絕
   （`RefusedUnreadableTarget` / `RefusedIncompleteTarget`）。要跨過去必須明示
   `Overwrite::DiscardTargetContent`，而且**原文一定先被備份**
   （`<name>.rejected`，必要時加序號；備份永不覆寫任何既有名字）。

`target_is_safe_to_overwrite()` 與 `dry_run_save(name)` **與 `save()` 用同一個述詞**，
不得給出比它寬鬆的答案——修訂 2 的 `target_is_readable()` 在「元件被丟棄」的那一刻回
`true`，呼叫端照契約問了、得到綠燈、然後資料沒了。那比「沒東西可問」更糟。

##### 守衛放在「提交的當下重讀目標」—— 以及它擋不住什麼

重讀目標擋得住「從來沒 restore 過就 save」（查 session 狀態擋不住）。
但它**只保護同名目標**：`restore("home")` 失敗之後 `save("work")` 仍會覆寫完好的 `work`
（驗收 R7）。修訂 2 的 CHG 把重讀寫成嚴格更好的方案是**不對的**——兩者覆蓋的是不同集合。
本層不處理後者：它分不出「使用者剛失敗就誤存到別的 profile」與「使用者刻意從空白建一份
新的 work」，那需要呼叫端契約。已列入「已知限制」。

關於「**寫入過程中斷**」：本層的提交點只有一個（`storage_.put()`），之前已完成序列化、
自驗與目標檢查，所以本層不可能產生寫到一半的存檔。**真正的檔案系統原子性
（temp + fsync + rename）不在本單元**：相位 1 的後端是 `MemoryLayoutStorage`。
相位 2 接磁碟後端時 `put()` 必須做 temp + fsync + rename，且「重讀目標 → 寫入」之間
存在 TOCTOU 空窗（相位 1 單執行緒、記憶體後端無此問題），兩者都必須在那個單元複查。

#### 5. 公開 API 一律不 throw

host 層把例外丟進 UI 迴圈等於整個桌面掛掉。所有失敗都是具名 enum ＋ `EditStats` 計數器
＋ `last_intake_status()` / `last_edit_status()` / `last_save_status()` / `last_message()`
（照 H1-08 `RingStatus` / `RingGaugeStats` 的做法）。

## 知識庫條目的落實

- **K-016 / K-002（NaN 比較）**：所有「可不可用」的判定一律**明寫 `std::isfinite(v)`**
  （`LogicalPlacement::finite()`、`clamp_finite()`），不靠任何比較順便擋住。
  `clamp_finite` 先判有限再夾，NaN 不可能原封通過。
  回歸測試：`AbsurdNumbers.SanitizersNeverLetNanThrough`（突變 M1 / M2 都被它殺死）。
- **float-cast-overflow**：`double → int` 之前先消毒、再夾到 `kDeviceLimit = 3.2e7`
  （遠小於 int 值域）才 `lround`。`AbsurdNumbers.ResolveNeverOverflowsTheDoubleToIntCast`
  以 NaN / ±Inf / 1e308 × 荒謬縮放的笛卡爾積跑過整條路徑。
- **K-013（懸空參考）**：`EditAssembly` 以參考 / 指標持有 `LayoutStorage` /
  `ReloadSource` / `MigrationRegistry`，生命週期需求寫在標頭；`source_->content()`
  一律按值接住。**本單元實際踩到一次**（在測試的遷移 lambda 裡讀一個正在被整個指派掉的
  `Value`），見 worklog。
- **K-014（同名不同型別的 ODR）**：`host/edit/` 的任何 target **都不**連入任何
  `e4_*` / `c2_*`；只連 `h1_06_dispatch`（它自己也刻意不相依任何 E4 target）。
  `test_h1_09*` 這兩個程式內 `ds::elements::RenderModel` 的定義數為 **0**。
- **K-012（斷言要能被突變殺死）**：見下節。

> 有一條突變釘住這個方向，才證明判據是**兩邊都對**，不是單純變嚴。

#### 一條存活的突變是**等價突變**（複驗者已獨立驗證）

- **M27**（`within_limits()` 只拿掉 `finite() &&`）：後面每個 `>=` / `<=` 對 NaN **與 ±Inf**
  都是 false，所以行為完全相同。複驗者以 `19^4 = 130,321` 組窮舉加 4,000,000 組隨機輸入
  實測，兩式**差異 0 組**。保留該行的理由是 K-016 要的「明寫 `isfinite`」，而不是它改變了
  什麼；危險的是「刪掉它**之後**把範圍檢查改寫成 NaN 寬容的 `!(a<b)` 形式」——那是
  **M28，已 KILLED**。

#### 更正：M31 **不是**等價突變（修訂 2 的用詞錯誤）

修訂 2 把 M31（右緣改成 `left + width*scale`）稱為等價突變，說「差異只在極少數 ULP」。
**這個用詞是錯的**：等價突變的定義是「不可能被任何測試殺死」，而 M31 殺得死。
複驗者構造了 663,135 組貼著 `lround` 的 `.5` 邊界的輸入，找出 **39,124 組真實的 1 px 差異**
（不是 ULP —— ULP 差落在 `.5` 邊界上就會翻面）。本修訂直接採用它給的兩組反例寫成測試
（`PixelPrimitives.RightEdgeIsTheScaledSumNotTheSumOfScaledParts`），**M31 現已 KILLED**。

正確的說法應該是「存在行為差異，但需要刻意構造，且只差 1 px」。
教訓：「等價突變」是一個很方便的標籤，用它之前要先證明**不可能**被殺死，
而不是「我想不到怎麼殺」。M27 有窮舉證明，M31 當時只有一句推論——而那句推論是錯的。

## 本單元查出的上游問題（**未修，不在鎖定範圍**；建議收進知識庫）

**`ds::format::parse()` 會丟例外，而它的契約是「回傳帶行號的 `ParseError`，不得靜默失敗」。**
兩條路徑，實測（g++ 13.3，`engine/format/document.cpp`）：

| 輸入 | 位置 | 結果 |
|---|---|---|
| 值為 `1e400`（**上溢**） | `numeric_token()` 的 `std::stod` | `THREW St12out_of_range: stod` |
| 值為 `1e-400`（**下溢**；修訂 1 漏報，由獨立驗收補出） | 同上 | `THREW St12out_of_range: stod` |
| `format_version: 99999999999999999999.0` | `parse_version()` 的 `std::stoi` | `THREW St12out_of_range: stoi` |

兩者都是**使用者在設定檔裡手打一個很大的數**就走得到的路徑。任何直接呼叫 `parse()`
而沒有 try/catch 的呼叫端，會在那一刻整個行程結束——對本專案就是「桌面不見了」，
而這正是驗收標準那條「不得進入救不回來的狀態」要防的事。

本單元的處置（**不改上游**）：
- `peek_format_version` **不用 `std::stoi`**，自行以溢位檢查累加；位數放不進 `int` 一律
  判為 `MalformedVersion`，因此那種文字根本不會被餵給 `parse()`。
- 對 `parse()` 的呼叫一律包 try/catch，例外轉成具名的 `IntakeStatus::Malformed`。
- 兩條路徑各有回歸測試：`VersionGate.MalformedVersionNeverThrows`、
  `AbsurdNumbers.ParserThrowFromOutOfRangeLiteralIsContained`。

> 這幾條**應該在 `engine/format/` 修**（`stod` / `stoi` 換成帶錯誤回報的解析），
> 本層的 try/catch 只是圍堵，不是修復。已回報 I1。
> **下溢（`1e-400`）與上溢是同一個 `stod` 呼叫**，補測試時容易只補上溢那一半——修訂 1
> 就只報了上溢。本單元的圍堵本來就涵蓋兩者（同一個 try/catch），修訂 2 另把下溢加進
> `AbsurdNumbers.ParserThrowFromOutOfRangeLiteralIsContained` 的輸入表。
