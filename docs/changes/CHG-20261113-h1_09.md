## Motivation

H1-09 是**裝配單元**：上面那些上游各自都已完成且各自有測試，但沒有任何一處把它們接成
「使用者真的會走的那一條路」——

```
加元件 / 拖動 / 換 kind / 拖放  →  就地編輯設定值  →  存檔（帶 format_version）
        →  重啟  →  還原  →  熱重載  →  依 kind 分派重畫
```

驗收標準的兩句話就是這條路的兩個端點：「拖動組件 → 存檔 → 重啟 → 位置還原」、
「換 kind → 熱重載 → 造型改變」。

### 真正的難點不在接線，在第三句話

> 「**使用者可直接改動持久化狀態，故錯誤不得讓佈局進入救不回來的狀態。**」

存檔是一份使用者拿編輯器就能改的文字檔。`NaN`、`Infinity`、`1e400`、空字串、負尺寸、
截斷、缺欄位、版本寫成 `2.0` —— 全部是現實輸入。而既有上游在這條路上的預設行為是
**嚴格失敗**：`E9-05 deserialize_layout` 對「某個元件缺 `id`」是 `throw`。接在 host 層就是
**使用者手滑刪掉一行，整個桌面回不來**。

### 關鍵設計決定

#### 1. 讀與寫刻意不對稱

- **寫**：一律 E9-05 `serialize_layout`（`LayoutStore::save` 用的同一個函式）。
  格式的單一事實來源在上游，本層**不自造格式**，結構與 `format_version` 全部沿用。
- **讀**：**不**用 E9-05 `deserialize_layout`（理由見 Motivation）。本層以**同一個結構**
  做容忍式讀取：壞元件具名丟棄並計數，其餘照常還原。

兩條路不得各自漂移 → `FormatParity.TolerantReaderAgreesWithE905OnValidInput` 釘住：
合法輸入下本層讀出的 `LayoutState` 必須與 `deserialize_layout` **逐欄相等**。

#### 2. `format_version` 四種分流

`ds::format::parse()` 自己會擋版本，但不相容一律回行號 0 的泛用訊息，分不出是哪一種。
本層在 parse **之前**先掃一次版本行（`peek_format_version`，純字串、不解析內容）：

| 情況 | 具名狀態 | 行為 |
|---|---|---|
| 缺 `format_version` | `MissingVersion` | 拒收。**不猜**版本 |
| 版本無法解析 | `MalformedVersion` | 拒收 |
| 版本比程式新 | `VersionTooNew` | 拒收、保留現有佈局、不寫回（不降級） |
| 版本比程式舊 | `Migrated` / `MigrationUnavailable` | 走 E7-08 遷移鏈；無鏈則拒收 |

**已知取捨（明文記錄，非靜默）**：E7-01 `parse()` 在版本不相容時直接拒收，舊版文件連
「讀成 `Value` 樹」都做不到。本層的作法是**僅**把版本行的值換成本實作支援的版本
（`restamp_format_version`，只動那一行、其餘位元組不動）以通過 E7-01 的版本閘，取得
**結構**後，把**原始宣告版本**交給 E7-08 `MigrationRegistry` 驅動遷移鏈。語意轉換全部由
註冊的遷移步驟負責，本層一行都不猜；沒有註冊步驟就是 `MigrationUnavailable`。
`restamp` 只換第一個版本行（重複的 key 留給 E7-01 去報錯），由
`VersionGate.RestampStopsAtTheFirstVersionLine` 釘住。

#### 3. DPI 語意（驗收標準明文）

存檔的 `x / y / width / height` 一律是**邏輯像素**（與 H1-07 `ComponentPlacement` 同慣例：
原點左上、widget 內相對）。裝置像素只在 `resolve_placement(placement, dpi_scale)` 這一步
產生，交出 **H1-06 的 `PaintBox`**（半開區間），不另造第二個像素矩形型別。
日後要改這條語意**必須走 E7-08 遷移並升 `format_version`**，不得默默改——
`LogicalPixelSemantics.PersistedGeometryIsScaleIndependent` 釘住「同一份存檔在不同 DPI 下
還原出相同的邏輯像素」。

#### 4. 「救不回來」的四道防線（第 4 道是修訂 2 補的）

1. 載入失敗 → **保留現有記憶體佈局**（與 E7-07「失敗保舊值」同一條原則）。
2. 載入失敗 → **不把壞狀態寫回**；`restore()` 那一次呼叫完全沒碰 storage。
3. `save()` 先序列化、再**往返自驗**（序列化 → 以本層讀回 → 逐欄比對），過了才
   `storage_.put()`。
4. **`save()` 在提交前重讀目標存檔；目標存在但本層讀不出來 → 具名拒絕覆寫**
   （`SaveStatus::RefusedUnreadableTarget`）。要丟棄必須明示
   （`Overwrite::DiscardUnreadable`），而且**連明示丟棄都會先把原文另存為
   `<name>.rejected`**。

**第 4 道是修訂 1 缺的那一塊，也是獨立驗收的阻擋項 F1。** 修訂 1 的 CHG 在這裡寫
「載入失敗 → 不把壞狀態寫回；storage 原文原封不動，**使用者還改得回來**」——
前半句屬實（就 `restore()` 那一次呼叫而言），**後半句不成立**：
「還改得回來」要求檔案活到使用者去改它，而修訂 1 的下一個正常操作就會把它刪掉：

```
開機 → restore("desktop") 被拒收（檔案裡多了一個 tab）→ 記憶體佈局是空的
     → 離開時自動 save("desktop") → 使用者的佈局永久消失，而 save 回報 Ok
```

使用者沒做錯任何事。`VersionTooNew` 尤其諷刺：本層拒收它正是為了保護它（不降級），
結果下一次 `save()` 就把它刪了。修訂 1 的 32 支復原測試裡，
`EXPECT_EQ(fx.stored(), before)` 全部只跨越 `restore` 這**一次**呼叫，
**沒有任何一條斷言跨越「拒收 → save」**，所以那個洞一條測試都沒踩到。

關於「**寫入過程中斷**」：本層的**提交點只有一個**（`storage_.put()`），且在它之前已經
完成序列化、自驗與目標檢查，所以本層不可能產生「寫到一半的存檔」。
**真正的檔案系統原子性（temp + fsync + rename）不在本單元**：相位 1 的 `LayoutStorage` 是
`MemoryLayoutStorage`（純記憶體，E9-05 明文「真實磁碟後端留待後續相位」），沒有磁碟可以被
寫到一半。相位 2 接真實磁碟後端時，**`put()` 的實作必須做 temp + fsync + rename**。

> **修訂 1 的論證錯在哪裡**（獨立驗收指出，此處記下以免重蹈）：用「相位 1 沒有磁碟可以被
> 寫到一半」把整個「救不回來」的條款論證掉。那對**撕裂寫入**成立，但相位 1 真正的資料毀損
> 路徑不是撕裂寫入，是**一次完整、合法、通過往返自驗的寫入，蓋掉本層刻意拒絕讀取的資料**。
> 那一條本層擋得住（`ingest_layout_text` 就在手上），所以本層就該擋。

**守衛刻意做在「提交的當下重讀目標」，而不是查「這個 session 上一次 restore 的結果」**：
後者只擋得住「restore 失敗 → save」這一條路，擋不住「從來沒 restore 過就 save」
（例如開機流程根本沒載入就存檔）——而那一條毀的資料一模一樣。
成本是每次 `save()` 多一次解析，佈局檔很小。

#### 5. 公開 API 一律不 throw

host 層把例外丟進 UI 迴圈等於整個桌面掛掉。所有失敗都是具名 enum ＋ `EditStats` 計數器
＋ `last_intake_status()` / `last_edit_status()` / `last_save_status()` / `last_message()`
（照 H1-08 `RingStatus` / `RingGaugeStats` 的做法）。

#### 兩條存活的突變都是**等價突變**，不是覆蓋面的洞

這兩條與修訂 1 的 M13（那一條**真的是**測試資料沒蓋到，補了資料才殺得死）**性質不同**，
所以處置方式也不同：不是補測試，而是**證明它們改不出行為差異**，再各補一條「真的會改出
行為差異」的兄弟突變並殺死它。等價突變硬要「殺死」只能靠斷言實作的寫法（而不是行為），
那種測試擋不住任何真實的錯誤，只會讓重構寸步難行。

- **M27**（`within_limits()` 只拿掉 `finite() &&`）：後面每一個 `>=` / `<=` 對 NaN 都是
  false，所以 NaN 在有沒有這個 `&&` 的情況下都會被擋掉——**行為完全相同**。
  保留它的理由是 K-016 要的「明寫 `isfinite`」，而不是它改變了什麼。
  危險的不是「刪掉它」，而是「刪掉它**之後**有人把範圍檢查改寫成 NaN 寬容的
  `!(x < lo) && !(x > hi)` 形式」——那一條就是 **M28，已 KILLED**。
- **M31**（右緣 `left + s.width * scale`）：`left` 是**還沒取整的 double**
  （`s.x * scale`），所以 `left + s.width*scale` 與 `(s.x + s.width)*scale` 是同一條
  double 算式，差異只在極少數 ULP。真正危險的是「**先各自取整再相加**」
  （`round(left) + round(width*scale)`），那會在非整數縮放下讓相鄰組件出現 1px 的縫
  ——正是 H1-07 `scale_box` 註解明文要避免的——那一條就是 **M30，已 KILLED**
  （`ComposeBridge` 的反漂移表裡刻意放了 `(1,1,1,1) @1.5` 這種
  「`(1+1)*1.5 = 3` 但 `round(1.5)+round(1.5) = 4`」的例子）。

## 本單元查出的上游問題（**未修，不在鎖定範圍**；建議收進知識庫）

**`ds::format::parse()` 會丟例外，而它的契約是「回傳帶行號的 `ParseError`，不得靜默失敗」。**
兩條路徑，實測（g++ 13.3，`engine/format/document.cpp`）：

| 輸入 | 位置 | 結果 |
|---|---|---|
| 值為 `1e400`（**上溢**） | `numeric_token()` 的 `std::stod` | `THREW St12out_of_range: stod` |
| 值為 `1e-400`（**下溢**；修訂 1 漏報，由獨立驗收補出） | 同上 | `THREW St12out_of_range: stod` |
| `format_version: 99999999999999999999.0` | `parse_version()` 的 `std::stoi` | `THREW St12out_of_range: stoi` |

兩者都是**使用者在設定檔裡手打一個很大的數**就走得到的路徑。任何直接呼叫 `parse()`
而沒有 try/catch 的呼叫端，會在那一刻整個行程結束——對本專案就是「桌面不見了」，
而這正是驗收標準那條「不得進入救不回來的狀態」要防的事。

本單元的處置（**不改上游**）：
- `peek_format_version` **不用 `std::stoi`**，自行以溢位檢查累加；位數放不進 `int` 一律
  判為 `MalformedVersion`，因此那種文字根本不會被餵給 `parse()`。
- 對 `parse()` 的呼叫一律包 try/catch，例外轉成具名的 `IntakeStatus::Malformed`。
- 兩條路徑各有回歸測試：`VersionGate.MalformedVersionNeverThrows`、
  `AbsurdNumbers.ParserThrowFromOutOfRangeLiteralIsContained`。

> 這幾條**應該在 `engine/format/` 修**（`stod` / `stoi` 換成帶錯誤回報的解析），
> 本層的 try/catch 只是圍堵，不是修復。已回報 I1。
> **下溢（`1e-400`）與上溢是同一個 `stod` 呼叫**，補測試時容易只補上溢那一半——修訂 1
> 就只報了上溢。本單元的圍堵本來就涵蓋兩者（同一個 try/catch），修訂 2 另把下溢加進
> `AbsurdNumbers.ParserThrowFromOutOfRangeLiteralIsContained` 的輸入表。

### F1 的修法為什麼是這個形狀

驗收者列了兩個可能方向（「查上一次 intake」或「put 前另存備份」），本修訂**兩個都做了，
但位置不同**：

- 主防線**不是**查「上一次 intake」，而是**在提交的當下重讀目標存檔**。理由：查 session
  狀態只擋得住「restore 失敗 → save」那一條路；**從來沒 restore 過就 save**（開機流程根本
  沒載入就存檔）毀的資料一模一樣，而 session 狀態對它一無所知。
  `OverwriteGuard.RefusesEvenWhenRestoreWasNeverCalled` 就是釘這一條的。
- 備份不是放在預設路徑（那會讓每次正常存檔都多一份垃圾），而是放在**明示丟棄**那條路上：
  使用者說「丟掉」時仍然先留一份 `<name>.rejected`。

## 已知限制 / 沒做的事（供複驗者查證）

1. **檔案系統層級的原子寫入沒做**，理由與歸屬見 Impact §4。相位 2 的磁碟後端必須在 `put()`
   實作 temp + fsync + rename。
2. **邏輯像素在 API 面沒有型別標記**（R1）：`drag_element(id, dx, dy)` 收的是裸 `double`，
   呼叫端誤傳裝置像素本層收得下且無徵兆。H1-07 的 `ComponentPlacement` 同樣是裸數值，
   要改得兩層一起改，不是本單元能單方面決定的。**未處理，照實記下。**
3. **`restamp_format_version` 是 workaround**，正道是 E7-01 提供「只解析結構、版本檢查交給
   呼叫端」的入口（R2）。獨立驗收已驗證本做法的關鍵前提成立（E7-01 的**文法與版本無關**）。
4. **`poll_reload` 把同一份文字解析兩次**（R5）：一次在 E7-07 內（取得定位到行的診斷），
   一次在本層（取得容忍式讀取的結果）。相位 1 無正確性問題；相位 2 接真實檔案監看時，
   兩次讀取之間檔案可能變動，屆時 E7-07 的報告與本層採用的內容可能對不上。**未處理**，
   留給接真實後端的單元複查。
5. **`properties` 的非幾何欄位不消毒**：只有 `x / y / width / height` 會在載入時被消毒，
   其餘欄位原樣保留（本層不認得其語意，擅自改值等於猜使用者的意圖）；非有限數值在
   `resolve_draws()` 被濾掉不進 `ElementDraw::params`。經公開編輯 API 寫入的值現在**一律
   深層檢查**（F2 修正），所以這條只剩 `reset()` 一個入口。
6. **`EditAssembly::reset()` 仍不消毒**（刻意的後門），把關交給 `save()` 的往返自驗 +
   非有限掃描。現在失敗時**說得出是哪一個元件的哪一條路徑**，且可用 `remove_property()` 清掉。
7. **`root.is_map()` 那條防線只有遷移路徑走得到**（`parse()` 之後根一定是 Map）；
   它由 `MigrationReturningNonMapIsStructureInvalid` 從遷移路徑打進去殺死。
8. **`<name>.rejected` 的備份不做輪替**：同一個名字連續明示丟棄兩次，第二次會覆寫第一次的
   備份。備份的用途是「按錯了立刻救得回來」，不是版本史，故認為可接受，但記下。
9. **`save()` 每次多一次解析**（重讀目標）。佈局檔很小，相位 1 的後端是記憶體，實測無感；
   相位 2 接磁碟後端後若成為熱路徑，可改為「只在目標的 mtime / 版本變動時重讀」——
   但**不得**退回成「只查 session 狀態」，那就回到 F1 了。
