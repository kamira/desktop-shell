## 缺陷：`ds::format::parse()` 違反自己明文的契約

`engine/format/document.hpp:11`：

> **錯誤可定位、不得靜默失敗**（NFR-04 精神）：任何解析失敗一律回傳帶「行號 + 訊息」的
> ParseError；絕不安靜吞掉未知 / 錯誤的輸入。

回傳型別是 `ParseResult`（成功持 `Document`、失敗持 `ParseError`，二者互斥）。**契約裡沒有例外。**

### 實測（I1 自寫 probe，g++ 13.3）

```
正常文件                              → 回傳 ParseResult：成功
值為 1e400                            → **丟出例外** St12out_of_range: stod
format_version: 99999999999999999999.0 → **丟出例外** St12out_of_range: stoi
值為 -1e400                           → **丟出例外** St12out_of_range: stod
值為 1e-400（下溢）                    → **丟出例外** St12out_of_range: stod
```

成因（讀碼確認）：`document.cpp:282` 的 `std::stod(t)` 與 `:229/:230` 的 `std::stoi(maj/min)`
都沒有保護。該檔唯一的 try/catch 在 `:585`，接的是內部的 `ParseFail`，**接不到 `out_of_range`**。
`parse_version` 的 `all_digits()` 只擋非數字字元，而 `"99999999999999999999"` 全是數字。

四個輸入都是**使用者在設定檔裡手打一個數字**就走得到的。

### 為什麼後果是行程結束，而不是某處被吃掉（逐項量過）

```
八個生產呼叫端全部沒有 try/catch：
  engine/package/permission_store.cpp:136   engine/package/install_store.cpp:235
  engine/package/layout_store.cpp:111       host/tray/ui_state.cpp:46
  content/widgets/note_widget.cpp:71        content/widgets/process_top_widget.cpp:339
  content/widgets/calendar_todo_widget.cpp:115
  （note_widget 確實有一個 catch，但在 :87、包的是 set_text、接 invalid_argument）

layout_store.hpp:131 對呼叫端宣告的失敗模式是 throw std::runtime_error
std::out_of_range 屬 logic_error 分支（實跑驗證）
  → **照文件接 runtime_error 的呼叫端接不到它**

host/app/host_main.cpp 的 try 區塊 / catch 子句數 → 0（精確比對，見下）
  → std::terminate
```

**我自己在這裡犯過一次錯並當場更正**：第一次用 `grep -c 'try\|catch' host_main.cpp` 得到 8，
以為有最外層攔截。那 8 個命中的是 `MetricRegistry` 這類字裡的 "try"。
改用 `grep -nE '(^|[^A-Za-z_])try[[:space:]]*\{|catch[[:space:]]*\('` 之後是**零個**。
這是本 session 第四次同族的錯（量了一個比問題更寬／更窄的東西），寫在這裡存證。
