## Motivation

描述子系統的宣告式文件（E7-01 `Value` 樹）會引用「模組」。當一份設定引用了**當前不存在 /
未安裝的模組**時，若整份文件硬失敗，使用者的桌面就完全起不來——這對「引用了一個沒裝的小工具」
這種輕微、可局部化的問題而言是過度反應。

本單元提供**優雅降級解析**：偵測文件引用了哪些缺席模組、以**停用佔位節點**取代該模組所擁有的
區塊、產出一份仍可用的降級後 `Value`，並附一份「缺席模組 / 降級決策」清單供上層顯示。降級決策
**必須可見、不得靜默**（NFR-04 精神）——不是安靜吞掉，而是明確記錄「哪個模組缺席、在樹的哪裡、
做了什麼決定」。是否存在由**可注入的可用性判定**決定，可由 E9-02 已安裝 manifest 清單建立。

本單元屬 engine 層（平台中立純邏輯）：無任何 `#ifdef` / 系統呼叫 / 真實後端，換平台一行不動；
可完全單元測試。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 模組引用慣例 | Map 節點含字串鍵 `module`（`kModuleKey`）即「由該 module id 擁有」 | 建立在 E7-01 既有 `Value` 樹上，零新格式；辨識規則簡單可測 |
| 可用性判定 | 可注入介面 `ModuleAvailability::has(id)` | 降級只依賴「模組是否存在」的抽象；來源可換（測試 / manifest / 執行期）|
| 可用性來源 | `ModuleSet`（明確集合）、`FnAvailability`（任意函式）、`available_from_manifests`（E9-02 清單）| 覆蓋測試注入與真實整合；模組存在 = 有 manifest 的 name 相符 |
| 能力閘控保護 | 一律先 `avail.has(id)` 才視模組為存在（NFR-03 精神）| 缺席即走降級路徑，不誤用不存在的模組 |
| 缺席區塊處理 | 以**停用佔位節點**取代：保留 `module` id + `disabled: true` + `degraded_reason` | 「以佔位 / 停用節點取代」；佔位自身即可見說明降級，上層可辨識並顯示 |
| 可用區塊處理 | 原樣保留，但**續遞迴**處理其巢狀引用 | 巢狀引用：可用外層裡的缺席內層仍要被降級 |
| 巢狀缺席回報 | 缺席外層取佔位後，仍掃描其子樹把巢狀缺席引用記入 missing / notes（僅回報，不入值）| 「偵測引用了哪些缺席模組」要完整，不因外層降級而漏報內層 |
| 決策可見性 | `DegradeResult{value, missing[], notes[]}`；`notes` 每筆帶 `module_id` / `path` / `message` | 決策可見、不靜默；`path`（如 `root.layers[1]`）定位到樹中位置，便於上層顯示 |
| missing 去重 | 保首見序去重 | 同一缺席模組多次引用只列一次，但每次出現都有獨立 note |

介面平台中立：無 `#ifdef _WIN32` 等平台分支、不綁任何真實後端，符合相位 1（Mac / null）約束。
engine 層與平台無關（非 `src/kernel/backend/`，不涉 backend_guard）。無絕對座標 / 數字 z-order（NFR-02）。
