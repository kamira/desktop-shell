## Motivation

本機 IPC：行程內 / 同機的訊息傳遞通道，供獨立行程 widget 宿主等使用。宿主與主行程之間需要
一條與具體傳輸無關的訊息通道；若一開始就綁死 socket / pipe，通道語意會被平台傳輸細節污染，
且無法以單元測試驗證。

E10-01 於相位 1 採「行程內佇列模型」——只實現純邏輯的訊息路由與投遞語意，不綁任何真實
socket / pipe / OS IPC。等真實傳輸層（相位 2）到位時，本契約即為其上的通道抽象：傳輸細節換掉、
投遞語意（送收順序、發布訂閱、無訂閱者不崩潰）不動。因此可完全以單元測試驗證，且換平台一行不動。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 訊息型別 | 具名字串 `MessageType`（非數字 topic id） | 穩定、可讀、跨邊界不變形；與 E6-01 `CommandId` 取捨一致 |
| 訊息酬載 | 重用 E6-01 `ds::command::CommandArgs`（穩定值型別具名字典） | 跨模組邊界不變形；可直接攜帶命令參數，與命令匯流排無縫搭配 |
| 命令搭配 | `Message::from_command(Command)`；`target_link_libraries(e10_01 PUBLIC e6_01)` | 本機 IPC 可承載具名命令，投遞後由接收端交 `CommandBus` 分派 |
| 投遞模型 | 兩者並存：點對點佇列（send/receive）+ 發布訂閱（subscribe/publish） | 涵蓋「單一消費者拉取」與「多方廣播」兩類需求 |
| 佇列語意 | `send` 入列 / `receive` 出列，FIFO；空佇列回 `std::nullopt` | 決定性順序、不崩潰、不丟例外 |
| 發布順序 | 訂閱者存於有序 `std::vector`，`publish` 依註冊序投遞 | 決定性投遞（可測順序） |
| 無訂閱者 | `publish` 回 0（投遞數），不視為錯誤、不崩潰 | 保守、可預期的邊界 |
| 訂閱識別 | `SubscriberId`（自 1 遞增，0 保留為無效 / 失敗） | 可退訂、唯一、失敗回值清楚 |
| 無效訂閱輸入 | 空型別 / 空回呼一律拒絕回 0，不掛上 | 契約邊界清楚 |
| 契約版本 | `contract_version()` = "e10_01/1.0.0" | 承重抽象（widget 宿主消費），供相位 2 換傳輸時相容判斷 |

介面平台中立：無 `#ifdef _WIN32` / `cocoa` / `__APPLE__` 等平台分支、不綁任何真實 socket / pipe / OS IPC。
