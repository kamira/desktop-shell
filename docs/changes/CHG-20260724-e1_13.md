# CHG-20260724-e1_13 — 多 profile 實例並存（E1-13）

- Date: 2026-07-24 | Branch: feat/e1_13 | Risk: low | Implemented by: I1.110
- Skill: ai-sdlc-autopilot
- Unit: E1-13（多 profile 實例並存，platform 層 / kernel / phase 1 / null）
- depends_on: E1-01（具名圖層與 z-order LayerStack）

## Motivation

四個產品共用同一 surface kernel，但同一份**具名 profile 定義**（例如某個 widget）在實務上
常需**同時開多個**——同一顆時鐘 widget 被使用者拖出兩個實例、同一種提示面板同時存在多份。
E1-01 已能把**單一具名 surface** 指派到具名圖層並維持堆疊順序，但沒有人管理「同一份定義
被實例化成多份、各自獨立、可各別列舉 / 查詢 / 銷毀」這件事。

本單元補上這層管理：`ProfileInstanceRegistry`，把「多實例並存」收斂成一個以具名 id 為鍵、
組合 E1-01 `LayerStack` 做圖層指派的登記表。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 圖層指派 | **組合**（非繼承）一個 E1-01 `LayerStack` 實例 | 直接覆用已驗證過的具名圖層指派 / z-order 邏輯，不重造輪子；`instantiate` 內部呼叫 `layer_stack_.assign`，`destroy` 呼叫 `layer_stack_.remove` |
| 能力矩陣 | Registry 不另持一份 `CapabilityMatrix`；`has()` / `capabilities()` 透傳組合之 `LayerStack` | 單一資料來源，避免兩份矩陣互相漂移（曾考慮各自持有，但會有一致性風險） |
| 實例 id 生成 | `instantiate(definition)` **自動生成**具名 id，格式 `<definition_id>#<n>`（n 為內部遞增序號） | 貼合「instantiate(profile)->id」的介面期望；id 仍是純字串（`InstanceId = std::string`），序號只用於拼字串、從不以數字型別對外暴露，滿足 NFR-02。格式亦保留可讀性（可回溯所屬定義） |
| 實例狀態 | 每份實例持有**獨立複製**的 `SurfaceProfile` + 獨立 `visible` 旗標 | `visible` 示範「各實例獨立可變狀態」（同定義兩份實例各自 show/hide 互不牽連），purely local，不涉及能力（不需 has() 閘控） |
| 上限 | 建構子可注入 `max_instances`（預設 `kUnlimited`） | 供 NFR「實例上限報錯不靜默」測試；超額回 `RejectedInstanceLimit`，不改狀態 |
| 錯誤回報 | `InstantiateOutcome{status, id}`，`InstantiateStatus` 四態（`Ok` / `RejectedEmptyDefinition` / `RejectedNoCapability` / `RejectedInstanceLimit`） | 沿用 E1-01 `LayerAssign` 的「可分辨拒絕原因」風格，呼叫端可依原因分流，不靜默 |

## 語意保證（明確不靜默）

- `instantiate`：`definition.id` 為空 → `RejectedEmptyDefinition`；已達 `max_instances` →
  `RejectedInstanceLimit`；`has(kernel.surface) == false` → `RejectedNoCapability`（皆不改狀態，
  含不佔用序號建立殘留記錄）。成功回 `Ok` + 全新具名 id。
- 同一 `definition` 可重複呼叫 `instantiate` 任意次，每次都是一份**彼此獨立**的新實例——
  各自的 `SurfaceProfile` 為複製、各自的 `visible` 各自獨立、各自在 E1-01 `LayerStack` 有
  獨立的圖層指派記錄。
- `destroy`：未知 id / 已銷毀（重複銷毀）→ 回 `false`（**明確不靜默**）；
  `has(kernel.surface) == false` → 回 `false`（NFR-03 閘控拒絕，狀態不變）。成功只影響該筆，
  其餘實例完全不受影響（隔離保證，測試逐一驗證）。
- `get` / `layer_of` / `is_visible`：未知 / 已銷毀 id 一律保守（`nullptr` / `nullptr` / `false`）。
- `show` / `hide`：未知 id 回 `false`；只影響目標實例，不牽連同定義的其他實例。

## NFR 合規

- **NFR-02**（具名，不用數字索引 / z-order）：`InstanceId` / `ProfileDefinitionId` 皆為
  `std::string`；`list()` 對外只回具名 id 清單（建立序，不暴露內部 `std::vector` index）；
  圖層一律透過 E1-01 `SurfaceLayer` 具名列舉表達；內部生成 id 用的遞增序號從不以數字型別
  跨越 API 邊界。
- **NFR-03**（能力閘控 `has()` 保護）：`instantiate` / `destroy` 皆透過組合的 `LayerStack`
  之 `assign` / `remove` 內建 `has(kernel.surface)` 閘控；`show` / `hide` 純本地可見狀態、
  不涉及任何能力，故未加閘控（符合「若涉能力」的條件式要求）。

## 測試涵蓋（19 gtest）

同一 definition 實例化多份且 id 互不相同、空 definition id 拒絕、實例上限拒絕、`get` 個別
查詢（含未知 id 回 nullptr）、`list` 依建立序列舉（含空登記表）、經 E1-01 指派具名圖層（含
未知 id 查圖層回 nullptr）、銷毀個別且其餘實例不受影響（隔離）、未知 id 銷毀回 false、重複
銷毀回 false、show/hide 只影響目標實例（隔離）、show/hide/is_visible 未知 id 保守回 false、
同定義兩實例完全隔離（隱藏 + 銷毀一份不影響另一份）、NFR-03 預設能力可用、`instantiate` 於
無能力時拒絕且狀態不變、`destroy` 於無能力矩陣下一律結構化拒絕、`to_string` 四態具名字串。
