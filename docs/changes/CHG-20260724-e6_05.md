## Motivation

E1-13 讓同一份 widget profile 可同時實例化多份（多個獨立視窗），E6-01 提供具名命令的
匯流排分派，但兩者互不相知：呼叫端若要「同時對所有實例下命令」或「對一組指定實例下
命令」，得自己手寫迴圈 + 手動查 registry + 手動組 target 參數。E6-05 把這個重複模式收斂
成一層薄的協調器：**跨多個 surface / profile 實例的命令控制**——廣播、群組、指定具名
目標，經 E6-01 分派、經 E1-13 列舉與驗證目標存活性。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 目標指涉 | 一律具名 `InstanceId`（字串），群組為具名清單 | NFR-02：不出現數字索引 / 數字 handle |
| 目標存在性驗證 | `send_to` / `send_to_group` 各目標先經 `registry.contains()` | 未知目標不應誤觸發匯流排；「目標不存在」與「命令執行失敗」需可分辨 |
| 未知目標處理 | 回 `TargetDispatchStatus::UnknownTarget`，**不呼叫** `CommandBus::dispatch` | 避免處理器誤以為目標存在；報錯不靜默 |
| 命令未註冊處理 | `CommandBus::dispatch` 回 `NotFound` → 映射為 `CommandNotFound` | 與 `UnknownTarget` 語意分離：前者是命令問題、後者是目標問題 |
| 目標傳遞方式 | 把目標 id 併入參數（鍵 `"target"`）再交給 `CommandBus::dispatch` | `CommandBus` 本身不知道「實例」概念，只認命令 id；由本單元把目標資訊塞進參數，處理器可讀 `args.get_string("target")` 得知本次呼叫對象 |
| 廣播順序 | 依 `registry.list()`（建立序，穩定） | 決定性、可測試、不依賴任何數字序 |
| 空目標集合 | 回空 `CrossDispatchReport`，`all_ok()==true` | 語意上「全部」= 0 份、「一組」= 0 個都合法，不是錯誤 |
| 逐目標結果 | `CrossDispatchReport{ per_target: vector<TargetResult> }` + `ok_count`/`failed_count`/`all_ok` | 呼叫端可分辨整體與個別成敗，不必自己再彙總 |
| 群組內部分成敗 | 每個目標各自獨立分派，互不影響（部分成功可能） | 一個目標未知 / 失敗不應連坐其餘目標 |

介面平台中立：無 `#ifdef _WIN32` 等平台分支、不綁任何真實副作用 / OS 後端。本單元不新增
任何命令執行語意，處理器仍完全由呼叫端在 E6-01 註冊；本單元只做「目標選擇 + 逐目標分派」。
