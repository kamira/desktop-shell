## Motivation

`E9-07` 的 `InstallRegistry`（`engine/package/drop_install.hpp`）是純記憶體登錄
（`std::map<std::string, Package>`，介面只有 `contains/add/find/size`），檔內自己就明寫是
「相位 1 的安裝目標」——**重啟即失憶**。

`CHG-20260829-05` 已經把這個缺口指名出來：使用者要的語意是「設定項目依**安裝了哪些 widget**
而定，**有安裝即新增，即使沒打開**」。那份 CHG 的現況圖把 `E9-07 InstallRegistry` 標成
「**記憶體登錄，重啟失憶**」的斷線之一，目標圖則把 **E9-10** 定義為
「`InstallRegistry` 從記憶體升為可存可讀」，並讓 `E7-16`（設定分頁登錄）與 `E9-11`
（權限授予狀態）消費它。

所以 E9-10 要補的不是新功能，是**持久化那一層**：把「已安裝了哪些套件」的中繼資料寫成可重讀
的宣告式紀錄，讓登錄物件被銷毀重建之後**仍然列得出該套件**，而且**不需要載入套件本體**。

## 設計（可覆核可改）

照 **E9-05 `layout_store`** 的同構先例辦，不另闢蹊徑：以 E7-12 `serialize` 把狀態寫成 E7-01
宣告式文字、定義一個**可注入的抽象後端**、相位 1 預設實作為純記憶體替身、並宣告自身的格式
版本欄位。

### 新增型別（`engine/package/install_store.{hpp,cpp}`，namespace `ds::package`）

| 型別 / 函式 | 角色 |
|---|---|
| `InstallRecord` | 持久化單位。持有 E9-01 `Package`（manifest + 內含項目邏輯路徑清單）。`package_id()` = `manifest.name` |
| `InstallStorage` | **可注入的抽象後端**：`put/get/has/erase/names`（形狀同 E9-05 `LayoutStorage`） |
| `MemoryInstallStorage` | 相位 1 預設實作：純記憶體，**無真實檔案 I/O** |
| `kInstallRegistryFormat{1,0}` | 本持久化格式**自身**的版本欄位（Q3：格式從第一版就帶版本） |
| `serialize_install_records` / `deserialize_install_records` | 經 **E7-12 `serialize`** 產出 / 經 **E7-01 `parse()`** 讀回 |
| `InstalledPackageStore` | 登錄門面：**建構即自後端重讀（rehydrate）**、`record()` **寫入即落盤（write-through）**；`record/forget/contains/find/list/records/size/reload/serialized` |
| `mirror_into(store, InstallRegistry&)` | 把持久化紀錄重播進一個**全新的** E9-07 登錄（重啟後回填的接點） |

### 設計決定 1：持久化的對象是 E9-07 `InstallRegistry`，不是 E9-06 `PackageRegistry`

兩個對稱登錄並存（`drop_install.hpp` 的 `InstallRegistry`；`uninstall.hpp` 的
`PackageRegistry`，多了 `remove` 與相依邊查詢）。E9-10 持久化的是**前者所代表的語意**，理由：

1. `CHG-20260829-05` 的目標圖**明寫** E9-10 = 「`InstallRegistry` 從記憶體升為可存可讀」。
2. 下游消費者（`E7-16` 設定分頁、`E9-11` 權限狀態）要的是「**安裝了什麼**」這份清單與各套件的
   `manifest.permissions`，不是 E9-06 的**卸載相依圖**。相依邊是卸載決策用的，與「設定分頁該長
   出哪幾頁」無關。
3. E9-06 的相依邊是**登錄期宣告**的（`add(pkg, depends_on)`），不在 manifest 裡，因此它不是
   「已安裝這件事」的一部分；若一併持久化，就把兩個單元的語意綁死，E9-06 日後要改相依模型會
   被這份格式拖住。

**代價與誠實說明**：`InstallRegistry` 的公開介面**沒有列舉能力**（只有
`contains/add/find/size`，`by_name_` 為 private），所以**無法**從一個既有的 `InstallRegistry`
快照出內容。E9-07 已合併、可讀不可改，故本單元不去改它，而是新增 `InstalledPackageStore`
自行承載紀錄，並以 `mirror_into` 做**單向回填**（store → registry）。安裝路徑上的用法是：
E9-07 安裝完成後，呼叫端以 `registry.find(name)` 取回該套件並 `store.record(*pkg)`
（測試中即走這條真實路徑）。相位 2 若 E9-07 開放列舉，可再加一個反向的 `capture_from`，
介面不必改。

### 設計決定 2：套件名放在「清單項目的 `name` 欄位」，不當 map 鍵

E7-12 檔頭記載兩個已知限制，兩個都踩到了，處理如下：

| E7-12 已知限制 | 本單元怎麼處理 |
|---|---|
| **map 鍵不支援引號**（鍵為裸 token，不得含 `:` / 換行 / 前後空白） | **不把套件名當 map 鍵**。文件結構是 `packages:` 底下一個**清單**，每項是 `{name, format_major, format_minor, version?, description?, requires, permissions, entries}`。名字落在**值**的位置，由 E7-12 `needs_quote` 自動引號化 / 轉義，型別與內容不漂移。E9-02 對 `name` 只要求非空、**並未禁止** `:`，所以這不是理論風險——測試 `PackageNameWithColonSurvivesBecauseItIsAValueNotAMapKey` 用 `"weird: name"` 釘住它 |
| **空容器不 round-trip 為同型**（`key:` 下無縮排塌成 Null） | 讀取端把「缺鍵」與「Null」**一律視為空清單**（`packages` / `requires` / `permissions` / `entries` 四處皆然）。空登錄序列化成 `format_version: 1.0\npackages:\n`，再讀回即空登錄，**不是錯誤**。兩個測試釘住（`EmptyRegistryRoundTripsAsEmptyRatherThanFailing`、`ManifestOnlyPackageRoundTripsWithEmptyLists`） |

另有一個同族陷阱：manifest **自身**的 `format_version` 若寫成字串 `1.0`，會被 E7-01 的型別推斷
讀回成 **Number**（且無法區分 `1.1` 與 `1.10`）。故拆成 `format_major` / `format_minor` 兩個
整數存放，型別與語意都不漂移。

### 設計決定 3：不重造驗證、不靜默失敗

- 紀錄寫入與讀回都跑 **E9-01 `validate_package`**（manifest 有效性、格式版本相容性、邏輯路徑
  合法性與不重複）——不重造一套驗證規則。
- 失敗一律 `throw std::runtime_error`，訊息可定位（解析錯誤附**行號**）：文字損毀、根節點非
  Map、`packages` 非清單、項目缺 `name`、欄位型別不符、文件內**重名**、套件結構不合法。
- 特別是：**後端有內容但損毀時建構子拋錯**，絕不靜默當成空登錄——那會悄悄遺失所有安裝紀錄
  （測試 `CorruptBackendContentThrowsRatherThanLosingEveryInstall`）。
- `forget()` 查無套件回 `false` 而不拋錯是**刻意的**：「查無此套件」的語意與回報是 E9-06
  卸載流程的職責，E9-10 不搶。

### 相位 1 的「重啟」是以什麼機制模擬的，以及為什麼它在相位 1 成立

**誠實聲明：`MemoryInstallStorage` 是記憶體替身，不是真實磁碟後端。** 真實磁碟後端留待後續
相位（屆時 `InstallStorage` 介面一行不動）。這與 E9-05 `MemoryLayoutStorage` 是同一姿態——
相位 1 的 engine 層不得有真實檔案 I/O（G1b / `backend_guard`、`PHASE-PLAN.md`），所以替身是
此相位**唯一合法**的選擇，而不是偷懶。

在這個前提下，「重啟」被定義為：**後端存活、登錄物件被解構後重新建構**。
之所以成立，是因為持久化的真正斷點不在「行程有沒有結束」，而在「**資訊有沒有離開那個會死掉的
物件**」。`InstalledPackageStore` 解構後，記憶體索引不存在了；新建的 store 只能從後端取得
資訊。因此「新 store 指向同一個存活後端」在資訊流上**等價於**重啟後的狀態：唯一的資訊通道是
已序列化的文字。相位 2 把後端換成磁碟，這條資訊通道的兩端不變，只是中間換了媒介。

**刻意不這麼寫**：對同一個還活著的 store 再查一次。那證明不了任何事，正是
`CHG-20260829-05` 停點明指「記憶體登錄過不了」的那種寫法。

**驗收標準那句『安裝 → 不載入 → 重啟 → 仍列得出該套件』拆成三個獨立、名字講得出意圖的案例：**

| 案例 | 證明什麼 | 怎麼證 |
|---|---|---|
| `InstalledPackageIsStillListedAfterTheStoreObjectIsDestroyedAndRebuilt` | **重啟** | storage 在**外層** scope、store 在**內層** scope；內層結束（store 解構）後，以**新**的 store 指向同一後端 → `list()` 仍列得出 |
| `ListingAfterRestartNeverReopensThePackageSource` | **不載入** | 以**計數型** `InstallSource` 經 E9-07 `DropInstaller` 真實安裝（`open()` 計數 = 1）；重啟後列舉，計數**仍為 1** → 列舉過程完全沒有讀 / 載入套件本體 |
| `FreshInstallRegistryIsRehydratedFromStorageWithoutAnySource` | **回填 E9-07** | 來源物件在重啟前即銷毀（之後「載入本體」物理上不可能）；重啟後 `mirror_into` 一個**全新空白**的 `InstallRegistry` → `contains()` 為真、`size()==1`；再回填一次回 0（同名不覆寫） |

另有 `ManifestMetadataAndEntryInventorySurviveRestart`（重啟後拿到的不只是名字：
`version` / `description` / `requires` / `permissions` / `entries` 全在——下游 E7-16 / E9-11
要的就是這些）與 `MultiplePackagesSurviveRepeatedRestarts`（連續兩次重啟不衰減）。

格式組釘住：產出是 E7-01 可再解析的合法輸入且帶 `format_version`、round-trip 不變式、
