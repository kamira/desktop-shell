## Motivation

`-05` 讓 G0 開始跑 `tests/` 底下所有 Python 測試，但當時只有 4 支檔——
`scripts/` 七支治理工具裡，**`halt_gate.py`／`plan.py`／`scope_check.py` 一個測試都沒有**。

這三支不是邊角料：

| 腳本 | 它決定什麼 | 算錯的後果 |
|---|---|---|
| `halt_gate.py` | G6 停點契約：AUTO 還是 HALT | **該停的沒停**——medium 風險自動合併掉 |
| `scope_check.py` | G1 鎖定範圍 | **越權沒被擋**——subagent 改到別人的檔 |
| `plan.py` | 派工來源（AGENTS.md §3）+ G6 上半段 | 派出相依未滿足、或與別人搶同一片檔案的工作單元 |

`plan.py` 那一項的性質和另外兩者不同，值得說清楚：**它算錯不會有任何東西紅燈**。
G1 只檢查「你有沒有寫到範圍外」，不檢查「這個範圍是不是同時發給了兩個人」。
兩個 subagent 拿到重疊的 `write_scope`，各自都在自己範圍內、各自都過 G1，
然後互相覆蓋——直到有人發現某個檔案的內容莫名其妙變回去了。
這種錯沒有閘門會抓，只有 `ready()` 的範圍互斥邏輯在擋，而它沒有測試。

## 實作中的兩個決定

### 一、`scope_check.py` 抽出純函式（最小侵入）

判定邏輯原本內嵌在 `main()` 裡，而 `main()` 需要 argparse + 真實 git repo 才跑得起來——
等於**這道閘門的判定無法在測試裡單獨驗證**。抽出兩個純函式：

- `in_scope(path, allow)`：單一路徑是否落在允許清單
- `out_of_scope(files, allow)`：回傳越權清單

`main()` 改為呼叫後者，行為不變。**沒有動 `U` 的模組級載入**——那要改的東西更多，
而收益只是測試寫起來漂亮一點。

順帶修掉一處 K-009：`subprocess.run(["git","diff",...])` 沒有指定 `encoding`。
檔名多半是 ASCII 所以沒被踩到，但那正是 K-009 描述的形狀。

### 二、`plan.py` 用 context manager 換掉模組級 `M`／`U`

`plan.py` 在 import 時就讀死了真實 `units.json`，沒有注入點。
測試用 `FakeUnits` 暫時替換 `plan.M` / `plan.U`，**不改被測程式碼的結構**——
為了測試而重構排程器的載入方式，風險大於收益。

## Impact

### 影響範圍

- `tests/gates/test_halt_gate.py`（**新增**，15 測試）
- `tests/gates/test_scope_check.py`（**新增**，18 測試）
- `tests/gates/test_plan.py`（**新增**，26 測試）
- `scripts/scope_check.py`：抽出 `in_scope` / `out_of_scope`；補 `encoding="utf-8"`。
- **不動**：`halt_gate.py`、`plan.py`（兩支一行未改）、`.github/`、`AGENTS.md`
  （G0 自動收錄新測試，這正是 `-05` 的設計目的——補測試的人不必再碰 CI 設定）。

### 測試的重點放在哪

不是「正常情況會通過」，是**每一種失效都必須被抓到**：

- **`halt_gate`**：7 條 tighten-only。政策檔不存在、停點沒定義、`auto` 鍵缺漏、
  `auto` 是空清單、政策物件是空的、風險等級沒見過——**全部必須落在 HALT 這一邊**。
  一道在不確定時放行的停點閘門，比沒有停點閘門更危險：它讓人以為有守。
- **`scope_check`**：5 條越權必須被抓（別的單元的原始碼、根 `CMakeLists.txt`、
  `.github/workflows/`、`docs/knowledge/INDEX.md`、混在合法檔案裡的那一個）。
- **`plan`**：相依未滿足不得派工、範圍衝突不得同批派、`autonomy: halt`
  必須在呼叫 `halt_gate` **之前**就攔下。

### 順手釘住的三件事實（真實資料回歸）

這幾條不是測 `plan.py` 的邏輯，是測 `units.json` 的內容——它們一旦破了，
症狀都是「安靜地不會發生」而非報錯：

1. **每個 `depends_on` 都指向存在的 id**：指向不存在的 id → 該單元永遠不會被派工，
   而且不會有任何錯誤訊息。
2. **每個 `branch` 的 slug 與 id 互推得回去**：對不上 → `unit-for-branch` 查不到 →
   CI 的 unit 步驟紅燈。
3. **187 個單元的 `brief()` 都渲染得出來**：`BRIEF.format` 少一個欄位就 `KeyError`，
   而那會在**派工當下**才炸。

## 一個發現（記錄，未修）

`fnmatch` 的 `*` **會跨 `/`**，所以 `content/**` 這種較淺的 `write_scope` 實際上
放行整棵子樹。真實 `units.json` 裡有 5 個單元的 scope 只有一層深度。

**沒有修**：改成更嚴謹的比對會一次改變 187 個單元的鎖定範圍，
影響面遠大於本 CHG 的意圖。改為**用測試把現行語意釘住**
（`TestFnmatchRealBehaviour`），讓下一個想「順手換成更嚴謹的比對」的人先看到影響面。
前綴仍然是實的（`content_evil/` 不會被 `content/**` 放行），所以這是鬆，不是破。

## 不含（避免越界）

- 不改 `fnmatch` 的比對語意（見上）。
- 不重構 `plan.py` / `scope_check.py` 的模組級資料載入。
- 不處理 `docs/backlog/HANDOFF.md` §0-B 的 6 項操作驗收——
  **本機沒有 C++ 工具鏈**（`cmake`／`cl`／`msbuild`／`g++` 皆無），
  與原記載的防毒封鎖無關；那 6 項需要一台裝了工具鏈的機器。
