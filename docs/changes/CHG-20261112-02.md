## 本次最重要的一件事：一個貫穿全 session 的證據缺口

V1.3 的保留意見第 1 項指出——並由本收尾者實測確認——**repo 的預設建置沒有任何警告旗標**：

```
根 CMakeLists.txt:17   add_compile_options(/utf-8)      ← MSVC 專用，僅此一行
實際 CXX_FLAGS         -std=gnu++17                     ← 無 -Wall / -Wextra / -Werror
G3 的建置命令           cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
```

所以任何 CHG 裡「全 repo 建置零 warning」一句**幾近自動成立**，不管程式碼怎麼寫。

**這直接指向本收尾者自己的稽核做法。** `CHG-20261111-03`（E9-10 收尾）與
`CHG-20261112-01`（W1-08 收尾）都把「0 warning / 0 error」列為稽核證據，而那是在
預設旗標下取得的——真，但近乎空話。本檔起改為**兩個數字分開報**：預設旗標那句
標明其空洞，另以 `-Wall -Wextra -Wpedantic -Werror` 單獨複驗才算證據。

本單元的有內容版本（**實際取 g++ 的退出碼**）：

```
g++ -std=c++17 -Wall -Wextra -Wpedantic -Werror -c engine/format/settings_pages.cpp
  → exit=0、輸出 0 行
g++ … -fsyntax-only tests/e7/test_e7_16.cpp
  → exit=0、輸出 0 行
```

### 而取這個數字的過程本身又踩了同一族的坑

第一次複驗寫成 `g++ … 2>&1 | tail -5 && echo "零警告"`。編譯實際以
`fatal error: gtest/gtest.h: No such file or directory` 中止，但印出的 `exit=0` 是
**`tail` 的退出碼**，於是那行「零警告」是假的。重做時改為把輸出寫檔、單獨取 `rc=$?`、
並印出輸出行數，才取得上面那組有依據的數字。

**今天同一族已經第三次**：
1. 早上 `git push ... 2>&1 | grep -c` 吃掉 ref 刪除的 403，只留下一個靜默的 0；
2. `K-011`：G5 的 `bash -e -o pipefail` 下 `ls` 失敗讓賦值中止，`::error::` 永不印出；
3. 本次 `tail` 吃掉 `g++` 的失敗。

共同形狀：**管線最後一個命令成功，不代表前面那個做了它該做的事。** 而三次都發生在
「檢查某件事是否成立」的程式碼上——也就是說，失效方向都是**把未完成的檢查報成通過**。

## 設計決定的覆核：為什麼不連結 `e9_10`

`units.json` 的 `E7-16.depends_on` 含 `E9-10`，但實作只 `target_link_libraries(e7_16 PUBLIC e7_14)`。
實作者的論證與 V1.3 的覆核一致，本收尾者亦實讀原始碼確認：

- **E9-02 `Manifest`**（`engine/package/manifest.hpp`）只有 `format_version` / `name` /
  `version` / `description` / `required_capabilities`（文字 key `requires`）/ `permissions`
  ——**沒有任何承載設定宣告的欄位**。
- **E9-01 `Package`** 的內含項目清單只有 `kind` + `logical_path`（資源的**路徑**，不是**內容**）
  ——那正是 E9-10「列舉不需載入」的物理基礎。

故「這個套件宣告了哪些設定欄位」**不在 E9-10 的回答範圍內**；即使連上 `e9_10`，
仍需另有一層把那份內容交進來。改以可注入抽象 `SettingsContributionSource` 表達，
符合 `InstallStorage` / `LayoutStorage` / `ProcessSource` 的既有風格。

**代價已由 CHG 誠實列出**：本單元不含 `E9-10 → 設定分頁` 的端到端接線（屬 host 層、
不在 write_scope 內），且 ACC 明文**不宣稱**那條接線已被驗證。
