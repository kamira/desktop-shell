# CHG-20260724-e2_02 — 採集頻率分級與除頻（E2-02）

- Date: 2026-07-24 (UTC+0) | Branch: feat/e2_02 | Risk: medium | Implemented by: I1.20
- Skill: ai-sdlc-autopilot
- Unit: E2-02（採集頻率分級與除頻，engine 層 / 子系統 metrics / 承重 20x / 相依 E2-01）

## Motivation

E2-01 定義「一個指標是什麼」（名稱/值/單位/範圍/歷史/實例）。E2-02 定義「一個指標**多久
採集一次**、以及**多個消費者要同一指標時如何合併採集**」——這是把統一指標介面接上真實
採集迴圈前，必須先立好的資源治理契約（承重 20x，多個 sysinfo 提供者相依它）。

兩個問題直接關係 NFR-01（idle 門檻）：

1. **高頻採集吃資源**：若對每個指標都以最高頻採集，閒置時 CPU 被拉高，違反 idle 門檻。
   故把頻率**分級**（high/normal/low/on-demand），變動慢的指標（磁碟容量、電池健康）走低頻
   或隨需，只有要跟手的指標（前景動畫用的 CPU 負載）走高頻。
2. **重複採集**：多個掛件常要同一指標。若各採各的，同一感測器被讀 N 次。**除頻**把同一
   指標的多筆需求合併成一次採集，並按**最高需求頻率**供給——誰要得最頻繁就用誰的頻率，
   其餘消費者搭便車。

平台中立純邏輯：時間以**邏輯 tick** 表達（呼叫端每輪推進），不綁真實時鐘，故可完全單元
測試（注入時間、驗採集次數符合分級、驗多消費者除頻合併）。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 分級 | `enum class SamplingTier { High, Normal, Low, OnDemand }` | 四級涵蓋「跟手／常規／慢變／隨需」；OnDemand 非週期，只在被請求時採 |
| 位階 / 比較 | `tier_rank()`（High=3…OnDemand=0）、`higher_tier(a,b)` | 除頻挑「最高需求頻率」的基礎；純函式好測 |
| 分級→間隔 | `SamplingPolicy`：High=1 / Normal=8 / Low=64（tick），OnDemand=nullopt | 可調（`set_interval`，鏈式），省電模式可整組放慢；級距拉開讓 idle 門檻成立 |
| 時間模型 | 邏輯 `Tick`（`uint64_t`），`advance(now)` 推進 | 平台中立：本層只認識「第幾 tick」，真實時鐘由呼叫端綁定；可注入時間單測 |
| 需求登記 | `add_demand(id, tier)` 回 `DemandId` 票根；`remove_demand(id)` 撤銷 | 消費者以票根管理自己的需求；撤銷最後一筆即停止追蹤該指標 |
| **除頻合併** | 有效分級 = 同一指標所有存活需求中最高頻者；一次採集供全體 | 承重核心：`advance()` 對合併後的指標只回一份（非每消費者一份），按最高頻供給 |
| 提頻提前 | 新需求拉高有效頻率時，把下次採集時機提前到 `now + 新間隔` | 高頻消費者加入不必等舊的慢週期跑完 |
| 到期判定 | `advance(now)`：週期指標 `next_due <= now` 即到期，回傳決定性順序（首次登記序） | 供呼叫端據清單去讀感測器並更新 E2-01 Metric；順序穩定好測 / 好排 UI |
| **不補採** | 到期後 `next_due = now + 間隔`（非 `+= 間隔` 累加） | 跨多個間隔（閒置久了醒來）只採一份，不爆量——直接護住 idle 門檻 |
| 隨需觸發 | `request_now(id)`：下次 advance 強制採一份，無視間隔 | 驅動 OnDemand 指標；對週期指標亦可用於立即刷新 |
| 時間單調 | `advance(now)` 若 `now < now()` 視為不推進、回空清單 | 防止時鐘倒退造成重複採集 |

平台中立：無 `#ifdef`（僅 include guard）、無系統呼叫、無真實時鐘，符合 engine 層「換平台
一行不動」約束。相依 E2-01：沿用 `ds::metrics::MetricId` 作指標身分，不另造識別碼系統。

## 不含（避免越界）

- **不接真實時鐘 / 採集迴圈**：`advance` 由呼叫端（未來的採集器 / 測試）以邏輯 tick 驅動。
- **不實作任何真實感測器**，也不讀寫 E2-01 的 Metric 值：本單元只決定「何時該採、合併誰」，
  實際去讀感測器並 `update()` Metric 是呼叫端的事。
- 不引入優先權反轉 / 背壓 / 自適應降頻等進階排程策略——那些屬後續調校，塞進契約會過度綁定。
- 未動 `units.json`、根 `CMakeLists.txt`、`docs/structure/directory.md` 或任何鎖定範圍以外檔案。
