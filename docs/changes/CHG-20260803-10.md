# CHG-20260803-10 — 修復 K-003 契約鴻溝：契約第一次真的驗證真實後端

- Date: 2026-08-03 (UTC+0) | Branch: claude/contract-real-backends | Risk: **medium**（動 E1-25 契約組） | Implemented by: I1
- Unit: **E1-25**（kernel 後端契約測試組）
- Skill: ai-sdlc-autopilot v1.1
- 前置：`CHG-20260803-03`（發現並記錄 K-003）、`-04`/`-06`（W1-01/W1-02 win32 後端）

## Motivation

`CHG-20260803-03` 記錄的 **K-003**：repo 裡有**兩個毫不相干的 `KernelBackend`**——
真實後端實作的 `ds::kernel::KernelBackend`（具名 `SurfaceId` + `bool` + frame/input），
與契約組自帶的 `ds::kernel::contract::KernelBackend`（數字 handle + `Status` 三態 + `invoke_capability`）。

契約組**刻意不 link 任何真實後端**以「維持 E1-25 與 E1-24 的單元獨立」，
只測它自己目錄裡的 `StubBackend`。後果：**它從未驗證過任何真實後端，連 null 都沒有。**

PHASE-PLAN 寫的「契約測試不改一行拿去跑 win32 後端——**這才是相位 1 的投資回收點**」，
那筆投資根本不在帳上。這是相位 2 收尾前唯一還沒關的結構性缺口。

## Impact

### 契約重寫為針對真實介面

新增 `tests/contract/kernel_backend_contract.hpp`：對 `ds::kernel::KernelBackend`
的參數化 gtest 套件，**16 條斷言**，平台中立。

移除 `tests/contract/kernel_backend.hpp` 與 `stub_backend.hpp`——
那個平行介面與 stub 是問題本身，留著只會讓下一個人再次困惑。

### 一份契約，兩個註冊點

| 後端 | 註冊點 | 建置條件 | ctest 名稱 |
|---|---|---|---|
| null | `tests/contract/test_contract_backend.cpp` | 所有平台 | `contract_backend` |
| win32 | `tests/e1/test_contract_win32.cpp` | `if(WIN32)` | `contract_win32` |

**win32 的註冊刻意不放在 `tests/contract/`**：本目錄的目標在 ubuntu CI 也要建得起來，
而 win32 後端只能在 Windows 建。放在該後端自己的平台閘目標下，
契約本體即可維持平台中立（`backend_guard` G1b 會掃該目錄的前處理器指令行）。

**契約標頭一個字都不用改就跑起了第二個後端**——這正是相位 1 承諾的兌現方式。

### 契約涵蓋面比修復前廣得多

舊契約 8 條裡有 1 條（`invoke_capability`）在真實介面**沒有對應**——那是平行介面獨有的方法，
**沒有假裝移植過去**。其餘 7 條忠實移植（具名 `SurfaceId` 取代數字 handle）。

新增了真實介面上原本完全沒被契約涵蓋的部分：可見性隨 show/hide 改變、
四參數 profile 往返、frame 括號配對、輸入策略切換並反映於 profile、
`poll_input` 事件目標必為已知具名 surface、**多 surface 互相獨立**。

最後一條是真實後端最容易寫錯的地方（共用狀態、錯用第一筆記錄、把 HWND 表寫成單例）。

### `units.json`

E1-25 的 `depends_on` 由 `["E1-21"]` 改為 `["E1-21", "E1-24"]`——
契約組現在真的 link null 後端。修復前不相依是刻意的，而那正是 K-003 的成因。

## ⚠ 修好的當下就抓到一個分歧（K-007）

契約接上真實後端後**第一次執行就紅**：

```
[  FAILED  ] NullBackend/KernelBackendContract.CreateSurfaceRequiresInitialized/null
```

- **win32**：未 `init()` 則 `create_surface` 回 `false`（真實後端必須先註冊視窗類別，物理限制）
- **null**：未 `init()` 也能建立成功

舊契約**明明有這一條**（修復前的「契約 4」），但它測的是 stub，所以分歧從相位 1 存在至今。

**真正的損害不是那一條紅燈**：追下去發現 **16 個既有單元的測試**
（c1_01/02/03/07、c2_01/08/10、c3_02/03、c4_02/03、e1_02/08/09、e4_30、e10_05）
都在**未初始化的 null 後端上建 surface**——實測需要 151 個插入點才能補齊。
那些程式路徑在任何真實後端上都不可能成立。

### 本次處置：釘住，不對齊

對齊要改動承重單元 **E1-24 的行為**並牽動 16 個單元的測試，屬**獨立的方向決策**，
不該夾帶在「修契約鴻溝」這張 CHG 裡。為讓分歧可見且被追蹤，兩邊各留一條測試釘住現況：

- `tests/e1/test_backend_win32.cpp` → `CreateSurfaceRequiresInit`
- `tests/e1/test_backend_null.cpp` → `CreateSurfaceCurrentlyDoesNotRequireInit`（本次新增）

對齊之後這兩條應刪除，前置條件放回共用契約（契約標頭內已標註確切位置與理由）。
收錄為知識庫 **K-007**。

### 過程紀錄：一次走錯又退回

曾先行嘗試對齊（改 null 後端 + 以腳本批次補 151 處 `init()`），
結果腳本把 `init()` 插進非陳述句位置、弄壞多個測試檔，已完整 `git checkout` 還原。
**151 個插入點本身就是訊號**：問題不在工具，而在把方向決策塞進技術變更裡。

## 明確不改

- 未改 `phase.json`、`governance.yml`、任何 win32 後端實作。
- 契約本體不含任何平台分支（`backend_guard` G1b 綠燈）。
