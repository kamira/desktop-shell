## K-014 的事實基礎（逐項自驗，不採信回報）

`I1.1` 報「`ds::elements::RenderModel` 在 E4-03 與 E4-18 是同名不同型別」。實查為**三處**：

| 定義處 | 單元（自 `units.json` 查證，非由測試檔名推斷） | `sizeof` |
|---|---|---|
| `modules/elements/bar_gauge.hpp:68` | `E4-03` 長條 / 進度 / 量表 | **224** |
| `modules/elements/radial_pointer.hpp:50` | `E4-18` 徑向線 / 指針 | **144** |
| `modules/elements/scroll_view.hpp:54` | `E4-14` 長文捲動與分頁 | 未量（見下「我沒有量的東西」） |

三者皆在 `namespace ds::elements`，結構完全不同（成員名稱與型別無一相同）。

### 探針（四個，全部自己跑）

```
探針 1：兩個 TU 各含一份不同定義，各自 sizeof 後連成一個程式
  g++ -std=c++17 -Wall -Wextra -Wpedantic  編譯兩個 TU  → 各 rc=0、零診斷
  連結                                                   → rc=0、零診斷
  執行                                                   → 印出 a=224 b=144
  → 同一個執行檔裡，同一個型別名稱有兩種大小，而工具鏈一聲不響。

探針 2：同上，改用 -flto -Wodr
  → 零診斷。**抓不到。**（該型別只在各自 TU 內被 sizeof 用到，沒有跨 TU 進入簽章）

探針 3：改成真實形狀——該型別跨 TU 出現在同一個函式的簽章裡
  g++ -std=c++17 -Wall -Wextra         → 零診斷、連結成功
  g++ -std=c++17 -Wall -Wextra -Wodr -flto
     → modules/elements/bar_gauge.hpp:68:8: warning: type 'struct RenderModel'
       violates the C++ One Definition Rule [-Wodr]
  → **抓到了**，但只在這個形狀下。

探針 4：main 上是否已有 target 同時連進兩側（查全部 target_link_libraries）
  desktop_shell_host → h1_01_paint + c2_02        兩者都是 bar 側（E4-03）
  test_h1_06         → h1_06_paint_model → c2_02   bar 側
  test_h1_06_radial  → h1_06_radial     → e4_18    radial 側
  → **目前沒有實際違反。** 是陷阱，不是已踩的地雷。
```

### 為什麼這一條比 `K-013` 更難抓

`K-013`（懸空參考）至少 ASan 會以 `stack-use-after-scope` 報出來，那也正是
`CHG-20261112-04` 新增 `gate_sanitizers` 的理由。**本條連 ASan + UBSan 都零報告**——
`gate_windows`、G3 的 `-Werror`、新的 sanitizer 閘門，三道對它全部無效。
唯一機械化的抓法是 `-flto -Wodr`，而它有探針 2 / 3 畫出的那條邊界：
抓得到「會真的出事」的形狀，抓不到「定義已分叉但還沒出事」的狀態。

### 下一步就會踩

`H1-06` 之所以安全，是實作者刻意把兩側拆成兩個獨立程式（`test_h1_06` / `test_h1_06_radial`）。
但該單元交回的待辦明寫「把新 kind 註冊進 `host/app/host_main.cpp`」——那一步會讓
`desktop_shell_host` 同時連進 `c2_02`（bar 側）與 radial 側，**出貨的執行檔當場成為實際的 ODR 違反**，
而 CI 不會有任何一道閘門變紅。**接 radial kind 進 host 之前必須先處理同名問題。**
