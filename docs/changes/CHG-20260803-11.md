## Motivation

`CHG-20260803-10` 讓契約第一次真的跑在真實後端上，第一次執行就抓到分歧：

- **win32**：未 `init()` 則 `create_surface` 回 `false`（真實後端必須先註冊視窗類別，物理限制）
- **null**：未 `init()` 也能建立成功

**16 個既有單元的測試都在未初始化的 null 後端上建 surface**——那些程式路徑在任何
真實後端上都不可能成立。相位 1 全程無人察覺，因為 null 後端太寬容而契約沒在看。

## Impact

### E1-24：`NullKernelBackend::create_surface` 加上前置條件

```cpp
if (!initialized_ || id.empty() || find(id) != nullptr) return false;
```

介面註解同步寫明該前置條件（原本完全沒提），並註記其歷史成因。

### E1-25：前置條件回到共用契約

`tests/contract/kernel_backend_contract.hpp` 恢復 `CreateSurfaceRequiresInitialized`，
契約由 16 條增為 **17 條**，null 與 win32 **各跑一遍**。

移除兩條當初用來釘住分歧的後端專屬測試（對齊後不該存在，同一件事不需要兩個地方驗）：
`test_backend_win32.cpp` 的 `CreateSurfaceRequiresInit` 與
`test_backend_null.cpp` 的 `CreateSurfaceCurrentlyDoesNotRequireInit`。

### 26 個測試檔補上 `init()`

受影響單元：c1_01/02/03/07、c2_01/02/04/05/06/07/08/09/10、c3_02/03、c4_02/03、
e1_02/03/08/09/15、e4_30、e10_05，及 E1-24 自身測試。

**未改動任何產品程式碼**（除 E1-24 的前置條件本身）——這些全是測試在未初始化的後端上
建 surface，是測試衛生問題，不是產品缺陷。唯一建立 null 後端的產品程式碼
（`examples/cpu_gpu_validator`）不建立 surface，不受影響。

## 過程：批次插入連續失敗三次，每次成因不同

對 C++ 做文字批次處理踩到三種「看起來像宣告，其實不是」的樣式。全部記入知識庫 K-007：

| 樣式 | 為什麼不能直接插入 | 正確做法 |
|---|---|---|
| `struct Rig { NullKernelBackend b{...}; ... };` | 成員宣告區不能放陳述句 | 成員初始器 `bool b_initialized_ = b.init();`——C++ 保證成員依**宣告順序**初始化，故它在其後成員建構前完成。**不能用建構子本體**：那在所有成員建構之後才跑，太晚 |
| `NullKernelBackend make_backend(...) {` | 是**回傳型別為該型別的函式定義** | 排除以 `(` 接續且不以 `);` 結尾者 |
| `NullKernelBackend b(caps());` | 是宣告，卻被上一條規則誤殺 | 以「該行是否以 `);` 結尾」區分 |

每一輪都以完整建置 + 全套測試驗證，失敗即 `git checkout` 完整還原後再修規則。
最終每一處插入都經 MSVC 編譯與測試確認。
