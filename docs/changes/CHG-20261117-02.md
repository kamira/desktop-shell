## Motivation

`G5b`（CHG-20261117-01，同日上線）問的是「**驗收之後有沒有動到被驗的東西**」，
第一版的做法是比 `git diff --name-only <ACC 宣告的受驗 head> <PR 的 head.sha>`
的檔案清單，只准出現 `docs/acceptance/` 與 `docs/worklog/`。

那是**兩點 diff**，也就是兩棵樹直接比。於是：

### 洞一（誤殺）：分支在驗收後併入 base

`main` 改過的**每一個檔案**都會出現在那份清單裡，而本單元作者根本沒碰它們。實測：

```
V  = 實作提交（ACC 宣告的受驗 head）
     ACC 提交
     base 自己前進了一個 commit（改 engine/other.cpp）
     併入 base
git diff --name-only V HEAD → docs/acceptance/ACC-1.md, engine/other.cpp
過濾後 → engine/other.cpp        ← 擋下，但那不是本 PR 交付的內容
```

更難看的是**不併 base 反而會過**，可是兩種做法最後合併進 base 的結果是同一個：
**判定取決於你有沒有顯式併 base，不取決於交付的內容。** 而觸發條件（合併衝突逼你併 base）
並不罕見——`G5b` 上線時 `feat/h1_09` 恰好與 main 無衝突，所以沒有當場踩到。

CHG-20261117-01 的 PR 內文裡我自己寫過「**一道會誤殺的閘門很快就會被繞過去**」，
那正是我選擇跟 `head.sha` 比而不跟 `HEAD` 比的理由。這個情境是**同一類誤殺**，我漏了。

### 洞二（漏報）：驗收後刪掉本單元自己新增的檔案

這一個是在評估修法時量出來的，第一版也有。見下節的四候選對照。

## 四個候選述詞的五情境實測對照

修法不是只有一種，所以**先量再選**（五個情境各建一個真的臨時 git 倉庫實跑）：

| 情境 | ①只比檔案清單（第一版） | ②與「PR 自己改的檔案」取交集 | ③只准「原封照收 base」 | ④**本採用**：兩半對稱 |
|---|---|---|---|---|
| 驗收後什麼都沒動 | 放行 ✓ | 放行 ✓ | 放行 ✓ | 放行 ✓ |
| 只併入 base | **擋下 ✗** | 放行 ✓ | 放行 ✓ | 放行 ✓ |
| 併 base 後又推程式碼 | 擋下 ✓ | 擋下 ✓ | 擋下 ✓ | 擋下 ✓ |
| 驗收後刪掉本單元新增的檔案 | 擋下 ✓ | **放行 ✗** | **放行 ✗** | 擋下 ✓ |
| base 與偷推動到同一個檔案 | 擋下 ✓ | 擋下 ✓ | — | 擋下 ✓ |

候選②是我原本向人類描述、並取得「現在修」裁定的那一個。**實測後改用④**：
②在「驗收後刪掉本單元新增的檔案」漏報，而漏掉的正是「驗收者驗過的東西不見了」。
人類核准的是「修這個誤殺」，不是「非用這個實作不可」；改用更嚴的述詞已回報。

## 採用的判據

> 驗收之後動過的檔案，除了 `docs/acceptance/` 與 `docs/worklog/`，
> 只有在「**本 PR 對它沒有自己的貢獻——驗收當時沒有，現在也沒有**」時才放行。

兩半都不可少，而且各有一支測試釘住：

- 少了「驗收當時沒有」那半 → 驗收後**刪掉**本單元新增的檔案會放行（兩邊都查無此路徑 → 相等）。
- 少了「現在也沒有」那半 → 驗收後**新增**的檔案會放行（同樣兩邊都查無此路徑），而那是完全沒被驗過的程式碼。

「沒有貢獻」= 該路徑在 `<受驗 head>` 與 `merge-base(受驗 head, base)` 上是同一個 blob，
**且**在 `<當前 head>` 與 `base` 上是同一個 blob。查無路徑以 `MISSING` 代表，
讓「兩邊都不存在」與「兩邊同一個 blob」走同一條相等判斷。

**刻意的副作用**：衝突解在**本單元自己的檔案**上會被擋下（驗收者沒看過那個解法）。
那是要的行為，有專屬測試 `test_taking_the_bases_version_of_the_units_own_file_is_rejected`。

**M6 第一輪存活，而它存活的方式值得記下來。** 原本釘這一條的是一支**靜態**測試
（斷言腳本裡有 `"$HEAD_SHA"`、沒有 `..HEAD`）。把那一行的 `$HEAD_SHA` 換成 `HEAD` 之後，
腳本別處仍有 `$HEAD_SHA`，字串還在，所以靜態斷言照樣通過——**它釘的是字串出現，不是行為**。
補的是一支行為測試：fixture 真的重現 `pull_request` 事件下 `actions/checkout` 取 **merge ref**
的情形（detached 到 base 與 head 的合併，`HEAD` ≠ `head.sha`，分支本身不動），於是
拿 `HEAD` 比就會把 base 的變更算進來而誤殺，當場紅燈。補完即 KILLED。

這是 `K-012` 的同一族：**靜態斷言常常只釘住了字面，沒釘住行為。**

## 未關閉的缺口

- **述詞比的是 blob 相等，不是語意相等。** 把一個檔案改掉再改回來（淨變更為零）會被
  `git diff` 列進清單，但兩半相等判斷會放行它——那是對的（交付的內容確實沒變）。
  反過來說，若有人在驗收後**只改空白**而該檔案是本 PR 交付的，會被擋下並要求複驗。
  嚴格方向，刻意不放寬。
- `G3` 自己仍有一個 `K-011` 實例（`N=$(ctest ... | sed ...)` 無 `|| true`）。本輪未動；
  更好的修法是把「管線賦值必須有守衛」這條規則搬進 `scripts/workflow_lint.py`，讓它對
  **整份 workflow** 生效，而不是靠每個步驟各自的測試去釘。已列入待裁定。
