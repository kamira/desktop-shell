## Motivation

設定面板不是一頁，是**多頁**：一個核心分頁（平台自身的設定）加上每個已安裝套件各一頁。
而這件事的語意早在 `CHG-20260829-05` 就被使用者親自裁定過，原話是：

> 「這裡的由已安裝貢獻**不是複寫**，而是**額外增加**設定的 tab」

這條裁定是本單元的全部重點，而它的危險處在於**正向測試證明不了它**。
「安裝套件後多出一個分頁」很容易做到、也很容易測綠，但它只說明 append 成立，
**完全沒有說明 not-overwrite 成立**。一個把套件宣告併進核心設定樹的錯誤實作，
在所有正向測試下都是綠的——分頁確實出現了。

唯一能釘住裁定的是**衝突情境下的反向斷言**：讓套件宣告一個與核心**同名**的欄位，
再斷言核心分頁的值**原封不動**。這也正是本單元驗收標準指名的那一條。

### 設計決定 1：以可注入抽象表達「哪些套件貢獻了設定」，**刻意不連結 e9_10**

I1 給了兩條路（直接 `target_link_libraries(e7_16 PUBLIC e9_10)`，或以可注入抽象表達），
要求在 CHG 交代選擇理由。選**可注入抽象**，而理由不只是風格對齊——**直接連 e9_10 在資料上
不成立**：

1. E9-10 持久化的單位是 `InstallRecord`，持有 E9-01 `Package` = E9-02 manifest
   （`name` / `version` / `description` / `requires` / `permissions`）+ 內含項目的**邏輯路徑清單**。
2. E9-02 `Manifest`（`engine/package/manifest.hpp:51`）**沒有任何設定宣告欄位**；
   E9-01 `Package` 檔頭亦明寫其**不含套件本體 / 資源內容**，E9-10 檔頭更以此作為
   「列舉已安裝永不需要載入套件」的物理基礎。
3. 因此「這個套件宣告了哪些設定欄位」這份資料**不在 E9-10 的回答範圍內**——它在套件隨附的
   宣告式設定資源（E7-01 文字）裡。**即使連上 e9_10，仍得另有一層把那份內容交進來。**

換句話說，直接連結會多一條跨子系統相依，卻一個問題都沒解決。故本單元定義
`SettingsContributionSource`，回答「哪些 package id 有貢獻 + 其宣告的設定 `Value` 樹」。
這也與本 repo 既有風格一致（E9-05 `LayoutStorage`、E9-10 `InstallStorage`、
E2-19 `ProcessSource` 皆為可注入抽象），且使本單元不需跨子系統連結、測試不需真的建一個
安裝登錄。host 層組裝時才決定來源：屆時由 E9-10 列舉已安裝套件，再取其設定資源內容餵進來。

**代價（誠實列出）**：多一層間接。本單元因此**沒有**端到端證明「E9-10 的安裝登錄 → 設定分頁」
這條接線——那條接線的實際組裝屬 host 層，不在本單元的 write_scope 內。本單元證明的是
**分頁登錄這一側的契約**（含 append-only），E9-10 那一側已由 `CHG-20261111-e9_10` 證明。

### 設計決定 2：append-only 靠**結構**保證，不靠紀律

這是本單元最重要的一條。四項機械保證（詳見 `settings_pages.hpp` 檔首）：

1. **核心分頁的欄位只由核心 `Value` 樹算出**。套件貢獻一律產生**另一個** `SettingsPage`
   物件，持有**自己的** `Value` 樹。因此套件鍵名撞上核心鍵名時，**不存在任何寫入核心的程式
   路徑**——不是「檢查後拒絕覆寫」，是**連覆寫的管道都不存在**。這個差別很重要：
   前者是一道可以被未來的修改繞過的檢查，後者是資料流上的事實。
2. `refresh()` **只重建套件分頁集合**，`core_` 在該函式中從頭到尾未被讀寫（連重算都不做）。
3. `kCorePageId` 是**保留字**：貢獻來源若試圖佔用它 → `throw`（絕不靜默取代核心分頁）。
   守門放在 **registry** 這一層，故**任何**自訂 `SettingsContributionSource` 實作都繞不過；
   `MemorySettingsContributions::declare` 另有一道 fail-fast。
4. 列舉順序**固定**：核心分頁恆為第一，套件分頁依 package id 字典序。順序固定才使衝突
   **無法被排序遮蔽**——「先到先贏」「後到覆蓋」這類隱性語意無處藏身。

`refresh()` 另採**全有全無**：先在暫存容器把整批分頁建好，全部成功才整批替換。
中途失敗時登錄維持原狀，不留「一半新一半舊」的殘局（不靜默吞錯的另一面：錯誤不得留下殘局）。

### 設計決定 3：不重造欄位模型（驗收標準明文要求）

每一分頁的欄位清單一律是 **E7-14 `EditableField`** 的 `std::vector`，由 E7-14
`build_editor_model` 產出；欄位尋址轉呼 E7-14 `find_field`；分頁上的編輯一律經 E7-14
`apply_edit`（其內部再經 E7-12 `set_value`）。本單元**不新增任何欄位型別、不自造控制項型別、
不自造驗證規則**，連 Enum / 數值範圍的約束都是直接餵 E7-14 的 `EditorSchema`。

這一點由測試 `PageFieldsAreExactlyE7_14BuildEditorModelOutput` 正面釘住：對同一棵 `Value` 樹
直接呼叫 E7-14 `build_editor_model`，結果須與分頁的 `fields` **逐欄位**（path / kind /
current / label）相同。若哪天有人在本單元悄悄自造了欄位模型，這個測試會紅。

`values` 是分頁的**唯一事實來源**，`fields` 恆為由它算出的結果；每次編輯更新 `values` 後
**重算** `fields`，故二者不會漂移。

### 設計決定 4：「同一套件重新宣告自己那一頁」是合法的

append-only 約束的是「**套件不得改動核心分頁**」，不是「套件不得改自己那一頁」。
套件版本升級 / 重新安裝時重新宣告自己的設定是正常行為，故
`MemorySettingsContributions::declare` 對同 `package_id` **覆寫**既有貢獻
（與 E9-10 `InstalledPackageStore::record` 的「同名不覆寫」語意**刻意不同**——
那裡覆寫的是「安裝這件事」，這裡覆寫的是「這個套件自己宣告的設定內容」）。
測試 `PackageRedeclaringItsOwnPageIsAllowedAndStillSpareCore` 釘住它，並同時斷言核心不受影響。

### 誠實分界（沿用 E9-10 的同一誠實度，不誇大）

**`MemorySettingsContributions` 是相位 1 的記憶體替身**——無真實檔案 I/O、無跨行程持久化。
相位 1 的 engine 層不得有真實檔案 I/O（G1b `backend_guard`、`PHASE-PLAN.md`），故替身是
此相位**唯一合法**的選擇。

因此：**本單元不聲稱設定分頁跨真實行程重啟仍然存在。** 本單元所稱的「卸載」是
「貢獻來源不再列出該 package id」，`refresh()` 後該分頁即消失。真實的安裝 / 卸載落盤由
E9-10 負責（其 `MemoryInstallStorage` 同為相位 1 替身，真實磁碟後端留待後續相位）。
相位 2 換上真實來源時：`SettingsContributionSource` 介面一行不動。

### 一條 I1 要求實測的 CMake 風險：已驗，**不成立**

I1 提醒：若在 `engine/format/CMakeLists.txt` 連結 `e9_10`，引用的是一個**更晚**才被
`add_subdirectory` 加入的目錄裡定義的目標（根 CMakeLists 的 GLOB 順序 `engine/format` 先於
`engine/package`），失敗時會退化成 raw library name `-le9_10`，在 link 期才爆。

實測結論：**該風險在本 repo 的工具鏈上不成立**。以暫時 probe target
（`target_link_libraries(e7_16_probe PUBLIC e9_10)` + 一支真的 `#include "install_store.hpp"`
的翻譯單元 + 一個會產生真實 link step 的 executable）configure + build：

- configure / generate 無任何抱怨；
- `e9_10` 被當成**真實目標**排進建置順序（先建 `e9_07` / `e9_10` 才建 probe）；
- `#include "install_store.hpp"` 解析成功 → 證明 `e9_10` 的 PUBLIC include 目錄**有傳遞**
  （raw library name **不會**傳遞 include 目錄，故這一點本身即可排除退化）；
- link line 實際內容是 `… libe7_16_probe.a ../package/libe9_10.a libe7_12.a libe7_01.a …`
  —— **真實的 archive 路徑，不是 `-le9_10`**。

CMake 在 generate 期才解析目標名，與 `add_subdirectory` 的先後無關。
probe 已完全還原（`engine/format/CMakeLists.txt` 自備份還原、probe 的 `.cpp` 兩支皆刪除），
**未進入任何 commit**。

> 這條記錄的用途是給後人：`engine/format` → `engine/package` 這個方向的連結是可行的，
> 不必為了 GLOB 順序繞路。本單元最終**仍未**連結 e9_10，理由是設計決定 1（資料上不成立），
> 與這條 ordering 風險無關。
