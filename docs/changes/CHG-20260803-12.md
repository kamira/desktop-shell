## Motivation

使用者指定的四個功能之一。W1-03 的 `set_draggable` 已具備，缺的是選單入口與狀態持久化。

## Impact

### 鎖定位置開關

托盤選單新增 Checkbox「鎖定位置」（索引 `[2]`，其後索引順移），
綁 `widget.toggle_lock` 命令，處理器呼叫 `backend.set_draggable(id, !locked)`。

**語意轉換只在一處**：選單問「要不要鎖」，後端問「能不能拖」，兩者相反；
在命令處理器裡轉一次，其餘地方不必反覆推理。

### UI 狀態持久化（`host/tray/ui_state.*`）

`%LOCALAPPDATA%\desktop-shell\ui-state.conf`，**沿用 E7-01 宣告式格式**（不發明新格式）。
三個開關（最上層 / 穿透 / 鎖定）全部持久化——
**一個每次啟動都自己解開的「鎖定」等於沒有鎖。**

與位置檔分開存：`positions.conf` 的格式由 E1-08 擁有，UI 開關是 host 概念，
塞進去會讓 host 對上游單元的檔案格式產生隱性依賴。

## ⚠ 施工中發現並修掉的兩個缺陷

### ① 設定檔有 UTF-8 BOM 時，設定被靜默丟棄

操作驗收第一次執行就踩到：用 PowerShell 寫的設定檔帶 BOM，
app 讀進去解析失敗 → 退回預設值 → **鎖定自己解開，且沒有任何提示**。

設定檔是使用者會拿記事本改的東西，而許多 Windows 編輯器預設寫 BOM。
修在 `read_text_file` 一處，**同時涵蓋 UI 狀態檔與位置檔**（兩者都經由它讀取）。
屬 K-001 / K-004 的字集家族。已加兩條測試（去 BOM、不得誤刪非 BOM 位元組）。

### ② 主迴圈 250ms 才抽一次訊息，拖曳會頓

原本直接 `Sleep(kFrameIntervalMs)`，視窗在那 250ms 內**完全不回應**——
系統的拖曳移動迴圈是在 `DispatchMessage` 裡跑的。改為每 15ms 抽一次、累計到 250ms 才進下一幀。

取樣間隔必須維持 250ms（`GetSystemTimes` 是差分式，見 K-002），
但抽訊息不需要跟著慢；兩者本來就是不同節奏，先前只是恰好共用同一個 `Sleep`。

**誠實註記**：這個修改**不是**操作驗收間歇失敗的原因（改完仍然重現）。
它是調查過程中發現的另一個真實問題，一併修掉，但不宣稱它解決了什麼。

### 操作驗收：改用確定性探測，而非合成拖曳

合成滑鼠拖曳在本機**時好時壞**（同一份程式碼、同一組設定，重跑結果不同）。
與其用一個會說謊的檢查，改為直接問視窗本身——送 `WM_NCHITTEST` 讀回傳值：

```
locked=false → WM_NCHITTEST → HTCAPTION (2)  可拖
locked=true  → WM_NCHITTEST → HTCLIENT  (1)  不可拖
```

這正是拖曳能否發生的**唯一判準**（W1-03 就是靠 `HTCAPTION` 讓系統進入移動迴圈），
且完全確定性。合成拖曳的不穩定原因未查明，已記為已知限制。

### UI 狀態讀取的獨立驗證（含 BOM）

以外部可觀察的欄位（`passthrough` → `WS_EX_TRANSPARENT`）驗證檔案真的被讀入並套用：

| 檔案 BOM | `passthrough` | 實測 `WS_EX_TRANSPARENT` |
|---|---|---|
| 無 | true | True |
| 無 | false | False |
| **有** | true | True |
| **有** | false | False |

四種組合全部正確——BOM 修正在真實 app 上生效，不只在單元測試裡。

## 已知限制

- **合成滑鼠拖曳的驗收腳本不穩定**，原因未查明。功能本身以 `WM_NCHITTEST` 確定性驗證。
  影響的是驗收手法，不是產品行為（PR #199 的拖曳操作驗收曾成功過）。
- 全套測試曾出現一次 `backend_win32` 偶發失敗，單獨重跑即通過；
  時間點與驗收腳本對桌面送合成滑鼠事件重疊，推測為互相干擾，未進一步追查。
- 鎖定狀態不隨個別 widget 記錄（目前只有單一 widget）。
