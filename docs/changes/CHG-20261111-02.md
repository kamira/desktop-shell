- Skill: ai-sdlc-autopilot

- 觸發：PR #225（E9-10）被 G5 擋下時，日誌只有一行 `Process completed with exit code 2`

## Motivation

E9-10 的 PR 在 ACC 尚未產出時被 G5 擋下——**判定是對的**。但去讀日誌想知道為什麼時，
`::error::` 一個字都沒有。追下去發現 G5 這六行裡有兩個獨立的缺陷，而且第二個比第一個嚴重得多。

### 缺陷一（K-011）：擋對了，但說不出原因

```bash
A=$(ls docs/acceptance/ACC-*-$S.md 2>/dev/null | head -1)
[ -z "$A" ] && { echo "::error::medium 風險需要 ACC，未找到"; exit 1; }
```

步驟的 shell 是 GitHub `shell: bash` 的預設展開式 `bash --noprofile --norc -e -o pipefail`。
ACC 不存在時 `ls` 回 2，`pipefail` 讓管線結果變成 2，**第一行的賦值失敗**，`-e` 當場中止腳本
——第二行永遠跑不到。同一步驟內 `IMP=` / `VER=` 兩處同構（`grep` 無命中回 1）。

這是本 repo 記過三次的同一族（[[K-009]]，及 `scope_check.py` / `status_check.py` 檔頭註解）：
**閘門「當掉」與閘門「擋下」在 exit code 上無法區分**。前三次都在 Python 閘門裡，
這次是同一陷阱在 workflow 的 `run:` 裡以 `pipefail` 形式再現。

### 缺陷二（K-012）：根本沒擋

G5 的第二項職責是「驗收者與實作者同一人即紅」。偽造一份兩邊都寫同一人的驗收去餵它：

```
CHG:  - Date: … | Branch: feat/x | Risk: medium | Implemented by: I1.1
ACC:  - Date: … | Unit: X | Verifier: I1.1 | Branch: feat/x
→ IMP=[I1.1]  VER=[feat/x]
→ G5 放過了，exit=0
```

`sed 's/.*: *//'` 的 `.*` 貪婪，吃到行內**最後**一個 `: `。房屋格式的 ACC 表頭以 `|` 分欄，
而 `Verifier:` 不在行尾，取出來的是 `feat/x`；CHG 的 `Implemented by:` 恰好在行尾才取對。
一邊取到人、一邊取到分支名，`[ "$IMP" = "$VER" ]` **結構上永遠不相等**——
這道防線從上線起沒有任何一次真的比對過身分。

兩個讓它活了 190 多個單元沒被發現的條件：**失效方向是「放過」**（不產生任何輸出，
看起來就像檢查過了），而且**歷來的輸入都是真的獨立驗收**，從沒有一個案例應該被擋。
正確的輸入掩護了壞掉的判定——與 [[K-003]] 是同一種掩護關係。

## 變更內容

`.github/workflows/governance.yml` 的 G5 步驟（三處取值 + 兩道新增的空值檢查）：

```bash
A=$(ls docs/acceptance/ACC-*-$S.md 2>/dev/null | head -1 || true)
[ -z "$A" ] && { echo "::error::medium 風險需要 ACC，未找到：docs/acceptance/ACC-*-$S.md"; exit 1; }
grep -q 'Result: *pass' "$A" || { echo "::error::ACC 未判定 pass：$A"; exit 1; }
IMP=$(grep -m1 -o 'Implemented by: *[^ |]*' docs/changes/CHG-*-$S.md | head -1 | sed 's/.*: *//' || true)
[ -z "$IMP" ] && { echo "::error::CHG 缺 'Implemented by:' 表頭，無法比對驗收者身分"; exit 1; }
VER=$(grep -m1 -o 'Verifier: *[^ |]*' "$A" | head -1 | sed 's/.*: *//' || true)
[ -z "$VER" ] && { echo "::error::ACC 缺 'Verifier:' 行，無法比對驗收者身分：$A"; exit 1; }
[ "$IMP" = "$VER" ] && { echo "::error::驗收者與實作者同一人：$IMP"; exit 1; } || true
```

### 兩個設計決定

**1. `|| true` 不可單獨用在 IMP / VER 上。** 取值失敗會得到空字串，而空字串讓身分比對自動
「不相等」——只加 `|| true` 會把「擋下」悄悄換成「放過一份沒有 `Verifier:` 的 ACC」，
即 fail-closed 退化成**真的假綠燈**。故每個取值後各補一道空值檢查。
「讓訊息印出來」與「維持擋下」是兩件事，要分別做到。

**2. `[ -z "$A" ] && { …; }` 不動。** 實測確認它**不受 `-e` 影響**（`&&` 列表中非最後一個
命令豁免於 `-e`），A 非空時不會中止——這也正是 190 多個單元一直正常通過 G5 的原因。
順手「一起修」它只會製造一個不存在問題的修正。

## 回歸測試

新增 `tests/gates/test_g5_acc_identity.py`（7 個案例，G0 會跑）。
它**不測某個函式，而是用 PyYAML 從 `governance.yml` 把 G5 的 `run:` 腳本原封不動抽出來，
以同一組 shell 旗標執行**。在本檔出現之前，G5 的判定邏輯沒有任何入口可被測試
——與 `CHG-20260810-06` 把 `scope_check` 判定抽成純函式所解決的是同一個問題，
只是這段 shell 抽不成函式，那就直接跑它。抽出來跑而不是複製一份腳本，
是為了讓「改了 workflow 卻沒改測試」必然紅燈；複製只會讓兩邊各自漂移而測試仍綠。

三個設計要點：

- 斷言一律是「**非零退出 + 訊息真的印出來**」兩件事一起驗。只驗退出碼的測試會讓 K-011 原封不動回來。
- fixture **一律用房屋格式表頭**（`Verifier:` 排在 `Branch:` 之前）。用單冒號的簡化格式寫測試
  正好會漏掉 K-012——因為簡化格式下貪婪 `sed` 恰好取對。
- 另有一條**靜態**測試：掃 G5 腳本裡所有含管線的賦值，任一缺 `|| true` 即紅。
  行為測試只涵蓋現有的失敗路徑，這條擋住「日後新增一行而忘了」。

## 未關閉的缺口

1. **`governance.yml` 其餘步驟尚未逐一審過 K-011 同一陷阱。** 本次只修 G5（踩到的那一步），
   靜態測試也只掃 G5 的腳本。其他步驟的同類風險仍然開著。
2. **K-012 空轉期間的存量已全量複查，結論是乾淨的。** 以修正後的取值方式對
   **全部 16 份 ACC** 跑一次（不是抽查）：

   ```
   ACC 總數：16   對得到 CHG 並完成比對：16   對不到 CHG：0
   驗收者與實作者同一人：0   缺欄位：0
   ```

   歷來 ACC 都確實由獨立 V1 署名——這也正是 K-012 能活這麼久的原因：
   **正確的輸入掩護了壞掉的判定**。此項缺口視為已關閉。

3. **但複查過程中查出另一個獨立的、仍然開著的缺口：unit 工作走 infra 分支會繞過
   G1 / G5 / G6。** 比對「已完成且 risk != low 的單元」與 ACC 檔，發現 **3 個已合併的
   medium 單元根本沒有 ACC**：

   | 單元 | risk | 進 main 的途徑 |
   |---|---|---|
   | `W1-01` | medium | PR #195，head 分支 `claude/phase2-desktop-widget` |
   | `W1-02` | medium | 同批 |
   | `W1-03` | medium | 同批 |

   原因不是 G5 當時還沒上線（`git log -S'G5 ACC + identity'` 顯示它自 bootstrap commit
   `0438076` 就存在），而是**分支名**：`gate` job 以 `GITHUB_HEAD_REF == feat/*` 反查單元，
   對不到就設 `is_unit=false` 並**跳過 G1 scope / G5 ACC / G6 halt**，只跑 repo 級閘門。
   PR #195 是一個跨三張 CHG 的「相位 2 開場」綑綁 PR，分支是 `claude/…`，
   於是其中的 W1-01（medium）在**沒有範圍檢查、沒有 ACC、沒有停點**的情況下進了 main，
   並由 `github-actions[bot]` 走 infra 自動合併路徑合併。

   `is_unit=false` 跳過 unit 專屬閘門本身是**刻意設計**（`governance.yml` 註解寫明是為了
   讓 root CMake / governance / 全庫重構這類變更也能拿到 G3 綠燈）。缺的是另一側的判定：
   **沒有任何東西檢查「一個非 `feat/` 分支裡是不是夾帶了工作單元的程式碼」。**
   PR #195 的內文確實坦承「W1-01 / H1-01 不在任何 CI 閘門守備範圍」，但講的是
   `if(WIN32)` 讓 ubuntu 的 G3 看不到它們；**G1/G5/G6 也一併跳過這件事沒有被記下來。**

   本檔**不修這個缺口**——它牽涉「該如何判定一個 PR 夾帶了單元工作」的設計決定
   （依分支名、依 CHG 的 `Unit:` 欄位、或依 diff 路徑反查 `write_scope`），
   不是一行可改的事，且會改變未來所有 infra PR 的門檻。記錄在案，待裁示。
4. **infra 分支不跑 G5，所以本變更本身沒有機器強制的獨立驗收。**
   `is_unit=false` 時 G1 / G5 / G6 皆跳過，`Risk: medium` 在此僅為文件標註。
   本檔的證據是上面那組負向測試，且它們已成為 repo 裡的常駐回歸測試——
   但「改這道閘門的人同時是驗這道閘門的人」這件事，在 infra 路徑上目前無人可擋。
   這是說出來而不是藏起來：**治理層自己的變更缺少對等的獨立驗收，是這套流程結構上的缺口。**
