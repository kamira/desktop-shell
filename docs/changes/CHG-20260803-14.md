## Motivation

使用者指定的四個功能之三。`CHG-20260803-06` 的已知限制寫著：
「匣圖示為系統預設圖示；`set_icon` 如實保存具名值，但具名圖示 → 實際資源的對照尚未建立」。
本 CHG 補上。

## Impact

### 具名 id → 檔案路徑

```
icon.tray  →  <base>/icons/tray.ico
```

去掉 `icon.` 前綴後即為套件內邏輯路徑，**與 E9 套件格式的 `asset: icons/tray.png`
慣例對齊**——之後 skin 套件載入圖示走同一套命名，不需要第二種規則。

`base`：環境變數 `DESKTOP_SHELL_ASSETS` 優先，否則 `<執行檔目錄>/assets`。

`icon_path_for()` **只算路徑、不檢查存在**——分開才能分別測試「路徑算對」與「檔案讀得到」。

### 找不到檔案時：程式繪製後備，**不是** Windows 通用圖示

**本單元最重要的決定。** 若後備直接用 `IDI_APPLICATION`，
「資源沒部署好」與「功能還沒做」在畫面上完全一樣，沒有人查得出差別。
後備圖示長得像自己（同色系同構圖），一眼可辨。`icon_from_file()` 對外回報走了哪一條。

### 圖示所有權

`LoadImageW` 載入者**必須** `DestroyIcon`；`LoadIcon(IDI_APPLICATION)` 的系統共用圖示
**不得**銷毀。混淆會造成洩漏或損毀系統資源，故以 `icon_owned_` 明確記錄。

### 圖示資源

`assets/icons/tray.ico`（16x16 + 32x32、32bpp、5430 bytes）：
深色圓角底 + 三條量表長條，構圖與配色刻意呼應 widget
（底色 `RGB(18,20,26)`、量表 `RGB(88,176,255)`）——系統匣看到的是 widget 的縮影。
以腳本手工組 ICO（BMP-in-ICO，無影像函式庫相依）。

### 部署

`host/app/CMakeLists.txt` 的 POST_BUILD 把 `assets/` 複製到執行檔目錄。

### 測試涵蓋兩條路徑，且能分辨走了哪一條

- 路徑解析：`icon.tray` → `<base>\icons\tray.ico`；無前綴時整個 id 當葉名；
  空 id / 只有前綴 → 回空字串（不得組出 `icons\.ico` 這種垃圾路徑）；
  未設環境變數時退回執行檔目錄且為絕對路徑
- 真的從檔案載入：指到 repo 的 `assets/` 時 `icon_from_file() == true`
- **後備不得是系統圖示**：路徑不存在時 `icon_from_file() == false`，
  且 `native_icon() != LoadIcon(IDI_APPLICATION)`
- 重複切換圖示後仍能正常加入系統匣（所有權旗標一致）
- 已顯示時換圖示走 `NIM_MODIFY`，不得變成未加入

### 過程紀錄：第一版圓角沒生效

初版的圓角判定式多寫了一個 `or (abs(dx) <= radius and abs(dy) <= radius)`，
使角落區域無條件通過，**圓角完全失效、畫成方形**。
是把圖示渲染成預覽圖看過才發現的——只看「Windows 載入成功」不會發現這件事。

## 已知限制

- 只有一個圖示（`tray.ico`），沒有淺色 / 深色主題分版。
- 沒有依 DPI 選擇尺寸的邏輯，交由 `LR_DEFAULTSIZE` 讓 Windows 決定。
- 圖示洩漏無法在單元測試中真正驗證（需外部工具）；
  測試只釘住「多次切換後仍可用」與所有權旗標的一致性。
- E9 套件內圖示的載入管線尚未接通，本單元只對齊命名慣例。
