# CHG-20260803-02 — 驗證器 Windows CPU 取樣修正 + 堵住會放行假綠燈的驗收條件

- Date: 2026-08-03 (UTC+0) | Branch: claude/ai-sdlc-autopilot-content-check-bdf414 | Risk: low | Implemented by: I1
- Skill: ai-sdlc-autopilot v1.1
- 前置：`CHG-20260803-01`（MSVC `/utf-8`，先有它才編得出這支驗證器）

## Motivation

`CHG-20260803-01` 讓 176 單元在 MSVC 全建通過後，第一次在 Windows 上實際執行最終交付的
CPU/GPU Usage Widget 驗證器（`examples/cpu_gpu_validator`）。**畫面渲染正常，但 CPU 量表 12 幀有 10 幀讀到 0.0%**。

`CHG-20260731-01` 寫的 Windows 取樣路徑（`GetSystemTimes`）當時只能靠讀程式碼推斷正確性
——該 CHG 自己也註明「本機 macOS 無法實編驗證，屬 Windows day-1 全建時一併確認」。現在確認了：**它不正確**。

## 三個缺陷

### ① 取樣間隔（0.0% 的直接來源）

`GetSystemTimes` 回傳的是**累計**時間，必須兩次取樣之間真的經過時間才有差分可算；
而系統時鐘約 **15.6ms** 才跳一次。原本的 12 幀迴圈**完全沒有間隔**，兩次取樣只隔幾微秒，
`d_kernel + d_user` 恆為 0，直接命中 `if (total == 0) return 0.0;`。

以 ctypes 複製同一算式實測（scratchpad，未進 repo）：

```
A) 無間隔（＝現行迴圈）    total_delta = 0        每次都命中提前返回 → 0.0%
B) 每幀間隔 200ms          total_delta ≈ 6.5e7    8.2 / 7.7 / 7.9 / 8.0 / 11.5 / 27.0%
```

### ② 首次呼叫回傳「開機至今的平均值」，與自己的註解相反

原註解寫「首次呼叫無前值 → 回 0」，但程式碼沒有這麼做：`prev_*` 靜態初值是 0，
第一次呼叫的差分等於**開機至今的全部 CPU 時間**，算出來是**開機以來的平均 CPU**。
它會印出一個看起來很合理的數字（實測 15.2%），因此比回 0 更難察覺。

### ③ 驗收條件弱到會放行假綠燈（**三者中最嚴重**）

原驗收只檢查 `available && fill_ratio ∈ [0,1]` —— 而 `0.0` 完美滿足這兩條。
於是 **CPU 指標整輪死掉、量表全程停在 0.0%，驗證器照樣印 `✓ PASS` 並回 exit 0**。

這比讀不到值本身危險：讀不到值只是一個缺陷，而一個會給假綠燈的驗收條件，
會讓**未來任何**指標故障都靜默通過。

## Impact

僅改 `examples/cpu_gpu_validator/main.cpp`（example 層，非治理 src/ 單元）。

### 1) `real_cpu_percent()` 改用負值表示「取樣無效」

**不可以拿 `0.0` 當無效值**——0.0 是合法的 CPU%，混用會讓「量表死掉」與「CPU 很閒」
在呼叫端與驗收條件眼中完全一樣。改為：

- 首次呼叫**只建立基準點**，回 `-1.0`（不再拿 `prev_* = 0` 去差分）。
- `total == 0`（時鐘未前進）回 `-1.0`，不再回 `0.0`。
- `GetSystemTimes` 失敗回 `-1.0`。
- POSIX 路徑同步：`getloadavg` 失敗回 `-1.0`（原為 `0.0`）。其餘邏輯**一字未改**。

### 2) 迴圈加取樣間隔

`std::this_thread::sleep_for(std::chrono::milliseconds(250))`，250ms 遠大於一個時鐘刻度。
**標準 C++，不引入平台分支**（`<chrono>` / `<thread>`）。進迴圈前先取樣一次填好基準點。

Mac / Linux 的 `getloadavg` 是無狀態的、不依賴取樣間隔，**行為不受影響**——
只是迴圈從「瞬間跑完 12 幀」變成真的 live 更新（總執行時間約 3 秒）。

### 3) 驗收加條件②：CPU 每幀都必須取到有效樣本

輸出改為兩條分列，讓「組裝成功」與「資料有效」不再混為一談：

```
驗收①組裝：3/3 指標成功組裝呈現（fill_ratio ∈ [0,1]、display_text 已格式化）。
驗收②取樣：CPU 有效樣本 12/12 幀。
```

`invalid_cpu_samples != 0` 時條件②紅燈、結論 `✗ FAIL`、exit 1，並直接印出
「**量表停在 0.0% 不是 CPU 很閒，是取樣失效**」——把最容易誤判的那句話講死。

## 明確不改

- 未改任何 `src/` / `engine/` / `modules/` / `content/` / `apps/` 單元——**176 個單元一行未動**。
- 未改根 `CMakeLists.txt`（`/utf-8` 屬 `CHG-20260803-01`）。
- 未改 `phase.json` / `units.json` / `governance.yml`；未實作任何 win32 後端。
- POSIX 取樣邏輯除「失敗回 -1.0」外未動。

## Verification

環境同 `CHG-20260803-01`（MSVC 19.44 / Windows SDK 10.0.26100 / CMake 4.4.1）。

### 正向

```
驗收①組裝：3/3 指標成功組裝呈現（fill_ratio ∈ [0,1]、display_text 已格式化）。
驗收②取樣：CPU 有效樣本 12/12 幀。
結論：... ✓ PASS        exit = 0
```

CPU 逐幀讀到真實變動的主機負載（實測 13.4% / 8.8% / 13.1% / 15.6%），不再是常數 0.0%。

### 負向（**證明條件②真的會紅，不是裝飾**）

把 `kSampleInterval` 暫時改為 `0ms`（＝還原缺陷發生的條件）重建重跑：

```
驗收①組裝：3/3 指標成功組裝呈現          ← 舊條件在缺陷完全存在下仍然全綠
驗收②取樣：CPU 有效樣本 0/12 幀——**量表停在 0.0% 不是 CPU 很閒，是取樣失效**。
結論：... ✗ FAIL        exit = 1
```

這同時證明了缺陷③的存在：**若只有條件①，這一輪會被判 PASS**。
負向測試後已還原 `250ms` 並重建重跑確認回到 PASS，工作區無殘留（無 `TEMP-` 痕跡）。
