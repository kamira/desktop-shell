# CHG-20261112-h1_06 — 實作 H1-06 繪製層消費 E4 RenderModel（依 kind 分派）

- Date: 2026-11-12 | Branch: feat/h1_06 | Risk: medium | Implemented by: I1.1
- Skill: ai-sdlc-autopilot

## Motivation

H1-06「繪製層消費 E4 元件的 RenderModel（依 kind 分派）」。驗收標準是**平台承諾本身**
（Guideline §1：「本 repo 的產品是平台，不是桌面工具」）——**新增一個元件型別後，
不改 `src/` 與 `engine/` 任何一行即可被畫出**。

### 現況（問題）

H1-01 的 `host/paint/widget_painter.cpp` 把 `SystemStatusRenderModel` 的每一筆指標都畫成
**同一個固定版面**：標籤 + 水平軌道 + 數值文字。它只讀 `entry.element.fill_ratio`，
**`entry.element.kind` 從未被讀過**（改寫前全檔 grep `kind` 零命中）。後果：
`host/app/host_main.cpp:134-141` 設定的三個指標 **CPU=`gauge` / GPU=`bar` / RAM=`progress`**
在畫面上長得一模一樣 —— C2-02 老老實實依 kind 產出了 E4-03 的三種 `RenderModel`
（`system_status_widget.cpp:367-398`），而繪製層把三者的差別整個丟掉。

而且「新增一個元件型別」在改寫前**沒有任何入口**：畫法寫死在 `paint_widget()` 的迴圈裡，
加一種元件就是改這個檔案。

### 第二個問題：這個單元原本不會被任何 CI 閘門看到

`host/` 的**每一個**子目錄（app / menu / paint / position / tray）的 CMakeLists 整份包在
`if(WIN32)` 裡。若照 H1-01 原樣把新程式碼也放進守衛內：

- ubuntu 的 **G3**（`CHG-20261112-04` 起 `-DDS_WERROR=ON`）與新的 **`gate_sanitizers`**
  （ASan + UBSan）**一行都看不到**；
- `gate_windows` 的第二道防線是一份**硬編碼名單**（`backend_win32` / `tray_win32` /
  `h1_01_paint` / `h1_02_controls`），不含本單元 —— 連「有沒有被建進來」都沒人查
  （`CHG-20261111-w1_08` §已知限制 1 已載明此缺口）。

而本單元的驗收標準是**純邏輯命題**，根本不需要 Windows。故照 **W1-08 的先例**
（`CHG-20261111-w1_08`：政策層抽到守衛外；更早的先例是 H1-01 自己——版面計算抽成不碰 GDI
的純函式）把「依 kind 分派」整層搬到真的有人看守的平台上。

## Impact

改寫後 `host/paint/` 分三層，**前兩層平台中立、在 `if(WIN32)` 之外建置並各自 `add_test`**。

### 新增 `host/paint/render_dispatch.{hpp,cpp}` → target `h1_06_dispatch`（守衛外）

平台中立的分派核心。不 include `windows.h`、不呼叫任何 GDI API、無 `#ifdef`，
**也不相依任何 E4 元件 target**（只認 `ElementDraw`）。

- `PaintSink`：**可注入的抽象繪製介面**，三個原語 —— `fill_box` / `draw_text`（UTF-8）/
  `draw_needle`（中心 + 角度 + 長度 / 粗細比例）。顏色以**具名角色** `PaintRole`
  （Background / Title / Label / Value / Track / Fill / Unavailable）表達而非 RGB 數字：
  Windows 側給 GDI 實作，測試給記錄型假實作。
  **三個原語就夠用**是刻意的設計目標：新增一種元件不得需要平台新增繪製原語，
  否則「不改平台」只是口號（本 CHG 的兩個新 kind 都只用這三個原語，見下）。
- `ElementDraw`：平台中立的元件繪製描述。`kind` 是**具名字串鍵**而非 enum ——
  enum 一加值就得改本層，字串鍵不必；另帶一個 `params`（具名 double 袋子）讓擴充 kind
  攜帶平台不認得其語意的參數。這兩點是「新增元件型別不改平台」的機制本體。
- `ElementRendererTable`：kind → renderer 的**分派表**。
  `with_builtin_kinds()` 內建 E4-03 的三種（`bar` / `progress` / `gauge`）；
  `register_kind()` 新增（**已存在同名即回 false，不靜默覆寫**——靜默覆寫等於讓兩個元件
  型別互相吃掉對方）；`replace_kind()` 是「我知道我在覆寫」的明確入口。
  查不到 kind → 回 `DispatchResult::UnknownKind`，**不靜默**（NFR-04 精神）。
- 版面幾何純函式：`row_geometry`（`label` / `cell` / `track` / `value`）、`title_box`、
  `track_strip`、`dial_box`、`fill_span`、`clamp_unit_ratio`。
  **`cell`（整列高度的格位）是交給 renderer 的東西 —— 格位內怎麼畫由該 kind 自己決定**，
  這就是「不再自訂固定版面」的落點。
- `clamp_unit_ratio()` 是繪製層**所有**比例夾限的唯一來源，含 `!(r > 0.0)` 的 NaN 處理
  （K-002：壞掉的讀數不得偽裝成滿格）。GDI 側的指針長度 / 粗細也用它，免得同一條判斷
  在兩個平台上各寫一次、各錯一次。

### 新增 `host/paint/widget_render.{hpp,cpp}` → target `h1_06_paint_model`（守衛外，link `c2_02`）

- `project_entry()`：**E4-03 `RenderModel` → `ElementDraw`** 的內建投影（kind / 方向 /
  比例 / 三個角度 / 標籤逐欄帶過，不假造 E4-03 沒說過的欄位）。
- `WidgetRenderer::paint()`：背景 → 標題 → 每列（標籤文字 → **依 kind 分派**元件 →
  數值文字），回傳 `PaintSummary{rows, drawn, degraded, unknown_kind, empty_area}`。
  **NFR-03** 在此實施：該筆不可用 → 文字改用 `Unavailable` 角色、元件**仍畫軌道但不畫
  填充 / 指針**，迴圈不中斷、不丟例外，其餘筆完全不受影響。
- `add_projector()`：**新元件型別的認領入口**。新元件型別有自己的 `RenderModel` 型別，
  投影那一步必須由認得它的人提供；投影器依註冊的**反序**詢問，第一個回 true 的勝出，
  都不認領則走內建 E4-03 投影。**可用性政策不交給投影器改寫**（有測試釘住：
  一個硬把 `available` 改成 true 的「樂觀」投影器不會讓降級失效）。

### 新增 `host/paint/radial_draw.{hpp,cpp}` → target `h1_06_radial`（守衛外，link `e4_18`）

**E4-18（徑向線 / 指針）的接入** —— 一個**真實的上游元件型別**，分派核心原本不認得它：

> 漏了第三處。I1 複查為三處，V1.5 獨立複核確認）：

> 失敗；同一個**程式**連入兩份不同定義是 **ODR 違反**（UB —— K-013 那一族「綠燈不代表正確」的形狀）。
> **勘誤二**：原稿寫「警告旗標與 sanitizer 都抓不到」太滿。精確的分界（I1 與 V1.5 各自實測）：

> `test_h1_06`）與 E4-18 側（`h1_06_radial` / `test_h1_06_radial`）是**兩個獨立的程式**，

### 三種 kind 的畫面差別（「既有三個指標的呈現不得退步」的實質內容）

| kind | 畫法 | 既有行為 |
|---|---|---|
| `bar`（GPU） | 細長軌道 + 依比例的填充 | **與 H1-01 完全相同**（幾何數值已釘住） |
| `progress`（RAM） | 同上，另把元件自帶的讀數畫在軌道中央（`show_label` 時） | 不退步 |
| `gauge`（CPU） | **置中正方形錶盤 + 依角度的指針** | **升級**：不再被畫成與 bar 一樣的長條 |

**誠實說明**：C2-02 目前對三種 kind 都 `set_show_label(false)`
（`system_status_widget.cpp:373/382/391`；**勘誤**：原稿寫 381，V1.5 複核為 382），所以 `progress` 在畫面上**暫時**與 `bar` 相同。
那是上游的設定選擇，不是分派沒有發生 —— 兩者各自走自己的 renderer，
`DispatchResult` 與測試都看得到（`ProgressWithoutLabelLooksLikeBarButIsStillItsOwnKind`）。

**另一個誠實說明（上游限制，刻意不猜）**：C2-02 對 `available=false` 的條目**不填** element
（維持預設建構，`system_status_widget.cpp:357-363`），所以降級列的 kind 一律是預設的 `bar`。
繪製層沒有資訊可以還原它原本的 kind，也不該自己發明一個 —— 降級列因此畫成「軌道 + 灰字」，
與 H1-01 既有行為一致。

**M3 原本只打紅 1 案例 —— 這是突變測試真的抓到的一條缺斷言。** 第一輪跑完時只有
`ProjectionCarriesEveryE403FieldThroughUnchanged` 變紅：「投影」有被釘住，但**從
`paint()` 到指針的端到端路徑沒有** —— `AllThreeAreDrawnEachByItsOwnKind` 當時只斷言
「有一根指針」，沒斷言那根指針的角度。已補上
`EXPECT_DOUBLE_EQ(cpu_needle->angle, 270.0)`（= 135 + 0.5×270）與該指針所在的錶盤矩形，
重跑後 M3 變成 2 紅。

**M5 的覆蓋範圍要說清楚（誠實分界）。** 它只打紅直接測 `clamp_unit_ratio` / `fill_span`
的那一條；`ThreeMetrics.NanRatioPaintsNoFill`（paint 層的 NaN 斷言）**仍然通過**，
因為 `fill_span` 還有第二道夾限（`if (out.right < out.left) out.right = out.left;`），
NaN→int 的結果恰好被它收掉 —— NaN 在這裡有兩道防線，M5 只拆掉第一道。
另實測：把 M5 放進 **sanitizer 建置**（ASan + UBSan，`-fno-sanitize-recover=all`）重跑，
UBSan **沒有任何報告**（`runtime error` 零命中），測試仍只紅同一條。所以這個形狀
**不能**指望 sanitizer 代替斷言，K-002 的防線就是那條直接斷言本身。
