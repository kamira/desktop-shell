## 人工放行紀錄（medium 停點）

PHASE-PLAN §相位 2 切換程序明列相位翻轉為 **Risk: medium**，屬停點契約上需人放行者。
**使用者於 2026-08-03 明示核准「核准，翻到相位 2」**，並指定本輪範圍為
「最小可見成果：一個浮在桌面的 CPU widget」。本 CHG 依該授權執行，非 I1 自主。

方向上與 PHASE-PLAN 原定案（Q1 Windows 優先、相位 2 = win32）一致，**非翻案**。

## Motivation

需求：把 176 個擴充點單元變成**真的浮在 Windows 桌面上的 widget**，而非主控台 ASCII 模擬。
依 `docs/backlog/phase2-desktop-runtime.md`，此需求的功能**全部已是現成單元**，
缺的只是「win32 真實後端 + host shell app」——即相位 2 的 WS2 + WS3。

`backend_guard` 依 `phase.json` 白名單擋 `src/kernel/backend/*`，相位 1 只允許 `null`，
故不翻相位連目錄都建不起來。

## Impact

### 1) 相位翻轉（`docs/backlog/phase.json`）

`"phase": 1` → `2`，頂層 `allowed_backends` 由 `["null"]` → `["null","win32"]`
（與既有 `phases["2"]` 定義一致）。`backend_guard` 自動放行 `src/kernel/backend/win32/`。
`phases` 區塊本身未動——相位 3（cocoa）的定義原封不動。

### 2) 修復 `backend_guard` 反向檢查（**它從上線起就是空轉的**）

`scripts/backend_guard.py` 的反向檢查原本只掃 `tests/contract/**/*.py`，
但契約測試其實是 **C++**（`test_contract_backend.cpp` / `kernel_backend.hpp` / `stub_backend.hpp`），
**該目錄下 `.py` 檔數為 0**。也就是說「契約測試不得分平台」這道保護**一次都沒有真正執行過**。

在放行 win32 後端的此刻，這是最不能留的漏洞：相位 1 的紀律全靠「契約測試對所有後端一視同仁」，
而現在正是最容易不知不覺把契約測試改成遷就 win32 的時候。

新增 C/C++ 掃描。**刻意不沿用 Python 那組全文比對**——契約測試的中文註解本來就會寫
「不得出現 `win32` / `cocoa`」，全文比對會把這些自我約束的說明判成違規，反而逼人刪註解。
改為只檢查**前處理器指令行**（第一個非空白字元為 `#`）：真正的平台分支一定寫在
`#if` / `#ifdef` / `#include` 上，而註解行永遠不以 `#` 開頭，天然免疫誤判。

偵測目標：平台條件編譯巨集（`_WIN32` / `_WIN64` / `__APPLE__` / `__linux__` / `__unix__` /
`__MACH__` / `_MSC_VER` / `__MINGW32__`）與平台專屬標頭（`windows.h` / `cocoa/` / `appkit/` /
`unistd.h` / `sys/` / `x11/`）。Python 檔行為完全不變（向後相容）。

### 3) 桌面 runtime 單元入冊（`docs/backlog/units.json`）

AGENTS.md §3「工作單元來自 `units.json`，不得自行發明任務」，故先入冊再施工。新增 2 個單元：

| id | title | layer | risk | write_scope |
|---|---|---|---|---|
| **W1-01** | win32 kernel 後端（視窗 / 具名圖層 / 輸入策略） | platform | medium | `src/kernel/backend/win32/**` |
| **H1-01** | host shell app（GDI 繪製橋接 + 主迴圈 + 浮動 CPU widget） | artifact | low | `host/**` |

`totals` 同步更新（units 176→178、medium 16→17、waves 9→10、by_layer / by_platform / by_stage）
——否則 units.json 的自述數字與實際脫節，下一個人會被誤導。

**為何是 2 個而非路線圖的 P-01…P-07 + H-01…H-04**：本輪範圍是使用者指定的「最小可見成果」。
托盤選單、拖曳、點擊穿透切換、設定持久化、skin 格式留待後續 CHG。

**為何繪製橋接放 `host/` 而不是後端**：它吃 E4 的 `render_model`（engine / module 層型別），
放進 `src/kernel/backend/win32/` 會讓 **platform 層反向依賴 engine 層**；
且繪製必然涉及座標，放進 kernel 契約會直接違反 NFR-02。
`phase2-desktop-runtime.md` §WS3 原本就把 host shell 放在「artifact/app 或新 `host/`」。

## ⚠ 契約缺口（本 CHG **不修**，但必須記錄在案）

**`tests/contract/`（E1-25）測的不是任何真實後端，且 win32 後端也掛不上去。**

repo 裡有**兩個毫不相干的 `KernelBackend`**：

| | `src/kernel/backend/null/null_backend.hpp` | `tests/contract/kernel_backend.hpp` |
|---|---|---|
| 型別 | `ds::kernel::KernelBackend` | `ds::kernel::contract::KernelBackend` |
| surface 指涉 | 具名 `SurfaceId`（字串） | `SurfaceHandle`（`unsigned long long`） |
| 回傳 | `bool` | `Status` 三態列舉 |
| 特有 | `SurfaceLayer` / `InputPolicy` / `begin_frame` / `poll_input` | `invoke_capability` |

契約測試組**刻意不 link E1-24 null 後端**（其檔頭寫明「維持 E1-25 與 E1-24 的單元獨立」），
只測它自己目錄裡的 `StubBackend`。它的註解寫「未來 null / win32 / cocoa 各加一個 factory 即納入」，
但 `NullKernelBackend` 並未實作 `contract::KernelBackend`，**加不進去**。

後果：PHASE-PLAN 寫的「契約測試不改一行拿去跑 win32 後端——**這才是相位 1 的投資回收點**」，
**那筆投資目前不在帳上**。

本輪處置：W1-01 以 `tests/e1/` 自有 gtest 驗證，**不宣稱通過 E1-25 契約測試**
（已寫進該單元的 acceptance 欄位）。修復契約缺口是另一個 medium 級工程（需重寫 E1-25
或加轉接層），留待獨立 CHG，不與本次桌面 runtime 混做。已收錄為知識庫 **K-003**。

## 明確不改

- 未動 176 個既有單元的任何一行原始碼。
- 未動 `phases` 區塊（相位 3 定義不變）、未動 `tests/contract/` 任何檔案。
- 未動 `governance.yml`（windows runner 仍未加，見已知限制）。
- 尚未建立 `src/kernel/backend/win32/` 或 `host/`——本 CHG 只開路，施工在 W1-01 / H1-01。

### 已知限制

CI 仍在 ubuntu。相位 2 之後 `src/kernel/backend/win32/` 在 ubuntu 編不過，
W1-01 / H1-01 必須以 CMake `if(WIN32)` 條件納入才不會讓 G3 紅。
**這代表 win32 後端的正確性在閘門上依然是空的**——要補仍需 windows runner
（`phase2-desktop-runtime.md` §6 checklist 步驟 3）。
