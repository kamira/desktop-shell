## Motivation

人類裁定：「**鍵序那一軸的安全論證，另開單元讓驗收者先量**。」

`H1-09` 的覆寫判據（`host/edit/edit_assembly.cpp` 的 `same_properties()`）對 properties 的
鍵序敏感，使用者在自己的存檔裡把兩個鍵對調就會收到 `RefusedTargetChangedSinceLoad`
而存不了檔（`V1.13` 的 R21 實測）。那**看起來**是誤報。

### 為什麼不是直接開一個「放寬鍵序」的單元

因為同一個判據的**數值軸**剛剛才因為「看起來是誤報」而出事。`H1-09` 修訂 7 放寬了
Number 的比較（只比 `num_`、不比 `integral_`），承重論證是：

> 「兩份文件若只差在 `integral_` 旗標與 Map 鍵序，這一層帶走的每一個欄位都一模一樣，
> 覆寫不會丟掉任何它帶得走的東西。」

`V1.15` 的 **F8** 證偽了它。機制（I1 自行從原始碼複核）：`engine/format/editor_model.cpp:27`
的 `infer_kind()` 是 `v.is_integer() ? EditKind::Integer : EditKind::Number`，同檔第 297 行
`"' 為 Integer，但給的是非整數 Number"`。所以 `integral_` **在資料模型裡、而且承載行為**：
存檔寫 `x: 1` 的掛件拖不動，寫 `x: 1.0` 的拖得動。放寬之後 `save()` 會把使用者為了「能拖」
而改成的 `1.0` 無聲改回 `1`。

**那個錯誤論證是 I1 給實作者的，不是實作者自己推的。** 錯在一個聽起來漂亮的類比
——「`save()` 本來就會毀掉註解與縮排，所以字面寫法不是內容」——而註解與縮排**根本不在
資料模型裡**，`integral_` 在。`V1.13` 當初建議「只改註解」的理由正是「放寬要重新論證會不會
放行真正的內容變更」，那個要求被我跳過去了。

鍵序軸的「看起來是誤報」目前**處於同樣的證據狀態**：沒有人量過有沒有消費端讀鍵序。
所以本單元的交付物是**一個被量出來的答案**，不是一次放寬。

### 驗收標準的兩個結構性決定

**一、必須實測的消費端普查**，逐一列出並各附最小輸入的實測，不接受從程式碼推論：
序列化是否依插入順序寫 Map（會重排使用者檔案裡的鍵）；E7-14 / `editor_model` 列舉欄位是否
依 Map 順序（若是，鍵序就跟 `integral_` 同類）；其他依序走訪 properties 而非以 `find()` 取鍵的
消費端；以及重複鍵的不可達性複核（`V1.15` 的 R24 指出 `same_map_unordered()` 的註解理由寫反了
——多重集在重複鍵下比「用鍵查第一個」更**寬**，不是更嚴）。

**二、兩個結果都算 pass。** 這一條是本單元的重點：

- **每個消費端都實測為與鍵序無關** → 才可以放寬，每條無關性各一支測試，並補反向斷言。
- **任何一個消費端讀了鍵序** → **正確的結果是不放寬**，交付的是「註解寫明鍵序會觸發 +
  依據行號 + 釘住該依賴的測試 + CHG 寫明為何不能放寬」，**判 pass**。

**本單元不以「有沒有放寬」論成敗，以「有沒有量出答案並照答案行事」論成敗。** 寫成這樣是
刻意的：若驗收標準寫「放寬鍵序」，實作者就有壓力把它放寬，而這個判據的失效方向是
**放行一次會毀資料的覆寫**，比誤殺嚴重得多。

另外明寫不得破壞的既有不變式：R18 的「公開 API 一律不 throw」（改語意不等於改回直接用上游
`operator==`），以及元件順序一律不得放寬（`resolve_draws` 依 `state_.elements` 順序產出並原封
帶給繪製層，那是繪製／疊放順序）。並要求**獨立驗收者自己重做消費端普查**，不得採信實作者列的
清單——這個判據已被兩句沒測過的話擋下兩次（F7 是宣稱、F8 是理由），而第二次是 I1 說的。
