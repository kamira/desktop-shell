### `K-015` — 檢查器看不見的那一半

`H1-07` 的反向斷言現況命中數 **0**，兩個方向都以突變證明過。**但那個 0 有一半來自
檢查器看不見**：三條規則對 **`float` 型的絕對擺放幾何零覆蓋**，而 kernel 的公開介面上
正有四個（`anchor_model.hpp:88 Size`、`:97 ResolvedPlacement`、`edge_snapping.hpp:79
SnapResult::rect`、`edge_hot_zone.hpp:44 ScreenExtent`）。

**本收尾者逐項驗證的事實**（不採信回報）：

```
src/kernel/anchor_model.hpp:8   「具體像素數字只在 resolve() 這個純佈局計算的邊界出現」
                          :88   struct Size { float width; float height; }
                          :96   「元件在容器座標系內的矩形（x, y = 左上角）」
                          :97   struct ResolvedPlacement { float x, y, width, height; }
host/position/position_store.cpp:73
    out_x = area.x + static_cast<int>(std::lround(placed.x));   ← 真的成為螢幕絕對座標
```

最尖的一處：`ResolvedPlacement` 把「**x, y = 左上角**」這個**原點慣例**寫進 kernel 的公開介面，
而 **Cocoa 的 `NSRect` 原點在左下角**。相位 3 接 macOS 時這個失配零診斷——無編譯錯誤、
無 sanitizer 報告、`backend_guard` 擋路徑不擋型別、`H1-07` 的斷言掃不到 `float`。
**那正是該驗收標準擔心的失敗，只是它穿了 `float` 的外套。**

判定（`V1.6` 裁定、`I1` 同意）：**不算「已被違反」**（單位由呼叫端決定，宣告式 API 仍是
正規化分數，符合 NFR-02 的正面表述），**但「機器承諾小於文字承諾」**。修法要動 kernel
的公開契約，必須另開單元（與 `K-014` 同類）。**已向人類提出待裁定。**

### `K-002` 的一次獨立復發

`engine/package/palette.cpp:16`：

```cpp
double clamp01(double v) noexcept { return v < 0.0 ? 0.0 : (v > 1.0 ? 1.0 : v); }
```

NaN 的兩個比較都是 false → **NaN 原封不動被回傳**；下游 `round_channel` 對它
`std::lround`（未指定回傳值 + FE_INVALID）再夾進 `[0,255]`，產出一個**看起來正常的顏色**。
那是 `K-002` 標題那句「讓壞掉的值看起來像正常資料」的字面重現。

對照 `I1.1` 在 `H1-07` 施工中自查並修掉的同形狀（`sane_scale`，改用
`!(scale > 0.0) || !std::isfinite(scale)` 並以突變 M14 證明斷言承重）——**同一個陷阱，
一邊修好了，一邊還在**，而且在 ubuntu CI 的建置範圍內。

**沒有任何自動防線接得住它**：`-Wall -Wextra -Werror` 不警告；`gate_sanitizers` 的
ASan + UBSan 不報（`std::lround` 的定義域錯誤不在 UBSan 涵蓋內，**加 `float-cast-overflow`
也補不到**）。修它要動已合併單元，必須另開單元。**已向人類提出待裁定。**
