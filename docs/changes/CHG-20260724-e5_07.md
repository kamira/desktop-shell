# CHG-20260724-e5_07 — 區域內連續拖曳判定（E5-07）

- Date: 2026-07-24 | Branch: feat/e5_07 | Risk: low | Implemented by: I1.165
- Skill: ai-sdlc-autopilot
- Unit: E5-07（區域內連續拖曳判定，engine 層 / 角色 / low，depends_on=[E5-14]）

## Motivation

E5-14 已交付「滑鼠事件命中某具名 surface 後，若該 surface 登記了 E1-05 具名子區域，就把
命中之具名區域 id + 參數附加到派發事件上」的橋接能力，但那只是**單次命中判定**——每個
Down/Up/Click 各自獨立判定，彼此互不相關。使用者互動中常見的「拖曳」（按下某具名區域、
移動、放開）是一段**連續**的指標事件序列，需要額外的狀態追蹤才能判定：這段序列自始至終
是否都落在**同一個**具名區域內；中途離開該區域算不算數；整段序列該回報什麼語意（開始 /
進行中 / 正常結束 / 中斷）。這正是 E5-14 沒有交付、E5-07 要補上的部分。

本單元**不重新實作任何命中測試或區域查詢邏輯**——是否命中具名區域、命中哪個、帶什麼參數，
完全委派已合併的 E5-14 `RegionEventDispatcher`（其再委派 E5-01 `MouseEventRouter` + E1-05
`NamedRegionMap`）。新增的邏輯只有「連續拖曳」這一層更高階的狀態機語意：起拖 / 拖曳中 /
結束 / 中斷。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 綁定方式 | `RegionDragRecognizer` 建構時綁定**一個** E5-14 具名 surface + 其 E1-05 具名子區域集合，內部私有持有一個**專屬**的 `RegionEventDispatcher` 實例（不與外部共用） | 拖曳辨識是針對「某個具名區域」的專用狀態機，綁定單一 surface/region 集合語意最清楚；私有持有 dispatcher 避免與呼叫端其他滑鼠處理邏輯共用同一內部 router 狀態（多擊游標等）互相干擾 |
| 事件序列來源 | 呼叫端以 `feed_down()` / `feed_move()` / `feed_up()`（或統一入口 `feed(PointerAction, position)`）逐一注入 | E5-01/E5-14 的 `MouseAction` 僅有 `Down/Up/Click`，無「移動」語意；本單元定義自己的指標事件序列 API，移動事件的語意（是否仍在區域內）完全是本單元新增的判定 |
| 移動事件的區域查詢 | 借用 E5-14 `inject_button(button, MouseAction::Click, position)` | 該注入語意「直接以 `topmost_hit()` 判定命中並分派，不讀取 / 修改多擊追蹤游標」（見 E5-01 文件）——故可在 Down 與 Up 之間對同一內部 dispatcher 任意次查詢命中的具名區域，而不會擾動 Down/Up 本身的按鍵狀態機；Down/Up 仍以真正的 `inject_down()` / `inject_up()` 注入，語意對稱、行為一致（皆讀取同一個 `RegionEvent`：`region_hit` / `region_name` / `region_params`） |
| 狀態機 | `Idle --Down(落在區域內)--> Dragging`；`Dragging --Move(仍在同區域)--> Dragging`（分派 Move）；`Dragging --Up(仍在同區域)--> Idle`（分派 End）；`Dragging --Move/Up(離開該區域)--> Idle`（分派 Cancel） | 對應題目語意「按下→移動保持在區域內→放開」為正常拖曳；「中途離開區域則中斷」為 Cancel；區分 End（在區域內放開）與 Cancel（不在區域內放開）讓訂閱者能分辨「拖曳是否成功完成」 |
| 不亂序保護 | `Idle` 狀態下的 `feed_move()` / `feed_up()` 為 no-op（不分派任何事件）；`Dragging` 狀態下重複 `feed_down()` 為 no-op（不重新起拖、不重複分派 Begin） | 呼叫端可能傳入不完整或有雜訊的事件序列（漏收 Down、重複 Down 等）；狀態機需在這些情形下保持一致（不崩潰、不誤發事件），而非假設呼叫端一定送出完美配對的序列 |
| 事件型別 | `DragEvent{ kind, surface, region_name, position, region_params }`；`kind` 為 `Begin/Move/End/Cancel` | 純資料、平台中立；`region_name`/`region_params` 沿用 E1-05/E5-14 既有的具名區域 + 封閉型別參數字典慣例（NFR-02），不引入新的參數表達方式 |
| 訂閱表 | 本類別自身獨立的 `subscribe()` / `unsubscribe()` / `listener_count()`（`DragEvent` 訂閱者），與內部 dispatcher 的訂閱表（`RegionEvent`，僅供內部橋接使用）分離 | 呼叫端只看得到拖曳語意事件，不會意外拿到內部查詢用的原始 `RegionEvent`；空 listener 拒絕、快照分派慣例與 E5-01/E5-14 一致 |
| 命名空間 | `ds::events`（同 E5-01/E5-14） | 沿用既有事件系統的命名空間慣例 |

介面平台中立：無 `#ifdef _WIN32` 等平台分支、不綁任何真實滑鼠後端，符合相位 1（Mac/null）約束。
engine 層與平台無關（非 `src/kernel/backend/`，不涉 backend_guard）。

- 12 個 gtest 案例：按下區域內起拖（帶區域 id + 參數）、移動保持在區域內產生多次 Move、
  放開結束拖曳、中途離開區域中斷（移動到 surface 內非該子區域 / 完全離開 surface 兩種情形）、
  Up 時已離開區域判為 Cancel 而非 End、未在區域內按下不起拖（含命中 surface 但非子區域 /
  完全未命中 surface 兩種情形）、多次拖曳序列（正常完成 + 中途取消交替）、狀態機不亂序
  （非拖曳中的 Move/Up 為 no-op、拖曳中重複 Down 為 no-op）、統一入口 `feed()` 與專用方法
  等價、訂閱生命週期（空 listener 拒絕、未知 id 取消 no-op、多訂閱者依序皆收）。
