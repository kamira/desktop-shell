## Motivation

E9-01 定義了「一個元件套件」的整體結構（manifest + 內容清單），但沒有回答**多個元件如何互換組合**：
一個宿主/組合需要若干「角色」（如 renderer、storage），每個角色可由任一符合該角色介面的元件填入，
且要能在執行期**替換**為另一相容元件、在一堆候選中**挑出**相容者，並在組合層**驗證相容性**。

**可互換元件組合**單元把這件事封裝為組合層 API：
- 以 E9-01 的元件（`ds::package::Package`）為單位，不重造元件模型；
- 以具名**插槽 / 角色**（`ComponentSlot`）表示可互換位置，插槽宣告其對元件的介面要求；
- 綁定/替換前於組合層檢查相容性，**不相容一律明確報錯、不靜默**（帶人類可讀原因）；
- 相容性直接建於 E9-01 元件模型之上，並複用 E9-01 `validate_package` 確保不放行破損元件。

平台中立、純邏輯：無任何 `#ifdef` / 系統呼叫 / 平台分支。屬 engine 層，可完全單元測試。

## 設計（可覆核可改）

插槽介面定義：一個插槽宣告一組 `required_kinds`（所需資源類別）。元件與插槽**相容** iff
(a) 元件本身結構完整（E9-01 `validate_package` 通過）；且 (b) 對每個 `required_kind`，元件內容清單
（`entries`）至少提供一項該 kind 的資源。`required_kinds` 為空 = 無額外介面要求，接受任一有效元件。

| 項目 | 選擇 | 理由 |
|---|---|---|
| 元件單位 | 直接沿用 E9-01 `Package` | 不重造元件模型；命名空間 `ds::package` 與上游一致 |
| 插槽/角色 | `ComponentSlot{id, required_kinds}` | 具名可互換位置；介面以「元件須提供哪些 kind」表達，直接可從 `Package.entries` 檢查 |
| 相容性 | `check_compatibility(slot, component) -> CompatibilityResult` | 先驗結構（複用 `validate_package`）再驗 required_kinds；不相容帶原因、不靜默 |
| 操作結果 | `BindResult{ok, message}` / `CompatibilityResult{compatible, reason}` | 皆有 `explicit operator bool()`；失敗一律附人類可讀原因 |
| 首次綁定 | `bind(slot_id, component)`：插槽須存在且**為空**、元件須相容 | 未知插槽 / 已綁定（請改 swap）/ 不相容 → 皆 failure，狀態不變 |
| 替換 | `swap(slot_id, component)`：插槽須存在且**已綁定**、新元件須相容 | 可互換替換；不相容則**保留原綁定**不覆寫（不半途破壞狀態） |
| 清空 | `unbind(slot_id)` | 回到空狀態；本已空則明確報錯（不靜默）；清空後可重新綁定任一相容元件 |
| 查詢 | `has_slot` / `is_bound` / `bound_component` / `slot` / `slot_ids` | 空插槽狀態可查；未知插槽查詢一律安全（回 false / nullptr） |
| 列舉候選 | `compatible_candidates(slot_id, candidates) -> vector<size_t>` | 回相容候選在原清單中的索引（依序）；不修改組合狀態；未知插槽回空 |
| 組合完整性 | `validate()` | 每插槽皆綁定且綁定仍相容才通過；有未綁定插槽 → failure(指名)；空組合視為完整 |

介面平台中立：無 `#ifdef _WIN32` 等平台分支、不綁任何真實後端。engine 層與平台無關
（非 `src/kernel/backend/`，不涉 backend_guard）。不含能力閘控呼叫（純邏輯組合），無 `has()` 降級需求。
