## Motivation

E9-02 manifest 宣告一個套件**想要**哪些權限（`permissions`）；E8-04 載入時依
`HostEnvironment` 判斷 host **是否授予**（未授予 → `MissingPermission`，附缺項）。中間缺的那
一層一直沒有人做：**誰在什麼時候對哪個套件的哪個權限做了什麼決定，而這個決定要活過重啟。**

`CHG-20260829-05` 裁定「**Q-C 權限在安裝時問**」，並把 E9-11 定義為消費 E9-10 的下游。
「在安裝時問」這件事要能實作，前提是分得出「**從沒問過**」與「**問過被拒**」——前者該問，
後者不要再問。這就是本單元為何是三態而不是一個 bool。

### 設計決定 1：三態活在本單元，有損投影到 E8-04 的兩態（方向決定對錯）

E8-04 的 `HostEnvironment`（`engine/script/module_loader.hpp:78-103`）只有兩態：某權限**在**
`permissions_` 集合裡或**不在**（檔頭明寫「空集合 = 什麼都不提供 / 不授予」）。它**沒有**
deny / revoke / 任何第三態，而驗收標準明文「**不得修改 E8-04**」。故：

```
已授予 Granted    →  grant_permission(id)     （進集合）
未決   Undecided  →  不呼叫                    （不進集合）
已拒絕 Denied     →  不呼叫                    （不進集合）
```

這個投影**刻意有損**，而有損的方向是唯一正確的：

- **安全方向**（採用）：未決與已拒絕都不授予 → 載入時 E8-04 回 `MissingPermission`。
  兩者在**載入閘控**上行為相同，這沒問題。
- **禁止方向**：把「未決」當成「預設授予」（樂觀預設）。那會讓一個從未被問過的權限直接通行，
  正是驗收標準禁止的靜默降級，只是方向相反。突變測試 **M3** 就是刻意做出這個錯，見下。

**三態的意義不在閘控，在決策流程。** 若用一個 bool 表示，「從沒問過」與「問過被拒」會塌成
同一個狀態，`CHG-20260829-05` 的「Q-C 權限在安裝時問」就實作不出來（不知道該問誰）。故：
- 型別上就是具名三態；`decision()` 直接回三態之一，查無紀錄 → `Undecided`（**不是** `Denied`）。
- `revoke()` → 回到 `Undecided`（日後可以再問）；`deny()` → 留下 `Denied`（不要再問）。
- 測試 `E9_11_Tristate.UndecidedIsDistinguishableFromDeniedInTheQueryInterface` 與
  `RevokeReturnsToUndecidedRatherThanDenied` 釘住「未決 ≠ 已拒絕」在**查詢介面**上可區分。

**有損不等於資訊被丟掉**：`evaluate_permissions()` 回傳的 `PermissionGate` 把被扣住的權限
**按原因**分成 `undecided` / `denied` 兩個清單，呼叫端因此知道該問哪些、哪些不要再問——
資訊只是不在 `HostEnvironment` 裡，而不是不存在。

### 設計決定 2：後端沿用 E9-10 的 `InstallStorage`，不造第三個同形狀抽象

本單元需要的後端契約（以 slot 名稱為鍵的序列化文字鍵值儲存：`put/get/has/erase/names`）與
E9-10 `InstallStorage` **完全相同**。E9-05 造了 `LayoutStorage`、E9-10 造了 `InstallStorage`，
到這裡若再造第三個一模一樣的，相位 2 就要寫三個真實磁碟實作。故直接沿用，僅取別名
`PermissionStorage` / `MemoryPermissionStorage` 讓呼叫點讀得懂語意，並用不同 slot
（`"permissions"` vs E9-10 的 `"installed"`）保證互不干擾（測試
`SeparateSlotsAreIndependentOnTheSameBackend` 釘住）。

**誠實聲明：`MemoryInstallStorage` 是相位 1 的記憶體替身，不是真實磁碟後端**——相位 1 的
engine 層不得有真實檔案 I/O（G1b / `backend_guard`、`PHASE-PLAN.md`），所以替身是此相位
**唯一合法**的選擇。相位 2 換上真實實作時，E9-10 與本單元共用同一個，介面一行不動。

### 設計決定 3：持久化格式沿用 E7-01 + E7-12，兩個已知限制的處理同 E9-10

```
format_version: 1.0
decisions:
  -
    package: com.example.hello
    permission: fs.read
    decision: granted          # granted | denied
```

| E7-12 已知限制 | 本單元怎麼處理 |
|---|---|
| **map 鍵不支援引號**（鍵為裸 token，不得含 `:`） | **套件名與權限名都不當 map 鍵**，放在清單項目的**值**位置（由 E7-12 `needs_quote` 自動引號化 / 轉義）。E9-02 對 `name` 只要求非空、**未禁止** `:`，所以這不是理論風險——測試 `IdentifiersContainingColonsSurviveBecauseTheyAreValuesNotMapKeys` 用 `"weird: package"` / `"odd: permission"` 釘住 |
| **空容器不 round-trip 為同型**（`key:` 下無縮排塌成 Null） | 讀取端把「缺鍵」與「Null」**一律視為空帳本**（尚未做過任何決定，**不是錯誤**）。測試 `EmptyLedgerRoundTripsAsEmptyRatherThanFailing` 釘住 |

另：**未決不被寫出**（未決 = 沒有紀錄），故序列化只寫 `granted` / `denied`；
把一筆 `Undecided` 丟給序列化 → **throw**（語意矛盾，明確拒絕而非靜默略過）。
讀取端對人工編輯可能出現的字面 `undecided` **接受並略過**（它不帶任何資訊），
對**其他**任何字面值則 throw（不靜默當成某一態）。

### 設計決定 4：不靜默降級 —— 兩個方向都要守

1. **被擋時要擋得明白**：`PermissionGate::withheld` 與 E8-04 `LoadResult::missing` 按同一順序
   （manifest 宣告順序）列出同一組權限。**只斷言 status 不夠**，故測試把 `missing` 的
   **內容與順序**也釘住（`MissingListFollowsManifestDeclarationOrderAcrossBothWithholdingReasons`）。
   誠實邊界：manifest **重複宣告**同一權限時 `withheld` 去重、E8-04 的 `missing` 不去重，
   兩者為「同序但 E8-04 多出重複項」的關係——另有一個測試釘住這個差異，而不是假裝兩者永遠相等。
2. **沒被擋時功能要真的在**：`loadable` 為真 iff 該套件宣告的**每一項**權限都是 `Granted`，
   不存在「部分授權也可載入」的路徑。而正向案例
   `GrantingEveryPermissionActuallyLoadsAndRegistersTheCapability` 刻意**不只**斷言「沒被擋」：
   它斷言註冊入口**真的被呼叫過一次**（SpyModule 計數）、能力**真的進了載入器的能力表**、
   `provider_of` 是該模組、`is_loaded` 為真、`capability_count()==1`，再卸載確認能力確實離開。
   一個回 `Ok` 但其實沒生效的載入會在這裡被抓到。

### 相位 1 的「重啟」是以什麼機制模擬的（與 E9-10 同一誠實度）

「重啟」定義為「**後端存活、狀態物件解構後重新建構**」：`PermissionLedger` 建構即自後端重讀、
每次決定寫入即落盤，故「新 ledger 指向同一個存活後端」在資訊流上等價於重啟後——唯一的資訊
通道是那份已序列化的文字。測試一律把後端放**外層** scope、ledger 放**內層** scope。
**刻意不寫**「對同一個還活著的 ledger 再查一次」（那證明不了任何事）。

**撤銷也落盤**是本單元特有的那一刀：否則「已授予 → 撤銷 → 重啟 → 又變成已授予」就是另一種
靜默降級。突變測試 **M1** 專打這一點。
