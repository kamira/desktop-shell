## ⚠ 更正二：「`--delete-branch` 持續無聲失敗」是錯的，而我在五份 CHG 裡重複寫了它

`CHG-20261111-03` 首次寫下這條，之後 `-01`（W1-08）、`-02`（E7-16）、`-03`（E9-11）、
`-04`、`-05` 一路承繼。本次合併後實查，結論相反：

| 合併路徑 | head 分支 |
|---|---|
| #236（bot 以 `gh pr merge --auto --squash --delete-branch`） | **已刪** |
| #235（I1 以 GitHub API `merge_pull_request`） | `feat/h1_06` **仍存在** |
| `feat/e9_10` / `feat/w1_08` / `feat/e7_16` / `feat/e9_11` / `feat/c2_11`（皆經 API 合併） | **全部仍存在** |

遠端現有 **222** 條分支，其中 `feat/*` **179** 條。

**真正的成因**：`--delete-branch` 是有效的，但它只出現在 workflow 的 **AUTO 合併**那一步。
medium 風險單元依停點契約走**人工核准後手動合併**，而那條路徑（GitHub API 或網頁按鈕）
根本沒有刪分支的動作。於是每一個 medium 單元合併後都留下一條分支——**這與 medium
單元的數量一致**，而本 repo 絕大多數單元是 medium。

**我先前的證據為什麼誤導我**：`CHG-20261111-03` 記的是「#226 以 `--delete-branch` 合併，
但其 head 分支合併後仍存在」。最合理的解釋是**我隨後又往同名分支推了東西、把它重建了**
（本 session 反覆使用同一個 `claude/project-analysis-readme-njkw18`）。那一點我無法回溯
證明，但今天 #236 的直接觀察足以確定該指令本身有效，而「API 合併不刪分支」解釋了全部。

**修法建議（比修 `--delete-branch` 有效，且與合併路徑無關）**：打開 GitHub repo 設定的
**「Automatically delete head branches」**。那是一個勾選框，對每一次合併生效，不論是 bot
還是人工合的。**本環境仍無法代為清理既有的 179 條**：`git push origin :ref` 與
`gh api -X DELETE` 皆被出站代理回 403，GitHub MCP 亦無刪分支工具（已查）。
依 `/root/.ccr/README.md`，政策拒絕不重試。**已向人類提出待裁定。**

本單元的分派層是平台中立的，所以那件事其實**可以**在 ubuntu 上看：I1 寫了一個只存在於

顏色是佔位色（真實 `PaintTheme` 在守衛內、取不到），幾何與指針角度則是真實程式碼算出來的。

查出的事見 `CHG-20261112-h1_06` §已知限制 5：**`gauge` 的指針掃向是逆時針、從下方經過**
（0% 左上 → 50% **正下方** → 100% 右上），而慣例的圓弧量表從上方掃。成因是 E4-03
`GaugeElement` 的預設弧（start 135° / sweep +270°）配上數學慣例加 y 翻轉，
**不是 H1-06 的錯**；但在 H1-06 之前 gauge 一直被畫成長條，所以這個預設從上線起從未被看見。
人類已裁定「合併，指針方向另案」。
