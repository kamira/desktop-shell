## Motivation

`CHG-20260803-04` / `-05` / `-06` 三張都在「已知限制」寫了同一句話：
**本單元不在任何 CI 閘門的守備範圍內**。累積下來，main 上約 1200 行 win32 程式碼、
四個單元（W1-01 / W1-02 / H1-01 / H1-02）的正確性**只有開發機的手動證據**——
任何人（包括後續的我）改壞都不會紅。

這是 `docs/backlog/phase2-desktop-runtime.md` §6 checklist 的**步驟 3**，
也是該文件 §5 標記為「風險①（阻斷）」的那一項。功能再往上疊，
未被守護的表面積只會更大、之後補閘門的成本與風險也更高。

## Impact

### 1) `.github/workflows/governance.yml` — 新增 `gate_windows` job（G3w）

`windows-latest` 上跑 **MSVC 全建 + ctest**：

```bash
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Debug --parallel 4
ctest --test-dir build -C Debug --output-on-failure
```

**`gate` job 以 `needs: gate_windows` 相依於它。** 這是刻意的 fail-closed 設計：
Windows 建置紅燈 → `gate` 被跳過 → 自動合併的指令**根本不會執行**。
不依賴 branch protection 的「required checks」設定（那是 repo 設定，不在本 repo 版控範圍內，
若只新增一個非必要檢查，`gh pr merge --auto` 仍會在它紅燈時合併）。

代價：兩個 job 序列化，PR 多等約十餘分鐘。以「Windows 正確性完全無人看管」的現況換，值得。

### 2) 第二道真空綠燈防線：確認 Windows 專屬單元真的有被建進來

只跑 `ctest` 不夠。四個 Windows 單元的 CMakeLists 都以 `if(WIN32)` 包住，
若條件納入被改壞（GLOB 深度不對、target 名改了、守衛寫錯），
它們會被**靜默排除**，而 ctest 仍會拿 176 個平台中立測試印出綠燈——
**看起來有守、其實沒守**，正是本專案 G3 「真空綠燈防線」要防的同一類假象。

故逐一點名 `backend_win32` / `tray_win32` / `h1_01_paint` / `h1_02_controls`
是否在測試清單中，缺任一即紅燈。

### 3) `scripts/backend_guard.py` — 相位閘門擴及 `src/` 下所有平台目錄

`CHG-20260803-06` §閘門涵蓋缺口記載：相位閘門只掃 `src/kernel/backend/*`，
而 W1-02 落在 `src/host/win32/`——**完全不受相位白名單保護**。
也就是說相位 1 時只要把平台碼放在 kernel/backend 之外就能繞過閘門。

改為掃描 `src/` 之下**任何**以平台命名的目錄
（`win32` / `cocoa` / `wlroots` / `x11` / `wayland` / `macos` / `linux` / `android`），
連同既有的 `src/kernel/backend/*` 一併比對相位白名單。

### 4) `docs/backlog/state.json` — 重建 done-set

該檔一直是空的 done list，`plan.py status` 因此顯示「180 單元｜已完成 **0**」，
與實際完全相反（180 個全數合併）。此假象自 2026-07-28 起存在，
已在本輪多次被指出但未處理。

由 `docs/changes/` 反推重建（權威來源是 CHG，不是此檔）：
178 個由檔名 slug 判定、2 個（W1-02 / H1-02，CHG 檔名未帶 slug）由 CHG 內文的單元 id 判定。
