## Motivation

兩個缺口由 `E9-11` 的獨立驗收者 `V1.4` 查出，並在 `CHG-20261112-03` 載明：

1. **CI 完全不跑 sanitizer**：`sanitize|asan|ubsan|valgrind` 全 repo **0 命中**。
2. **CI 與預設建置都沒有任何警告旗標**：`-Wall|-Wextra|-Werror|/W[0-9]` 全 repo **0 命中**；
   根 `CMakeLists.txt` 只有 MSVC `/utf-8`，G3 只有 `-DCMAKE_BUILD_TYPE=Debug`。
   故每一份 CHG 寫的「建置零警告」幾近自動成立，不管程式碼怎麼寫。

觸發點是 `K-013`：E8-04 `ModuleLoader` 以 const 參考持有 host，而
`compose_host_environment()` 按值回傳，於是 `ModuleLoader loader(compose_host_environment(...))`
抓著一個在該敘述結束就被銷毀的臨時物件。**那份測試當時是 35/35 全綠的**，
只有 I1.1 的突變 M3 把它逼成 SIGSEGV 才暴露。換句話說，本 repo 對「綠燈下的潛伏 UB」
在此之前沒有任何自動防線。

## 加入前的實測：為什麼這兩道必須一起，而不是先補一道

把兩個方向的錯誤各做一次，看兩道防線分別說了什麼（`tests/e9/test_e9_11.cpp`，g++ 13.3.0）：

| 突變 | `-Wall -Wextra` | ASan + UBSan |
|---|---|---|
| **M-A**：把懸空參考形狀放回去（`loader` 綁到建構子的值參數） | **0 警告，完全靜默** | **抓到**：`stack-use-after-scope`，`ctest` rc=8、測試 FAILED |
| **M-B**：把 `GatedLoader` 的成員宣告順序對調（重新製造同一個 UB） | **抓到**：`-Wreorder` ×3 + `-Wuninitialized` | **0 報告，測試通過**，完全靜默 |

**任一道單獨都不夠。** 旗標守「後人把對的寫法改壞」，sanitizer 守「一開始就寫錯」。
這也更正了一件事：`V1.4` 當時測得「原始寫法連 `-Wdangling-reference` 都不警告」，
本檔的 M-A 以完整建置重現並確認——該族錯誤在任何警告旗標下都不可見。

## 變更內容（4 檔）

### 1. 根 `CMakeLists.txt`：加入警告旗標

```cmake
option(DS_WERROR "把警告升級為錯誤（CI 的 G3 以 -DDS_WERROR=ON 開啟）" OFF)
if(NOT MSVC)
  add_compile_options(-Wall -Wextra)
  if(DS_WERROR)
    add_compile_options(-Werror)
    if(CMAKE_CXX_COMPILER_ID STREQUAL "GNU")
      add_compile_options(-Wno-error=dangling-reference)
    endif()
  endif()
endif()
```

四個設計決定，每個都有實測依據：

**(a) 插在 `FetchContent_MakeAvailable(googletest)` 之後、收各單元 CMakeLists 的 foreach 之前。**
`add_compile_options` 設的是目錄屬性，只在目標**被建立時**被讀取，而 googletest 的目標在
`MakeAvailable` 當場就建立完了。實測確認（`compile_commands.json`）：

```
改檔後  本庫目標 engine/command/command_bus.cpp
          → -Wall -Wextra -Werror -Wno-error=dangling-reference
        googletest 目標 → -Wall -Wextra（**沒有** -Werror）
對照組（改檔前配置的建置目錄）
        googletest 目標 → -Wall -Wextra     ← googletest 自己加的，不是外溢
        本庫目標        → （無）
```

所以旗標只套到本庫，日後升 googletest 版本冒出的是別人的警告，不由本庫的 `-Werror` 承擔。

**(b) `-Werror` 不進預設建置，只由 CI 以 `-DDS_WERROR=ON` 開啟。** 編譯器升版會新增警告種類；
把 `-Werror` 寫死在預設建置等於讓任何人換個編譯器就建不起來。

**(c) `-Wno-error=dangling-reference`（僅 GNU）。** 實測：全 repo 在 `-Wall -Wextra` 下
只有 **3** 個警告，全部是 `tests/e7/test_e7_09.cpp:142/198/224` 的 `-Wdangling-reference`，
而且**全為誤判**：

```
const Value& child(const DegradeResult& r, const std::string& key) { return r.value.at(key); }
...
const Value& panel = child(r, "panel");     // r 是具名區域物件
```

三個站點的 `r` 都是 `DegradeResult r = resolve_with_fallback(doc, avail);`，
回傳的參考指向 `r.value` 擁有的 map，活得比該敘述久；GCC 只是無法證明它不指向
`key` 那個臨時字串。**實測佐證**：`e7_09` 在 ASan + UBSan 下乾淨通過、零報告。

故以 `-Wno-error=` 而**不是** `-Wno-` 放行：警告仍會印出來（日後真有一個會看得見），
但不擋紅。這樣也**不必為了開旗標去動已合併單元的測試**——`E7-09` 是已合併單元，
不在本 infra 變更的改動範圍內。限定 `CMAKE_CXX_COMPILER_ID STREQUAL "GNU"` 的理由：
`-Wdangling-reference` 是 GCC 13 才有的旗標，clang 不認得，而在 `-Werror` 之下一個
不認得的 `-Wno-error=` 會自己變成 `-Wunknown-warning-option` 錯誤。

**(d) MSVC 刻意不加 `/W4`。** 本變更是在 Linux 上做的，**無法實測** MSVC 下會冒出多少警告。
未經實測就打開等於替 `gate_windows` 製造一道不知深淺的紅燈。另案處理（見缺口第 2 項）。

### 2. `.github/workflows/governance.yml`：新增 `gate_sanitizers` job

ubuntu-latest，ASan + UBSan 全建 + `ctest`。四個設計決定：

**(a) `-fno-sanitize-recover=all` 不可省。** UBSan 預設只印 `runtime error:` 訊息、
程序照樣回 0，於是會出現「報告印出來了而 `ctest` 全綠」——那是 `K-011` 的鏡像：
K-011 是擋對了卻印不出原因，這個是印出來了卻沒擋。`ASAN_OPTIONS=detect_leaks=1` 同理。

**(b) 註冊數必須與同平台普通建置**相等**，不只是「大於 0」。** sanitizer 旗標若讓某個單元的
CMake 條件走進別的分支，該單元會被**靜默排除**，而其餘一百多個測試照樣印綠燈。
取「普通建置」的註冊數只需一次 configure、不必建置（`ctest -N` 讀的是 configure 時
產生的 `CTestTestfile.cmake`）——**已實測**：未建置的目錄回 `181`，與 sanitizer 建置一致。

**(c) 兩個管線賦值都帶 `|| true`，並以 `-n` 檢查空值 fail-closed。** 前者是 `K-011` 的直接教訓；
後者不可省，因為 `|| true` 的代價是值可能為空字串，而兩邊都空時
`[ "$GOT" = "$EXPECT" ]` 會**相等而放行**——fail-closed 就變成 fail-open（`K-012` 同族）。

**(d) `gate` 的 `needs` 改為 `[gate_windows, gate_sanitizers]`。** 照 `gate_windows` 既有的
fail-closed 設計：前置 job 紅燈 → `gate` 被跳過 → 自動合併的指令**根本不會執行**。
不接上去的話，本閘門紅燈時仍會自動合併，它就只是裝飾。兩個前置 job 彼此獨立並行，
故牆鐘成本是兩者的較大值而非總和。

`-j 2` 沿用 G3 的理由（每個 Debug gtest TU 峰值可達 ~1.5–2GB，sanitizer 另加開銷）；
註解已寫明若 runner 被 SIGTERM（exit 143）即為 OOM，應降為 `-j 1` 而非改回無限並行。

## 影響面與代價（本變更影響**每一個**後續 PR）

1. **`gate` 多一個前置 job。** 任何 PR 的 sanitizer 紅燈 → `gate` 被跳過 → 不會自動合併，
   也不會貼 HALT。這是刻意的 fail-closed。
2. **牆鐘成本**：`gate_sanitizers` 與 `gate_windows` 並行，故增加的是
   `max(sanitizer, windows) - windows`。sanitizer 建置比普通 Debug 慢（本機 `-j 8` 相當，
   CI `-j 2` 未知），首次實跑的數字應記入後續 CHG。
3. **`-Werror` 的風險我無法完全排除**：CI 的 g++ 版本可能與本機的 13.3.0 不同，
   新版可能新增警告種類而讓 G3 紅。若發生，修法是針對該類加 `-Wno-error=`，
   **不是**去動已合併單元的程式碼。首次 CI 實跑即為驗證。
4. **三個誤判警告仍會印在每次 G3 的 log 裡**（不擋紅）。清掉它們需要動 `E7-09` 的測試，
   屬該單元範圍，不在本變更內。

## 未關閉的缺口

1. **⚠ G3 自己有一個 K-011 實例，本檔刻意不修。** G3 的真空綠燈防線寫成：

   ```bash
   N=$(ctest --test-dir build -N 2>/dev/null | sed -n 's/.*Total Tests: //p')
   [ "${N:-0}" -gt 0 ] || { echo "::error::repo 沒有任何 CTest 測試，綠燈無意義"; exit 1; }
   ```

   管線賦值沒有 `|| true`，而 `2>/dev/null` 另把 `ctest` 自己的訊息吃掉。若 `ctest -N`
   真的失敗（**也就是這道防線唯一要抓的災難情境**），賦值失敗 → `-e` 當場中止 →
   下一行的 `::error::` 永遠印不出來。與 `K-011` 同形，只是換了個步驟。
   修法一行（補 `|| true`、去掉 `2>/dev/null`），另可把「管線賦值必須有 `|| true`」
   這條規則移進 `scripts/workflow_lint.py`（G8 已以縮排解析全部 `run:` 區塊），
   讓它對**每個**步驟生效而非只有 G5 與本次新增的 job。
   **不併入本檔的理由**：那是另一個步驟的另一個缺陷，人類授權的是「補兩道防線」；
   擅自擴大範圍與「不得自行發明任務」相違。**已向人類提出待裁定。**
2. **MSVC 無警告旗標。** `gate_windows` 仍以預設旗標建置。加 `/W4` 需先在 Windows 上實測
   既有程式碼會冒出多少警告，本環境做不到。
3. **`tests/e7/test_e7_09.cpp` 的三個誤判警告仍在。** 清掉需動已合併單元。
4. **draft PR 會讓 infra AUTO 合併步驟失敗，而表現為「`gate` 紅燈」（新增）。**
   PR #233 的十一道閘門全綠，但第 18 步 `gh pr merge 233 --auto --squash --delete-branch`
   回 `GraphQL: Pull request Pull request is a draft (enablePullRequestAutoMerge)` 並 exit 1，
   使整個 `gate` job 變紅——**從 check 狀態看起來像某道閘門擋了你，實際上沒有任何閘門擋**。
   解法是把 PR 標為 ready（`ready_for_review` 已在 workflow 的觸發清單裡，會重跑並合併）。
   若要修在 workflow 裡：該步驟應先判斷 draft 並給出可讀訊息，而非讓 `gh` 的錯誤冒上來。
5. **`標記待人工核准（HALT）` 每次重跑都重貼一次相同留言**（承 `CHG-20261112-03` 第 8 項）。
6. **`gate_windows` 硬編碼名單覆蓋不全**（承前，12 個僅 Windows 建置的測試只點名 4 個）。
7. **`--delete-branch` 持續無聲失敗**（承前）。
8. **`directory.md` 各列與 `units.json` 不符**（承前：engine 記 64 / 實 67；artifact 記 24 / 實 37）。
9. **unit 工作走 infra 分支會繞過 G1 / G5 / G6**（承前）。
