## Motivation

桌面殼需要對系統產生一組電源相關副作用：休眠、鎖定畫面、登出、重新啟動、關機。
若一開始就綁死 `shutdown` / IOKit / `NSWorkspace` / win32 電源 API，動作語意會被平台細節污染、
無法以單元測試驗證，且呼叫端會被迫相依具體致動器，更嚴重的是——**電源操作不可逆**，
在相位 1 直接接 OS 會有真的把機器關掉的風險。

E3-04 走 E6-01「擴充點 3：動作」的既定路線：把這五種電源副作用以具名命令
（`power.sleep` / `power.lock` / `power.logout` / `power.restart` / `power.shutdown`）掛上命令匯流排，
呼叫端只需 命令 id 即可觸發，不需相依本致動器或任何 OS 電源 API。相位 1（Mac / null 期）
**絕不真的執行任何電源操作、也不呼叫任何 OS 電源 API**——所有請求交由可抽換的 `PowerBackend`
承接，預設 `NullPowerBackend` 只把請求記錄下來供測試 / 診斷驗證。相位 2 換上真實平台後端
（win32 / cocoa）時，本致動器與命令契約一行不動。

## 設計（可覆核可改）

| 項目 | 選擇 | 理由 |
|---|---|---|
| 動作列舉 | `PowerAction`：Sleep / Lock / Logout / Restart / Shutdown（+ Unknown 哨兵） | 一組承重的電源意圖；不含 OS 語意假設 |
| 命令 id | 具名字串 `power.sleep` / `power.lock` / `power.logout` / `power.restart` / `power.shutdown`（非數字 opcode） | 穩定、可讀、跨邊界不變形；與 E6-01 CommandId 取捨一致 |
| 掛載方式 | `PowerActuator::register_on(CommandBus&)` 註冊五個具名命令 | 呼叫端經 `bus.dispatch(id)` 觸發，零相依本型別 |
| 副作用抽象 | `PowerBackend` 純虛介面 + `perform(PowerRequest)→CommandResult` | 相位 1 null、相位 2 真實後端可抽換，介面不動 |
| 相位 1 後端 | `NullPowerBackend`：**絕不觸碰 OS、絕不執行電源操作**，只記錄請求（有序 vector） | 讓「註冊→分派→記錄」完整跑通並可單元驗證；不真的關機 / 重啟 |
| 請求型別 | `PowerRequest{action}`（平台中立） | 不含 OS handle / 電源 API 假設；承載呼叫端意圖交後端實現 |
| 參數契約 | 電源動作無需額外參數；多餘參數被忽略 | 命令 id 本身即完整表達意圖 |
| 無效動作保護 | `handle_action(Unknown)` / 無法辨識的動作字串回 `CommandResult{Failed}` | 不崩潰、不丟例外、不記錄無效請求 |
| 註冊回滾 | `register_on` 任一命令掛失敗即回滾本次成功者並回 false | 不留半掛狀態、不遮蔽既有其他致動器 |
| 契約版本 | `contract_version()` = "e3_04/1.0.0" | 承重抽象，供相位 2 換後端時相容判斷 |

介面平台中立：無 `#ifdef _WIN32` / `cocoa` / `__APPLE__` / `darwin` / IOKit / 真實 `shutdown` /
`system()` / exec；唯一 `#ifndef` 為 header guard，唯一 `#ifdef` 字樣為註解說明。

## Impact

### 1. `modules/actuators/e3_04/power_actuator.hpp`（新增）
- `PowerAction`（Sleep / Lock / Logout / Restart / Shutdown / Unknown）、
