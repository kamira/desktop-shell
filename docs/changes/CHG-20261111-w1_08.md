# CHG-20261111-w1_08 — 實作 W1-08 win32 行程列舉後端

## Motivation

W1-08「win32 行程列舉後端」：實作 **E2-19**（行程監看）宣告的 `ds::sysinfo::ProcessSource`
抽象的 **win32 真實後端**（E2-19 的 `backend_followup`）。E2-19 在相位 1 只有
`NullProcessSource`（注入式假資料），其檔頭即寫明「真實後端（相位 2+）於此讀 sysctl /
`/proc` / **EnumProcesses**」。本單元補的就是 `EnumProcesses` 那一路。

**E2-19 的提供者與下游 widget 一行不動**：`ProcessMonitorProvider`（指標身分、top-N 排序、
指標實例、歷史環、採樣分級）與 C2-11 `ProcessTopWidget` 都只透過 `ProcessSource` 抽象取資料，
換後端就是換建構時注入的物件 —— 這是「平台差異靠換實作、不靠 `#ifdef`」的落地，也是驗收
標準「**契約測試不得含平台分支**」成立的前提（`tests/contract/**` 一個字未改）。

本單元同時**首次建立 `src/sysinfo/`**，作為 sysinfo 平台後端的家（`CHG-20260829-05` 已預告，
G4 會擋 → `docs/structure/directory.md` 與 `docs/structure/units/w1_08.md` 同步更新）。

## Impact

### 新增 `src/sysinfo/win32/process_policy.{hpp,cpp}`（`namespace ds::sysinfo::win32`）

**平台中立的政策層**：不碰 win32 API、不 include `windows.h`、不含任何平台條件編譯。

- `Ticks100ns` / `kTicksPerSecond`：win32 原生的 100ns 刻。取樣時刻與行程 CPU 時間同單位，
  中間不經浮點換算 —— 浮點換算放在邊界上是「讀數」與「算出來的數」混在一起的開端。
- `RawProcessEntry`：單一 pid 的原始讀數（pid / name / busy / created / memory / liveness）。
- `RawLiveness`：**三態**（Running / Exited / Unknown）。刻意不是 bool：`GetExitCodeProcess`
  可能失敗，而「讀不到存活狀態」與「已結束」是兩件事；用 bool 就得挑一個當預設值，
  而那個預設值會變成假讀值。
- `RawSnapshot`：一次列舉的完整結果 —— `enumerated`（列舉本身成功與否）、`wall_100ns`、
  `processor_count`、`listed_pids`、`skipped`、`entries`。
- `SampleOutcome`：具名結果 `Ok` / `BaselineOnly` / `EnumerationFailed` / `NoTimeElapsed` /
  `InvalidCpuCount` / `NoUsableEntries`（各附 `to_string()`，NFR-02 慣例）。
  `unknown()` 有五種成因，混為一談就等於吞錯。
- `cpu_percent_from_delta(busy_delta, wall_delta, cpus)`：`100 * busy / (wall * cpus)`，
  clamp 到 E2-19 宣告的 `[0,100]`。**無法計算時回 -1.0**（不可能是合法 CPU%，與合法值域
  不撞號，正是 K-002 的解法原文），而不是 0.0。
- `status_from_raw()`：三態 → `ProcessStatus`。
- `ProcessDeltaTracker`：連續 `RawSnapshot` → `ProcessSample` 的差分換算與政策判斷，
  附 `last_outcome()` / `last_error()` / `skipped_in_last_sample()` / `tracked_count()` /
  `has_baseline()` / `reset()`。

## 本單元的核心陷阱：K-002（讀不到 ≠ 很閒）

E2-19 的 `ProcessSample` 只有一個 `valid` 旗標，`ProcessInfo` 的五個欄位**沒有** per-field
的「無讀值」表示法。所以「讀不到」只有兩種合法表達：**不回報該筆**，或**不回報整份**。
絕不以 `0.0`、空字串或空清單充數。

| 情形 | 行為 | 理由 |
|---|---|---|
| `EnumProcesses` 回 FALSE | 整份 `unknown()`，**保留基準點** | 列舉失敗 ≠ 沒有行程。基準點保留 → 下一輪仍能差分，只是區間較長（那仍是真實區間的平均） |
| 兩次取樣時間差為 0 | 整份 `unknown()`，**不推進基準點** | K-002 第 1 層：差分式 API 的兩次取樣之間必須真的經過時間 |
| 處理器數讀不到（0） | 整份 `unknown()` | CPU% 的除數不存在 |
| 第一次 `sample()` | 整份 `unknown()`（只建基準點） | K-002 的解法原文：首次呼叫只建立基準點 |
| **單一 pid 開不起來** | **跳過該筆，整份仍 valid** | 受保護行程（Idle(0) / System(4) / 防毒 / 剛結束）是**常態**。讓它污染整份快照，行程清單在一般使用者權限下就永遠是未知的 |
| 單一 pid 五欄位有任一讀不到 | 同上（跳過並計數） | 回報一筆「有些欄位是猜的」紀錄比不回報更糟 |
| 列舉成功但可用筆數 0 | 整份 `unknown()` | 機器上至少有「我們自己」。0 筆必然是讀取側壞了（權限不足 / 全數開不起來），不是「沒有任何行程」 |
| 某 pid 本次首見 | 本輪跳過，下一輪回報 | 無基準點算不出區間 CPU%。拿「行程開始至今的平均」充數會印出一個**看似合理**的數字，比回 0 更難察覺（K-002 附記） |
| 同 pid 但建立時間不同（**pid 重用**） | 同上（基準點換成新行程的） | 只比 pid 會拿另一個行程的累計時間去差分，算出憑空的使用率 |
| 累計 CPU 時間倒退 | 跳過該筆 | 單調量倒退表示讀數不可信，回 0.0 會讓壞讀數看起來像「很閒」 |

**唯一該出現 `0.0` 的地方**：取樣有效、該行程真的沒用 CPU。它是**讀值**，不是失敗值 ——
與無讀值在呼叫端眼中必須可分辨（後者 `valid == false`），有專門的案例釘住這兩者。

不靜默吞錯：`last_outcome()`（具名列舉）+ `last_error()`（人類可讀原因，含數字）+
`skipped_in_last_sample()`，讓「為什麼這份是 unknown」永遠留得下來。
