## Motivation

`document.hpp` 檔首第 11 行起就寫著一條明文契約：

> **錯誤可定位、不得靜默失敗**（NFR-04 精神）：任何解析失敗一律回傳帶「行號 + 訊息」的
> ParseError；絕不安靜吞掉未知 / 錯誤的輸入。

這條契約有兩類輸入**根本走不到**——它們不回傳任何東西，而是終結行程。

### 第一類：例外穿出 `parse()`

`numeric_token()` 以 `std::stod` 轉換、`parse_version()` 以 `std::stoi` 轉換。
兩者在 `errno == ERANGE`（上溢 / 下溢 / 溢位）時丟 `std::out_of_range`。
而 `parse()` 的 `try` 只接自家的 `ParseFail`：

```cpp
} catch (const ParseFail& f) {          // ← 只接這一個
    return ParseResult::failure(f.err);
}
```

於是 `std::out_of_range` 一路穿出 `parse()`。嚴重性鏈（本次實測，非推論）：

| 環節 | 事實 |
|---|---|
| 呼叫端 | 八個生產呼叫端（`permission_store` / `install_store` / `layout_store` / `ui_state` / 三個 widget）皆無 `try`/`catch` |
| 最外層 | `host/app/host_main.cpp` 零最外層攔截 |
| 型別分支 | `std::out_of_range` 繼承自 **`std::logic_error`**，不是 `runtime_error`。`layout_store.hpp:131` 文件承諾接 `runtime_error` 的呼叫端**接不到它** |
| 結果 | 一份含 `1e400` 的設定檔 = 行程結束 |

第三列是本次最值得記住的一點：那不是「漏接」，是**接錯分支**——一個看起來已經做了
錯誤處理的呼叫端，對這個例外的防護是零。故本單元的測試一律斷言
`parse()` 這一層**完全不丟**（任何型別），不斷言「不丟某個特定型別」。

### 第二類：深層巢狀打爆堆疊

遞迴下降解析（`parse_block` → `parse_map_block` / `parse_list_block` →
`parse_child_or_null` → `parse_block`）無深度上限，而 `Value` 樹的**解構也是遞迴的**。
故就算解析成功，把樹丟掉時同樣吃堆疊。

兩類表面上無關，實際是同一句話：**`parse()` 可以讓行程結束**。故一併修。

## 實測基線（改動前，pristine `383c8d7`）

以獨立 probe 連 pristine `document.cpp`，預設堆疊 8 MiB（`ulimit -s` = 8192）：

| 輸入 | 改動前 |
|---|---|
| `x: 1e400` | **THROW** `std::out_of_range: stod`（且 `dynamic_cast<logic_error*>` 命中 → 確為 logic_error 分支） |
| `x: -1e400` | **THROW** `std::out_of_range: stod` |
| `x: 1e-400` | **THROW** `std::out_of_range: stod` |
| `format_version: 99999999999999999999.0` | **THROW** `std::out_of_range: stoi` |
| `x:` + 400 個 `9` | **THROW** `std::out_of_range: stod` |
| `x: 1e-310`（次正規） | **THROW** `std::out_of_range: stod` |
| 巢狀深度 1000 / 4000 / 8000 | 正常回傳 ParseResult |
| 巢狀深度 **14000**（98 MB 輸入） | **SIGSEGV，退出碼 139** |

> 與派工簡報的 196 MB 差在縮排寬度（簡報每層 2 格、本 probe 每層 1 格）；
> 深度與結果一致。

## 設計（可覆核可改）

### 第一類：把「會丟例外的轉換」換成「會回報範圍的轉換」

**不是**用 try/catch 把例外包起來——那是遮蓋，不是修正。改在成因上：

| 位置 | 改動前 | 改動後 |
|---|---|---|
| `numeric_token` | `out = std::stod(t);` | `errno = 0; std::strtod(...)`，`errno == ERANGE` → `NumericResult::OutOfRange` |
| `parse_version` | `out.major = std::stoi(maj);` | `digits_to_int()`：乘加前先驗上界的累加，溢位回 `false` |

兩個布林回傳值都升成三態列舉，因為**「不是數字」與「是數字但超出範圍」必須分開**：

```cpp
enum class NumericResult { NotNumeric, Ok, OutOfRange };
enum class VersionResult { Ok, Malformed, OutOfRange };
```

若讓 `OutOfRange` 沿用「不是數字」那條路，`1e400` 會悄悄變成**字串 `"1e400"`**——
失敗偽裝成一個看起來正常的值，正是知識庫 K-002 那一族。故 `OutOfRange` 一律
`fail(line_no, ...)`，成為帶**該值所在行號**的 `ParseError`。

**為什麼 `strtod` 的行為與改動前完全對齊。** libstdc++ 的 `std::stod` 正是
「呼叫 `strtod`，然後檢查 `errno == ERANGE` 就丟 `std::out_of_range`」。
本實作改成檢查同一個 `errno == ERANGE` 然後回傳 `OutOfRange`。
於是「本實作拒絕的輸入集合」與改動前「會丟例外的輸入集合」**逐一相同**：
凡是改動前能正常解析的輸入，改動後解析結果一個都沒有變（有回歸測試釘住，見下）。

`digits_to_int` 刻意不用 `std::stoi`，上界檢查寫成 `v > (INT_MAX - d) / 10`
（先除後比，全程不觸發有號溢位 UB；已在 UBSan 下跑過）。

### `parse_scalar()`（公開 API）的連帶決定

`parse_scalar("1e400", v)` 改動前同樣**丟例外**（它共用 `numeric_token`）。
改動後回 `false`，而不是退化成裸字串——理由同上（K-002）。標頭已補上這條契約。

唯一的生產呼叫端是 `engine/format/writeback.cpp:222` 的 `needs_quote()`：
它把 `false` 解讀為「必須引號化」，所以字串 `"1e400"` 現在會被正確地加引號序列化，
而不是讓序列化流程整個把行程帶走。**這是嚴格的改善，不是行為退化。**

### 第二類：明示的巢狀深度上限

```cpp
inline constexpr std::size_t kMaxNestingDepth = 64;   // document.hpp，契約的一部分
```

`depth` 參數貫穿四個遞迴函式（根 map = 深度 1，`parse_child_or_null` 是唯一加深的地方）。
檢查放在 `parse_block` 的**最前面**，也就是**建任何東西之前**：

```cpp
if (depth > kMaxNestingDepth) {
    fail(L[i].line_no, "巢狀層數超過上限（最多 " + std::to_string(kMaxNestingDepth) + " 層）");
}
```

這個位置是刻意的。它同時保證兩件事：
1. 超限是帶行號的 `ParseError`（不是例外、不是 SIGSEGV）；
2. **已經建起來的 `Value` 樹永遠不深於 `kMaxNestingDepth`**——因為超限的那一層在
   建出任何 `Value` 之前就被擋掉了。這一點是必要的：解構是遞迴的，一棵「剛好超限時
   留下來的樹」若太深，提早回傳也救不了它（詳見下節實測）。

#### 上限值為什麼是 64

**刻意不去逼近實測的崩潰門檻。** 那個門檻（本機約在 8000～14000 之間）隨堆疊設定、
最佳化層級與編譯器漂移，寫進契約就不穩。改用兩端夾擊的挑法：

| 方向 | 依據 | 數字 |
|---|---|---|
| 下界：對真實文件要綽綽有餘 | 掃全庫所有宣告式文件字面值（skin / profile / manifest / layout / 設定），最深者 `tests/c2/test_c2_09.cpp` 的 **10 格縮排 = 6 層** | 64 是其 **10 倍有餘** |
| 上界：對堆疊要明顯安全 | 見下節實測：深度 64 的解析 + 複製 + 解構在 **128 KiB** 堆疊上即可完成 | 預設 8 MiB 是其 **64 倍** |

`kMaxNestingDepth` 寫在標頭上、由測試引用（測試用常數本身產生「剛好到上限 / 剛好超限」
的輸入），所以日後若真有需要調整，測試會跟著調整而不必重寫。
同時測試對這個常數設了 `16 ≤ kMaxNestingDepth ≤ 1024` 的雙向界限：
前者擋「調得比真實文件還淺」，後者擋「調成天文數字 = 等於沒有上限」這種假修法。

## 實測（改動後）

> 以下每一格都是本次跑出來的，不是推論。推論的部分另標「推論」。

### 第一類

| 輸入 | 結果 |
|---|---|
| `1e400`（放在第 4 行） | `ParseError` **line=4**，訊息含該 token |
| `-1e400`（第 4 行） | `ParseError` **line=4** |
| `1e-400`（第 4 行） | `ParseError` **line=4** |
| `format_version: 99999999999999999999.0`（第 4 行） | `ParseError` **line=4**，訊息含 `format_version` |
| 其餘 40 餘種數值邊界（上溢／下溢／長數字串／前後綴垃圾），各餵 4 個位置 | 零例外穿出 |
| `1e3` / `-5` / `-2.5` / `0` / `1.7976931348623157e308` / `2.2250738585072014e-308` / `12ab` | 解析結果與改動前逐一相同 |

### 第二類（巢狀深度，預設 8 MiB 堆疊）

| 深度 | 結果 |
|---|---|
| 6（真實文件最深） | ok |
| 63 | ok |
| **64**（= 上限） | ok |
| **65**（剛好超限） | `ParseError`，**line=66**，訊息「巢狀層數超過上限（最多 64 層）」 |
| 1000 | `ParseError`（不崩） |
| **14000**（98 MB，改動前 SIGSEGV 139） | `ParseError`（不崩） |
| 50000（1.25 GB） | `ParseError`（不崩） |

> CI 的回歸測試**不生成那種尺寸的輸入**：上限生效後，超限只需略超過 64 層就測得到，
> 「遠超限」那一條用深度 2000（約 2 MB，每層只縮排 1 格）。
> 14000 / 50000 是本次以獨立 probe 在 CI 之外量的，不進測試套件。

### 解構也是遞迴的 —— 堆疊餘裕實測

這一條容易漏：就算 `parse()` 超限時提早回傳，**已建好的那棵 `Value` 樹在解構時仍會遞迴**。
以 probe 在**刻意縮小的堆疊**下跑「解析深度 64 → 遞迴複製一棵同樣深的樹 → 讓兩棵都解構
→ 再跑一次超限路徑（部分樹在例外展開中解構）」：

| `ulimit -s` | 結果 |
|---|---|
| 8192 KiB（預設） | 全程通過 |
| 1024 KiB | 全程通過 |
| 256 KiB | 全程通過 |
| **128 KiB** | 全程通過 |
| 64 KiB | SIGSEGV |

對照組（確認 64 KiB 的失敗確實來自深度、不是行程起步就不夠）：同樣 64 KiB 下
深度 1 與深度 32 都全程通過。

即：上限深度所需堆疊介於 64–128 KiB，預設 8 MiB 有 **64 倍以上**餘裕。
這也是「64 這個數字對堆疊明顯安全」的量化依據。

## 測試

`tests/e7/test_e7_17.cpp`（15 個 TEST：7 支第一類 + 8 支第二類，`add_test(NAME e7_17 ...)`，
`platform: neutral` 故**不**包在 `if(WIN32)` 內）。

- `E7_17_ExceptionLeak.*`：四種點名輸入各一支（壞值一律放在**第 4 行**，
  斷言 `line == 4`——只斷言「有行號」或「行號 > 0」擋不住任何東西）；
  反向斷言 `NoExceptionEscapesParseForAnyNumericBoundary` 窮舉 40 餘種邊界 token
  × 4 個位置（純量 / 清單元素 / `format_version` / `parse_scalar`）確認零例外穿出；
  `LegalNumbersUnchanged` 釘住既有合法輸入；
  `OutOfRangeIsNotSilentlyAString` 擋 K-002 式的退化。
- `E7_17_NestingDepth.*`：上限內 / 剛好超限（含行號）/ 遠超限不當機 / 清單路徑同受管束 /
  上限常數的雙向界限 / **解構深樹實測** / **超限展開實測** / 真實深度不受影響。

測試輔助函式一律由 `kMaxNestingDepth` 推導輸入，不寫死 64。

14 條突變，**每一條的錨點都剛好命中一次**（命中 0 或 2 次視為作廢重做），
全部被殺，**零存活**：

| # | 突變 | 被哪支測試殺死 |

| M6 | 整段拿掉深度檢查 | `FarBeyondLimitDoesNotCrash`、`ListNestingIsLimitedToo`、`OneOverLimit...`、`UnwindingAfterOverLimitFailureIsSafe` |
