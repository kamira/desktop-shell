## 具名 id → 檔案路徑

```
icon.tray  →  <base>/icons/tray.ico
```

去掉開頭的 `icon.` 之後即為套件內邏輯路徑，**與 E9 套件格式的 `asset: icons/tray.png`
慣例對齊**——之後 skin 套件載入圖示時走的是同一套命名，不需要第二種規則。

`base` 解析順序：
1. 環境變數 `DESKTOP_SHELL_ASSETS`（覆寫，供測試與自訂部署）
2. `<執行檔所在目錄>/assets`

`icon_path_for()` **只算路徑、不檢查檔案存在**——分開才能分別測試
「路徑算對」與「檔案讀得到」，前者是純字串邏輯，後者需要檔案系統。

## 找不到檔案時：程式繪製後備，不是 Windows 通用圖示

**這是本單元最重要的決定。** 若後備直接用 `IDI_APPLICATION`，
「資源沒部署好」與「功能還沒做」在畫面上完全一樣，沒有人查得出差別。
後備圖示長得像自己（同色系、同構圖），一眼就能分辨是「資源沒找到」而非「沒實作」。

`icon_from_file()` 對外回報走了哪一條路徑，供測試與診斷區分。

## 圖示所有權

`LoadImageW` 載入的圖示**必須** `DestroyIcon`；`LoadIcon(IDI_APPLICATION)` 取得的
系統共用圖示**不得**銷毀。兩者混淆會造成洩漏或損毀系統資源，
故以 `icon_owned_` 明確記錄，替換與解構時都依此判斷。

## 圖示資源本身

`assets/icons/tray.ico`：深色圓角底 + 三條量表長條，構圖與配色刻意呼應 widget
（底色 `RGB(18,20,26)`、量表 `RGB(88,176,255)`），使用者在系統匣看到的是 widget 的縮影。
以腳本手工組 ICO（BMP-in-ICO，無影像函式庫相依）。

## 部署

`host/app/CMakeLists.txt` 的 POST_BUILD 步驟把 `assets/` 複製到執行檔目錄。
不複製的話 app 只會拿到後備圖示，**而且不會有任何錯誤訊息**——
這正是上面「後備要長得不一樣」的理由。
