## 三個選單項 = 三個 E6-01 命令

| 選單項 | 命令 id | 處理器做的事 |
|---|---|---|
| 最上層顯示（Checkbox） | `widget.toggle_topmost` | `Win32KernelBackend::set_surface_layer(Topmost / Normal)` |
| 點擊穿透（Checkbox） | `widget.toggle_passthrough` | `KernelBackend::set_input_policy(PassThrough / Accepting)` |
| 結束（Action） | `app.quit` | 設定結束旗標，主迴圈收攤 |

Checkbox 命令會收到 `"checked"` 參數（E11-01 先切換勾選狀態再分派）；
沒有該參數時退回「就地反轉」，讓同一組命令也能被腳本 / 熱鍵直接叫用。

## 為什麼抽成獨立單元而不是寫在 wWinMain 裡

托盤最關鍵的一段是「**使用者選了某項 → E6-01 命令 → 後端狀態真的改變**」這條鏈。
寫在 `wWinMain` 裡就只能靠人工點擊驗證；抽出來之後，`tests/h1/test_h1_02.cpp`
可以直接呼叫 `SystemTray::click(path)` 走完整條鏈，斷言真實視窗的 ex-style 有沒有變。

**只留「滑鼠實際點在托盤圖示上」那一步給操作驗收。** 換句話說：若整合測試全綠而實機無效，
問題只可能出在那一個環節，範圍很窄。

`host_main.cpp` 與測試共用**同一份**裝配，避免「被測到的那份」與「實際跑的那份」慢慢分岔。

## 測試斷言的取向

一律去問 Windows（`GetWindowLongPtrW(GWL_EXSTYLE)`），不問程式自己的旗標：
- 點「最上層」→ 視窗真的失去 `WS_EX_TOPMOST`，再點一次真的加回來
- 點「穿透」→ 視窗真的取得 `WS_EX_TRANSPARENT`
- **兩個開關互不干擾**（切最上層不得動到穿透）
- 點分隔線 → `NotClickable`，且任何視窗狀態都不得改變
- 越界 / 空路徑 → `InvalidPath`，不崩潰
- click 後選單模型的勾選狀態要跟著翻面（否則下次打開選單會說謊）
