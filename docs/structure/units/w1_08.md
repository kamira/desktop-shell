## 契約對映（E2-19 具名概念 → win32 原語）

| E2-19 契約 | win32 |
|---|---|
| `ProcessSource::sample()` | `EnumProcesses` + 逐 pid `OpenProcess`，再經政策層差分 |
| `ProcessInfo::pid` | `EnumProcesses` 回傳的 `DWORD` |
| `ProcessInfo::name` | `QueryFullProcessImageNameW` 取基本名（UTF-16 → UTF-8） |
| `ProcessInfo::cpu_percent` | `GetProcessTimes`（kernel+user）的**兩次取樣差分** / 經過時間 / 核心數 |
| `ProcessInfo::memory_bytes` | `GetProcessMemoryInfo().WorkingSetSize` |
| `ProcessStatus::Running` / `Zombie` | `GetExitCodeProcess`：`STILL_ACTIVE` / 其他 |
| `ProcessStatus::Sleeping` / `Stopped` | **永不產生**（win32 的行程層級無此語意，見下） |
| `ProcessSample::unknown()` | 列舉失敗 / 無經過時間 / 核心數讀不到 / 可用筆數 0 / 首次取樣 |
| top-N 排序、指標實例、歷史 | **不實作** —— E2-19 的 `ProcessMonitorProvider` 已有，一行不動 |

## 為什麼拆成「政策層 + win32 層」兩個目標

開發容器是 Linux、無交叉編譯器，而 win32 目標被 `if(WIN32)` 排除 ——
**win32 那一層在開發機上連編譯器都碰不到**，唯一證據是 CI 的 `gate_windows`。
但本單元最容易出錯的部分（K-002 的「讀不到 ≠ 很閒」邊界、差分式 CPU% 的除數、
pid 重用、單一 pid 失敗與整份失敗的區分）**全是純算術與政策判斷，不需要 win32**。

故照 H1-01 的先例（`CHG-20260803-05-h1_01`：版面計算抽成不碰 GDI 的純函式）把它們抽到
`process_policy.*`，由**不包 `if(WIN32)` 守衛**的 `w1_08_policy` 目標建置 ——
於是這一半真的進入 ubuntu G3 的守備範圍，win32 層薄到可以用肉眼審。

## 三個邊界（皆有負向測試證明會擋）

**1. 單一 pid 失敗是常態，整份失敗才是無讀值。** 受保護行程（Idle(0) / System(4) / 防毒）
`OpenProcess` 失敗是日常，跳過該筆並計入 `skipped_in_last_sample()`，**整份快照仍 valid**。
只有「`EnumProcesses` 回 FALSE」或「可用筆數 0」才整份 `unknown()` —— 後者的理由是機器上
至少有「我們自己」，0 筆必然是讀取側壞了，不是「沒有任何行程」。

**2. 沒有基準點就不回報該筆。** CPU% 是差分式的：首次 `sample()` 只建立基準點並回
`unknown()`（K-002 的解法原文）；某 pid 本次首見、或 pid 被重用（以**行程建立時間**判定）、
或累計時間倒退，該筆延後一輪，不以 0.0 或「行程開始至今的平均」充數 ——
後者會印出一個看似合理的數字，比回 0 更難察覺（K-002 附記）。

**3. 不假造狀態。** win32 的**行程**層級沒有 Sleeping / Stopped 語意（那是執行緒層級），
故 `RawLiveness` 是**三態**（Running / Exited / Unknown）而非 bool —— 用 bool 就得挑一個
當預設值，而那個預設值會變成假讀值。`status_from_raw()` 窮舉三態，沒有任何路徑產生
Sleeping / Stopped。

## 平台差異如何表達（驗收標準：契約測試不得含平台分支）

靠**換注入的 `ProcessSource` 實作**，不靠 `#ifdef`：E2-19 的 `ProcessMonitorProvider`、
E2-01 的 `MetricRegistry`、C2-11 widget 全部一行不動，只是建構時注入
`Win32ProcessSource` 而非 `NullProcessSource`。`tests/contract/**` 一個字未改。
政策層測試另以 `ReplaySource`（預錄原始快照驅動，結構與 `Win32ProcessSource` 相同）
在**沒有任何平台分支**的前提下驗證同一條路徑。

## 測不到的部分 / 已知限制

- **開發機完全無法建置或測試 win32 那一層**（Linux 容器、無 mingw 於 repo 工具鏈、
  `if(WIN32)` 排除）。該層的正確性證據來自 `gate_windows`（windows-latest + MSVC + ctest）。
- `GetExitCodeProcess` 無法分辨「以 259（`STILL_ACTIVE`）為結束碼的行程」與「仍在執行」。
  影響僅限 `status` 欄位，不影響其餘四欄位。
- 系統時鐘被調整會讓該一個區間失真：往後跳 → `wall_delta == 0` → 回報無讀值（fail-closed）；
  往前跳 → 低估，仍在值域內。
- ⚠ **`gate_windows` 的「Windows 專屬單元真的有被建進來」是硬編碼名單**
  （`backend_win32` / `tray_win32` / `h1_01_paint` / `h1_02_controls`），本單元的
  `process_win32` 不在其中。補名單需改 `.github/workflows/governance.yml`，
  **不在本單元 write_scope 內** —— 已交回 I1（見 CHG-20261111-w1_08 §已知限制）。
