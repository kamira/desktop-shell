# 結構註記 — E9-11 權限授予狀態與決策記錄

- 目錄位置：`engine/package/`（engine 層 / package 子系統）。
  CHG-20260730-03 目錄扁平化後**無 per-unit 子目錄**，本單元源碼直接置於該目錄。
- 放了什麼：
  - `permission_store.hpp` / `permission_store.cpp` — 權限決策帳本與投影：
    - `PermissionDecision{Undecided, Granted, Denied}` + `to_string` /
      `parse_permission_decision` — **具名三態枚舉**（刻意不是 `bool`、也不是
      `std::optional<bool>`）。三態的意義不在閘控（未決與已拒絕都擋），而在**決策流程**：
      分得出「從沒問過 → 該問」與「問過被拒 → 不要再問」，`CHG-20260829-05` 的
      「Q-C 權限在安裝時問」才實作得出來。
    - `PermissionRecord` — 持久化單位 `(package_id, permission_id, decision)`。
      **未決 = 沒有紀錄**（故 `decision` 恆為 `Granted` / `Denied`）。
    - `kPermissionLedgerFormat{1,0}` — 本持久化格式**自身**的版本欄位（Q3）。
    - `serialize_permission_records` / `deserialize_permission_records` — 經 **E7-12
      `serialize`** 產出 / 經 **E7-01 `parse()`** 讀回，不發明新格式。
    - `PermissionStorage` / `MemoryPermissionStorage` — **E9-10 `InstallStorage` /
      `MemoryInstallStorage` 的別名**（契約完全相同，不新增第三個同形狀抽象；
      相位 1 替身，無真實檔案 I/O）；`kDefaultPermissionSlot`（`"permissions"`，與 E9-10 的
      `"installed"` 不同 slot）。
    - `PermissionLedger` — 帳本門面：**建構即自後端重讀（rehydrate）**、
      `grant`／`deny`／`revoke`／`revoke_package` **寫入即落盤（write-through，撤銷亦然）**；
      `decision`（查無紀錄 → `Undecided`，**不是** `Denied`）／`is_decided`／`size`／
      `records`／`records_for`／`packages`／`reload`／`serialized`。
    - `PermissionGate` + `evaluate_permissions`（`Package` 版與權限清單版）— 把三態 → 兩態的
      **有損投影顯式化**：`granted`／`undecided`／`denied`／`withheld`（皆依 manifest 宣告
      順序）＋ `loadable`（iff 每一項都是 `Granted`，**不存在部分授權也可載入的路徑**）＋
      `needs_prompt()`。
    - `compose_host_environment`（`Package` 版與權限清單版）— **組出 E8-04
      `HostEnvironment`**：`host_capabilities` → `provide_capability()`；**只有 `Granted`** →
      `grant_permission()`，`Undecided` 與 `Denied` 都不呼叫。
    - `PermissionPrompt` + `permissions_awaiting_decision(InstalledPackageStore&, ledger)` —
      與 **E9-10** 的接點：掃過已安裝登錄列出**未決**的 (套件, 權限)，即安裝時要問的那些
      （已拒絕不再問、已授予不必問）；全程**不載入套件本體**。
  - `CMakeLists.txt`（追加 `e9_11` 區塊）— `add_library(e9_11 STATIC permission_store.cpp)`，
    `target_link_libraries(e9_11 PUBLIC e8_04 e9_10)`（E8-04 位於 `engine/script/`，E7-12 /
    E7-01 經 e9_10 傳遞，E9-01 / E9-02 / E5-08 經 e9_10 → e9_07 傳遞）；契約測試
    `tests/e9/test_e9_11.cpp` 註冊為 CTest `e9_11`。
    **不修改 E8-04**（`engine/script/module_loader.{hpp,cpp}` 一行未動）：只呼叫其公開介面
    `provide_capability` / `grant_permission`。
- 對外介面一句話：把「**誰在什麼時候對哪個套件的哪個權限做了什麼決定**」變成活過重啟的紀錄，
  再**有損投影**成 E8-04 載入閘控所吃的兩態 `HostEnvironment`——投影的方向是唯一正確的方向
  （未決與已拒絕**都不授予**，載入時回 `MissingPermission` 且 `missing` 附缺項），
  **嚴禁**把未決當成預設授予（樂觀預設 = 方向相反的同一個靜默降級）。投影有損但資訊不丟：
  被扣住的原因由 `PermissionGate` 分成 `undecided` / `denied` 兩個清單回報。
- 平台中立：無 `#ifdef`、無平台分支、無系統呼叫、無真實檔案 I/O、無 GUI 後端；
  持久化走 E9-10 的可注入抽象後端（相位 1 實作為記憶體替身），換平台一行不動，
  相位 2 只需換上 `InstallStorage` 的真實磁碟實作（E9-10 與本單元共用同一個）。
- 相關 NFR：
  - NFR-02：API 面不出現絕對座標欄位與數字 z-order（本單元只承載權限決策）。
  - NFR-04：空 id、未決被寫成紀錄、文字損毀（附**行號**）、根節點非 Map、`decisions` 非清單、
    缺必要欄位、欄位型別不符、無法辨識的 `decision` 字面值、文件內重複的 (套件, 權限)、
    空 slot 名 —— 一律 `throw std::runtime_error`，不靜默失敗。特別是**後端有內容但損毀時
    建構子拋錯**，絕不靜默當成空帳本（那會把所有「已拒絕」悄悄變回「未決」，
    下一次安裝流程就會重新詢問已被拒絕過的權限）。
  - NFR-03 不適用：本單元不含能力閘控呼叫（`has_capability` 的**供給端**資料由呼叫端傳入，
    本單元不自行呼叫可能不存在的平台能力），無 `has()` 降級路徑需求。
