## 鎖定 = 停用拖曳，語意在一處轉換

選單問使用者的是「要不要**鎖住**」，後端問的是「能不能**拖**」——兩者相反。
轉換只發生在 `kCmdToggleLock` 的處理器裡（`set_draggable(id, !locked)`），
其餘地方不必反覆推理哪個是哪個。

## UI 狀態檔

`%LOCALAPPDATA%\desktop-shell\ui-state.conf`，**沿用 E7-01 宣告式格式**（不發明新格式）：

```
format_version: 1.0
widget.controls:
  topmost: true
  passthrough: false
  locked: false
```

**與位置檔分開存**：`positions.conf` 的內容與格式由 **E1-08 擁有**
（`serialize_positions` / `load_positions` 是它的 API）。UI 開關是 host 層的概念，
塞進去會讓 host 對一個上游單元的檔案格式產生隱性依賴。

還原失敗（無檔 / 壞檔 / 型別錯）一律沿用預設值，**全有或全無**，與 E1-08 同語意。

## 為什麼一定要持久化

**一個每次啟動都自己解開的「鎖定」等於沒有鎖。** 三個開關都存，不只鎖定。

## `read_text_file` 去 UTF-8 BOM

設定檔是使用者會拿記事本改的東西，而許多 Windows 編輯器預設寫 BOM。
BOM 會讓 E7-01 的第一行變成 `﻿ormat_version:`，解析失敗 → 設定被**靜默**丟棄、退回預設值。
使用者只會看到「我的鎖定又自己解開了」，完全查不到原因。

修在 `read_text_file` 一處，**同時涵蓋 UI 狀態檔與位置檔**（兩者都經由它讀取）。
屬 K-001 / K-004 的字集家族問題。

## 主迴圈的抽訊息節奏

`host_main` 的等待改為「每 15ms 抽一次訊息，累計到 250ms 才進下一幀」。
原本直接 `Sleep(250)` 會讓視窗在那段時間**完全不回應**——系統的拖曳移動迴圈是在
`DispatchMessage` 裡跑的。取樣間隔必須是 250ms（`GetSystemTimes` 是差分式，見 K-002），
但抽訊息不需要跟著慢；兩者本來就是不同節奏，先前只是恰好共用同一個 `Sleep`。
