## 一份契約，多個註冊點

契約標頭只依賴 E1-24 宣告的 `KernelBackend` 介面。每個後端各自提供一個 factory：

| 後端 | 註冊點 | 建置條件 | ctest 名稱 |
|---|---|---|---|
| null | `tests/contract/test_contract_backend.cpp` | 所有平台 | `contract_backend` |
| win32 | `tests/e1/test_contract_win32.cpp` | `if(WIN32)` | `contract_win32` |

**win32 的註冊刻意不放在 `tests/contract/`**：本目錄的目標在 ubuntu CI 也要建得起來，
而 win32 後端只能在 Windows 建。把註冊放在該後端自己的平台閘目標下，
契約本體就能維持平台中立（`backend_guard` G1b 會掃本目錄的前處理器指令行）。

這就是 PHASE-PLAN 說的「契約測試不改一行拿去跑新後端」的落地方式——
新增後端時，契約標頭一個字都不用動。

## 16 條契約涵蓋什麼

具名（`name()` 穩定非空）· 能力查詢一致性與保守性（NFR-03，含 init 前查詢安全）·
生命週期狀態轉移與冪等（含未 init 即 shutdown）· surface 建立 / 銷毀往返 ·
無效輸入（空 id / 重複 id）結構化拒絕 · **未知 id 的每一個操作都安全** ·
可見性隨 show / hide 改變 · 四參數 profile 往返 · frame 括號配對 ·
輸入策略可切換且反映於 profile · `poll_input` 事件目標必為已知具名 surface ·
shutdown 釋放所有 surface · **多 surface 互相獨立**。

最後一條特別重要：真實後端最容易在此寫錯（共用狀態、錯用第一筆記錄、把 HWND 表寫成單例）。

## ⚠ 刻意不在共用契約裡的一條：`create_surface` 是否需要先 `init()`

null 與 win32 對此**行為不一致**（見知識庫 **K-007**）。分歧由兩邊各自的測試釘住：
`tests/e1/test_backend_win32.cpp` 的 `CreateSurfaceRequiresInit` 與
`tests/e1/test_backend_null.cpp` 的 `CreateSurfaceCurrentlyDoesNotRequireInit`。
對齊之後應刪除那兩條並把前置條件放回本契約——`kernel_backend_contract.hpp`
內已標註確切位置與理由。

## 修復前的樣貌（K-003，供對照）

原本契約組**自帶**一套 `ds::kernel::contract::KernelBackend` 介面與一個 `StubBackend`，
與真實後端實作的 `ds::kernel::KernelBackend` 是**兩個不相容的型別**
（數字 handle vs 具名 `SurfaceId`、`Status` 三態 vs `bool`、有無 frame / input）。
契約組**刻意不 link 任何真實後端**以「維持 E1-25 與 E1-24 的單元獨立」。

結果：它從未驗證過任何真實後端，連 null 都沒有。
`kernel_backend.hpp` 與 `stub_backend.hpp` 已於 `CHG-20260803-10` 移除，
`units.json` 的 E1-25 `depends_on` 補上 E1-24。

**獨立性是手段，不是目的。**
