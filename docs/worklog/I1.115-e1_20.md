## 我要做什麼（動工前計畫）

相位 1（Mac / null 期，platform 尤嚴）：只寫**平台中立介面 + 事件驅動復原邏輯 + 契約測試**，
**絕不**接真實電源 API（無 IOKit / IORegisterForSystemPower / SetThreadExecutionState /
cocoa / `#ifdef`），**不建 `src/kernel/backend/win32|cocoa/`**。以**已合併的 E1-01
`LayerStack`**（具名圖層指派狀態）+ **可注入的 E5-08 `SystemEventSource`**（`SystemSleep` /
`SystemWake`）實作純復原邏輯，狀態全存記憶體。參考 E1-19 顯示器熱插拔復原的事件驅動範式
（訂閱 / 快照 / 復原三段式）。

設計（C++17，`namespace ds::kernel`，依 kernel platform 慣例）：

- `SleepWakeRecovery`：非樣板（相較 E1-19 的 `LayoutRecoveryManager<Layout>`，本單元直接
  操作 E1-01 既有的具名圖層型別，不需再引入泛型佈局）。建構時訂閱事件源；`SystemSleep`
  觸發時走訪 `LayerStack::stacking_order()` 為每個已指派 surface 拍「具名圖層 + 可見性」
  快照（可見性經可選注入的 `VisibilityProvider`，無 provider 保守視為可見）；`SystemWake`
  觸發時以 `LayerStack::assign()` 逐一重建指派，並經可選 `on_wake` 回呼通知消費者恢復
  可見性。額外設計 `ResourceValidator` / `on_invalidated`：喚醒當下判定已失效的資源不重建
  指派，改通知消費者處理殘留狀態（覆蓋「處理喚醒後可能失效的資源」這條規格）。

## 關鍵設計決策（為何這樣切）

- **快照即取代**：每輪 `SystemSleep` 都是全新快照（不與前一輪合併），語意對應「這一輪
  睡眠前的狀態即是這一輪喚醒要還原的目標」，避免跨輪快照疊加造成語意混淆。
- **可見性快照於睡眠當下拍板、喚醒時原樣回放**：`on_wake` 回呼帶的是**睡眠當下**查得的
  可見性，而非喚醒當下重新查詢——這是本單元的核心語意（「睡眠前保存...喚醒後還原」），
  已用專門測試（`VisibilityRecoveredViaCallbackReflectsSleepTimeSnapshot`）驗證：睡眠後、
  喚醒前刻意改變外部可見性狀態，確認回呼仍回報睡眠當下的舊值。
- **重建指派委由 `LayerStack::assign()`**：不在本單元重複實作 NFR-03 閘控邏輯，而是直接
  呼叫上游既有、已閘控的 `assign()`；能力不可用時該筆保守略過、不改動任何狀態、絕不崩潰，
  復原邏輯與能力閘控關注點分離。
- **失效資源處理**：`ResourceValidator` + `on_invalidated` 讓消費者可以在喚醒當下判斷某
  surface 底層資源是否還存在（如視窗控制代碼已隨睡眠週期失效），本單元不擅自臆測，缺省
  一律保守視為有效（不主動丟棄任何快照項目）。
- **不引入座標 / 事件源與堆疊皆注入**：與 E1-01 / E5-08 一致的 NFR-02 / 相位 1 紀律；
  `LayerStack&` 與 `SystemEventSource&` 皆為呼叫端既有實例的非擁有引用，測試以
  `NullSystemEventSource::inject()` 手動注入事件驅動全流程。
