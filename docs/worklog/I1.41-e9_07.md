## 我要做什麼（動工前）

把「拖放一個套件來源 → 安裝」的流程模型化：接收攜帶套件來源參照的拖放事件 → 解析來源 →
以 E9-01 解析/驗證為套件 → 登錄到記憶體安裝目標，逐階段回報、失敗明確報錯。相位 1 平台中立：
不接真實 OS 拖放/檔案系統，來源為可注入抽象、目標為記憶體登錄。命名空間與 E9-01 一致（`ds::package`）。

## 關鍵設計決定

- **E5-08 實際整合而非空連結**：E5-08 的 `SystemEvent` 刻意為純資料（僅 type + detail），無法直接
  攜帶套件來源物件。因此：(1) `DropEvent` 沿用 E5-08「純資料、平台中立」的事件風格並以
  `const InstallSource*` 攜帶來源參照；(2) `DropInstaller` 於建構時**訂閱** E5-08 `SystemEventSource`，
  以系統事件維護「安裝閘門」——`SessionLocked`/`SystemSleep` 關閉、`SessionUnlocked`/`SystemWake`
  開啟；閘門關閉時拒絕拖放安裝（session 不在場/睡眠時不安裝，屬合理安全姿態）。此路徑實際呼叫
  E5-08 的分派實作（`system_event.cpp`），故連結為真、本機驗證亦需連上游 .cpp。
- **不重造格式**：解析/驗證一律走 E9-01（`parse_package` + `validate_package`）；不相容套件由
  E9-02 的格式相容性檢查於 Parsed 階段報錯。
- **生命週期可回報且失敗不靜默**：`InstallStage` Received→Resolved→Parsed→Validated→Registered，
  逐階段經 `InstallLifecycleListener` 回報；`InstallResult` 於失敗時指出 stage 與原因。
- **重複安裝**：`InstallRegistry` 以 manifest.name 為鍵、不覆寫；重複拖放於 Registered 階段明確報錯。
