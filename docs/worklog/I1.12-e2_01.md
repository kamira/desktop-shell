## 我要做什麼（動工前計畫）

擴充點 1 的契約，承重 27x —— 契約優先於功能。目標是把「名稱/值/單位/範圍/歷史/可列舉實例」
六要素定成最小且穩定的 API，讓約 25 個 sysinfo 提供者與眾多 widget 只依賴介面、不依賴任何
具體感測器。

- 契約分兩層：抽象介面（`Metric`/`MetricInstance`/`MetricProvider`/`MetricRegistry`）+ 記憶體內
  實作（`InMemory*`）供相位 1 假感測器與測試。
- 值型別：`MetricValue`（數值 + 可選文字 + valid）、`MetricRange`（可無界 + 正規化）、
  `MetricHistory`（固定容量環狀）。
- engine 層純邏輯：無 `#ifdef` / win32 / cocoa / 系統呼叫，可完全單元測試（塞假指標）。

## 設計決策要點

- **Metric 用抽象介面而非純資料**：真實感測器與假感測器更新值的方式不同（前者讀硬體、
  後者存值），介面讓提供者自由實作 —— 這正是「消費者不依賴具體感測器」的本質。
- **實例(instance) 為第一級概念**：單值指標恰一個實例、每核心 CPU / 每顆磁碟多個。掛件
  綁定到「一個實例」讀 value+history。避免「metric 直接帶一個值」在多實例時破裂。
- **範圍可無界 + normalized()**：長條 / 直方圖需要把任意指標正規化成比例，卻不能認識感測器。
  有界才可正規化，無界回 nullopt 讓消費者改用其他呈現。
- **重複 id 保守拒絕**（與 E1-21 能力矩陣「後定義者為準」相反）：兩個感測器爭同一 id 是 bug，
  不該靜默勝出；註冊回 false 讓錯誤浮現。
- **未知指標保守**：`get()` 回 nullptr、`contains()`/`unregister` 回 false，不擲例外，呼叫端安全。
