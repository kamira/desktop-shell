## 我要做什麼（動工前計畫）

相位 1（Mac / null 期）：只寫**平台中立介面 + null 後端（純記憶體 map 模擬）+ 契約測試**，
**絕不呼叫真實 OS 系統設定 API**，**不得**出現 `#ifdef` / win32 / cocoa / `defaults` /
NSUserDefaults 等。**消費 E6-01 命令匯流排契約、不自造匯流排或值型別**，範式對齊已合併的
E3-05（注入式後端 + null 樣式）。

設計（C++17，`namespace ds::actuators`，與 e3_05 一致）：

- 每個具名旗標四動詞命令：`flag.<name>.on` / `.off` / `.toggle` / `.status`。
- `FlagVerb` + `flag_verb_suffix` + `flag_command_id`：組裝穩定可讀命令 id。
- `is_valid_flag_key`：旗標鍵驗證（非空、僅 `[a-z0-9_]`，排除 `.` 命令分隔符），致動器層
  唯一的合法化點。
- `SystemFlagBackend` 抽象後端（`set(flag,bool)` / `get(flag)`，字串鍵）+ `NullSystemFlagBackend`
  （純記憶體 map、未設定視為關、初值可注入、`has`/`size` 內省）。
- `SystemFlagActuator`：`add_flag`（驗證 + 去重登記）、`register_on` / `unregister_from`
  （回滾語意）、四個處理器（未登記 / 無後端以 `has_flag()` 保護回 Failed）、`current` /
  `flag_names` 內省。

## 關鍵設計取捨

- **每旗標四命令、旗標鍵烘焙進命令 id**：命令 id `flag.<name>.<verb>` 直接把旗標鍵編入，
  handler 以 lambda 捕捉旗標鍵 + 動詞，呼叫端不需傳參數。因 E6-01 匯流排無萬用字元分派，
  未登記旗標的命令自然從未掛上 → dispatch 回 NotFound，即「未註冊旗標鍵報錯」的第一道防線。
- **旗標鍵驗證集中在致動器層**：`is_valid_flag_key` 排除點號，避免旗標鍵破壞
  `flag.<name>.<verb>` 的可解析性；驗證在 `add_flag` 一處完成，後端契約可信任傳入鍵已合法。
- **冪等與自逆語意**：on/off 為冪等（重複設同值不變），toggle 為其自身之逆（切換兩次回原態），
  status 唯讀不改狀態——符合系統開關直覺，且可完全單元測試。
- **未登記旗標的第二道防線**：直接呼叫處理器（不經匯流排）時以 `has_flag()` 保護，未登記
  旗標鍵回 Failed（不崩潰、不改後端狀態），與 E3-05 的 no-backend / 缺參數保護同構。
- **版本標記命名**：`ds::actuators` 命名空間已有其他致動器的版本函式；本單元用
  `system_flag_contract_version()` 前綴避免符號衝突（多致動器可能同時連入同一 target）。
- **成功結果回操作後布林狀態**：所有成功 CommandResult 的 value 皆為操作後旗標狀態（bool），
  訊息帶 `flag=on/off`，供呼叫端 / 測試一致驗證。
