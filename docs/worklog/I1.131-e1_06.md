## 我要做什麼（動工前）

E1-06 要「確保命中層序與繪製層序一致」——給定一組具名 surface 的**繪製順序**，命中測試依
**繪製反序**（最上層先）判定，保證視覺最上者即互動最上者。底層幾何 / alpha 判定用 E1-04
既有的 `HitTester::hit_test_alpha`，本單元不重新實作任何幾何邏輯，只加一層「依繪製順序決定
問誰、以什麼順序問」的薄封裝。

## 關鍵設計判斷

1. **「繪製順序」如何在 NFR-02 下表達**：繪製順序本質是一個順序關係，但 NFR-02 禁止數字
   z-order。解法：用 `std::vector<HitSurface>` 的**陣列宣告順序**直接表達繪製順序（索引 0 =
   最先繪製 / 最底層，末端 = 最後繪製 / 最上層），不引入任何數字索引當作對外 API 的一部分
   （`size()` 只回報數量，不當 z 用）。與 E1-01/E1-04「具名 + 宣告順序決定優先」的既有慣例
   一致。

2. **命中反序判定，且要與 E1-04 語意相容**：`hit_topmost` 從陣列末端往前走訪（最後繪製 / 視覺
   最上層先檢查），逐一呼叫 `HitTester::hit_test_alpha`；反序中第一個命中者即結果，且不因
   已找到命中就提前跳出——要繼續走訪剩餘（較底層）surface 以偵測是否有無效形狀 / 座標，
   語意與 E1-04 `topmost_hit`（掃描全部、任一無效即整體 `Invalid`）一致，避免「排序不同 →
   錯誤偵測行為也不同」的不一致。

3. **與具名圖層 `SurfaceLayer` 的關係**：`HitSurface.layer` 欄位保留（E1-04 的 `hit_test_alpha`
   本身不看 layer，只有 E1-04 自己的 `topmost_hit` 才用 layer rank 排序）；E1-06 刻意**不**
   額外讀取 `SurfaceLayer` 來重新排序——排序依據只有呼叫端給的繪製順序本身。專門寫了一個
   測試（`PaintOrderRulesEvenWhenNamedLayerRankDisagrees`）驗證：即使兩個 surface 的具名圖層
   rank 與繪製順序相反，命中結果仍完全依繪製順序決定，避免「兩套排序邏輯打架」的混淆。

4. **與 E1-04 `topmost_hit` 的一致性**：當呼叫端把繪製順序組成得恰好等於「具名圖層語意序
   （Wallpaper→BelowNormal→Normal→Overlay→Topmost）+ 各層內宣告順序」時，`PaintHitOrder::
   hit_topmost` 與直接呼叫 `HitTester::topmost_hit` 對同一組 surface / 同一點應給出相同命中者
   ——寫了測試 `ConsistencyWithE1_04` 直接比較兩者輸出鎖定這個不變式，確保「繪製層序」與
   「具名圖層層序」在此交集情境下不矛盾。

5. **結果型別與錯誤處理不重新發明**：直接複用 E1-04 的 `TopmostHit` / `HitStatus`，不新增
   平行的結果型別，降低下游（可能同時用到兩個單元）的適配成本；任一 surface 無效 → `Invalid`
   （報錯不靜默，沿用 E1-04 契約）。
