## 關鍵設計決策

- **目標存在性驗證優先於分派**：`send_to`/`send_to_group` 每個目標先經
  `ProfileInstanceRegistry::contains()`；未知目標回 `UnknownTarget` 且**不呼叫**
  `CommandBus::dispatch`——避免處理器誤以為目標存在而執行副作用。
- **`UnknownTarget` 與 `CommandNotFound` 分離**：前者是本單元自己判定（目標問題），
  後者是 `CommandBus::dispatch` 回的 `NotFound` 映射而來（命令問題）。兩者原因不同，
  混為一談會讓呼叫端難以判斷該修「哪個具名清單」還是「哪個命令註冊」。
- **目標以參數傳遞**：`CommandBus` 本身無「實例」概念，只認命令 id + 參數；本單元把
  目標 id 併入參數（鍵 `"target"`）交給 `dispatch`，處理器可用 `args.get_string("target")`
  取得本次呼叫的目標。這樣 E6-01 完全不需改動，兩單元組合而非耦合。
- **廣播依 registry.list() 序（建立序，穩定）**：決定性、可測試，不引入任何額外排序邏輯。
- **空目標集合合法**：broadcast 於空 registry / send_to_group 於空清單皆回空報告，
  `all_ok()==true`（沒有目標就沒有失敗者），不是錯誤路徑。
- **群組內互不連坐**：`send_to_group` 逐一分派，一個目標未知/失敗不影響其餘目標的判定。
