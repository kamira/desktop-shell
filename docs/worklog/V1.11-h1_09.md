## 2. 判定：**pass**

驗收標準五條逐條自行查證全部成立。被打回四次的第五條（「使用者可直接改動持久化狀態，
故錯誤不得讓佈局進入救不回來的狀態」）由統一判據收口：
**「這次寫入會不會刪掉目標現在有、而我手上沒有的內容？」**
＝ `baseline_`（上次看見目標時它的內容）＋ 提交前比一次。
F1 / F4 / F5 / F6 四個入口收進同一條述詞；四個入口共用同一串閘；
每種拒絕具名、目標位元組未動、逃生門一定先備份且備份永不覆寫既有名字。
我用上一輪推翻封閉性論證的同一套方法再追一次，**找不到第五個入口**；
`migrations_`（上一輪的 R17）確實被第 4 道閘涵蓋。

**第 1 點的裁決**：第 4 道閘擋「任何狀態差異」而非只擋「會損失內容的差異」——**選得對**。
窄述詞會讓「使用者在外部刪掉一個掛件」被下一次存檔悄悄復活，而刪除也是使用者對持久化
狀態的編輯；保守述詞的代價（修 typo 後要重新載入）有正確且被訊息寫明的逃生門。

**非阻擋缺陷 R18（新發現，修訂 5 引進的回歸）**：第 4 道閘比對兩個 `LayoutState` 時會
走到 E9-05 `normalized_properties()`，它對「`properties` 非 Map 非 Null」**會 throw**；
於是經 `reset()`（明文不消毒的後門）注入這種狀態後，`overwrite_check()` 與
`target_is_safe_to_overwrite()` 兩個公開 API 會丟例外，違反本單元「公開 API 一律不 throw」
的自我承諾。**不毀資料**（目標未動，`save` / `dry_run_save` 先走 `serialize_verified()`
仍回具名 `SerializeFailed`），倉庫內無產生途徑，故不阻擋——但**請人類核准者知悉**，
修法一行。另記 R19（狀態名實為「目標的 state 被改過」，只改註解不觸發）、
