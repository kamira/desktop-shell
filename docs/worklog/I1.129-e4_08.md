## 我要做什麼（動工前）

E4-08 是把多個已透過 E4-06 定址的具名 surface，依**具名圖層順序**合成為最終畫面**描述**
的 engine 層工具。先讀了 `docs/backlog/BUILD.md`（建置慣例），再讀上游
`modules/elements/e4_02/image_element.hpp`（圖片元件渲染描述模型，展示了「目標具名

確認設計方向：E4-08 不重建 surface 存在性判斷，而是在 `SurfaceSwitcher` 之上加一層

## 關鍵設計決策

- **`add_layer` 前置 `switcher.has(id)` 檢查**：把「以 E4-06 定址」具體落地為一個硬性前置
  條件——未經 `SurfaceSwitcher` 註冊的 surface 一律 `NotFound`，不加入。這樣 `compose()`
  產出的合成計畫永遠只描述「已知的」具名 surface，不會憑空引用不存在的東西。
- **混合模式防禦性驗證**：`BlendMode` 雖是 C++ enum class，只有四個具名值，但仍在
  `add_layer` 內用 `switch` 窮舉檢查是否為已知值，擋下呼叫端 `static_cast` 硬塞的非法值，
  對齊規格「無效...模式報錯不靜默」的要求，而非信任呼叫端一定傳合法列舉。
- **拒絕重複加入同一 surface**：同一 `surface_id` 只能是一層，重複加入回 `Invalid`（不
  覆蓋、不新增第二筆），理由與 E4-06 `register_surface` 拒絕重複註冊一致——避免同一
  surface 出現在多個位置造成順序歧義。
- **兩種錯誤語意分開**：`add_layer` 對「未經定址存在」用 `NotFound`、對「格式不合法」
  （空 id / 非有限透明度 / 未知混合模式 / 重複加入）用 `Invalid`；`remove_layer` 對「本
  合成器內未知的圖層」用 `NotFound`。與 E4-06 `SwitchStatus` 的 `Invalid`/`NotFound`
  分工慣例一致，比單一錯誤碼更精確。
- **`compose()` 是純查詢，不重新驗證**：驗證全部發生在 `add_layer`（寫入路徑），
  `compose()` 只是把已驗證過的 `layers_` 複本包成 `CompositionPlan` 回傳——與
  `SurfaceSwitcher::list()`、`ImageElement::render_model()` 同慣例：查詢端不做業務驗證。
- **層序純以加入 / 移除操作表達**：沒有任何「插入第 N 層」「取得第 N 層」的數字索引 API；
  要調整順序，呼叫端自行 `remove_layer` 後依新的具名順序重新 `add_layer`。這是本單元
  滿足 NFR-02（無數字 z-order）的核心設計選擇。
