## 我要做什麼（動工前計畫）

在 E2-01 統一指標介面之上，建立採集的資源治理層：控制指標多久採一次（分級）、多消費者
要同一指標時合併採集（除頻）。承重 20x，多個 sysinfo 提供者相依它，直接關係 NFR-01 idle 門檻。

- `SamplingTier`（high/normal/low/on-demand）+ `SamplingPolicy`（分級→間隔 tick 映射）。
- `SamplingScheduler`：邏輯 tick 排程器，`advance(now)` 回「此刻該採集的指標」；除頻合併
  同一指標的多筆需求，按最高需求頻率供給。
- 平台中立純邏輯：用邏輯 tick 不綁真實時鐘，可完全單元測試（注入時間、驗採集次數符合
  分級、驗多消費者除頻）。`target_link_libraries(e2_02 PUBLIC e2_01)`，沿用 `MetricId`。

## 設計決策要點

- **邏輯 tick 而非真實時鐘**：平台中立的關鍵。本層只認識「第幾 tick」，真實時鐘由呼叫端
  （未來採集迴圈）綁定 —— 讓排程可注入時間、完全可測。
- **除頻 = 取最高頻需求**：`higher_tier` 於同一指標所有存活需求中挑最高頻者為有效分級，
  `advance()` 對合併後指標只回一份。這是「一次採集供全體消費者」的本質。
- **不補採**（到期後 `next_due = now + 間隔`，非 `+=` 累加）：閒置久了醒來只採一份不爆量，
  直接護住 idle 門檻。若改成累加，跨越 N 個間隔就一次灌 N 份採集，正好違反 NFR-01。
- **提頻提前**：高頻消費者中途加入時把下次採集時機提前，不必等舊慢週期跑完。
- **撤銷降頻於下次採集後生效**：撤銷高頻需求後不硬改 next_due，讓其自然於下次到期後改以
  新（較慢）間隔續行 —— 邏輯簡單且決定性。
- **OnDemand 非週期**：`effective_interval` 回 nullopt，只有 `request_now` 能觸發一次。
  OnDemand 需求不壓制同指標的週期需求（有效分級仍取較高頻的週期者）。
- **時間單調**：`advance(now)` 對 `now < now()` 視為不推進，防時鐘倒退造成重複採集。
