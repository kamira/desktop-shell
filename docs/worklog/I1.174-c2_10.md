## 組裝設計

`ds::widgets::WebWidget`（`content/widgets/c2_10/web_widget.hpp/.cpp`）：

- 注入式相依（不擁有生命週期）：`KernelBackend&` + `LayerStack&`（透傳給內部自持的 C1-01
  `SkinProfile shell_`）+ `ProcessLauncher&` + `MessageChannel&`（透傳給內部自持的 E10-05
  `WidgetHost host_`）+ 選填 `AlphaSurfaceService*`（透傳給 `host_`）。
- widget id 即殼層的具名 `SurfaceId`；另衍生 `<id>.proc`（內容行程的具名 `WidgetId`）與
  `<id>.surface`（畫面 surface 的具名 `SurfaceId`，僅能力可用時才會實際建立）。
- **能力閘控（NFR-03）設計要點**：`surface_capable()`（`surface_service_ != nullptr &&
  surface_service_->supported()`）是所有「是否請求橋接」決策的**唯一**前置閘門——`load()`
  一律先查詢此函式才決定 `WidgetSpec::surface_id` 是否非空，**從不**盲目把 `surface_id`
  設好再呼叫 `WidgetHost::start()` 期待它自己回報 `SurfaceUnsupported`。因此「能力後端存在
  但不支援」與「完全未注入能力後端」兩種降級成因，在本單元皆走同一條優雅降級路徑（不橋接、
  仍正常啟動行程、內容仍正常經注入載入），以兩個獨立測試 fixture（`IncapableEnv` /
  `NoServiceEnv`）分別驗證。
- **狀態機**：`Idle`（未 configure）→ `Configured`（已設定 URL / reload 後等待重新 load）→
  `Loading`（墊片單次求值下為 load()/reload() 內部瞬態）→ `Loaded`（完整，含 surface）/
  `Degraded`（僅內容，無 surface）／`Failed`（無效內容注入 / host 啟動失敗）。
- **load 的「行程存活即不重啟」設計**：`load()` 只在 `!host_.is_alive()` 時才呼叫
  `WidgetHost::start()`；行程已存活時直接更新 `content_`（模擬同一頁面的內容重新整理 /
  多次注入，不當作換頁）。`reload()` 則明確走 `WidgetHost::restart()`（新 handle），語意
  上代表真正的「重新載入」，兩者刻意區分並各自可測（`process_handle()` 比對）。
- **configure 換 URL 的清理**：若換 URL 時行程仍在跑，先 `host_.stop()` 再套用新 URL，避免
  留下「行程仍指向舊 URL 但 widget 已認定新 URL」的不一致殘留狀態。
- **解構安全**：仿 C1-01 `SkinProfile` 慣例，解構子在行程仍存活時強制 `host_.stop()`。

無效操作一律明確回具名 `WebWidgetStatus`（Invalid / Unsupported / NotConfigured /
HostError），不靜默；`configure()` 失敗全有或全無（不改動既有狀態）。
