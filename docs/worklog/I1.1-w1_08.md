## 為什麼要拆兩層（純邏輯 / win32 呼叫）

本機是 Linux 容器、無 mingw、且 win32 目標被 `if(WIN32)` 排除 ——
**win32 那一層在本機連編譯器都碰不到**，唯一的正確性證據是 CI 的 `gate_windows`（MSVC）。
而本單元最容易出錯的部分（K-002 的「讀不到 ≠ 很閒」邊界、差分式 CPU% 的除數、
pid 重用、單一 pid 開不起來與整份列舉失敗的區分）**全都是純算術與政策判斷，不需要 win32**。

故照 H1-01 的先例（`CHG-20260803-05-h1_01`：版面計算抽成不碰 GDI 的純函式）把這些抽成
`ProcessDeltaTracker` + 自由函式，**在 ubuntu / 本機真的被建置與測試**。
win32 那層因此只剩「填好 `RawSnapshot` 的欄位」，薄到可以用肉眼審。

## 政策設計（K-002 的直接應用，每條都要有測試釘住）

`ProcessSample` 只有一個 `valid` 旗標，`ProcessInfo` 的五個欄位**沒有**per-field 無讀值表示法。
因此「某欄位讀不到」只能靠**不回報該筆 / 不回報整份**表達，絕不可以 `0.0` 或空清單充數。

| 情形 | 回傳 | 理由 |
|---|---|---|
| `EnumProcesses` 回 FALSE | `ProcessSample::unknown()` | 列舉失敗 ≠ 沒有行程 |
| 列舉成功但兩次取樣之間時間差為 0 | `unknown()` | K-002 第 1 層：差分式 API 必須真的經過時間 |
| 第一次 `sample()` | `unknown()`（只建立基準點） | K-002 的解法原文：首次呼叫只建立基準點 |
| 某個 pid 開不起來（受保護行程 / 剛結束） | **跳過該筆，整份仍 valid** | 這是**常態**，不該讓整份快照變成 unknown |
| 某個 pid 的五欄位有任一讀不到 | 同上（跳過該筆並計數） | 回報一筆欄位是猜的紀錄比不回報更糟 |
| 列舉成功但可用筆數為 0 | `unknown()` | 機器上至少有「我們自己」這個行程；0 筆必然是讀取側壞了，不是「沒有行程」 |
| 某 pid 本次首見（含 pid 重用，以行程建立時間判定） | 本輪跳過該筆，下一輪才回報 | 無基準點就算不出區間 CPU%；拿「開機至今平均」充數正是 K-002 附記的陷阱 |

CPU% = `100 * busy_delta / (wall_delta * processor_count)`，clamp 到 `[0,100]`（契約值域）。
狀態映射只產 `Running` / `Zombie`（已結束待回收）/ `Unknown`：win32 的**行程**層級沒有
`Sleeping` / `Stopped` 語意（那是執行緒層級），**刻意不假造**。

不靜默吞錯：`last_outcome()`（具名列舉）+ `last_error()`（人類可讀原因）+
`skipped_in_last_sample()` 計數，讓「為什麼這份是 unknown」永遠留得下來。

  但本單元的測試是以它**實作的契約**命名（`test_process_win32`），不是以單元代號命名，

### 2. 本機沒有任何方式驗證 win32 那一層

- **錯誤**：`ctest -N | grep -i win32` 在本機命中 0；既有的 `backend_win32` / `tray_win32`
  在本機完全看不到，新寫的 win32 碼也一樣無法建置。
- **根因**：開發容器是 Linux，repo 工具鏈無交叉編譯器，而 win32 單元的 CMakeLists 整段以
  `if(WIN32)` 包住（W1-01 的先例；不包守衛則 ubuntu 的 G3 必紅）。
- **解法**：把政策與換算（本單元最容易出錯的部分）抽成不碰 win32 的純邏輯層，由**不包守衛**
  的 `w1_08_policy` 目標建置 → 這一半在本機與 ubuntu G3 都真的被測試（30 案例 + 7 次負向
  測試）。win32 那一層另以臨時安裝的 mingw 做語法檢查（零輸出）作為**旁證**，
  並在 CHG 明寫它不等於 MSVC 驗證；真正的證據是 CI 的 `gate_windows`。
  mingw 工具鏈未寫進 repo 任何檔案。
