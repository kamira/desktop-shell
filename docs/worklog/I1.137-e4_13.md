## 我要做什麼（動工前）

E4-13 是把「文字流中內嵌非文字物件」（emoji / 小圖示 / 行內圖片）這個常見 UI 需求，變成一個
平台中立的排版工具：物件要佔一個排版位，跟著文字一起換行、對齊，而不是另外拼一份絕對座標。
先讀了 `docs/backlog/BUILD.md`（建置慣例），再讀上游 `engine/render/e4_01/text_layout.hpp`
（`TextLayout`：`FontMetrics` 度量注入介面、`LayoutConstraints` 換行/對齊約束、
`decode_utf8` UTF-8 解碼、貪婪詞界換行演算法）與 `modules/elements/e4_02/image_element.hpp`
（`ImageElement`：載入注入來源、產出 `ImageRenderModel` 顯示描述）。

確認設計方向：E4-01 的 `TextLayout` 本身只認識文字（`std::string`），不認識「內嵌物件」這種
概念，不能直接呼叫它排版混合內容；但它的換行演算法（貪婪詞界斷行）與資料結構（`FontMetrics`
度量注入、`LayoutConstraints` 約束）都值得重用。於是決定：把文字（拆成字符/空白/硬換行）與
內嵌物件攤平成同一個 token 序列，重寫一份**與 E4-01 邏輯等價、但泛化到混合 token** 的斷行
演算法——內嵌物件在斷行判斷上等價於「一個不可拆的字」，這樣物件自然能跟文字混排、換行、
對齊，且直接沿用 `ds::render::LayoutConstraints`/`FontMetrics`/`decode_utf8` 型別，不重造
一套約束或字型度量介面。內嵌物件的顯示描述（縮放模式/裁切/透明度/目標 surface）則直接
attach 上游 E4-02 `ImageElement::render_model()` 產出的 `ImageRenderModel`，本單元不重造
任何顯示屬性欄位。

## 關鍵設計決策

- **泛化 E4-01 的斷行演算法，而非呼叫它**：`TextLayout::layout(text, constraints)` 的簽名
  只接受 `std::string`，無法表達「這裡插入一個物件」。與其在文字流裡塞入特殊佔位字符（會
  污染 UTF-8 語意、也難以承載物件的 `ImageRenderModel`），選擇把「文字字符/空白/硬換行/
  內嵌物件」四種 token 攤平成一個序列，複製 E4-01 的貪婪詞界換行規則（同樣的空白 run
  暫存/落地邏輯、同樣的過寬溢出處理、同樣的省略號裁切演算法），只是操作對象從單純
  `CodePoint` 換成帶 `advance` 的泛型 token。這保留了「與 E4-01 換行結果完全一致」的行為
  （純文字輸入時，斷行點與 E4-01 逐字元比對會相同），同時讓物件能無縫參與換行判斷。
- **內嵌物件是「不可拆的一個字」**：換行時，內嵌物件與其緊鄰的文字字符（若中間無空白）會
  被視為同一個不可斷開的 run；只有空白/換行才是斷點。這正是規格「該物件佔一個排版位」的
  字面落地——物件不會被斷行演算法拆成一半留在上一行、一半跑到下一行。
- **排版槽尺寸與來源固有尺寸分離**：`add_inline_object(image, size)` 的 `size` 只是「這個
  物件在文字流中要佔多大」，跟 `image.source_dimensions`（來源圖片的固有像素尺寸）完全獨立
  ——一個 32x32 的來源圖可以在流裡顯示成 16x16 的小圖示，也可以是 64x64 的大貼圖。這給呼叫端
  更大彈性，且與 E4-02 `ImageElement` 的縮放模式（fill/fit/stretch/center/tile）語意不衝突
  （縮放模式描述「來源怎麼填進顯示框」，`size` 描述「顯示框本身多大」）。
- **省略號/裁切演算法完全泛型化，不特例處理物件**：裁切迴圈操作的是「行尾 token 的
  `advance`」，不管該 token 是文字字符還是內嵌物件都一視同仁地移除，直到省略字元放得下。這
  是把泛化做徹底的結果——不需要為「行尾恰好是物件」寫一份額外分支。
- **逐行有效行高，而非全域固定行高**：E4-01 對純文字排版用單一固定行高就夠了（字型度量
  一致）；但內嵌物件常見尺寸大於文字行高（圖示/貼圖），若強制每行同高，物件會溢出行框。故
  改為 `line_heights[li] = max(基礎行高, 本行內嵌物件最大 height)`，逐行可能不等高，`y` 累加
  也隨之調整（不再是簡單的 `行索引 × 固定行高`）。
- **`add_text`/`add_inline_object` 的錯誤處理分工**：`add_text` 對非法 UTF-8 直接重用 E4-01
  `decode_utf8` 的例外行為（`std::invalid_argument`），因為那是「結構性壞資料」；
  `add_inline_object` 對「無來源」「非法尺寸」回傳 `InlineFlowStatus::Invalid`（不擲例外），
  因為那是「業務規則不合法」，與 E4-02 `ImageElement` 對同類輸入的處理慣例一致。兩種錯誤
  類別分開處理，而非統一成單一機制，是刻意對齊各自上游單元既有的慣例。

## 錯誤紀錄（錯誤 + 根因 + 解法）

- 實作本身無編譯錯；一次自查修正：`add_inline_object` 最初的尺寸檢查只有
  `size.width <= 0.0 || size.height <= 0.0`，漏掉非有限值（`NaN`/`Inf`）。對照規格「無效...
  尺寸處理不靜默」與 E4-02 `ImageElement::set_crop`/`set_opacity` 對非有限值一律拒絕的一貫
  作法，在動筆寫測試前先補上 `std::isfinite` 檢查，避免非有限尺寸靜默流入排版產生 NaN 位置。
- 本地 gtest 墊片（scratchpad 共用 `gtest.h`）沒有 `EXPECT_NEAR`/`EXPECT_GT`/`EXPECT_LT`/
  `EXPECT_THROW`（測試需要驗證浮點相對位置與例外拋出）。根因：墊片是精簡版、非完整 gtest。
  解法：比照 E4-08 的既有作法，另建一份僅供本單元本機驗證用的墊片副本
  （`e4_13_shim/gtest/gtest.h`），補上這四個巨集，不改動其他單元仍在用的共用墊片。
