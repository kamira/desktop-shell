## 1. 我要做什麼

把「就地編輯」四條上游在 host 層裝配起來，並讓裝配後的狀態可存檔、可還原、可熱重載：

- **E7-14** 圖形化設定與就地編輯 → 欄位驗證 + `apply_edit` 寫回
- **E7-15** 拖放產生設定項 → `DropContent` → `ConfigItem` → 寫進元件 properties
- **E7-12** 設定值寫回 → `set_value` / `serialize`
- **E9-05** 佈局存檔與還原 → `LayoutState` / `LayoutStore`（**寫入端沿用它，不自造格式**）
- **E7-07** 熱重載 → `ReloadSource` / `HotReloader`（來源變更 → 重新載入 → 造型改變）
- **H1-06** 繪製層分派 → `ElementDraw` / `PaintBox` / `ElementRendererTable`（換 kind → 換畫法）

驗收標準那兩條端到端情境：
1. 拖動組件 → 存檔 → **重啟**（以「丟掉 assembly、用同一個 storage 重建一個」模擬）→ 位置還原
2. 換 kind → 熱重載 → 造型改變（以分派表記錄到的繪製指令序列斷言，不是看註解）

## 2. 設計決定（動工前先寫下，便於獨立驗收者逐項查證）

### 2.1 讀寫兩路不對稱 —— 刻意的

- **寫**：一律走 E9-05 `serialize_layout` / `LayoutStore::save`，格式單一事實來源在上游，
  本層不自造格式、不自己拼字串。`format_version` 由 E9-05 的 `kLayoutFormat{1,0}` 帶上。
- **讀**：**不**直接用 E9-05 `deserialize_layout`。理由是驗收標準最硬的那一條——
  使用者可以直接手改存檔，而 `deserialize_layout` 對「單一元件缺 id」這種局部損壞是
  `throw`，等於**一個壞元件炸掉整份佈局**，正是「救不回來」。
  本層改用**容忍式讀取**：同一個結構（`{format_version, elements:[{id,type,properties}]}`）、
  逐元件判定，壞的元件具名丟棄並計數，其餘照常還原。
- 兩路不得漂移 → 以測試釘住：合法輸入下，本層讀出的 `LayoutState` 必須與
  `ds::layout::deserialize_layout` **逐欄相等**。

### 2.2 `format_version` 的三種異常

`ds::format::parse()` 自己會擋版本（不相容一律 fail，含「比程式新」），但它只回一個
行號 0 的泛用訊息，分不出「太新 / 太舊 / 缺失」。本層在 parse 之前先**掃一次版本行**
（`peek_format_version`，純字串掃描、不解析內容）再分流：

| 情況 | 具名狀態 | 行為 |
|---|---|---|
| 缺 `format_version` | `MissingVersion` | 拒收。**不猜**版本（猜錯 = 默默改語意） |
| 版本無法解析 | `MalformedVersion` | 拒收 |
| 版本比程式新 | `VersionTooNew` | 拒收、保留現有佈局、**不寫回**（實作不降級） |
| 版本比程式舊 | 走 **E7-08** 遷移鏈 → `Migrated`；查無路徑 → `MigrationUnavailable` | 遷移成功才採用 |

舊版文件的取用細節（**已知取捨，寫進 CHG**）：E7-01 的 `parse()` 在版本不相容時直接拒收，
所以舊版文件連「讀成 Value 樹」都做不到。本層的作法是：**僅**把版本行換成本實作支援的
版本以通過 E7-01 的版本閘，取得結構後，**把原始宣告版本**交給 E7-08 `MigrationRegistry`
驅動遷移鏈。語意轉換全部由註冊的遷移步驟負責，本層一行都不猜 —— 沒有註冊步驟就是
`MigrationUnavailable`，不會「反正結構看起來一樣就收下」。

### 2.3 DPI 語意

存檔裡的 `x / y / width / height` 一律是**邏輯像素**（與 H1-07 `ComponentPlacement` 同慣例）。
裝置像素只在 `resolve_placement(placement, dpi_scale)` 這一步產生，交出 H1-06 的 `PaintBox`
（半開區間），**不另造第二個像素矩形型別**。日後要改這條語意必須走 E7-08 遷移並升版本，
不得默默改。

### 2.4 K-016 / K-002 / sanitizer

存檔是使用者可手改的，`NaN` / `Infinity` / `1e400` / 負尺寸 / 空字串都是現實輸入。

- 任何「這個值可不可用」的判定一律**明寫 `std::isfinite(x)`**，不靠某個比較剛好擋住
  （K-016：`!=` 對 NaN 回 **true**，正向比較的口訣在 `!=` 上反過來）。
- 夾值函式先 `isfinite` 再夾，NaN **不得原封通過**（K-002）。
- `double → int` 之前先 `isfinite` + 夾到遠小於 `int` 值域的範圍再 `lround`
  （`-fsanitize=float-cast-overflow` 會讓一次溢位轉換當場 FAILED，不是印訊息）。

### 2.5 失敗 = 具名、可觀測的降級（照 H1-08 的做法）

`IntakeStatus` / `EditStatus` / `SaveStatus` 三組具名 enum ＋ `EditStats` 計數器 ＋
`last_intake_status()` / `last_edit_status()` / `last_message()`。公開 API **一律不 throw**
（host 層把例外丟進 UI 迴圈等於整個桌面掛掉）。

「救不回來」的三道防線：
1. 載入失敗 → **保留現有記憶體佈局**（HotReloader 的「失敗保舊值」同一條原則）
2. 載入失敗 → **不把壞狀態寫回** storage，原文原封不動留著給使用者手改
3. `save()` 先序列化、再**自我往返驗證**（序列化 → 重新讀入 → 逐欄比對），
   驗證過了才 `put()` —— 提交點只有一個，要嘛整份已驗證的文字落地、要嘛什麼都沒變

## 3. 錯誤記錄（錯誤 + 根因 + 解法）

> 動工中遇到的錯誤往下追加。機密只記位置不記值。

### E1 — E7-14 `apply_edit` 對「空路徑」的行為與我的預期不同

- **錯誤**：`EditorModelBridge` 第一版斷言 `edit_property(id, "", …)` 回 `BadPath`，實際回
  `RejectedByModel`。
- **根因**：E7-12 `parse_path("")` 是**合法**的（空路徑 = 指向根本身），所以它不是語法錯；
  走到 E7-14 時變成「拿一個 Number 去取代整個 `properties` Map」→ 型別驗證不過。
  我把「空字串」直覺當成語法錯，但上游的語法裡它有明確語意。
- **解法**：斷言改為 `RejectedByModel`（並在測試裡寫明為什麼），另外用真的語法錯的路徑
  `"bad["`（未閉合的 `[`）補一條 `BadPath`。兩種失敗都被釘住，而不是混成一種。

### E2 — 測試裡的遷移 lambda 讀一個正在被整個指派掉的 `Value`（K-013 第三代）

- **錯誤**：第一版的 0.9 → 1.0 遷移 lambda 這樣寫：
  ```cpp
  const Value* elems = out.find("elements");
  for (i …) {
      const Value& item = out.at("elements").as_list()[i];
      const Value* px = item.find("properties")->find("pos_x");
      out = ds::format::set_value(out, …);   // ← out 被整個換掉
      …再用 px / elems…                      // ← 全部懸空
  }
  ```
- **根因**：`set_value` 是純函式、回傳**新的樹**，所以 `out = set_value(out, …)` 會把 `out`
  原本持有的整棵樹換掉；任何指進去的指標 / 參考當場懸空。K-013 記的是「const 參考綁臨時
  物件」，這是同一族的另一種形狀：**參考指向的物件還活著，但它的內容被整個換掉了**。
  警告旗標一樣零診斷。
- **解法**：**從不變的 `root`（函式參數）讀、只往 `out` 寫**。寫在程式碼註解裡，免得下一個
  人又改回去。寫的時候就發現了（沒有進到建置），但同一個檔案裡的另一個錯是 ASan 抓的，
  見 E3。

### E3 — 我自己的測試字串長度手數錯 → ASan 報 global-buffer-overflow

- **錯誤**：`std::string("\x01\x02\xff\xfe nonsense \x00 bytes", 26)`，字面值實際只有 22 個
  位元組（含結尾 NUL）。普通建置下 31 個測試全綠；ASan 建置下當場
  `global-buffer-overflow … in memcpy`，整個測試程序 ABORT。
- **根因**：要在字串裡嵌入 `\0` 就必須明寫長度，而我用手數的。多算 5 個位元組，就讀過了
  字面值的尾端。普通建置讀到的是相鄰的常量資料，不會有任何徵兆。
- **解法**：把字面值放進具名的 `static const char[]`，長度用 `sizeof(kGarbage) - 1`。
  **順帶的證據**：`gate_sanitizers` 不是裝飾品，它在這一輪真的抓到了普通建置看不見的東西。

### E4 — （上游，未修）`ds::format::parse()` 會丟 `std::out_of_range`

- **錯誤**：含 `x: 1e400` 的存檔餵進 `ingest_layout_text`，預期 `Repaired`，實得 `Malformed`。
  追下去發現是 `parse()` **丟例外**，被我在 `parse()` 外圍的 try/catch 接住了。
- **根因**：兩處用了會丟例外的標準函式，而 `parse()` 的契約是「回傳帶行號的 `ParseError`」：
  - `engine/format/document.cpp` `numeric_token()` 的 `std::stod` —— 值超出 `double` 值域
  - `engine/format/document.cpp` `parse_version()` 的 `std::stoi` —— 版本號位數放不進 `int`
  實測（g++ 13.3）：兩者分別丟 `St12out_of_range: stod` / `St12out_of_range: stoi`。
  兩條都是「使用者在設定檔裡手打一個很大的數」就走得到的路徑；任何沒有 try/catch 的
  呼叫端會在那一刻整個行程結束 —— 對本專案就是桌面不見了。
- **解法（本層的圍堵，不是修復）**：
  1. `peek_format_version` **不用 `std::stoi`**，自行帶溢位檢查累加；位數爆掉 →
     `MalformedVersion`，那種文字因此根本不會被餵給 `parse()`。
  2. 所有 `parse()` 呼叫包 try/catch，例外轉成具名的 `IntakeStatus::Malformed`。
  3. 兩條路徑各補一支回歸測試。
  **真正的修法在 `engine/format/`（不在本單元鎖定範圍）**，已在 CHG 與回報中寫明，請 I1
  決定是否收進知識庫並另開單元。

### E5 — 第一輪突變驗證有一條存活（M13）

- **錯誤**：拿掉 `restamp_format_version` 裡的 `break`（變成換掉每一個根層版本行），
  32 支測試全綠 —— 那條 `break` 的行為當時沒有任何斷言保護。
- **根因**：測試資料裡只有一個根層 `format_version`，所以有沒有 `break` 完全等價。
  斷言寫了，但**資料沒有觸及那個分支**。
- **解法**：補 `VersionGate.RestampStopsAtTheFirstVersionLine`（兩個根層版本行 + 斷言
  只換第一個 + 該文件讀進來是具名的 `Malformed`）。重跑後 14/14 全部殺死、0 存活、0 作廢。
