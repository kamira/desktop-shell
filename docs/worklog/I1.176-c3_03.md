## 組裝設計決策

- **外觀組的宣告式定義即 E9-01 套件描述文字**：不另造一套「外觀清單」文字格式。內容清單中
  `kind == "look"` 的項目即一個外觀；其餘 kind（如 `asset`）本單元不解讀，原樣保留在
  `package()` 供呼叫端內省——外觀組可以和其他資源類別共用同一份套件描述，本單元只挑自己
  認得的部分。
- **互動區域不進套件文字格式**：E9-01 內容清單是純文字 `kind: path`，無法表達幾何形狀。
  故互動區域維持「呼叫端以 `NamedRegionMap::add_region()` 建好、再以 `set_regions(look,
  regions)` 指派給某個已註冊外觀」的程式化路徑（與 C1-02 `set_regions()` 同慣例），未知
  look 一律回 false、不新增游離區域。
- **`apply_to()` 對表情切換採「儘力而為」**：外觀組管理「有哪些外觀 + 各外觀互動區域」，
  不管理表情圖片本身（那是 C1-02 `add_expression()` 的職責，屬立繪 profile 自己的
  write_scope）。因此 `apply_to()` 只在目標 profile **已經**註冊同名具名表情時才切換，
  未註冊時略過表情切換但仍套用互動區域，回傳 `Ok`（不因「外觀組定義了一個立繪尚無對應
  表情圖片的外觀」這個合法情境而整體失敗）。互動區域缺失、無目前外觀、profile 未載入
  三種前置條件則各自回具名的失敗結果（`NoRegions` / `NoCurrentLook` /
  `ProfileNotLoaded`），且皆不觸碰 profile 狀態（全有或全無）。
- **`switch_look` 直接回傳 E4-06 `SwitchStatus`**：純委派、不重新包一層自有列舉，理由與
  C1-02 對 E1-08 `DragStatus` 的處理同——保留上游精確碼（`Ok` / `NotFound`），避免資訊
  折損。`load_appearance_set` 則回自有的 `AppearanceStatus`（`Ok` / `Invalid` /
  `AlreadyLoaded`），因其語意（套件解析 + 批次註冊）是本單元自己的組裝步驟，非單純委派。
