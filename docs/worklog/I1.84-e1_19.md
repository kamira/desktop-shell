## 我要做什麼（動工前計畫）

相位 1（Mac / null 期，platform 尤嚴）：只寫**平台中立介面 + 注入式來源 + 契約測試**，
**絕不**接真實顯示器 API（無 CGDisplay / EnumDisplayMonitors / cocoa / `#ifdef`），
**不建 `src/kernel/backend/win32|cocoa/`**。以 **E1-18 的顯示器拓撲抽象**（`ScreenRegistry` /
`PerScreen<T>`）+ **可注入的 E5-08 事件源**（`SystemEventSource` / `DisplayChanged`）實作
純復原邏輯，狀態全存記憶體。

設計（C++17，`namespace ds::kernel`，依 kernel platform 慣例）：

- `topology_key(ScreenRegistry)`：由具名 ScreenId 排序串接導出的拓撲簽章，識別「顯示器組態」。
  排序 → 與後端列舉順序無關，故拓撲恢復（拔除後重接同一組螢幕）可被辨識。純具名（NFR-02）。
- `LayoutRecoveryManager<Layout>` 樣板：Layout 佈局表示由消費者提供（本單元不引入座標型別，
  沿用 E1-18 `PerScreen<T>` 泛型哲學）。訂閱 E5-08、僅 DisplayChanged 觸發、注入式 TopologyProvider
  取當前拓撲、以「拓撲簽章 → PerScreen<Layout>」多組態記憶、有記錄回記錄否則回預設。

## 關鍵設計決策（為何這樣切）

- **拓撲 = 一組具名螢幕**，以排序串接的簽章當「組態鍵」。這自然滿足：復原往返（切走再切回同
  一組螢幕即命中同一簽章）、新顯示器（新組態無記錄 → 預設）、拔除（螢幕不在當前拓撲，但其
  在原組態的記錄仍在，重接即還原）、多組態記憶（不同簽章各自獨立）。
- **事件源與拓撲皆注入**：相位 1 由測試以 `NullSystemEventSource::inject(DisplayChanged)` +
  `TopologyProvider` lambda 驅動；相位 2 換真實後端時，介面與復原語意一行不動，後端只需在 OS
  顯示器事件到達時呼叫既有 inject 路徑並讓 provider 回報實際列舉。本單元**永不查 OS**。
- **保守（NFR-03）**：`layout_for` 以 `PerScreen::find` 保護，未知 / 無記錄一律回預設、不崩。
- **不引入座標（NFR-02）**：佈局載荷泛型化留給消費者；本單元自身零座標、零數字 z-order。
