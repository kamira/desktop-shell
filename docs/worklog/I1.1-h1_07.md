## 2. 反向斷言的判定規則（這一條最容易寫成空轉）

驗收標準：**E4 與 kernel 的公開介面不得出現任何像素型別**。

天真的 `grep -rnE '\bpixels?\b|_px\b|Pixel'` 會命中 `AlphaMode::PerPixel` /
`kPerPixelAlphaCapability` /「per-pixel alpha」等 —— 那些是**alpha 合成模式的名稱**
（逐像素 alpha 通道 vs 整體透明度），不是像素座標／尺寸型別。所以規則必須針對
**像素值的幾何型別**（座標／尺寸／偏移），而不是「pixel 這個字」。

本單元的判定由三條互補規則構成（三條都只掃**去註解、去字串字面值**後的原始碼）：

- **R1 型別名滲透**：host 像素層自有的像素幾何型別名（`PaintBox`（H1-06）、
  `PixelPoint` / `PixelSize` / `WidgetLayout` / `ResolvedComponent`（本單元）、
  以及 `RECT` / `POINT` 這類平台像素矩形）不得作為識別字出現在 E4 / kernel 標頭。
- **R2 像素單位識別字**：識別字同時含「像素單位詞」（px / pixel / pixels）**與**
  「幾何角色詞」（x / y / left / top / width / height / offset / rect / box / …）者 →
  命中。`PerPixel` 無幾何角色詞 → **不命中**；`kPerPixelAlphaCapability` 同理。
- **R3 整數型幾何欄位**：NFR-02 之下，E4 / kernel 的幾何一律是**比例值**（`float` /
  `double`）或**具名／索引值**；**整數型**的幾何欄位才是像素的形狀。故
  「宣告型別含整數型別 token（int / unsigned / long / short / size_t / intN_t…）
  且欄位名含幾何角色詞」者 → 命中。名稱自帶**非像素單位詞**（lines / ratio / fraction /
  index / count / rows / columns / chars / cells）者排除（`offset_lines` 是行數不是像素）；
  私有成員（尾端底線）排除（非公開介面）。

**R3 的實測基線不是零，必須誠實寫明**：現況恰好命中 **2** 筆 ——
`modules/elements/image_element.hpp` 的 `ImageDimensions{int width; int height;}`
（其註解明寫「固有像素寬／高」）。該型別是**來源影像自身資料的固有尺寸**
（換平台後端不會改變一張 PNG 的像素數），且該標頭已明寫「非螢幕座標／非擺放位置」，
**不是 widget／螢幕的擺放幾何**，故不是本驗收標準要防的那種滲透。
處理方式：把它列入**具名、附理由的預期基線**，並斷言
「命中集合 == 預期基線」——
- 新增任何一筆（真的滲透）→ **紅**；
- 預期基線那兩筆消失（掃描器瞎了：路徑錯、regex 壞、檔案讀不到）→ **也紅**。
後者就是防「寫成只比對不存在的字串就永遠綠」的那道鎖。

兩個方向的突變證明見 CHG 的 §Verification。

## 3. 錯誤記錄（錯誤 + 根因 + 解法）

本次共四條。**都不是靜默吞掉的**，每一條都是某道檢查先叫出來的。

### E-1 反向斷言的「天真 grep」在現況就會給出假的「已被違反」

- **錯誤**：`grep -rnE '\bpixels?\b|_px\b|Pixel' modules/elements/*.hpp src/kernel/*.hpp`
  排除註解行後仍有命中（`AlphaMode::PerPixel`、`kPerPixelAlphaCapability`、
  四個 E4 標頭的 `AlphaProfile composite_{}`）。若照字面寫斷言，現況直接紅。
- **根因**：那些是**alpha 合成模式的名稱**（逐像素 alpha 通道 vs 整體透明度），
  不是像素座標／尺寸型別。驗收標準要防的是「像素**值的幾何型別**往上滲」。
- **解法**：R2 規則寫成**合取** —— 識別字必須同時含「像素單位詞」與「幾何角色詞」。
  `PerPixel` 的詞是 {per, pixel}，沒有幾何角色詞，故不命中。
  該合取條件的**承重性**由突變 M10 證明（拿掉它，真實標頭的掃描當場變紅）。

### E-2 `ImageDimensions` 確實是 E4 公開介面上的像素單位型別（基線不是零）

- **錯誤**：以為「現況零命中」，實作後 R3 規則在 `modules/elements/image_element.hpp`
  命中 2 筆：`ImageDimensions { int width; int height; }`，其註解明寫「固有**像素**寬／高」，
  而 `ImageRenderModel::source_dimensions` 用了它。
- **根因**：I1 的派工補充只查了「pixel 這個字」的命中並判定「現況沒有被違反」，
  沒有查「整數型幾何欄位」這個形狀。那兩個欄位的像素性只寫在註解裡。
- **解法**：**不挖洞、不假裝零**。列成具名、附理由的**預期基線**，斷言形式是
  「命中集合 == 基線」：多一筆→紅，基線消失（掃描器瞎了）→也紅。
  同時在 CHG §已知限制 2 把「它到底該不該留在 E4 的公開介面上」提請 I1 / V1 裁定
  （要移走得動 E4-02 的公開契約，必須另開單元）。

### E-3 `ctest -N | grep -c h1_07` 回 5309 —— grep 命中的是我自己造出來的路徑

- **錯誤**：為確認 base（`origin/main`）上沒有本單元的測試，跑
  `ctest --test-dir <...>/h1_07-base-build -N | grep -c h1_07`，得到 **5309**
  （而 base 其實一個都沒有）。
- **根因**：我把 base worktree 的建置目錄命名為 `h1_07-base-build`，
  `ctest -N` 的輸出**每一行都帶那個路徑**，grep 命中的是路徑而不是測試名。
- **解法**：錨住測試列的格式 —— `grep -E '^ *Test +#[0-9]+: h1_07'`，得 0。
  與 **K-012**（貪婪的 `sed 's/.*: *//'` 取到表頭最後一欄）同族：
  **樣式沒錨住，命中的是上下文而不是目標**。

### E-4 sanitizer 全建 `rc=2`，而 `ctest` 印出 55 個失敗、sanitizer 報告數 0

- **錯誤**：`cmake --build <...> -j 4` 回 2，錯誤是
  `fatal error: error writing to /tmp/ccXXXX.s: No space left on device`（根分割區 100%）。
  後續 `ctest` 當然大量失敗 —— 那 55 個失敗**不是程式的問題**。
- **根因**：我同時留了 5 個建置目錄（含一個 3.5G 的 sanitizer 目錄），把磁碟撐滿。
- **解法**：刪掉**我自己的**多餘建置目錄（不動其他 session 的產物）並改用 `-j 2`
  （CI 的 `gate_sanitizers` 也用 `-j 2`，理由同樣是峰值資源）。重跑後
  註冊 185 = 普通 185、100% 通過、報告數 0。
  **教訓**：建置退出碼必須與測試退出碼**分開取**，否則「建置失敗」會被讀成「測試失敗」。

### E-5 自己的程式裡有一處潛伏 UB，而 CI 的兩道防線同時沉默

- **錯誤**：`metric_px()` 把呼叫端給的任意 `double` 呈現參數直接 `static_cast<int>`。
  `params["button_px"] = 1e20` 時那是**未定義行為**（C++17 [conv.fpint]/1）。
- **根因**：呈現參數刻意設計成「平台不解釋其語意的具名 double 袋子」，於是值域完全由
  呼叫端決定，而我在換算成像素時忘了那件事。
- **為什麼沒被現成防線抓到**（本機實測，g++ 13.3.0）：
  `-Wall -Wextra -Werror` 零警告；**GCC 的 `-fsanitize=undefined` 不包含
  `float-cast-overflow`**，所以 CI `gate_sanitizers` 的旗標組合下**零報告、exit=0**；
  單獨加 `,float-cast-overflow` 才會報
  `1e+20 is outside the range of representable values of type 'int'`。
  → 與 K-013（ASan 抓得到）、K-014（ASan + UBSan 都抓不到）同族，分界是「UBSan
  抓得到但要額外開旗標」。**已在 CHG 寫成完整條目供 I1 收進知識庫並評估 infra 修法。**
- **解法**：`metric_px` 與 `scale_logical` 兩處都改成「轉型前先在 double 的值域內夾限」，
  並補一條斷言。該斷言的形狀見下。

### E-6 把未提交的修正交給 `git checkout --` 當突變還原 → 修正被一起抹掉

- **錯誤**：我先在工作樹改好 E-5 的夾限（**沒有 commit**），緊接著跑突變 M18 ——
  驅動腳本的還原動作是 `git checkout -- <file>`，於是還原回的是**上一個 commit**，
  我的修正被一併抹掉。之後重跑測試看到紅燈，一度以為是新斷言寫錯。
- **根因**：突變驅動的還原語意是「回到 HEAD」，而我假設它是「回到我剛才的狀態」。
- **解法**：**修正先 commit，再跑突變。** 另外這一次的紅燈恰好證明了新斷言是承重的
  （沒有夾限就會紅），所以我把它記成證據而不是只記成誤判。

### 另記：突變測試抓到的三條缺斷言（不是錯誤，是這道程序的產出）

- **M1 第一輪 0 紅**：原本的 DPI 相鄰對齊測試用 (12,100)/(112,88) @1.5，
  而那組數字下「右緣 = 絕對座標縮放」與「右緣 = left + 寬度縮放」**算出一樣的結果**。
  已補一條用兩種算法會分歧的最小例子（`round(2*1.5)=3` vs `2+round(1.5)=4`）。
- **M17 第一輪 0 紅**：原本只斷言 `resolve()` 回 `IncompleteComposition` 且訊息非空，
  但本層的防禦性分支會回**同一個狀態碼**，所以「不呼叫 E9-03 `validate()`」看不出差別。
  已補「原因必須逐字等於 `composition().validate().message`」。
- **M18 第一輪 0 紅（且 UBSan 也 0 報告）**：原本只斷言「所有部件框非退化且落在組件框內」，
  而拿掉夾限後 `static_cast<int>(1e20)` → `INT_MIN` → `max(0, …)` → 0 → **整列按鈕不產出**，
  剩下的部件仍然非退化且在框內。已改成「巨大值必須被夾限成填滿格位的大按鈕、
  **四顆按鈕仍然存在**；只有 NaN / 負值才視為 0」——
  K-002 的形狀：崩塌成 0 是一個看起來正常的空版面。
