## 關鍵設計判斷

1. **如何取用 KernelBackend 介面**：`KernelBackend` 介面宣告於上游 E1-24 的
   `null_backend.hpp`（與 `NullKernelBackend` 同檔）。因此本單元 CMakeLists
   `target_link_libraries(e1_03 PUBLIC e1_21 backend_null)`——連 `backend_null`（E1-24 target）
   即取得該 header 的 include 目錄（backend_null 的 `PUBLIC` include dir 是 `src/kernel/backend/null/`），
   且 backend_null 已 `PUBLIC` 連 e1_21，故 `capability_matrix.hpp` 的 include 亦傳遞可得。
   本單元 `alpha_surface.hpp` 只 `#include "null_backend.hpp"` 即拿到 `KernelBackend` / `SurfaceId`
   / `SurfaceProfile` / `CapabilityMatrix`。

2. **不改上游介面 → 用組合擴充**：`KernelBackend` 為固定抽象介面、其 `SurfaceProfile` 不含 alpha
   欄位。不能在上游加虛擬方法，故設計 `AlphaSurfaceService` 持 `KernelBackend&` 參考，實體 surface
   委由後端 K1 原語，alpha 語意（模式 + 不透明度）由本服務層**另存記憶體**（即相位 1 null 模擬）。
   這也讓服務與具體後端解耦：測試以 `KernelBackend&` 基底參考亦成立。

3. **能力閘控 + 降級路徑**：per-pixel alpha = 可選能力 `surface.per_pixel_alpha`。上游
   `defaults()` 未宣告 → `has()` 保守回 false（能力不可用）。要模擬「支援」平台，提供
   `alpha_capable_matrix()`：複製 `defaults().all()` 並追加該能力宣告（矩陣「後定義者為準」故生效），
   注入 `NullKernelBackend`。所有變更操作先 `supported()`，不可用回 `Unsupported` 且零副作用——
   acceptance 要求的降級路徑測試據此覆蓋。

4. **NFR-02 無座標**：逐像素 alpha 相位 1 不以 (x,y) 設值（那會引入絕對座標）；改以具名
   `AlphaMode`{Opaque, PerPixel} + **正規化** opacity∈[0,1]（比例值，非座標 / 非數字 z-order）
   表達整體不透明度。surface 一律具名 `SurfaceId` 指涉。
