## 我要做什麼（動工前計畫）

相位 1（Mac / null 期）：只寫**平台中立介面 + null 後端 + 契約測試（含降級路徑）**，
**不得**出現 `#ifdef` / win32 / cocoa / 真實平台後端。

設計（C++17，`namespace ds::events`）：

- `GestureType` enum class：具名手勢 —— 全域滑動 SwipeLeft/Right/Up/Down、
  角落觸發 CornerTopLeft/TopRight/BottomLeft/BottomRight、縮放 PinchIn/PinchOut。
- `Gesture` struct：具名手勢 `type` + 平台中立正規化參數 `magnitude` + 人類可讀 `detail`
  （不含絕對座標，NFR-02）。
- `GlobalGestures` 抽象介面：`has()`（能力閘控入口）/ `subscribe(gesture, cb)→id` /
  `unsubscribe(id)` / `listener_count()`。
- `NullGlobalGestures` null 後端：`inject(gesture)` 模擬手勢，只分派給訂閱對應類型者；
  可用性由建構決定或 `from_capability(matrix)` 以 E1-21 能力矩陣為單一資料來源。

**能力閘控項的關鍵設計 —— 降級契約**：`has()==false` 時 subscribe 一律回 0、
listener_count 恆 0、inject 為 no-op。這使呼叫端縱使漏查 has()，也不會建立永不觸發的
假訂閱或誤觸回呼 —— 對應驗收硬性要求「不崩、不誤觸、明確回報不可用」。

## 降級路徑測試怎麼寫的（medium 驗收關鍵）

測試群 `GlobalGestureDegradation`（6 案），逐一覆蓋「呼叫端如何安全降級」：

1. **明確回報**：`has()` 回 false —— 呼叫端可查詢的不可用信號。
2. **訂閱被拒**：不可用時 `subscribe` 回 0 且 listener_count 為 0（不建假訂閱）。
3. **不誤觸**：模擬「有瑕疵、漏查 has()」的呼叫端仍嘗試訂閱後注入各種手勢 —— 回呼
   計數恆 0，證明 inject 為 no-op、絕不誤觸。
4. **不崩**：`EXPECT_NO_THROW` 包住 has/subscribe/unsubscribe/inject 全部操作。
5. **正規範式**：一個依 `has()` 閘控的呼叫端 helper —— 可用則走手勢主路徑、不可用則
   走鍵盤 fallback；兩態各驗一次，證明降級乾淨且不誤觸。
6. **端到端**：由 E1-21 預設能力矩陣（未宣告 input.gesture → 不可用）驅動，呼叫端據此降級。
