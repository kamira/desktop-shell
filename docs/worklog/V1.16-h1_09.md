## 4. 我自己犯的錯 / 踩到的坑（記下來，免得下一輪重踩）

### E1 —— 區間 diff 會把別人的 commit 算到實作者頭上

`git diff --name-only 6dd80ce f6f7fe0` 列出 `docs/acceptance/`，看起來像實作者越權寫了 ACC。
**根因**：那個區間含 `060adaf`（`V1.15` 自己的 ACC commit）。
**解法**：改用 `git show --name-only` **逐 commit** 查。實作者那兩個 commit 一次都沒碰
`docs/acceptance/`。**派工簡報也點明了這一點（「不要併入 base」會把 base 帶進來的檔案算進去）**，
同一個陷阱的另一面。

### E2 —— 一條突變的「寫法」會決定它量到什麼

我第一次寫 M82（「型別不同也視為相同」）寫成「把型別檢查整段拿掉」
（`if (false) { return false; }`）→ 只紅 1 支，與 CHG 報的 2 支不符。
**根因**：那樣寫會讓 `switch (a.type())` 用 a 的型別去取 b 的值，當場丟例外，
`OverwriteCheckNeverThrowsOnUnsanitisedState` 先紅並改變了後續執行；它測的不只是判定。
**解法**：改成忠實的「型別不同 → `return true`」→ 紅的正是 CHG 報的那 2 支。
**教訓**：報「某條突變與 CHG 不符」之前，先確認自己的突變與它描述的是同一個語意。

### E3 —— 差點把一個「存活突變」當成等價突變放過去

MV-C（List 長度檢查 `!=` → `>`）存活時，我的第一反應與 MV-A 一樣是「可能是等價的」。
**解法**：不要用「我想不到反例」當結論——**先寫探針把後果印出來**。印出來之後很清楚：
使用者刪掉 List 尾端元素的那次編輯被無聲還原，檔案位元組被寫回原樣，無訊息、無備份。
**等價與存活的差別不在「有沒有想到反例」，在「有沒有去量」。** 這正是這個單元
F7（沒測過的宣稱）與 F8（沒量過的理由）兩輪的同一個教訓，這次換我自己踩。

### E4 —— `grep -c` 不能用來數多行錨點（沿用，沒有重踩）

派工簡報與 CHG 都點明了（`V1.15` 踩過）。我一律用 Python 的 `str.count()` 數子字串，
10 條突變的錨點全部先數過才動，命中數都是 1。
