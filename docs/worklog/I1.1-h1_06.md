## 我要做什麼

### 現況（問題）

`host/paint/widget_painter.cpp`（H1-01）把 `SystemStatusRenderModel` 的每一筆指標都畫成
**同一個固定版面**：標籤 + 水平軌道 + 數值文字，只讀 `entry.element.fill_ratio`，
**完全忽略 `entry.element.kind`**。host app 設定的三個指標 CPU=`gauge` / GPU=`bar` /
RAM=`progress`（`host/app/host_main.cpp:134-141`）在畫面上長得一模一樣。
且整個 `host/paint/` 包在 `if(WIN32)` 裡 → ubuntu 的 G3 與新的 `gate_sanitizers`
一行都看不到，`gate_windows` 的硬編碼名單也只點名 `h1_01_paint`。

### 做法（I1 的設計決定：把錯得起來的那一半搬到真的有人看守的平台上，與 W1-08 同做法）

拆成三層，**前兩層平台中立、在 `if(WIN32)` 之外建置並各自 `add_test`**：

1. `host/paint/render_dispatch.{hpp,cpp}` → target `h1_06_dispatch`（**守衛外**）
   - `PaintSink`：可注入的抽象繪製介面，三個原語 `fill_box` / `draw_text` / `draw_needle`。
   - `ElementDraw`：平台中立的元件繪製描述（由各 E4 元件的 RenderModel 投影而來），
     `kind` 是**具名字串鍵**而非 enum —— 這是「新增元件型別不改平台」的關鍵。
   - `ElementRendererTable`：kind → renderer 的**分派表**，內建 `bar` / `progress` / `gauge`
     三種（E4-03 的三個 `ElementKind`），`register_kind()` 可在**不改本層**的前提下加新 kind。
   - 幾何純函式 `row_geometry` / `fill_span`（不碰 GDI，H1-01 已確立的做法）。
   - 不 `#include <windows.h>`、不呼叫任何 GDI API、無 `#ifdef _WIN32`。
2. `host/paint/widget_render.{hpp,cpp}` → target `h1_06_paint_model`（**守衛外**，link `c2_02`）
   - 把 `MetricRenderEntry`（含 E4-03 `ds::elements::RenderModel`）投影成 `ElementDraw`。
   - `WidgetRenderer::paint()`：版面 + 逐筆分派 + NFR-03 降級，回傳可斷言的 `PaintSummary`。
   - `add_projector()`：新元件型別的認領入口（投影端的擴充點）。
3. `host/paint/widget_painter.{hpp,cpp}`（**留在 `if(WIN32)` 內**）
   - 只剩 GDI：`GdiPaintSink` 實作 `PaintSink`（具名色彩角色 → `COLORREF`）。
   - **對外 API 一字不改**（`PaintTheme` / `RowLayout` / `row_layout` / `fill_rect` /
     `paint_widget` 兩個多載），因為 `tests/h1/test_h1_01.cpp` **不在本單元 write_scope**，
     必須原封不動地繼續通過（它會讀真實像素）。

另：`host/paint/radial_draw.{hpp,cpp}` → target `h1_06_radial`（**守衛外**，link `e4_18`）
把 **E4-18 的** `RenderModel`（徑向線 / 指針）投影成 `ElementDraw` 並註冊 `needle` kind。
**為什麼要獨立成 target 與獨立的測試執行檔**：`ds::elements::RenderModel` 在
`modules/elements/bar_gauge.hpp`（E4-03）與 `modules/elements/radial_pointer.hpp`（E4-18）
**是同名不同型別的兩個 struct**——同一個 TU 同時 include 兩者編譯失敗，同一個程式連入兩份
不同定義則是 ODR 違反（repo 內 C1-06 / C2-07 的橋接範式處理的是同一族問題）。
故拆成兩個**程式**：`test_h1_06`（E4-03 側）與 `test_h1_06_radial`（E4-18 側），
各自只存在一份 `ds::elements::RenderModel` 定義，不留 ODR 地雷。

## 遇到的錯誤（錯誤 + 根因 + 解法）

### 1. `-Werror=dangling-else`：`for` + 裸 `if` + `EXPECT_EQ` 一起用就建不起來

- **錯誤**：`tests/h1/test_h1_06.cpp:519: error: suggest explicit braces to avoid ambiguous
  'else' [-Werror=dangling-else]`，`-DDS_WERROR=ON` 下整個建置紅燈。
- **根因**：gtest 的 `EXPECT_*` 巨集展開後**自帶一個 `if ... else`**
  （`switch (0) case 0: default: if (...) ; else ...`）。寫成
  `for (...) if (cond) EXPECT_EQ(...);`（兩層都沒有大括號）時，那個 `else` 在語法上
  可以綁到外層的 `if`，GCC 於是警告。平常沒人發現，是因為這個 repo 在
  `CHG-20261112-04` 之前**根本沒有開任何警告旗標**。
- **解法**：凡 `if` / `for` 的主體裡有 gtest 巨集，一律補大括號。

### 2. 測試前提寫錯：「新 kind 還沒接上」時 `unknown_kind` 並不是 1

- **錯誤**：`PlatformPromise.TheNewKindIsNotKnownBeforehand` 預期
  `summary.unknown_kind == 1` / `drawn == 0`，實際是 `0` / `1`。
- **根因**：我把「**沒有畫法**（renderer 未註冊）」與「**沒有認領**（projector 未註冊）」
  混為一談。沒有投影器時，那筆指標會走**內建的 E4-03 投影**，而 C2-02 對沒掛元件的條目
  留下預設建構的 `RenderModel`（`kind = Bar`）—— 所以它被當成 `bar` 正常畫出來了。
- **解法**：拆成兩個測試。前提一只斷言「`has_kind("sparkline")` 為假、且此時走內建投影
  得到 `bar`」；前提二（`ClaimedButUnregisteredKindIsReportedNotSilentlyMisdrawn`）
  才是「認領了但沒有畫法 → `unknown_kind == 1`、且**沒有**假裝畫成長條」。
  這個錯其實讓測試變強：原本的寫法根本證明不到「不靜默誤畫」這件事。

### 3. `sink.ops.back()` 不是那根指針

- **錯誤**：`EXPECT_DOUBLE_EQ(sink.ops.back().angle, 45.0)` 拿到 0。
- **根因**：組版順序是「標籤文字 → 元件 → **數值文字**」，所以最後一道指令是數值文字，
  不是元件的指令。把「最後一個 op」當成「我剛才那個 op」是錯的假設。
- **解法**：改用 `first(Op::Type::Needle, PaintRole::Fill)` 依型別 / 角色找。

### 4. 突變測試 M1 根本沒跑到執行期（而我差點把它記成「建置失敗 = 有擋到」）

- **錯誤**：突變「分派表拿掉 `progress` kind」→ 建置 rc=2，測試一次都沒跑。
- **根因**：拿掉 `register_kind(kKindProgress, &render_progress)` 之後，
  匿名 namespace 裡的 `render_progress` 變成**未使用的 static 函式**，
  `-Wunused-function` + `-Werror` 在編譯期就擋下 —— 擋得很好，但這**不是**我要測的東西
  （我要測的是「執行期查不到 kind 會不會被斷言抓到」）。
- **解法**：另做 M1b，把它註冊到一個永不命中的鍵（`"progress-disabled"`），
  函式仍被使用、但 `progress` 這個 kind 真的從表上消失 → 6 個案例變紅。
  兩個結果都記進 CHG，不把編譯期的擋法當成執行期的斷言。

### 5. 突變測試抓到一條缺斷言（M3 只紅 1 個案例）

- **錯誤**：突變「`project_entry` 把 `angle_degrees` 接成 `start_angle_degrees`」
  只打紅 `ProjectionCarriesEveryE403FieldThroughUnchanged` 一條。
- **根因**：`AllThreeAreDrawnEachByItsOwnKind` 只斷言「有一根指針」，沒斷言那根指針的
  **角度** —— 從 `paint()` 到 sink 的端到端路徑上，欄位接錯會整條溜過去。
- **解法**：補 `EXPECT_DOUBLE_EQ(cpu_needle->angle, 270.0)`（= 135 + 0.5×270）
  與該指針所在的錶盤矩形；重跑後 M3 變成 2 紅。

### 6. mingw 交叉編譯 `desktop_shell_host` 連結失敗（**不是**本變更造成的）

- **錯誤**：`undefined reference to 'WinMain'`。
- **根因**：`host/app/host_main.cpp:161` 的進入點是 `wWinMain`；mingw 需要 `-municode`
  才會用 Unicode 進入點，MSVC 原生支援。`host_main.cpp` 本身**編譯成功**
  （我要驗的「改了標頭之後呼叫端還編得過」已經成立）。
- **解法**：不處理 —— 這是我這台機器上交叉工具鏈的差異，`host/app/**` 也不在本單元的
  write_scope 內。CHG 的 §Verification 已明寫此分界，不拿它當成任何結論。

### 7.（事前避開，非踩到）`ds::elements::RenderModel` 有兩個同名不同型別的定義

- **問題**：`modules/elements/bar_gauge.hpp`（E4-03）與
  `modules/elements/radial_pointer.hpp`（E4-18）同在 `namespace ds::elements`、同名
  `RenderModel`、成員不同。同一個 TU 同時 include → 重定義；同一個**程式**連入兩份
  → **ODR 違反**（UB，警告旗標與 sanitizer 都抓不到）。
- **解法**：E4-03 側與 E4-18 側拆成**兩個獨立的程式**（`test_h1_06` /
  `test_h1_06_radial`），各自只有一份定義。已在 CHG、CMakeLists 與兩個標頭的檔頭寫明。
  **建議 I1 把這條收進 `docs/knowledge/errors.md`**（K 編號由 I1 決定，避免並行單元搶號）：
  任何同時想消費 E4-03 與 E4-18 的下游單元都會踩到，而它不會有任何編譯警告或
  sanitizer 報告 —— 與 K-013 同一族「綠燈不代表正確」。
