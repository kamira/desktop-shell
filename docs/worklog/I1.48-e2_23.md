## 我要做什麼（動工前計畫）

相位 1（Mac / null 期）：只寫**平台中立介面 + 記憶體內假來源 + 契約測試**，**絕不接真實
檔案系統**（無 `<filesystem>` 實體存取、無 `opendir`、無 `#ifdef` / win32 / cocoa）。
**消費 E2-01 契約、不自造指標模型**，沿用 E2-16 已安裝應用列舉的隨選列舉樣式。

設計（C++17，`namespace ds::sysinfo`）：

- `DirEntry`（name / type / size / mtime）+ `DirEntryType`（File/Directory/Other）：
  子項目描述 + 檔/目錄類型區分。mtime 以 Unix epoch 秒（平台中立整數）。
- `FsError` + `ListResult` / `StatResult`：**錯誤不靜默**——無效路徑 / 非目錄 / 權限錯以
  明確錯誤碼回報，消費者可分辨「空目錄」與「路徑錯誤」。
- `FileSystemSource` 抽象後端：`list(path)` / `stat(path)`。相位 2+ 由真實平台後端實作；
  提供者只依賴此抽象介面（換後端不動提供者）。
- `NullFileSystemSource` 記憶體內假來源：持有記憶體目錄樹，`add_file`/`add_dir`/
  `set_permission_denied`/`clear` 供測試；POSIX 風格路徑切分、字典序 map 保證決定性。
- `FileSystemEnumProvider : public ds::metrics::MetricProvider`：`register_metrics()` 對
  目標路徑 `list()`，每個子項目建成一個 `MetricInstance`，掛上單一指標 `"fs.entries"`。

## 指標形狀的關鍵設計（為何每個子項目 = 一個實例）

E2-01 六要素含「可列舉實例」。本單元名即「檔案系統**列舉**」，天然對應此要素：
- 指標身分：id=`fs.entries`、name=`Filesystem Entries`、unit=``、range=`at_least(0)`。
- **每個目錄子項目建成一個 `MetricInstance`**（instance_id=label=項目名、
  value=存在(1.0)+類型文字 "file"/"dir"、history_capacity=0，因項目無時序歷史）。
- 於是「清單」= 依序列舉實例、「數量」= `Metric::instance_count()`。消費者（掛件）只透過
  E2-01 抽象介面走訪，**完全不觸及 sysinfo / fs 型別**——新增此指標，掛件一行不用改。

保守設計：列舉錯誤（無效路徑 / 權限 / null source）→ 仍掛上「空指標」
（instance_count()==0）並以 `last_error()` 明確回報，不崩、不靜默；重複 id 由 E2-01 註冊表
保守拒絕、不覆寫既有。
