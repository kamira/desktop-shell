  區分，非「不靜默」規則的對象。`handle_key` 在彈出未顯示時安全略過（不呼叫
  move_selection/accept，故不擲例外）——事件到達與否是分派層語意，與「呼叫端顯式呼叫」
  的不靜默要求分屬不同責任層級。

## 錯誤紀錄（錯誤 + 根因 + 解法）

- 起初設計 `move_selection()` 在候選清單為空時是否該和 E4-15 的 `move_cursor` 一樣
  「安全無動作」曾猶豫過：但規格明確要求「空建議…選取處理不靜默」，且 E4-15 的
  `move_cursor` no-op 之所以合理是因為「游標永遠存在（[0,length()]，即使 length()==0
  游標仍是合法值 0）」；而本單元的選取索引在候選清單為空時**根本沒有合法值可指**（不
  存在「選第 0 項」這件事，因為沒有第 0 項），語意上與 E4-15 的邊界 no-op 並不對等，
  改為擲 `std::logic_error`——同時把「非空清單的邊界移動」與「空清單移動」明確拆成兩條
  不同規則，於標頭與本 worklog 皆有說明區分依據。
- 硬性限制要求 CMakeLists 只能 `target_link_libraries(e4_16 PUBLIC e4_01 e4_15)`（不得
  另外顯式連結 e5_13），但本單元的 `handle_key`/`attach` 直接使用 `ds::events::KeyEvent`
  /`KeyboardInputSource`。本機編譯前先確認：e4_15 的 CMakeLists 對 e5_13 是
  `PUBLIC` 連結（非 `PRIVATE`），依 CMake 語意 `PUBLIC` 相依的 include 目錄與連結庫會
  遞移傳遞給任何連結 e4_15 的下游目標（本單元）及再下游——故 e4_16 不需（也不應）重複
  宣告對 e5_13 的連結。本機以 g++ 直接補上 e5_13 的 include 路徑與其 .cpp 驗證此假設
  （編譯與連結皆順利、行為正確），CMake 下的語意等價，已於 CHG 文件 Verification 段落
  記錄依據。
