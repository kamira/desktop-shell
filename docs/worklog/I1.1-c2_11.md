## 設計要點（含停點裁定的落地方式）

- **切換排序維度 = 換掉註冊的指標**（CHG-20260829-05 Q-A）：widget 不持有 provider、不要求
  provider 有 setter（E2-19 的 `sort_key`/`top_n` 本就只有建構子參數）。設定裡的維度只做一件事:
  **決定 `refresh()` 去 registry 要哪一個 id**。維度改了就是去要另一個 id；舊 id 的指標還留在
  registry 也一律**不讀**（否則單位會從 % 偷偷變成 MB，正是 K-002 那種「看起來正常」的假資料）。
- **單位對帳**：讀到的 `Metric::unit()` 必須等於該維度的期望單位（`%` / `MB`），不等就是
  registry 裡那個 id 不是 E2-19 掛的那個指標 → 具名回報 `UnitMismatch`，不畫、不猜。
- **歷史不保留**：widget 不碰 `MetricInstance::history()`、自身不存任何時序；`configure()` 與
  每次 `refresh()` 都把列重建。provider 由 host（H1-11）重建，**本單元不負責重建**。
- **沒有範圍就不要畫長條**（K-002）：`proc.memory` 的 range 是 `at_least(0)`（無上界）。
  憑空給一個上界去畫長條，會把「用了 8 GB」與「用了 100 MB」畫成一樣滿——看起來正常、
  其實是假資料。故：解不出顯示範圍（無宣告式 `min`/`max`、指標 range 又非有界）時，該列
  **不掛 E4-03 元素**（`has_range=false`、element 維持未綁定），只出文字。
- 不碰 E7-03（非本單元相依）：公式作用域只含 `value`，不支援 `vars:` 段落。
- 命名避免與 C2-02 在同一 namespace 撞號（`ProcessRowElementKind` / `ProcessTopStatus`）。

## 錯誤紀錄（錯誤 + 根因 + 解法）

**實作期間沒有踩到編譯 / 測試失敗**（首次建置即綠）。以下兩件是動工中發現、在寫成紅燈之前
就先擋掉的坑，記下來是因為它們都會長成「看起來正常的假資料 / 假綠燈」：

1. **錯誤（避開）**：原打算照 C2-02 的作法，解不出顯示範圍時退回保守預設 `[0,100]`。
   **根因**：`proc.cpu` 的 range 是 `bounded[0,100]`，但 `proc.memory` 是 `at_least(0)`
   ——**無上界**。拿 `[0,100]` 去畫 MB，「用了 8 GB」與「用了 100 MB」都是滿格，而
   `fill_ratio ∈ [0,1]` 這類值域檢查全數通過（知識庫 **K-002** 的原形：值域檢查不等於
   有效性檢查）。
   **解法**：解不出範圍時該列 `has_range=false`、**不掛 E4-03 元素**，只出誠實的文字；
   要畫就得在宣告式設定裡明寫 `min`/`max`。並補一條負向測試證明這條規則會擋。

2. **錯誤（避開）**：測試原以 `88.25` 當 CPU% 並期望顯示 `"88.3%"`。
   **根因**：`88.25` 在二進位可精確表示，`printf("%.1f")` 對恰好的半值用 round-half-even
   → 實得 `"88.2"`（已實測確認）。這種測試會在「看起來最無害」的地方紅，而且紅的理由跟
   被測邏輯無關。
   **解法**：改用 `88.5`（無歧義），不去改格式化行為本身。

3. **設計注意（非錯誤）**：C2-02 已在 `ds::widgets` 定義 `MetricElementKind` 與
   `to_string()`。若本單元沿用同名型別，兩個標頭在同一翻譯單元就會撞號（與 C2-07 踩過的
   `HitResult` 同類問題，只是那次是上游帶進來的）。故本單元一律用
   `ProcessRowElementKind` / `ProcessTopStatus` / `ProcessMetricState` 等前綴名。

（三者皆屬本單元內的設計取捨與測試寫法，不是跨單元的新坑，故**不**追加
`docs/knowledge/errors.md` 條目——第 1 條本身就是 K-002 的既有條目在新單元上的應用。）
