## 我要做什麼（動工前寫）

在 `engine/format/` 新增「設定分頁登錄」：一個**核心分頁** + **每個已安裝套件一頁**，
套件的貢獻是 **append-only**（額外增加 tab，**不覆寫**核心設定）。

### 消費的上游（可讀不可改）

- **E7-14** `engine/format/editor_model.hpp` — `EditableField` / `build_editor_model` /
  `validate_edit` / `apply_edit`。驗收標準明寫「**不得重造欄位模型**」，故每一頁的欄位清單
  一律是 `std::vector<ds::format::EditableField>`，由 `build_editor_model` 產出；編輯一律走
  E7-14 `apply_edit`（其內部再走 E7-12 `set_value`）。本單元**不新增任何欄位型別**。
- **E9-10** `engine/package/install_store.hpp` — 已安裝套件登錄的持久化。

### 設計決策：以可注入抽象表達「哪些套件貢獻了設定」，不跨子系統連結 e9_10

I1 補充給了兩條路（直接 `target_link_libraries(e7_16 PUBLIC e9_10)`，或以可注入抽象表達）。
我選**可注入抽象**，理由不只是風格對齊（E9-05 `LayoutStorage` / E9-10 `InstallStorage` /
E2-19 `ProcessSource` 皆如此），而是**直接連 e9_10 在資料上不成立**：

- E9-10 持久化的單位是 `InstallRecord`，持有 E9-01 `Package` = E9-02 manifest
  （`name` / `version` / `description` / `requires` / `permissions`）+ 內含項目的**邏輯路徑清單**。
- `Manifest` **沒有任何設定宣告欄位**（我讀過 `engine/package/manifest.hpp:51`），而 `Package`
  檔頭明寫「**不含套件本體 / 資源內容**」。
- 所以「這個套件宣告了哪些設定欄位」這份資料**不在 E9-10 的回答範圍內**——它在套件隨附的
  宣告式設定資源裡（E7-01 文字）。即使連上 e9_10，仍得另有東西把那份內容交進來。

故本單元定義 `SettingsContributionSource`（抽象）回答「哪些套件 id 有貢獻 + 該套件宣告的
設定 `Value` 樹」，相位 1 附 `MemorySettingsContributions` 替身（`declare` / `withdraw`）。
host 層組裝時才決定來源（屆時由 E9-10 列舉已安裝、再取其設定資源內容餵進來）。
代價是多一層間接，好處是 E7-16 不需跨子系統連結、測試不需真的建一個安裝登錄。

**誠實分界（沿用 E9-10 的誠實度）**：`MemorySettingsContributions` 是**相位 1 的記憶體替身**，
無真實檔案 I/O、無跨行程持久化。本單元**不聲稱**設定分頁跨真實重啟仍存在。

### append-only 的機械保證（本單元的核心）

- 核心分頁的欄位**只**由核心 `Value` 樹算出；套件貢獻一律產生**另一個 page 物件**，
  兩者的 `Value` 樹各自獨立，套件的鍵名撞到核心的鍵名時**沒有任何寫入核心的程式路徑**。
- 保留 page id（核心分頁 id）**不得被套件佔用** → `throw`（不靜默覆寫）。
- 列舉順序固定：核心分頁**恆為第一**，套件分頁依 package id 字典序 → 衝突不會被排序遮蔽。

### 要釘的反向斷言（正向證明不了 append-only）

1. 套件宣告與核心**同名欄位** → 核心分頁該欄位的值**原封不動**、欄位數不變；套件分頁持自己的值。
2. 兩個套件**彼此同名** → 各自一頁、互不影響，核心亦不受影響。
3. 套件宣告核心**本來不存在**的欄位名 → 核心分頁**不會長出**該欄位（append 的是分頁，不是欄位）。
4. **卸載**（withdraw）→ 該分頁消失、核心分頁不受影響、其他套件分頁不受影響。
5. 套件試圖佔用核心保留 page id → `throw`。
6. 編輯核心欄位不動任何套件分頁；編輯套件欄位不動核心分頁。
7. 列舉順序穩定（核心恆首位、套件字典序）。

另做**負向測試**（把 append-only 守門改壞，確認反向斷言真的會紅），結果記於下方。

### 1. I1 要求實測的 CMake ordering 風險 → **實測不成立**

I1 提醒：`engine/format/CMakeLists.txt` 若連結 `e9_10`，引用的是更晚才被 `add_subdirectory`
加入的目錄裡定義的目標（根 CMakeLists 的 GLOB 順序 `engine/format` 先於 `engine/package`），
失敗時會退化成 raw library name `-le9_10`，在 link 期才爆、訊息與根因無關。

**實測方式**（動手初期、在寫任何實作之前做的）：在 `engine/format/CMakeLists.txt` 暫時加一個
probe target `target_link_libraries(e7_16_probe PUBLIC e9_10)`，配一支真的
`#include "install_store.hpp"` 並呼叫 `InstalledPackageStore::size()` 的翻譯單元，
再加一個 executable 以產生**真實的 link step**（static library 不 link，驗不到這條風險）。

**結果：風險不成立。**
- configure / generate 無任何抱怨；
- `e9_10` 被當成真實目標排進建置順序（先建 `e9_07` / `e9_10` 才建 probe）；
- `#include "install_store.hpp"` 解析成功 → 證明 `e9_10` 的 PUBLIC include 目錄**有傳遞**
  （raw library name **不會**傳遞 include 目錄，故這一點本身即足以排除退化）；
- link line 實際是 `… libe7_16_probe.a ../package/libe9_10.a libe7_12.a libe7_01.a …`
  —— 真實 archive 路徑，**不是** `-le9_10`。

根因：CMake 在 **generate 期**才解析目標名，與 `add_subdirectory` 的先後無關。
**給後人**：`engine/format` → `engine/package` 這個方向的連結可行，不必為 GLOB 順序繞路。

probe 已完整還原（`CMakeLists.txt` 自備份還原、probe 的兩支 `.cpp` 皆刪除），未進入任何 commit。
本單元最終**仍未**連結 e9_10，但理由是「E9-10 回答不了『套件宣告了哪些設定欄位』」
（見 CHG 設計決定 1），與這條 ordering 風險無關——兩件事不要混為一談。

### 2. 自己寫出一個弱測試，發現後改強

第一版的 `FailedRefreshLeavesRegistryUnchanged` 我偷懶寫成「同一個 registry 重複 refresh 為
幂等」，並在註解裡自圓其說「來源是建構時注入的，故無法讓同一個 registry 中途失敗」。
那是假的——寫一個**可切換成壞掉**的 `FlakySource`（`break_it()` 後改列出重複 id）就做得到。
改強後該案例才真的在測「全有全無」，並由突變 6（refresh 改成就地建）確認會紅。
留此一筆是因為：這正是本 repo 一直在防的那種「看起來有測、其實沒測」的案例，
而這次是我自己寫出來的。
