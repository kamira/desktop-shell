# 架構定位 — desktop-shell 是底層平台

- Date: 2026-07-24 (UTC+0)
- 對應：`docs/requirements.md`（需求敘述）、`docs/backlog/units.json`（`layer` / `stage` 欄位）

---

## 定位

**本 repo 的產品是平台，不是桌面工具。**

一個平台由它的擴充點定義，不由它的功能定義。所以驗收條件不是「能不能顯示一個
CPU 掛件」，而是：**能不能在不修改平台任何一行的前提下，讓外部加上一個
CPU 掛件。**

這兩者聽起來相近，實作起來完全不同。前者允許把感測器編進核心，後者不允許。

---

## 核心與組件

```
核心（本次主要需求）
├── 監測子系統   CPU / GPU / 儲存 / IO / 網路 / 頻寬 / 電池 / …
├── 互動子系統   事件、命令分派、致動器
├── 視窗子系統   surface kernel、四參數 profile
├── 繪製子系統   paint / transform / clip / text 基座
├── 描述子系統   宣告式格式、變數、求值
├── 擴充子系統   腳本引擎、模組載入
├── 封裝子系統   套件格式、manifest、持久化
└── 介接 / 宿主 / 治理

第三方組件（後續範例）
├── CPU Usage Widget
├── GPU Usage Widget
└── …
```

| 層 | 現況 | 定義 |
|---|---|---|
| **platform** | **30** | 對系統的操作。29 項語意分歧全在此，加 `E1-24` null 後端 1 項。全部位於 `src/**` |
| **engine** | **64** | 平台中立的引擎邏輯，換平台一行不動。`engine/**` 62 條 + 後端契約 `E1-25`(tests)/`E1-26`(scripts) 2 項 |
| **module** | **58** | 掛在擴充點上的能力提供者，分為具名 `subsystem`：`sysinfo` 25 / `elements` 22 / `actuators` 11。**語意分歧 0** |
| **artifact** | **24** | 桌面上顯示的產出物（profiles / widgets / 內容 / apps）。**角色是驗證器，不是產品**。語意分歧 0 |
| 合計 | **176** | |

> **`platform` + `engine` 合計 94，即平台本身**（先前的單一 `core` 層已拆為此二值）。
>
> 分層規則（機械可複算，寫在 `units.json` 的 `layer` / `subsystem` 欄位）：
> `write_scope` 落在 `content/**`、`apps/**` → **artifact**；
> `E2` 除 `E2-01`/`E2-02` 外 → **module/sysinfo**；`E3` 全部 → **module/actuators**；
> `E4` 除繪製基座 8 項外 → **module/elements**；
> 其餘平台本身者：`src/**` → **platform**；`engine/**` 及後端契約 `E1-25`/`E1-26`（於 tests/、scripts/）→ **engine**。
>
> 草案原記「平台核心 97 / 模組 56 / 組件 21」，與本表 94 / 58 / 24 相差 −3 / +2 / +3，
> 差額與那 5 個未點名的工作單元同源（草案總數 181，`units.json` 現況 176）。
> **派工一律以 `units.json` 為準。**

### 產出物（artifact）的角色是驗證，不是功能

CPU Usage Widget 存在的意義不是「有一個 CPU 掛件」，而是**證明監測子系統的擴充點
真的能被外部使用**。所以組件不是「之後有空再做的功能」，是每一塊核心能力的
驗收條件。

推論：**沒有驗證器的核心能力不該先做。** 在沒有消費者的情況下設計 API，
形狀只能靠猜，而錯誤會在寫第 20 個組件時才浮現，那時已有 19 個要改。

### 四個階段，每階段配一個驗證器

`stage` 欄位以 `group` 機械對映為預設值：核心 + 監控 → A，角色 → B，啟動 → C，工具 → D。
**例外（明示覆寫）**：`E7-13`「階層式項目結構」group 為 `啟動` 但 stage 為 **A** ——
它是 `src/format/` 下的共用格式原語（P0、wave 1、被 `E11-02`(A)/`C1-05`(C)/`C2-09`(D)/`C3-01`(C)
跨階段消費），只是當初以啟動器選單樹為動機才被歸進 `啟動` 群。依「被依賴者應提前」原則提前，
由 `scripts/stage_check.py`(G1c) 強制。

| 階段 | platform | engine | module | artifact | 合計 | 驗證器 |
|---|---|---|---|---|---|---|
| **A** | 26 | 52 | 34 | 5 | **117** | CPU/GPU Usage Widget |
| **B** | 2 | 9 | 9 | 4 | **24** | 最小角色範例 |
| **C** | 2 | 1 | 7 | 2 | **12** | 最小啟動器範例 |
| **D** | 0 | 2 | 8 | 13 | **23** | 最小浮層範例 |
| 合計 | **30** | **64** | **58** | **24** | **176** | |

階段 A 佔全部單元的 66%、佔平台本身（platform+engine）的 83%。B/C/D 各自的能力目前**沒有消費者**，
所以它們排在後面——不是因為不重要，是因為現在設計它們的 API 等於猜。

每階段的完成定義：核心能力做完，**且**該階段的範例在不修改 `src/` 的前提下
載入運作（測試斷言 `src/` 的 git diff 為空）。

## 五個擴充點

平台的實質內容就是這五個契約。其餘項目都在支撐它們。

| # | 擴充點 | 契約 | 掛什麼 |
|---|---|---|---|
| 1 | **指標** | `E2-01` 統一指標介面（名稱/值/單位/範圍/歷史/列舉實例） | 感測器：CPU、GPU、網路、任意來源 |
| 2 | **元件** | `E4` 繪製基座 + 元件註冊 | 視覺元件：長條、直方圖、任意繪製型別 |
| 3 | **動作** | `E6-01` 命令匯流排 | 致動器：音量、電源、任意副作用 |
| 4 | **Profile** | `E1` 四參數（圖層／輸入策略／命中策略／生命週期） | surface 型態：skin、立繪、浮層、面板 |
| 5 | **腳本** | `E8-01` 腳本引擎 + `E8-04` 模組載入 | 行為：對話、自訂邏輯 |

**指標介面之所以是第一個，是因為它決定了「不限於」能不能成立。** 若掛件直接
相依個別感測器，每加一個指標就要改掛件——那不是「包含但不限於 CPU/GPU/RAM…」，
是「限於當初寫進去的那幾個」。

## 新增的驗收單元：`E8-06` 擴充點自證測試

平台若無法在不修改自身的前提下載入模組，它就不是平台。所以加一個會失敗的測試：

> 在 `examples/hello-module/` 放一個第三方視角的最小模組（一個感測器 + 一個元件
> + 一個動作），不修改 `src/` 任何檔案即可被載入並運作。
> **測試斷言 `src/` 的 git diff 為空。**

這條寫成可執行的斷言而不是原則，因為原則守不住。開發過程中「先把這個感測器塞進
核心，之後再抽出來」是最自然的動作，而「之後」不會來。

連帶把 `E8-04`（行程內模組載入）從 `P1` 升為 `P0` —— 它從輔助設施變成主要擴充機制。

### 驗證器歸類為 `example`

四個階段的驗證器（A：CPU/GPU Usage Widget；B：最小角色範例；C：最小啟動器範例；
D：最小浮層範例）與 `E8-06` 的 `hello-module`，**分類為 `example`**——不是 `artifact`。
區別在角色：`artifact`（C1–C4）是隨附的第一方內容；`example` 純粹是「證明擴充點可用」的
最小驗收範例，位於 `examples/`。名稱本身就在防止它們被當成交付目標。

> **狀態：尚未進入 `units.json`。** 這 4 個驗證器 + `E8-06` 的相依、wave、風險分級待規格確認後
> 開 CHG 寫入；屆時 `layer` 值域將新增 `example`。目前 backlog 仍為 176 單元。

> **狀態：尚未進入 `units.json`。** `E8-06` 的相依、wave、風險分級屬設計判斷，
> 不由本檔逕自決定；`E8-04` 的 `P1 → P0` 同理。兩者待決後開 CHG 一併寫入。

## 對既有規劃的影響

### 相位 1 的重心變了

**（經 `units.json` 查證）** 平台耦合完全依分層集中：

| 層 | 語意分歧 | API 分歧 | 平台中立 |
|---|---|---|---|
| platform | **29** | 0 | 1 |
| engine | **0** | 0 | 64 |
| module | **0** | 34 | 24 |
| artifact | **0** | 0 | 24 |

29 項語意分歧**全部落在 platform**；`engine` / `module` / `artifact` 三層合計 146 項**完全沒有語意分歧**。

這意味著相位 1 的順序應該是：先把 `platform` 層的擴充點契約定下來並用 null 後端驗證，
`engine` / `module` / `artifact` 隨後可以無限並行，而且**與平台後端完全無關**——
唯一需要 per-platform 後端的就是 `platform` 那 29 項。

### 模組的位置

第一方模組雖然隨附，但機制上與第三方無異，所以它們**不該編進核心目錄**。
建議 `src/` 只放平台，模組放 `modules/`，範例放 `examples/`。
這讓「第三方能不能加」變成目錄結構就看得出來的事——若某個感測器出現在 `src/`，
那就是擴充點沒做好的訊號。

> **狀態：`module` 層已遷移**（CHG-20260723-08）—— 58 項移至 `modules/<subsystem>/`，
> `src/actuators/` 因此清空。
> **`artifact` 層仍在 `content/**`、`apps/**`**，是否遷移待決。

### `src/` 再收斂為「只放對系統的操作」

`src/` 只放平台還不夠 —— 平台本身也分兩種：**對系統的操作**（需要 per-platform 後端）
與**平台中立的引擎邏輯**（換平台一行都不用動）。兩者混在一起，「跨平台要改哪裡」
就仍然看不出來。

故再切一刀：**`src/` 只留對系統的操作，平台中立邏輯遷至 `engine/`。**

| 目錄 | 內容 | 項數 | 換平台時 |
|---|---|---|---|
| `src/` | surface kernel、全域事件、宿主整合、null 後端 | 30 | **只有這裡要改** |
| `engine/` | 宣告式格式、封裝、非全域事件、繪製基座、命令匯流排、腳本、IPC、指標契約… | 62 | 一行不動 |
| `modules/` | sysinfo / elements / actuators | 58 | 一行不動 |
| `content/`、`apps/` | artifact（驗證器） | 24 | 一行不動 |

這讓語言選擇（A1）的驗證範圍變得明確：真正需要驗證的就是 `src/` 那 30 項對系統的操作。
語言本身不限定（C/C++ 允許，見 `docs/requirements.md`），被驗證的是這批項目的 API 面
能否跨平台表達，而不是用什麼語言寫。

> **狀態：遷移完成**（CHG-20260723-10 第一批 39 項、CHG-20260723-11 其餘 23 項）。
> `engine/` 共 62 項（format 15 / package 9 / events 11 / render 8 / command 5 / script 5 /
> ipc 5 / metrics 2 / common 2）。
> `src/` 只剩 **29 項對系統的操作**（kernel 23 / 全域 events 3 / host 3）加上 `E1-24` null 後端 ——
> 後者雖平台中立，**刻意留在 `src/kernel/backend/`**（後端家族不拆散，且 `backend_guard.py`
> 以 `src/kernel/backend/*` 執行相位閘門）。
> `E5` 事件子系統因此橫跨兩處：全域事件在 `src/events/`、非全域事件在 `engine/events/`。

### Q3 的意義加重

「先自用，格式預留未來開放」在平台定位下不再是選項。**平台的產品就是它的 API 面**，
格式與模組介面從第一版就得帶版本欄位與相容策略——不是為了外人，是因為
你自己的組件就是這個 API 的第一批消費者。

如果五個擴充點設計錯了，你會在寫第 20 個組件時發現，那時已經有 19 個要改。
